## 8 Rules

### Rule 1: Separate architecture discussions from coding
"别在一个聊天里又聊架构又写代码。你一边讨论方向，一边让它实现，模型就会自动'压缩上下文'，很多默认前提直接被吞掉。最后不是在做系统，是在打补丁。分工清楚，一个负责想清楚，一个负责动手。"

### Rule 2: Don't trust the UI — verify via logs
"别太相信界面。界面会告诉你'已经切换模型'，但真实调用可能根本没变。一定去看日志、看真实调用、看花了多少钱。不看这些，你是在用想象做决策。"

### Rule 3: Debug by asking agent to explain step-by-step
"调试最狠的一招，不是问'为啥不对'，而是让它一步一步讲清楚自己在干嘛。很多时候它一解释，你会发现设计过度了，几行代码就能解决的问题，被你绕了三天。"

### Rule 4: Agent's instinct is to "optimize everything" — set boundaries
"Agent的本能是'帮你优化一切'。听起来很好，但其实很危险。不给边界，它就会改所有能改的东西。真正可怕的不是小bug，而是不可逆的改动。重要操作必须确认，模糊指令直接停。"

### Rule 5: Watch for "fake success" — define failure criteria
"集成特别容易出现'看起来都连上了'。但其实只通了一部分。最可怕的是那种'假成功'。一定要有清单：它能看到什么？不能看到什么？允许做什么？什么算失败？"

### Rule 6: Plan before execution
"别一上来就开写。先把项目理解清楚，风险列出来，计划写好。AI会把执行速度拉满，但如果方向错了，只是更快翻车。"

### Rule 7: Manage chats like a team — persist to files
"把聊天当成一个团队在管理。一个主聊天负责架构，其他聊天负责执行。成果一定要落到文件里，不要只存在对话里。不然上下文一压缩，等于白干。"

### Rule 8: Git is memory, model is not
"Git才是记忆，模型不是。没commit的东西，下一次就可能消失。别迷信'它刚刚还记得'。版本控制才是你的保险箱。"

## Key Author Comments (self-commentary)

- "大多数AI协作项目失败，不是模型不够强，而是人没有定义清楚边界...真正稳定的系统，往往不是最聪明的，而是限制最多的。"
- "聊天只是临时记忆。上下文一压缩，之前精心打磨的方案就可能消失。真正可靠的成果必须写进文件、进版本库、留审计记录。"
- "很多复杂的Agent流程，其实是人为设计出来的复杂...删掉三层封装、砍掉两个中间状态，反而更稳定。真正厉害的不是把流程做复杂，而是敢于把它拆到只剩必要部分。"
- "AI系统最大的风险不是答错，而是悄无声息地'答对了一半'...真正成熟的做法，是提前定义什么算失败，而不是只定义什么算成功。没有失败标准的系统，本质上是不受控的。"
- "绝大多数人根本不知道自己在用哪个模型。界面显示什么，大家就信什么...真正专业的团队，第一步不是改提示词，而是拉日志，看调用链，看token消耗，再谈优化。"
