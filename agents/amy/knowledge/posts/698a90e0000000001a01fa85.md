# Compound Engineering：让AI写代码越写越好的方法论

---

用 AI 写代码，你有没有遇到过这种情况——项目刚开始的时候效果挺好，但写着写着，AI 开始反复犯同样的错、忘记之前定好的规范、代码风格越来越乱。你越用它，技术债越厚。

[Slide 2]
这不是 AI 不够聪明，是你的用法有问题。

2025 年底，美国 AI 公司 Every 的 CEO Dan Shipper 和 CTO Kieran Klaassen 发了一篇长文，把他们团队内部的工程方法论完整公开了。他们管这套方法叫 Compound Engineering（复合工程）。

核心理念一句话：每一次工程投入，都应该让下一次变得更容易，而不是更难。

**传统开发为什么越来越难？**

传统软件工程有个大家默认接受的"宿命"——代码越写越多，每加一个功能，下一个功能就更难做。更多代码意味着更多边界情况、更多 bug、更多维护成本。

AI 写代码把这个问题加速了。因为 AI 不记得之前干了什么，每次对话都是从零开始，同样的坑踩了又踩。

复合工程的思路正好反过来：每加一个功能，下一个功能应该更容易做。怎么做到？关键在于每次写完代码之后，多做一步——把经验沉淀下来。

[Slide 3]
四步循环： Plan → Work → Assess → Compound

1. Plan（计划）一 先研究，后动手

在 AI 写所有代码的世界里，开发者的大部分时间其实花在规划上。

一个好的计划从调研开始：让 agent 扫一遍当前代码库和提交历史，理解项目结构和已有的最佳实践；同时搜索互联网上跟当前问题相关的解决方案。调研结束后，agent 写出一份完整的计划文档——功能目标、架构方案、代码思路、参考来源、成功标准，全部列清楚。

规划的目的是在你和 agent 之间建立共同的心智模型：你们到底在造什么东西，先对齐了再动手。好的规划不是甩手委托，它需要开发者深入思考，把 agent 引到正确的方向上。

一旦计划写好了，最难的部分其实就过去了。

2. Work（执行）一 按计划来

这是最简单的一步：告诉 agent 开始干活。它会把计划拆成待办清单，按步骤构建。

[Slide 4]
这 里 有 个 关 键 技 巧 —— 用 Playwright 或 XcodeBuildMCP 这类工具，让 agent 在写代码的同时能像用户一样操作你的应用。它写一段代码，跑一遍 app 看看效果，发现问题就改，循环迭代直到搞定。对设计和交互类任务特别有用。

如果你的计划写得好，新一代模型产出的代码大概率能跑、没明显 bug，而且接近你要的样子。

但再好的产出也要检查。

3. Assess（审查）— 12 个 agent 帮你做 code review

这一步是传统工具和 AI 审查并用：lint 工具和单元测试抓基础错误，手动测试做合理性检查，再加上 Claude、Codex 等自动代码审查 agent 来抽查常见问题。

最狠的是并行审查——复合工程插件会同时派出 12 个 sub-agent，每个从不同角度审视代码：一个查安全漏洞，一个查性能问题，一个看有没有过度设计导致臃肿……所有视角的反馈汇总起来，由开发者决定哪些必须修、哪些可以放。

但复合工程真正的威力在下一步——确保你不会再

[Slide 5]
踩同样的坑。

4. Compound（沉淀）一 这才是灵魂

这是整套方法论中最值钱的一步。

把前面所有步骤中学到的东西——bug、性能隐患、新的解决思路——记录下来，让 agent 下次能用上。这就是"复合"的含义：经验不会蒸发，而是叠加。

举个具体例子：在 Every 的邮件助手 Cora 的代码库里，agent 在构建任何新功能之前，都必须先问自己几个问题——这个功能属于系统的哪个位置？该加到现有模块里还是单独建一个？以前有没有解决过类似问题？这些问题的答案，加上团队过去犯过的具体技术错误，会引导 agent 在正确的位置用正确的方式去写。

而且这些经验沉淀大部分是自动化的——代码审查结束后，agent 自己会总结评论、存下来备用。最新的模型已经聪明到能自己完成这些，下次也真的会用上。

更妙的是，这些积累会自动分发给整个团队。因为它们就写在代码库的文档和 CLAUDE.md 里，每

[Slide 6]
个人都免费获得。一个新入职的工程师，第一天就能享受到所有前人积累的经验，在避免常见错误上跟老员工一样从容。

**80% 的精力在计划和审查上**

这个比例是反直觉的。

大多数人用 AI 写代码的方式是：花 80% 时间让 AI 写，20% 时间自己检查。复合工程刚好反过来——80% 的精力花在 Plan 和 Assess 上，只有 20% 用来实际写代码。

因为 AI 最大的问题不是"写不好代码"，而是"不知道该写什么代码"。你给它足够的上下文——代码库现状、历史决策、框架规范、项目约定——它写出来的东西比你手写的好。但如果什么都不给，它就只能瞎猜。

所以复合工程的本质不是让 AI 更能干，而是让 AI 的上下文越来越丰富。每一轮循环沉淀的经验，都会成为下一轮的"起跑线"。跑十轮之后，AI 对你的项目已经比大多数新入职的工程师更了解了。

**这不是理论**

[Slide 7]
Every 团队用这套方法维护 5 个线上产品——Cora 、 Spiral 、 Sparkle 、 Monologue 、 Studio，每天服务几千用户。这不是实验室论文，是每天在用的东西。

如果你正在用 Claude Code、Cursor 或者其他 AI 编程工具，但总觉得"AI 越用越笨"，这篇原文值得仔细读一遍。核心 takeaway 就一句话： 不是 AI 不够好，是你没有帮它积累记忆。
