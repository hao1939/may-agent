# Aftermath review lessons

## Duration-gate sessions
- If a session is duration-gated for being too short, evidence of value must include at least one durable output: (1) an artifact summarizing findings + next steps, (2) a low-risk patch with verification, or (3) an escalation message with concrete evidence. Pure exploration (reads/queries) is not sufficient.

## Rolling research digests
- When a research session appends findings to a rolling workspace digest, judge task value from the session's landed commit diff plus source-fetch evidence, not only from the current digest contents after later sessions have appended more material.
- A small scout digest append is a real success when the session turns fetched external results into a specific reusable implication and lands a clean single-file commit; an initial ignored-path `git add` failure and a first `finish(success)` blocked for missing read-back are minor efficiency losses if recovery is immediate and the final diff is correct.

## Hypothesis-hardening heartbeats
- A heartbeat that extends an existing knowledge entry with a quantified baseline and explicit falsifier can be a genuinely valuable success even without code changes. Judge from the landed diff, commit, and post-write verification: if the session turns a vague system complaint into a measurable validation plan, treat it as substantive output rather than routine note-taking.
- A heartbeat that actually runs the cheapest listed falsifier and collapses a broader systems hypothesis into a verified local/config fix is high-value output. Score from the decisive experiment and landed artifact, not from the absence of product-code edits; a one-off `finish()` path correction after the fact is only minor efficiency loss if recovery is immediate.

## No-change heartbeat partials
- When a heartbeat ends `partial` with no write/edit calls, no commit, and unchanged project state, treat it as limited-value maintenance even if the agent behaved correctly and documented the blocker well. Routing hints like `project artifact` or `workflow-linked session` are not material output by themselves; confirm an actual landed diff, artifact write, or escalation before calling it a real success.
- An artifact-gate recovery heartbeat that appends a system-relevant status note and lands a clean single-file commit is a real but narrow success. Judge from the landed diff and recovery path, and cap quality when the note publishes live-looking metric values without fresh supporting queries in the session.
- A heartbeat that flips a project frontmatter status (`active` → `waiting`/`done`) does create real value when it resolves inbox/project-state drift, but review must verify semantic alignment across the whole project file. Header-only read-back is insufficient if `Current State`, `Next Action`, or plan text still describes unfinished work.
- A low-signal heartbeat that revalidates a project resume condition with fresh DB/event evidence and lands a project-state update is a real success even without product-code edits. Credit it when the session’s own queries support the new project state and the landed commit keeps reopen criteria explicit.
- A verification/report session that inspects the exact landed diff, validates the relevant tests, and commits a targeted explanation artifact creates real value even without changing product code. Keep credit for the shipped artifact, but downgrade quality if the session still finishes `success` after a post-commit `git status --short` shows the worktree is not clean and no explicit blocker is recorded.
- A persistent-project verification session can still be a real success without code or artifact writes when it resolves a live signal with fresh behavioral evidence (for example, rerunning tests and directly confirming comment/project state). Credit the operational value, but do not treat routed `project artifact` signals or nearby output files as this session's deliverable unless the transcript shows an in-session write/edit or file-producing shell command.
- A heartbeat that only samples global session/error counts and exits without checking the named project resume condition, writing a file, sending an escalation, or proving the failure mode is limited-value maintenance, not a material-output success. Null `sessions.error` fields alone do not justify a "likely timeout" diagnosis.

## Metric-triage completeness
- A repeated-alert session is not complete just because one prior KE explains part of the situation. For aftermath review, require separate live evidence for each red metric named in the task. If a schema-guessing query fails and the session never retries against the real table/columns, treat any claim that the alert was "triaged" as incomplete.
- When routing labels suggest "project artifact" or "knowledge update," verify attribution from actual files: check session IDs in `last-session.md`, current diffs, or committed artifacts before crediting nearby modified files to the reviewed session.
- A no-op metric-acknowledgment heartbeat can be falsely routed as a `success_candidate` when it only re-reads prior KEs and a digest, then finishes `success`. Require evidence of session-time output (write/edit/commit/message/escalation) before treating heuristic "knowledge update" labels as real value.
- When a heartbeat explicitly finishes with "no files written" and transcript evidence shows only queries/reads plus a reworded `finish()`, do not credit nearby earlier commits from a linked subagent/project session as this session's output. Verify attribution from this session's own tool actions before accepting `workflow-linked session` or `knowledge update` routing.
