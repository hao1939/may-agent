## What C1.4 checks

From `agents/may/handlers/convention-check.ts:575` (`checkC1_4_finishClearly`):
- Rule: **the last tool call in the session must be `finish()`**.
- Convention is finish-dependent: infra retroactively corrects failures when `sessions.status IN ('interrupted','error')` or when the session has no `sessions` row (orphan). See lines 216–263 of convention-check.ts.
- For interrupted sessions, checker skips finish-dependent conventions entirely (line 459).

## (b) Pattern of failures

All 11 failures share the same violation message: `"Last tool call was <X>(), not finish()"`. But the underlying *why* splits cleanly into **two disjoint clusters** by session kind:

### Cluster 1 — Heartbeat sessions aborted mid-git (5 sessions, Apr 14–15)

Sessions: `s_1776178278965_178`, `s_1776189080168_279`, `s_1776232826020_0`, `s_1776249024152_110`, `s_1776250825713_129`.

All are `kind=job, source=null, task="[heartbeat] Read agents/may/heartbeat.md..."`.

Transcript signature (checked all 5):
1. Agent calls `finish(success)`.
2. Commit-guard blocks: `"finish() blocked [uncommitted changes]: You have 1 uncommitted file(s) in agents/may/..."`.
3. Agent runs `bash("cd /app/agents && git add may/ && git commit -m ...")`.
4. `stopReason: "aborted"`, `errorMessage: "Request was aborted."` — the session is killed externally (timeout / heartbeat window end) before it can retry `finish()`.
5. `sessions.status` ends up as `"done"` (not `interrupted`), so the retroactive-fix code at convention-check.ts:216 does **not** correct them.

**This is the same "commit-guard launders an abort into a C1.4 fail" pattern coach documented for prove-the-loop Iter 11** (commit 79591a40a, 2026-04-17). It's not a new phenomenon; it just started showing up in may's C1.4 once May picked up heartbeat work that edits workspace files right before finish.

### Cluster 2 — Persistent-task "REVIEW ONLY" owner calls (6 sessions, Apr 16–17)

Sessions: `s_1776343206024_141` (Apr 16), and `s_1776432722205_308 / _318 / _322 / _362 / _368` (Apr 17).

All are `kind=call, source=workflow, task="[REVIEW ONLY — no file edits expected. You are assessing worker output..."`.

These are generated by `agents/shared/workflows/persistent-task.ts:561`: `ctx.runAgent(config.owner, reviewPrompt)`. The review prompt ends with *"Your response MUST start with one of: DONE, BLOCKED, CONTINUE"* (persistent-task.ts:318). **It does not instruct the reviewer to call `finish()`.** The reviewer naturally ends the turn with a `bash` (for evidence) or `read` followed by a plain text response; `stopReason=stop`.

First may workflow-kind session ever: 2026-04-16T14:35Z — i.e. exactly when may started being called as reviewer for persistent-task (tracker commits: ba0d12727 "inject commitAndMerge", 78a4227c3 "inject review rubric" on 2026-04-16).

**Cross-agent check:** same pattern exists on other reviewers: bob=2/283 fails, qa=1/3 fails, all on `kind=call, source=workflow` sessions. This confirms the root cause is the invocation pattern, not may.

## (c) Suspected cause

Two independent infrastructure problems, both legitimate-but-uninteresting C1.4 fails:

1. **Review calls don't require finish().** Persistent-task review calls are one-shot synchronous `runAgent` invocations where the response is the deliverable. Requiring `finish()` adds no value and costs ops. Currently C1.4 penalizes them.
2. **Commit-guard aborts don't classify as interrupted.** When a heartbeat is killed mid-`git commit` after commit-guard blocks `finish()`, the session ends with `status='done'` (because the session exited cleanly from the runtime's POV), so the retroactive interrupt correction at convention-check.ts:216 misses it. These should be classified the same as other externally-terminated sessions.

Neither is a checker bug strictly speaking, and neither is a behavioral regression in may. They're **coverage gaps** that got exercised by new workloads.

## (d) Recommended action

**Flag to may's owner** (not an intervention on may's behavior). Two concrete options, ordered by confidence:

### Patch 1 (high confidence): exempt review-only workflow calls from C1.4

In `agents/may/handlers/convention-check.ts`, in the `isInterrupted` computation (~line 297) or in `runAllChecks`:

```ts
// Review-only workflow calls are one-shot assessments that don't use finish()
const isReviewOnlyCall = sessionRow?.kind === 'call'
  && sessionRow?.source === 'workflow'
  && /^\[REVIEW ONLY/i.test(sessionTask ?? '');
if (isReviewOnlyCall) skipFinishDependent = true;
```

This fixes 6/11 failures (Cluster 2) and also cleans up bob/qa false-positives. Low-risk: whitelist gate, no change to behavior.

### Patch 2 (medium confidence): treat commit-guard-aborted sessions as interrupted

Extend the retroactive correction at convention-check.ts:216 to also match sessions whose transcript ends with `stopReason: "aborted"` OR `errorMessage: "Request was aborted."`, regardless of `sessions.status`. This fixes 5/11 failures (Cluster 1) and will benefit every heartbeat-driven agent.

Alternative (cheaper but noisier): update the commit-guard or the heartbeat runtime to set `sessions.status='interrupted'` when a heartbeat is killed after commit-guard aborted a finish retry chain. This belongs to tech-lead/may, not coach.

### Do NOT intervene on may behaviorally

- KE-002 (text rules 0/20) and KE-007 (workflow enforcement is the only reliable intervention) both say a behavioral intervention here would fail.
- The numeric "regression" (100% → 94.4%) is ~5pp noise driven by infra interactions, not by any may-side behavior change. Intervening on may to "always remember to call finish()" would be both pointless (it's already doing so) and harmful (it would add friction to review calls where finish is unnecessary).
