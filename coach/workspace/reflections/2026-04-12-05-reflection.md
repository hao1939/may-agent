## Synthesis

### Theme 1: Workflow-First Adoption Needs a Systematic Plan

**Core directive**: The system should adopt a "workflow first" approach to agent harnessing — meaning agents should default to using workflows rather than ad-hoc forked sessions. But this adoption needs a plan, not random incremental additions.

**Evidence connection**: Our data strongly supports workflow-first:
- EXP-028: Workflow collapse (heartbeat instruction removed) → 51pp done-rate degradation
- EXP-001: Workflow sessions = 89% done, 2.6% error vs non-workflow 76% done, 17.6% error
- EXP-050: implement-and-verify adds overhead for simple tasks but structure helps complex ones
- EXP-144: Structured gates serve as "task decomposition aids" that speed execution (+16% when removed)
- REGISTRY: implement-and-verify has 85% of all workflow usage (~79 sessions in 48h) — adoption IS happening where wired in

**What's missing**: A systematic adoption roadmap that says:
- Which agents should use which workflows
- When to use workflow.run vs direct fork
- Who owns creating/maintaining each workflow
- How to measure adoption success

### Theme 2: May's Dispatch-and-Review Pattern

**Gap identified**: May dispatches lots of work via `agents.fork()` or `agents.call()` but doesn't systematically review the output. Hao wants a workflow that:
1. Dispatches the work
2. Reviews the output quality
3. Potentially retries or escalates

**Coach observation**: This is essentially the `implement-and-review` pattern (coder + QA) but for May's operational dispatching. Our data shows implement-and-review had a broken verdict parser (6% completion rate in old version, fixed since). The `project-monitor` workflow in May's folder already does something similar but it's never used (0 runs).

### Theme 3: Async vs Sync Workflow Architecture

**Design tension**: Hao wants workflows to be async (non-blocking) but recognizes the complexity. Resolution: keep sync for now, design async later.

**Architectural constraint for May**: May must stay responsive to human commands. So May cannot block on a long workflow. Solutions:
1. May forks a session that runs a sync workflow (workflow in a fork)
2. May dispatches to another agent that runs the workflow
3. May uses `agents.call()` with a timeout

**For Coach**: This doesn't directly affect Coach (we don't interact with Hao in real-time). But it's relevant because Coach's workflows (growth-cycle, training-sprint) are already sync and work well. The async question is primarily a May/optimizer concern.

Hao's "Again" and "what's the data?" signals that the system hasn't been tracking and reporting workflow adoption status well enough. The REGISTRY has usage data, but it's not proactively surfaced.
