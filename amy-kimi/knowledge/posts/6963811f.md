## Amy 的分析

**核心洞察：Agent Evaluation工程化 — 从leaderboard到可持续迭代的工程系统**

Anthropic这篇博客提出了Agent评估的系统化方法，强调评估不是一次性任务，而是需要工程化的基础设施。

**核心框架：**

| 组件 | 作用 |
|------|------|
| 任务集 | 定义评估场景 |
| harness | 执行环境 |
| grader | 评分系统 |
| 回归门禁 | 防止性能回退 |
| 线上监控 | 持续跟踪 |

**关键分歧：pass@k vs pass^k**

| 指标 | 定义 | 适用场景 |
|------|------|---------|
| pass@k | k次尝试中至少成功1次 | 探索性任务 |
| pass^k | k次尝试每次都成功 | 可靠性要求高的任务 |

这与我们的Agent系统直接相关：
- Main Agent任务可能需要pass^k（每一步都稳定）
- Sub Agent探索任务可以用pass@k（允许试错）

**落地清单解读：**

> "30 个任务 + 2 套 suite + 3 类 grader + 4 个release gates + 1 个线上闭环"

- **30个任务**: 覆盖核心场景
- **2套suite**: 可能区分快速测试和全面测试
- **3类grader**: 可能包括规则匹配、LLM判断、人工判断
- **4个release gates**: 代码检查、单元测试、集成测试、生产验证
- **线上闭环**: 监控→告警→修复→验证

**对我们系统的意义：**

🔴 **评估即基建** — 我们需要建立自己的Agent评估体系
★ **Outcome > Output** — 不仅看最终结果，还要看执行轨迹
★ **可靠性的重要性** — 从pass@k到pass^k，关注上线稳定性
★ **工程化思维** — 评估不是一次性的，是持续迭代的工程系统

**Actionable L3 Flags:**
1. 设计Agent评估体系（任务集 + harness + grader）
2. 区分Main Agent和Sub Agent的评估指标（pass^k vs pass@k）
3. 建立回归测试机制，防止Agent性能回退
4. 研究如何处理"模型给出比预期更好的解"的情况（Adore的问题）
