## 正文
最近在折腾怎么让 OpenClaw 记住更多东西。

它自带的 qmd 方案轻量是好，但文档一多就吃力。之前几十页资料还能应付，后来项目变大，想找个更强力的记忆方案。

目前同时在试 3 个路线：

**第一版：memos**
让它把记忆写成笔记存进去，需要时再搜。目前基础功能跑通了，还在看长期稳定性怎么样。

**第二版：RAGFlow**
检索能力确实强，配置也相对完善。现在在做性能和易用性的对比测试。

**第三版：OpenViking（字节开源）**
这个月新试的 Agent 上下文管理方案。

它给资料做了个「虚拟文件系统」，自动分三层：
- **L0** 一句话摘要（知道这个文件讲啥）
- **L1** 详细概览（了解关键信息）
- **L2** 完整内容（需要时再读）

Agent 查资料时先搜关键词，命中之后只读 L1 概览。不够的话再按需加载 L2，不用每次塞整本书进 prompt。

语义搜索还结合了目录结构，找资料准了很多。

**配置步骤：**
pip 装一下，写个配置文件，设个环境变量，跑个测试脚本就通了。

**API 设计：**
- `add_resource()` — 扔文件进去
- `find()` — 语义搜
- `abstract()` / `overview()` — 拿摘要/概览
- `read()` — 需要时再读全文

最方便的是有人做了 OpenClaw 的 skill，装完直接 `viking.py search` 就能用。

⚠️ **成本警告**：记忆系统本身是依赖 Chat LLM 模型的。如果你本来没有开启 OpenClaw 的记忆功能，开启之后 Token 消耗会暴增 —— 因为每次对话都要带上一大堆历史上下文。这个成本要有心理准备。

目前 3 个方案都在跑，后续会把完整体验对比发出来，包括配置复杂度、检索准确度、维护成本这些维度。

## Amy 的分析

**核心洞察：OpenViking 的分层记忆架构验证了我们的知识分层设计**

OpenViking 的 L0/L1/L2 三层模型：
- L0 一句话摘要 → 对应我们的 `insights-index.json` / `insights.md` 顶部汇总
- L1 详细概览 → 对应 `insights.md` 中各条目的详细分析
- L2 完整内容 → 对应 `posts/<id>.md` 深度归档

这验证了我们现有的知识架构是合理的，但 OpenViking 提供了更系统化的实现：
1. **虚拟文件系统抽象** — 统一接口管理不同来源的知识
2. **按需加载机制** — 避免上下文爆炸
3. **语义搜索+目录结构结合** — 提高检索准确度

**对我们系统的意义：**
- 我们的 `insights/posts` 分层 = 自然的 L1/L2 分离
- 可以借鉴 OpenViking 的 `add_resource()` / `find()` / `abstract()` API 设计
- 成本警告很重要：记忆功能开启后 Token 消耗暴增 —— 这与我们在 NikolaFu 分析中提到的"链路一致性成本"相呼应
