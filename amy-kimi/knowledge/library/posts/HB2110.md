# HB2110: 你的Skill没用，因为你只写了个markdown

**作者**: Zero
**发布时间**: 27分钟前 上海
**热度**: 5赞/2收藏
**链接**: https://www.xiaohongshu.com/explore/69ba09fd000000002103a04e

## 核心观点

Anthropic内部使用几百个Skill后的经验总结，颠覆认知的关键洞察：

### 1. Skill不是一个文件，是一个文件夹
- 文件夹可以塞脚本、参考代码、数据
- Claude会自己翻阅这些文件，在需要时读取
- 渐进式披露：只在需要时才给完整信息

### 2. 三类最实用的Skill

**产品验证类**
- 用playwright自动走流程：注册→验证→断言状态
- Anthropic原话："值得让一个工程师花一周专门打磨验证类Skill"

**业务自动化类**
- 日报、建工单、发周报等重复劳动
- 可在Skill里存日志文件，Claude能读到上次记录，知道"昨天已汇报过，今天只说新的"

**Runbook类**
- 线上问题排查步骤：看日志→查监控→看部署记录
- Claude按步骤执行，最后出排查报告

### 3. 写Skill的关键技巧

**别写Claude本来就知道的东西**
- 不要写"使用React要注意组件生命周期"这种废话
- 要写能把它从默认思路里拉出来的信息
- Anthropic示例：前端设计Skill专门纠正Claude默认爱用Inter字体和紫色渐变的毛病

**Gotchas是Skill的灵魂**
- 记录Claude用你的Skill时犯过的错
- 下次生成前先自查
- Anthropic原话："Skill里最值钱的内容就是Gotchas"

**用文件夹做信息分层**
- 主文件写核心流程和注意事项
- 详细API签名放references/api.md
- 模板放assets/template.md
- 告诉Claude这些文件在哪，它会自己去读

**不要把Claude绑太死**
- 写清楚"做什么"和"千万不要做什么"就够了
- 不要把每一步都规定死，Claude需要灵活空间
- 示例：写"发布前必须跑测试"，不用写"先cd到项目目录，然后运行npm test..."

**description字段不是给人看的**
- Claude每次对话开始会扫所有Skill的description
- 靠这个判断"当前请求要不要用某个Skill"
- description是触发条件，不是摘要
- 要写清楚在什么场景下应该触发

## 对我们的意义

1. **验证我们的Skill设计方向** - 我们已将Skill定义为包含SKILL.md + 实现文件的文件夹结构
2. **Gotchas机制** - 需要建立错误记录和积累机制，让Skill越用越聪明
3. **description作为触发器** - 我们的SKILL.md中description字段需要重新审视，是否是条件触发式描述
4. **渐进式披露** - 大型Skill应采用多文件组织，避免单文件信息过载
