## 核心论点

AI交互方式经历了三阶段进化：

### 阶段1: Prompt Engineering (提示词工程)
- **比喻**: 教你怎么对马喊话
- **机制**: "你是一个资深专家"、"分步思考"
- **局限**: 单次小任务够用，复杂任务容易迷路

### 阶段2: Context Engineering (上下文工程)
- **比喻**: 给马塞一张地图
- **机制**: 喂背景资料、API文档
- **局限**: 上下文窗口有限，资料多了容易看花眼

### 阶段3: Harness Engineering (脚手架/护栏工程)
- **比喻**: 修一条带护栏的高速路
- **核心**: 包围AI的一整套运行环境、约束规则和闭环反馈系统
- **哲学转变**: 默认AI会犯错 → 通过环境兜住下限

## Harness系统三要素

| 要素 | 功能 | 比喻 | OpenClaw对应 |
|------|------|------|-------------|
| **装上手脚** | 工具执行 | AI接文件系统/命令行 | Skill系统 |
| **建防撞护栏** | 强约束与反馈 | 自动跑测试，报错甩日志 | **Error Log审计** |
| **外包记忆** | 状态管理 | 外部工作进度表，强制读档 | SIGNALS.md + AGENTS.md |

## 关键洞察

### 1. "护栏"隐喻的社区传播
Harness原意是**马具、缰绳**，引申为**约束系统**。

这与OpenClaw的"Claw"隐喻形成有趣对照：
- **Harness** = 从外部约束 (被动防护)
- **Claw** = 主动抓取/控制 (主动干预)

两者本质相同：**环境 > 提示词**

### 2. 错误认知转变
> "以前AI出错，总以为是提示词没写好；  
> 在Harness时代，AI出错是**系统工程问题**——测试环境和护栏没搭好"

这与OpenClaw的设计哲学完全一致：
- ❌ 不追求"更好的提示词"
- ✅ 追求"更好的约束环境"

### 3. 三阶段与OpenClaw架构映射

```
Prompt Engineering  →  AGENTS.md角色定义
Context Engineering →  上下文注入(文件+知识库)
Harness Engineering →  Error Log + SIGNALS.md + read_by
```

## 社区验证

该帖将Harness Engineering描述为：
> "眼下最前沿的玩法，让AI独立完成复杂大项目的**核心秘密**"

OpenClaw的核心机制 (Error Log审计、SIGNALS.md流程、read_by追踪) 正是Harness Engineering的**具体实现**。
