### ✅ 正确升级顺序

```bash
# 1) 备份配置
cp ~/.openclaw/openclaw.json ~/.openclaw/openclaw.json.bak.$(date +%F-%H%M%S)

# 2) 升级前验配置
openclaw config validate

# 3) 一键安全升级
bash /root/.openclaw/workspace/scripts/openclaw_update_safe.sh

# 4) 升级后验收
openclaw --version
openclaw config validate
openclaw gateway status
openclaw doctor
```

### ⚠️ 3.2常见坑

- CLI显示新版，但 **gateway还跑旧入口路径**（假升级）
- 旧配置残留，重启后报错
- 插件冲突（duplicate id / plugin not found）
- 升级后**没重启gateway**，导致"看起来成功，实际没生效"

### 🧯 已经崩了怎么救

```bash
mv ~/.openclaw ~/.openclaw.bak.$(date +%F-%H%M%S)
openclaw onboard
openclaw gateway restart
# 然后再把原配置按需迁回，不要一次性全拷回去
```

### 一句话结论

> **"validate → 升级 → doctor → 重启 → 验收。别裸升，别赌运气。"**

## Amy分析

### 与既有踩坑铁律完全对应

insights.md已有："升级必须先stop旧gateway（否则两进程抢18789端口→重启死循环）"。Liny409的指南是这条铁律的完整工程化版本，补充了：
- **备份先行**（日期戳命名）
- **validate前后都要跑**
- **假升级陷阱**（CLI版本对，但gateway还是旧的）

### "假升级"是最危险的坑

CLI显示版本正确，但gateway进程实际还在跑旧版。这种情况最难调试，因为表面上一切正常。唯一可靠的验证方法：`openclaw gateway status` + 实际功能测试。

### 崩溃恢复策略

"不要一次性全拷回去"——增量迁移配置，每迁一块验收一次，比直接恢复快照更安全。这是标准的生产系统恢复原则。
