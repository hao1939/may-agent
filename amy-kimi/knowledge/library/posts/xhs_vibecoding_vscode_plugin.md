**Vibecoding不是终点，架构不会自己长出来。**

作者将Vibecoding做成了真正能落地的VS Code插件(Dish AI Commit Message Gen)，分享了从Demo到产品的工程化思考。

---

## 关键洞察

### 1. 真正有价值的不是生成速度
> "很多人觉得 Vibecoding 就是'AI先写一版，能跑就行'。但真正有价值的是能否将Demo打磨成开发者愿意放入日常工作流的产品。"

### 2. 非"性感"但核心的工程问题

**统一Provider抽象**：支持20+模型供应商(OpenAI, Gemini, Ollama等)。如果不做底层抽象，随之而来的就是混乱的条件分支。

**兼容复杂现实场景**：处理多仓库Workspace、Git/CLI Fallback甚至SVN场景。工具的生命力在于处理这些"非理想路径"。

**上下文质量决定输出**：比起更换昂贵模型，通过Tree-sitter + Qdrant增强语义索引。开发者要的是"像靠谱同事写的东西"，这取决于喂给AI的上下文是否精准。

### 3. AI无法替代的核心判断
- 模块职责拆分与接口边界设定
- 配置迁移的稳定性与复杂度控制

> "我刻意用工程化约束去'驯服'AI：坚持模块化分层、遵守SOLID原则，避免让代码沦为一摊Prompt Spaghetti(提示词意面)。"

> **"AI可以写代码，但不能替我承担架构后果。"**

### 4. 从"炫技"走向"收敛"

| 阶段 | 特征 |
|------|------|
| Vibecoding作为放大器 | 降低"开始"的门槛，快速进入可验证阶段 |
| 拉开差距的是"收敛能力" | AI让生成代码变得廉价，稀缺的是判断"什么不该做" |
| 进入真实场景才有分量 | 减少工作摩擦、缩短决策链路 |

## 与OpenClaw的关联

**验证点**：
1. **架构不会自己长出来** → 与OpenClaw Skill分层设计、L0-L3架构理念一致
2. **上下文质量>模型能力** → 验证AGENTS.md被动上下文注入的价值
3. **工程化约束驯服AI** → Skill-Vetter作为安全边界的设计合理性
4. **什么不该做** → 与禁止运行时自进化的立场呼应

> "我选择的路不是让AI替我做产品，而是利用AI，把产品做得更快、更深、更完整。"
