## 正文
Codex 0.102.0更新后支持自定义Multi-Agent角色了。以前只有三个内置角色（Default继承父级、Explorer用Mini探索代码库、Worker实现和测试），现在你可以创建任意数量的自定义角色，每个都能独立配置model、reasoning、system prompt、权限、MCP和Apps。

配置结构是双层的。第一层在config.toml里注册角色，只需两个字段：description告诉Codex什么时候该调这个角色，config_file指向详细配置。第二层在.codex/agents/目录下，每个角色一个toml文件，定义model、reasoning level、developer_instructions等。角色配置只有被实际调用时才加载，不浪费父session的token。

配置文件层级化加载：全局~/.codex/→项目根目录→子目录，越深优先级越高。所以你可以在monorepo里给不同子项目定义专属角色，比如mobile-app目录下放一个专门的移动端reviewer。

9大配置项：Model和Reasoning Level（如5.3 Codex High）、developer_instructions（角色专属system prompt）、description（控制何时被调用）、权限（read-only或read-write沙盒）、MCP Servers（每个角色独立配，如Linear、GitHub）、ChatGPT Apps（Notion、Monday等按角色开关）、Features（memory和shell开关）、Scope（全局或项目级）、Personality（verbosity和风格）。大多数情况只需设model+reasoning+developer_instructions，其他省略自动继承父级。

隐藏技巧：默认最多6个并行agent，但config.toml里加[agents] max_threads = 12就能突破（太多会429限流）。Skills和Subagents可以互相调用，比如frontend_arch角色里写"Use the $frontend-design skill"。developer_instructions里加输出模板，agent会可靠遵循格式输出结构化结果。

作者最推荐的组合：5.3 Codex High做主编排agent负责规划和全局理解，Spark作为subagent负责快速执行实现任务。

25个预置角色已开源在GitHub（am-will/codex-skills/agents），包括security_auditor、performance、backend_arch、product_analyst、frontend_arch等，每个都有config.toml入口和完整role配置，直接下载放进.codex/agents/就能用。

## 关键引用
- Codex version: 0.102.0
- GitHub: am-will/codex-skills/agents (25 pre-built roles)
- Recommended combo: 5.3 Codex High (orchestrator) + Spark (executor)
- Max parallel agents: default 6, configurable to 12 (risk of 429 rate limit)

## Amy 的分析
**核心洞察：Codex Multi-Agent架构的深度技术解析**

奥森木这篇帖子是对Codex 0.102.0 Multi-Agent系统的最完整中文解读。与OpenClaw对比， reveals interesting architectural differences:

**Codex Multi-Agent Architecture:**
```
config.toml (registry)
    ↓ description → when to invoke
    ↓ config_file → agent definition
.codex/agents/
    ↓ per-role toml: model, reasoning, developer_instructions
    ↓ lazy loading: only loaded when invoked (token efficient)
```

**9 Configuration Dimensions:**
| Dimension | Purpose |
|-----------|---------|
| Model + Reasoning | e.g., 5.3 Codex High |
| developer_instructions | Role-specific system prompt |
| description | Invocation trigger |
| Permissions | read-only vs read-write sandbox |
| MCP Servers | Per-role (Linear, GitHub, etc.) |
| ChatGPT Apps | Notion, Monday, etc. |
| Features | memory, shell on/off |
| Scope | global vs project-level |
| Personality | verbosity, style |

**Key Design Patterns:**
1. **Hierarchical config loading** — ~/.codex/ → project root → subdir (monorepo-friendly)
2. **Lazy loading** — Role config only loaded when called, saves parent session tokens
3. **Skills ↔ Subagents interop** — `Use the $frontend-design skill` inside role definition
4. **Output templating** — Structured results via developer_instructions templates

**Codex vs OpenClaw Comparison:**
| Feature | Codex | OpenClaw |
|---------|-------|----------|
| Role config | 9 dimensions | SOUL.md + AGENTS.md |
| Loading | Lazy (on invoke) | Eager (heartbeat) |
| Parallel | 6 default, 12 max | Subagent spawn |
| MCP | Per-role | Global skill system |
| Hierarchy | Config file inheritance | Directory-based workspace |

**对我们系统的意义：**
★ **Lazy loading for roles** — Our eager loading may waste tokens; Codex's approach is more efficient
★ **Hierarchical config** — Our flat workspace structure vs Codex's nested config inheritance
★ **MCP per-role** — Fine-grained tool access control vs our global skill system
★ **Pre-built role library** — 25 roles open-sourced; community sharing of role definitions emerging
★ **Model + reasoning combo** — "5.3 Codex High + Spark" = orchestrator + executor pattern validates our multi-model approach

**Strategic observation:**
Codex is becoming a sophisticated "Agent OS" with deep configurability. OpenClaw's strength is simplicity and modularity. Different philosophies, both valid.
