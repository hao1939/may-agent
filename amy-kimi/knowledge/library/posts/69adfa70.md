## 核心内容

OpenClaw新版支持**ACP持久化绑定**，可直接将Telegram topic连接到Codex或Claude Code后端。

### ACP是什么
- **Agent Client Protocol** — 标准协议桥梁，不是模型也不是模式
- 将聊天工具与AI agent后端连接
- 会话持久化，重连后上下文保留

### 推荐群结构（三topic分离）
| Topic | 绑定 | 用途 |
|-------|------|------|
| General | 无 | 正常聊天，不绑ACP |
| Codex | ACP→Codex | 写代码、修bug、做功能 |
| Claude | ACP→Claude Code | 代码审查、重构复杂逻辑 |

### 配置三步
1. 在bindings里写映射（chat id + topic id → agent）
2. **启用ACPX runtime插件**（最容易漏）
3. 重载gateway生效

### 排查四步（发消息没反应）
1. 查binding存在性和id正确性
2. 查agent状态（ABSENT=后端没起）
3. 用ACP探针定位问题层
4. **查acpx插件是否enabled**（最常见根因）

### 两大坑
1. **General不要绑ACP** — 否则聊天=工作输入，彻底混掉
2. **不要用runtime spawn硬开** — 正确做法是在bindings写明确映射后重启gateway，原生绑定才稳

## 洞察

1. **聊天即工作界面** — ACP将生产环境agent能力直接注入日常通讯工具
2. **多Agent隔离而非协作** — Codex和Claude分topic独立运行，而非交互
3. **配置>功能** — "线插好了标签贴好了但工位没通电"，最常见问题是acpx插件未启用

## 对我们的意义

- **ACP协议定位**: OpenClaw作为Agent平台，通过ACP同时扮演Agent和Client角色
- **聊天优先界面**: Telegram/Slack成为主要交互层，IDE退居二线
- **生态连接**: ACP调用*别的*agent服务 vs Sub-agent调用*自己的* — 这是关键区别
