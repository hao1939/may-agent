## 内容摘要

作者读ClawdBot的GitHub代码后，总结其长期记忆实现原理：**两步法：持久化存储 + 精准检索**

### 第一步：持久化存储

对话全部写入 `memory/日期.md` 文件，文件变化触发自动索引：

```
文件监听（Chokidar）检测到 memory/日期.md 变化
  → 自动分块（chunking）
  → 向量化（OpenAI embedding，1536维）
  → 建索引
  → 写入五张SQLite表：
    1. 主表（原始内容）
    2. 向量索引表（chunks_vec，sqlite-vec）
    3. 全文索引表（chunks_fts，FTS5/BM25）
    4. 缓存表
    5. 元数据表
```

### 第二步：混合检索精准召回

查询时并行运行两路搜索，加权合并：

```
用户查询："Alice 负责的项目是啥？"
    ├── 向量检索（chunks_vec，70%）：理解语义，"负责"≈"负责人"
    └── 关键字检索（chunks_fts，30%）：精确匹配，"Alice"必须一致
                ↓ 加权合并（0.7:0.3）
            最相关几条 → 喂给 AI
```

为什么混合？
- 单用向量：专有名词容易混淆
- 单用关键字：换个说法就搜不到
- 两者互补，覆盖更多查询场景

### 技术栈
- **存储**：Markdown + SQLite
- **向量**：OpenAI embedding（1536维）
- **向量检索**：sqlite-vec
- **关键字检索**：FTS5（BM25算法）
- **文件监听**：Chokidar

### 核心设计哲学
> "本质是建立可检索的知识库，通过文件绑定数据库的方式。"
> "不是把历史对话全塞进prompt（token撑不住），而是按需召回：搜索→返回最相关的几条→喂给AI"

**长期记忆 = 持久化存储 + 精准检索**

## Amy分析

### 这就是我们系统的技术参照
ClawdBot的实现与我们现有的文件架构有直接对应：
- `memory/日期.md` ← 我们的 `JOURNAL.md`（按HB追加）
- 持久化存储层 ← 我们的 `knowledge/amy/posts/` + `insights.md`
- 按需召回 ← 我们的 `memory_search` 工具

关键区别：ClawdBot做了**向量化索引**（OpenAI embedding），而我们目前依赖`memory_search`的语义搜索（底层实现未知，但效果已够用）。我们没有自建SQLite，但memory_search已经承担了"按需召回"的角色。

### 混合检索的工程智慧
向量70% + 关键字30% 的比例值得记住：
- 70%语义（处理表达变化，"负责"≈"负责人"）
- 30%关键字（处理专有名词，"Alice"精确匹配）

这与我们的经验一致：在insights.md中，某些关键词（如"compact"、"HB244"）需要精确匹配，而概念（如"多Agent架构"）需要语义理解。

### Chokidar文件监听 = 我们compact触发的设计参照
ClawdBot用Chokidar监听文件变化自动触发索引。我们的compact是手动触发（行数达到阈值）。更理想的设计可能是：`insights.md`写入时自动检测行数，超过阈值自动compact——但这需要工具层面的支持，当前手动机制已经够用。
