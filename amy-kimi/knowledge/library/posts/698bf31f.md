## nanocode简介

单Python文件、零依赖、不到300行，核心闭环是通的。

**目标**：说明白"最少要有哪几块，Agent才能稳定干活"。

---

## 四个核心模块

### 1) 模型路由
环境变量控制API路径：
- 有`OPENROUTER_API_KEY`走OpenRouter
- 否则走Anthropic
- `MODEL`可直接覆盖默认模型

**取舍**：轻、快、好迁移，但多环境治理较弱 → MVP阶段成立

### 2) 工具执行面
六个必要动作：`read/write/edit/glob/grep/bash`

**关键细节**：`edit`默认只替换一次，匹配多处且无`all=true`时报错 → 避免手滑改错

### 3) 工具协议生成
`make_schema()`动态将`TOOLS`参数定义转成`input_schema`

**优势**：新增工具只需1)写函数 2)在`TOOLS`注册 3)主循环不用改

### 4) Agentic循环
```python
# agentic loop: keep calling API until no more tool calls
```

执行语义：
- 模型返回`tool_use` → 本地执行工具
- 将`tool_result`作为新消息回传
- 直到没有`tool_use`才结束本轮

## 分析

### 设计哲学
nanocode展示的是"Unix哲学"在Agent领域的应用：
- 只做一件事，做好它
- 工具组合优于功能堆砌
- 显式优于隐式（edit的all=true参数）

### 与我们的对比
| 维度 | nanocode | 我们的设计 |
|------|----------|-----------|
| 复杂度 | 300行极简 | 生产级完整 |
| 核心验证 | Agent能稳定运行的最小集 | 企业级安全+可扩展 |
| 取舍逻辑 | 快、轻、易验证 | 稳、隔离、可审计 |

### 关键洞察
nanocode验证了我们架构的**必要性判断**：
- ✅ Agent loop — 必要
- ✅ Tool调度 — 必要
- ✅ 上下文管理 — 必要
- ❓ Memory — nanocode无，但复杂任务需要
- ❓ 多Agent — nanocode无，特定场景需要
