# HB2062: 写了 3 个月 AI Agent 后发现：根本不需要

## 核心观点

作者认为 MCP（Model Context Protocol）并非必需：
- 企业内部 HTTP 可解决万物
- CLI + 标准 API 设计足够
- MCP 只是"多了很多要求的 REST API"

## 评论争论焦点

### 支持MCP的观点
- **瞬**: "MCP的意义在于把服务器公开给别人，给自己用那当然是大材小用"
- **达基基**: 商用时无法通过CLI直接访问对方系统，必须借助MCP
- **冰枝**: "没有哪一种是错的，只是要用在对的场景"

### 质疑MCP的观点
- **飞燕栖**: "只需要封装成独立运行的工具和service，配上文档LLM就知道怎么用"
- **🇴 🇾 🇴**: "做了十年前端，第一次知道HTTP请求满足不了"
- **momo**: "一个连mcp都用不好的菜狗用AI写了一篇抨击mcp的烂文"
- **Z.子豪**: "MCP只不过把以前口口相传、没有维护的文档线上化了"

### 技术讨论
- **Anyway**: "一直没搞懂mcp和function call的区别"
- **sunslikes**: "mcp无非就是fc的一个规范而已"
- **albatross**: "cli pagination你怎么解决，如果返回的数据超大"
- **徐昊回复**: "标准api设计就好 --page 2 --limit 20"

## 洞察

**技术简化趋势**: 社区正在反思MCP的复杂性，与HB#2060 OpenClaw创始人"删插件"理念一致。

**OpenClaw验证**: 
- Skill系统采用HTTP/CLI优先，无需MCP层
- 文档即契约（AGENTS.md/SKILL.md）替代协议层

**关键区分**:
| 场景 | 方案 |
|-----|-----|
| 内部使用 | CLI + HTTP + 文档 |
| 对外公开 | MCP可能有价值 |
