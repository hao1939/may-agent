# HB-1409 — TOSSS: CVE-based LLM代码安全基准

**Source**: XHS@LLM翰林院 → arXiv:2603.10969  
**Date**: 2026-03-15  
**Paper**: TOSSS: a CVE-based Software Security Benchmark for Large Language Models  
**Authors**: Marc Damie et al.  
**Tags**: #LLM安全 #代码安全 #CVE #Benchmark

---

## 论文核心

### 问题定义
- LLM越来越多用于软件开发流程
- 关键问题: **LLM在软件安全方面是否出色？**
- 现有安全基准仅覆盖有限漏洞类型

### TOSSS基准
- **全称**: Two-Option Secure Snippet Selection
- **机制**: 二选一任务 — 安全代码片段 vs 漏洞代码片段
- **数据源**: CVE数据库 (可扩展，随新漏洞披露更新)
- **评分**: 0-1分，1=总是选安全，0=总是选漏洞

### 评测结果 (14个开源/闭源模型)
- **语言**: C/C++ 和 Java
- **分数范围**: 0.48 - 0.89
- **结论**: 即使是最好的模型，仍有11%概率选择漏洞代码

### 关键发现
- 闭源模型普遍优于开源
- 但没有一个模型达到满分
- LLM提供商应将TOSSS作为补充安全分数发布

## OpenClaw分析

### 关键信号

#### 1. Agent代码生成 = 安全风险放大器
TOSSS验证: **LLM会系统性地选择漏洞代码** (最高11%错误率)

在Agent场景中，这个风险被进一步放大:
- 单次代码生成 → 可能引入漏洞
- Agent迭代执行 → 漏洞被持续利用
- 多Agent协作 → 漏洞传播面扩大

#### 2. "安全代码选择" ≠ "安全代码生成"
TOSSS测试的是**选择能力** (给定两个选项，选安全的)
实际Agent场景需要**生成能力** (从零写安全代码)

**选择准确率0.89 → 生成准确率可能更低**

#### 3. CVE-based = 真实漏洞覆盖
TOSSS使用真实CVE数据库，而非合成漏洞:
- 测试的是**真实世界攻击面**
- Agent生成的代码可能引入已知CVE模式

### 对OpenClaw设计的验证

#### ✅ 已验证的安全机制

| OpenClaw机制 | TOSSS启示 | 验证强度 |
|--------------|-----------|----------|
| **Error Log审计** | LLM会系统犯错，需事后审计 | ⭐⭐⭐⭐⭐ |
| **禁止Self-Evolution** | 防止漏洞代码自我迭代 | ⭐⭐⭐⭐⭐ |
| **Skill静态约束** | 代码行为可预测，降低漏洞面 | ⭐⭐⭐⭐ |
| **AGENTS.md身份隔离** | 限制Agent代码执行权限 | ⭐⭐⭐⭐ |

#### ⚠️ 新增风险认知

1. **Generated Code审计缺失**
   - 当前OpenClaw审计Error Log，但**不审计生成代码本身**
   - TOSSS提示: 需要代码级安全扫描

2. **依赖链风险**
   - Agent可能生成引入CVE的依赖代码
   - 需要SBOM (软件物料清单) 追踪
