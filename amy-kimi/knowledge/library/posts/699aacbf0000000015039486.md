**场景三：聊了半小时的上下文，一刷新全没了。**

这个不用多说，用过 AI 的人都懂。

问题的根源是什么？**Agent 之间没有共享记忆。**

每个 Agent 只记得自己的对话。它们不会互相通气，不会共享信息。你告诉 A 的偏好，B 不知道。你跟 C 确认的方案，D 没听说过。

而且每次重新输入这些背景信息，都在消耗 token。

**OpenViking 给的启发——把记忆当成"文件系统"来管理**

字节跳动最近开源了一个项目叫 **OpenViking**（GitHub 上已经 2900+ star）。

[Slide 6]
它的核心思路特别简单，一句话就能说清楚：

把 Agent 的记忆当文件系统来管理，不是当文档来读。

什么意思？打个比方。

当你打开电脑想去重温"老师们"的影视巨著，不会把硬盘里所有文件的内容全部读一遍吧？你会先看文件夹名字，找到你想复习的目标文件夹，再打开具体的xxx.AVI。

Agent 读记忆也该这样。但现在大多数 Agent 的做法是：每次启动，把整个记忆文件从头读到尾。

记忆文件 100 行的时候还好。等它涨到 8000 行，每次都全读，token 哗哗地烧，家有矿也不能这么烧啊。

# L0 / L1 / L2：三层按需加载

OpenViking 的解决方案是把记忆分成三层：

层级

[Slide 7]
内容

类比

token 消耗

L0

目录索引

文件夹名称

~100 tokens

L1

内容摘要

文件简介

~500 tokens

L2

完整内容

文件全文

~5000+ tokens

[Slide 8]
Agent 每次启动，只读 L0（目录索引）。大概 100 个 token，就知道记忆里有哪些内容。

- L2 → 按需深入 → 完整内容 ~5000+ Token

需要某个具体信息？再去读 L1 摘要。确认是要找的东西？最后才读 L2 全文。

**从"每次全读"变成"按需读取"。**

举个真实的例子。我的记忆文件有 8000+ tokens。以前每次对话都要全部加载。

加了 L0 索引之后：

*　· 问天气？读 L0 发现没有天气相关记忆，0 额外消耗

*　· 问写作风格？读 L0 → 定位到"写作偏好"→ 读 L1 摘要就够了，~600 tokens

[Slide 9]
* · 需要完整的项目历史？才去读 L2 全文

日常场景下，token 消耗降低 10 倍以上。
