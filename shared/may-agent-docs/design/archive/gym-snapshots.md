# Gym Benchmark Tracking — Making Results Useful

> **Status: DRAFT** — Reviewed by Bob (endorsed) and Tech-Lead (approved with phasing). Ready for implementation.

## Problem

We have 82 gym scenarios, a runner, a scorer, and a DB. But the results aren't useful yet:

- The web UI shows a flat table of pass rates. No sense of what's improving or degrading over time.
- No way to compare "before this change" vs "after this change."
- No grouping by ability/behavior category — you see 82 rows, not "bug-fixing: 12/14, judgment: 9/16."
- Runs have no identity beyond timestamp + agent name. You can't tell what changed between two runs.
- The `stats.db` (gym-record.ts) and `may.db` (web UI) are separate DBs with duplicate schemas.
- Check-level detail only shows the latest run, not history.

## Goals

1. **See trends**: Is the agent getting better or worse over time? At what?
2. **Compare runs**: What changed between run A and run B? Which scenarios flipped?
3. **Categorize results**: Group by ability axis (bug-fixing, root cause, reading comprehension) and behavior axis (integrity, judgment, convention compliance) — the axes defined in the gym README.
4. **Track what was tested**: Record enough about the agent config and framework version to know what was different between runs.
5. **Keep it simple**: Single DB, single HTML file, no build step.

## Design

### 1. Unify on one database

Remove `stats.db`. `gym-record.ts` writes directly to `may.db` via the existing `gym_runs` / `gym_checks` tables in `requests.ts`. The web UI already reads from there. One source of truth.

**Note** (Tech-Lead review): The `gym_runs` and `gym_checks` tables already exist in `may.db` (landed in `fda5082`). This step is partially done.

### 2. Add run identity columns

Add columns directly to the `CREATE TABLE` statement in `requests.ts` (not `ALTER TABLE` — we control the DDL). Existing rows get NULL for new columns.

```sql
CREATE TABLE IF NOT EXISTS gym_runs (
  -- existing columns ...
  batch_id TEXT,          -- shared across all runs in one gym-baseline.sh invocation
  run_tag TEXT,           -- user-supplied label: "post-slim-prompt", "baseline", etc.
  prompt_hash TEXT,       -- SHA-256 of the full assembled system prompt
  framework_sha TEXT,     -- git rev-parse --short HEAD
  model TEXT,             -- model name from agent.json
  categories TEXT,        -- JSON array: ["bug-fixing", "root-cause-analysis"]
  tags TEXT,              -- JSON array: ["ability", "workflow"]
  tier TEXT               -- "smoke", "standard", "full"
);
```

`prompt_hash` is computed by hashing the **full assembled system prompt** — the exact text sent to the LLM, including SOUL.md, common-sense.md, generated Runtime Environment section, and Available Tools section. This captures dynamic context that individual file hashes would miss (per Bob's review).

`run_tag` is optional — pass `--tag "baseline"` to label a batch of runs.

`framework_sha` comes from `git rev-parse --short HEAD`. Automatic.

`batch_id` uses human-readable format: `YYYY-MM-DD_HHmm_<tag>` (per Bob's suggestion). Generated by `gym-baseline.sh`.

### 3. Store the full assembled prompt

No file-level snapshots. Store the actual prompt text, deduplicated by hash:

```sql
CREATE TABLE IF NOT EXISTS gym_prompts (
  prompt_hash TEXT PRIMARY KEY,
  agent_name TEXT NOT NULL,
  model TEXT,
  framework_sha TEXT,
  created_at TEXT DEFAULT (datetime('now')),
  prompt_text TEXT NOT NULL   -- the full assembled system prompt sent to the LLM
);
```

Why the full prompt, not individual files:
- It's what the LLM actually sees. Dynamic context (runtime environment, tool list) is included.
- You can diff two prompts directly in the UI — no reassembly needed.
- ~6-7KB per prompt, ~50 distinct versions = ~350KB total. Negligible.
- A hash without the text is useless — you can tell two runs were different but not *how*.

The `gym-runner.ts` captures the prompt by calling the same `resolveSystemPrompt()` path the agent uses (or by reading the prompt from the session transcript after the run).

### 4. Store scenario metadata in the DB

Currently the web UI has no access to scenario categories/tags/tiers — that metadata lives in `scenario.json` files on disk. The `categories`, `tags`, `tier` columns on `gym_runs` (see section 2) are populated by `gym-runner.ts` reading `scenario.json` at run time.

### Recording flow

```
gym-baseline.sh
  → generates batch_id (YYYY-MM-DD_HHmm_<tag>)
  → for each scenario:
      gym-run.sh <scenario> --agent coder
        → gym-runner.ts runs the agent, scores result
        → captures the full assembled system prompt
        → reads scenario.json for categories, tags, tier
        → outputs JSON with all fields
      → gym-record.ts --batch <batch_id> --tag "baseline" --result <json>
        → hashes prompt text → prompt_hash
        → reads framework_sha from git
        → inserts prompt into gym_prompts if new hash
        → inserts run into gym_runs with all columns
```

Changes to `gym-runner.ts`:
- Capture the full assembled system prompt (from session transcript or by calling resolveSystemPrompt)
- Read `scenario.json` and include `categories`, `tags`, `tier` in RunResult
- Read `git rev-parse --short HEAD`
- Include `model` from agent.json

Changes to `gym-record.ts`:
- Accept `--batch`, `--tag` flags
- Hash prompt text, insert into `gym_prompts` if new
- Write to `may.db` instead of `stats.db`
- Populate all new columns on `gym_runs`

Changes to `gym-baseline.sh`:
- Generate batch_id (`YYYY-MM-DD_HHmm_<tag>`)
- Forward `--batch` and `--tag` to gym-record.ts
- Forward args through `gym-run.sh` (Tech-Lead review flag)
