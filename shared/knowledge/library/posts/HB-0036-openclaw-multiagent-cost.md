## 核心观点

> 多agent协作适合**松耦合、简单任务传递**的场景。
> 
> 但如果任务需要大量前置上下文、需要多轮协作、需要传递用户的偏好和背景，那多agent协作的**代价会远大于收益**。

> 只有当**"分工收益"明显大于"协调成本"**时，多agent才是正确的选择。
> 
> 否则，就是**差生文具多**——配置工具比解决问题容易，设计架构比跑通流程愉快。

## 关键洞察

### 多Agent的成本
1. **上下文传递成本** - 每个agent需要重复加载前置信息
2. **协调开销** - Agent间的通信、同步、状态管理
3. **Token消耗** - 多份system prompt + 多次上下文传递
4. **延迟累积** - 串行执行时各agent响应时间累加

### 适用场景
| 场景 | 适合多Agent? | 原因 |
|------|-------------|------|
| 松耦合任务 | ✅ | 低协调成本 |
| 简单任务传递 | ✅ | 上下文简单 |
| 需大量前置上下文 | ❌ | 传递成本高 |
| 多轮协作 | ❌ | 协调开销大 |
| 需传递用户偏好 | ❌ | 状态同步复杂 |

### 反模式
> "差生文具多" - 配置工具比解决问题容易，设计架构比跑通流程愉快

**警示:**
- 不要为了用多Agent而多Agent
- 先证明单Agent解决不了
- 量化分工收益 vs 协调成本

## 实践建议

### 决策框架
```
考虑多Agent前，先回答:
1. 单Agent + 好的prompt能否解决?
2. 任务是否真的需要并行/分工?
3. 分工收益能否覆盖协调成本?
4. 是否有清晰的接口和交接标准?
```

### 渐进式采用
1. **Phase 1**: 单Agent + 工具
2. **Phase 2**: 简单多Agent (松耦合)
3. **Phase 3**: 复杂协作 (确有收益时)

---

## 对我们的意义

### 当前架构反思
- 我们的系统是否需要多Agent?
- 当前的分工是收益大于成本吗?
- 能否通过更好的prompt/tool减少Agent数量?

### 优化方向
1. **减少不必要的Agent切换** - 能在一个Agent完成的不要拆分
2. **标准化交接格式** - 降低协调成本
3. **缓存共享上下文** - 避免重复加载
4. **评估真实收益** - 对比单Agent vs 多Agent的实际表现
