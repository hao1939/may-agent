## 核心论点

作者认为MCP (Model Context Protocol) 是多余的：
- 企业内部HTTP可解决万物
- CLI + curl 足够使用
- MCP只是"多了很多要求的REST API"

---

## 评论区技术辩论精华

### 支持MCP的观点

**瞬**: "mcp的意义在于把服务器公开给别人，给自己用那当然是大材小用了"

**达基基**: "商用时出于某些原因，无法通过CLI直接访问对方系统，必须借助MCP模拟用户登录对方系统去处理。"

**小马扎**: "mcp可能是不完美，不过数据不在你这你用啥http？"

**Z.子豪**: "企业内部确实http可解决万物，mcp只不过把以前口口相传没有维护的文档线上化了。程序员的黑工转正"

### 质疑MCP的观点

**飞燕栖**: "即使是公开给别人用的也只需要封装成一个个可以独立运行的工具和service，搭配上合适的文档LLM就知道怎么用了，根本不需要再封装一个MCP层"

**momo**: "mcp就是个多了很多要求的rest api...agent自己做下来感觉mcp其实挺多余的"

**Anyway**: "一直没搞懂mcp和function call的区别是什么，mcp就是别人帮你写好的function call吗"

**sunslikes**: "mcp无非就是fc的一个规范而已"

### 中立/ nuanced 观点

**冰枝**: "没有哪一种是错的，只是要用在对的场景"

**龙虾球**: "绝大多数企业内服务不会做cli吧，基本不都是网络通讯"

## 对我们的意义

1. **架构选择需要场景化** — MCP vs HTTP vs CLI 没有绝对优劣，关键看场景
2. **OpenClaw的skill机制** 是一种更轻量的替代方案
3. **标准化 vs 灵活性** 的永恒张力
4. **Function Call vs MCP** 的边界正在模糊
