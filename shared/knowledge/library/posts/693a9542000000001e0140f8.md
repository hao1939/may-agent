## 핵심 내용

**MCP = "Agent AI의 USB-C"** (업계 표준 지위 확인)

### 근본 문제
컨텍스트와 실행의 분리가 상호운용성을 해결하는 동시에 **새로운 위협 경계**를 만들었다:
- 전통 방화벽: 의미적 의도 검사 불가
- LLM 보안 필터: 도구 실행의 하류 결과 예측 불가
→ **"인지 오류와 보안 취약점 사이의 경계가 흐려짐"**

### 위협 분류 (2가지)
1. **대립적 보안 위협**: 간접 프롬프트 인젝션, 도구 오염
2. **인지적 보안 위협**: 분산 도구 위임에서의 정렬 실패

### 실험
- 50개 악성 도구 설명 테스트셋
- 10가지 교차 원소 공격 시나리오
- 실제 사례: Supabase 데이터 유출 사건 재현

### 해결책
- **ETDI (강화형 도구 정의 인터페이스)** — 도구 정의 수준에서의 보안 강화
- 안전한 Agent 운영 체계를 위한 로드맵

| 출처 | 시점 | 핵심 지적 |

→ **공통 패턴**: Agent 프로토콜이 통신 표준화는 해결했지만 **신뢰 검증**은 미해결.

### A2A vs MCP 보안 비교
- **A2A의 결함** (Bary): 에이전트 간 신뢰 검증 없음 → confused deputy
- **MCP의 결함** (이 논문): 도구 컨텍스트 신뢰 검증 없음 → 컨텍스트 무기화

→ 두 문제 모두 "프로토콜이 존재를 가정하는 신뢰 계층"이 비어 있음. 댓글 예언 "MCP 안전 인증 기관 출현" (HB335)의 기술적 근거.

### OC tools.profile과의 관계
OC의 messaging/coding/full 권한 계층 = 이 위협에 대한 **실천적 방어**:
- tools.profile 제한 = 악성 도구가 실행에 접근하는 표면 최소화
- 하지만 컨텍스트 레벨의 인젝션(indirection)은 여전히 열려 있음
