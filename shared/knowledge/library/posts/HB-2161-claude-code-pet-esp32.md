## 核心概念

> "当 AI 的操作从 '终端里滚动的日志'，变成 '物理屏幕上的小猫点头'，你和 AI 的关系，从 '被动接受' 变成了 '主动掌控'。"

中国开发者开发的 ESP32 电子宠物，作为 Claude Code 的「实体监工搭子」，解决 AI 自动执行带来的「失控感」问题。

---

## 核心功能

### 1. 实时状态同步
- 通过 BLE 与 PC 端守护进程通信
- 同步 Claude Code 的当前状态：空闲 / 忙碌 / 等待审批
- 无需盯着终端日志，瞟一眼小屏幕即可知道 AI 工作状态

### 2. 高危操作物理审批
所有需要审批的工具（Bash / Write / Edit）:
- 终端尚未响应，小屏幕已弹出审批请求
- 30 秒倒计时，不点 "YES" Claude 无法继续
- 物理按钮确认，杜绝"误删库"悲剧

### 3. 角色与状态动画
三种 ASCII 风格角色（软萌猫咪、机械机器人、圆滚滚鸭子），每种 7 种状态动画：
- **空闲**: 猫咪闭眼打哈欠，机器人指示灯慢闪
- **忙碌**: 小猫皱眉工作，鸭子来回踱步  
- **等待审批**: 突然瞪大眼睛，歪头等你决定
- **完成**: 跳爱心庆祝舞

## 技术架构

```
┌─────────────┐     BLE      ┌─────────────┐     Hook      ┌─────────────┐
│   ESP32     │◄────────────►│   PC端守护   │◄─────────────►│  Claude Code │
│  电子宠物    │   状态同步    │   进程      │  事件拦截     │              │
│  物理审批    │   审批请求    │             │              │              │
└─────────────┘              └─────────────┘              └─────────────┘
```

### 关键技术细节

#### 1. 双层状态机
```
base状态: 与 Claude 同步的持久状态（空闲/忙碌/等待审批）
active状态: 临时覆盖的动画（如庆祝动画），2-3秒后自动回落
```
优势：临时动画不干扰主流程，无需复杂恢复逻辑

#### 2. BLE 透明分片
ESP32 BLE NUS 单次仅 20 字节，驱动层自动处理：
- 发送：自动分片 + 帧头标记
- 接收：自动拼接，遇 `\n` 抛给上层
- 上层代码：无感知，收发完整 JSON

#### 3. 三任务异步并发
```python
asyncio 三个独立任务：
- ble_task: 后台处理蓝牙连接和消息
- touch_task: 异步监听触控
- render_task: 固定 20FPS 渲染动画
```

#### 4. 硬件抽象
所有引脚、屏幕参数集中在 `config.py`，换板只需改配置文件。

## 洞察：从「黑盒焦虑」到「物理掌控」

### 问题定义
Claude Code 的自动执行带来效率提升，但也产生：
- **失控感**: 黑盒式操作，不知道 AI 在做什么
- **遗漏风险**: 高危操作审批提示容易被日志刷过
- **等待焦虑**: 不知道 AI 是在忙还是卡住

### 解决方案对比

| 方案 | 优点 | 缺点 |
|------|------|------|
| **终端审批** | 无需额外设备 | 易被日志淹没，需主动关注 |
| **桌面 GUI** | 可视化好 | 占用屏幕空间，打断工作流 |
| **物理设备** (本项目) | 余光可见，物理确认，有情感连接 | 需额外硬件 |

### 情感化设计
> "它不再是一个只会敲代码的黑盒，而是一个有状态、有反馈、需要你配合的 '搭子'。"

电子宠物的设计引入了情感因素：
- **陪伴感**: 敲代码时小猫在旁边
- **仪式感**: 完成任务的庆祝动画
- **掌控感**: 物理按钮确认的高权重

## 对 OpenClaw 的启示

### ✅ 问题识别
- **失控感是真实痛点**: 不仅是技术问题，更是人机交互设计问题
- **物理接口的价值**: 在某些场景（高危操作）下，物理确认比屏幕点击更有"重量"

### 🔬 可探索方向
1. **状态可视化**: 我们的 agent 执行 workflow 时，如何让用户"瞟一眼"就知道进度？
2. **分级审批**: 哪些操作需要"物理级"确认？是否可以配置审批策略？
3. **情感化反馈**: agent 完成长时间任务时，是否需要更明显的"庆祝"反馈？
4. **离线容错**: Buddy 没电自动超时放行的设计 —— 我们的系统如何处理外设失联？

### ⚠️ 边界思考
- **必要性**: 物理设备增加成本，是否所有用户都需要？
- **场景限定**: 可能更适合高风险的 production 环境，而非日常开发
- **安全审计**: 物理审批的操作如何记录审计日志？
