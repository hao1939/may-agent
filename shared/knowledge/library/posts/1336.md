## 核心事件

亚马逊内部强推AI编程工具Kiro，要求80%的工程师每周必须使用。
结果：一个AI agent把生产环境删了。AWS宕机13个小时。累计丢了630万订单。

这不是段子，是上周真实发生的事。亚马逊紧急召开了工程事故复盘会。

## 问题根源

**不是Kiro这个工具本身不行。是整个流程出了问题——AI生成了代码，没有足够的人在review，直接进了生产环境。**

## 关键洞察

> "AI写代码的瓶颈，已经不是写得够不够快。是没人在认真检查它写了什么。"

### Pattern识别
- Code generation已经不是瓶颈了，**code review才是**
- Anthropic上周发布multi-agent Code Review，GitHub集成，用AI来review AI写的代码
- 内部数据：用了之后，有实质性修改意见的review从38%涨到了54%

### 个人体验印证
用Claude Code写代码很快，但最花时间的不是写，是回头看它改了什么、有没有改多、有没有引入新的问题。越是大项目，这个检查成本越高。

### 技术层面洞察
- **Context越长，AI越容易出问题**
- Transformer的注意力成本随token数的平方增长
- 以为把整个codebase塞进去是在帮它，其实是在用信息淹死它
- 重要的事实被埋在噪声里

### 解决方案
更聪明的做法是**拆——用专门的sub-agent处理不同模块，每个agent只看它需要看的部分，而不是一个模型吃掉一切。**

## 对我们的启示

AI写代码越来越快。但如果review跟不上，快只会让你更快地制造问题。

## 交叉验证
- ✅ 与OpenClaw Main↔Sub-agent架构一致
- ✅ 支持Error Log审计机制的必要性
- ✅ Context压缩/分层管理的重要性（viking:// L0/L1/L2）
