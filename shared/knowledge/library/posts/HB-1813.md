## 3 CLI分工架构

### 核心原则
> "最省时间的不是'让一个模型全做完'，而是把3件事拆开。"

| 角色 | 工具 | 职责 |
|------|------|------|
| **主执行** | Claude Code | 看项目、改代码、跑命令、改到能跑 |
| **快读资料** | Gemini | 长文档、更新说明、API变化，读完总结给主执行 |
| **复审** | GPT-5.4 / Codex | 专门看diff有没有跑偏、漏测试、低级bug |

---

## 实战示例

**需求**: "把一个旧页面的登录流程改掉，顺手补一下文档。"

### 步骤1: Claude Code主执行
```bash
claude "修登录流程，保持现有样式，改完后告诉我改了哪些文件"
```

### 步骤2: Gemini快读资料
```bash
gemini "读最新框架文档，告诉我这个登录流程改动最容易踩的3个坑"
```

### 步骤3: GPT-5.4/Codex复审
```bash
codex "根据这次改动检查：有没有漏边界、漏测试、漏异常处理"
```

## 分工好处

1. **主执行模型不会一边写一边乱查资料**
2. **查资料不会打断真正改代码的节奏**
3. **复审和主执行分开后，低级错误更容易被捞出来**

## 对OpenClaw的关键验证

### 分工理念验证
> "先把这3个角色分清：谁负责干活、谁负责查资料、谁负责挑错"

这与OpenClaw的Main Agent ↔ Sub-agent架构**完全对齐**：
- Main Agent = 主执行 (Claude Code角色)
- Sub-agent = 可配置为"查资料"或"挑错"角色

### OpenClaw价值定位
作者明确指出：
> "OpenClaw现在真正有用的地方，也不是'它会自动做所有事'，而是它很适合把这3路分工收成一条稳定工作流。"

**这是对OpenClaw Harness架构的强验证** —— 不是自动化一切，而是**稳定编排分工**。

### 与10-Agent方案的对比
作者明确反对：
> "不是'一上来把10个agent全堆上去'"

支持OpenClaw的**轻量Multi-Agent**立场：
- 3个角色足够覆盖主要场景
- 过多agent反而增加混乱
- 关键是**跑顺分工**，不是堆砌数量
