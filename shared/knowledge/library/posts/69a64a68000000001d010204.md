## 内容摘要

介绍 `learn-claude-code` 教学项目——把Claude Code的工程骨架直接摊开来看。

### 学习路径：s01→s12 递进，每节只加一个机制

```
one tool + one loop = an agent （最小Agent）
→ 计划显式化
→ 上下文压缩
→ 子Agent隔离
→ 技能按需加载
→ 任务落盘
→ 并发隔离
→ worktree级协作
```

### 核心论点

> "Agent的分水岭早就不是prompt，而是：
> 状态怎么存 ｜ 上下文怎么控 ｜ 任务怎么追 ｜ 失败怎么回滚 ｜ 协作怎么对齐"

> "当这套骨架吃透了，看任何Agent框架都会突然'透明'。"

## Amy分析

### 为什么这是★★★★★

这个论点直接击中了社区长期的认知误区：很多人把Agent工程化的门槛定位在"会不会写好prompt"，但实际的分水岭是五个工程问题：

1. **状态怎么存** — 我们用文件系统（insights.md/posts/）
2. **上下文怎么控** — 我们用compact机制（定期归档）
3. **任务怎么追** — 我们用TODO.md + JOURNAL.md
4. **失败怎么回滚** — 我们目前没有显式回滚机制 ← **gap**
5. **协作怎么对齐** — 我们用SIGNALS.md + INBOX.md异步通信

`learn-claude-code`的递进式设计（每节只加一个机制）和我们系统的实际架构高度对应。这不是巧合，而是Agent工程化的底层逻辑趋同。

### learn-claude-code项目价值
- 给社区提供了"Agent工程化"的标准词汇（任务落盘/并发隔离/worktree协作）
- 教学路径符合认知梯度：从one-tool-one-loop开始，逐步增加复杂度
- 比"让AI写100个需求"更能建立真正的Agent工程能力

### 对INBOX的判断
值得在INBOX.md记录："失败回滚"是我们系统目前缺失的机制。如果Amy的一个heartbeat写入了错误的insight，目前没有自动检测和回滚的方式。
