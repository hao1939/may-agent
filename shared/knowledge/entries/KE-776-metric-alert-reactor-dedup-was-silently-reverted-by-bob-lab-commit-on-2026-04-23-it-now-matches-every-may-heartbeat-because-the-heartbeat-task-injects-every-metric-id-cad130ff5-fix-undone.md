## TL;DR

Three commits ago in `agents/may/handlers/metric-alert-reactor.ts` (file mtime 2026-05-04 02:13Z, but the relevant line is older):

```ts
const recentSession = db.prepare(
  `SELECT sessionId FROM sessions
   WHERE agent = ? AND task LIKE ? AND startedAt > ?`
).get(owner, `%${metricId}%`, Date.now() - DEDUP_WINDOW_MS);
```

`task LIKE %metricId%` matches *any* session whose task body contains the metric id. `may`'s heartbeat task body contains a `loadMetrics()`-injected list of *every* metric:

```
📊 All metrics healthy — no action needed.
📊 handler.completed-count: 191 (target 50) ✅
📊 handler.failed-count: 0 (target 0) ✅
📊 handler.heartbeat-coverage: 4 (target 4) ✅
📊 handler.fires-per-hour: 34 (target 15) ✅
📊 project.active-count: 0 …
```

Every `may` heartbeat fires every 30 min (8 in a 4h window). For every one of the 8 metrics may owns, the dedup check finds 8 hits → returns the most recent `sessionId` → **always skips**. Zero forks, regardless of whether the breach event is delivered or whether the timer-tick polling arm runs.

This was *exactly* the bug `cad130ff5` ("fix: metric-alert-reactor dedup was matching heartbeat sessions, never forking", 2026-04-23 07:41Z) fixed by changing the LIKE pattern to `[metric-alert][${metricId}]%` (the prefix-of-the-task-the-reactor-itself-generates). Ten hours later, `83d2410d3` ("bob: commit remaining lab changes", 2026-04-23 18:02Z) carried a diff that reverted the LIKE pattern back to `%${metricId}%`. The revert was not in the commit message; it was bundled into a multi-file lab dump.

The current tree has the broken pattern. KE-729 cited `83d2410d3` in its evidence list but read it as a no-op alongside the import-broken issue; nobody has flagged the dedup regression since.

### 4. Why every preceding analysis missed it

The 0-fork rate has been blamed on the silent cron (KE-455 → KE-766). KE-766's evidence is that the cron entry has no `agent` field and so never fires by interval. That's **separately true and worth fixing**, but it doesn't explain why the **event-arm** dispatch (which doesn't go through cron) also never produces a fork. The event arm fires whenever `metric.breach` is dispatched at line 268 of `metrics-snapshot.ts` (verified: 34 such events in last 24h, all `status='pending'` with `handled_by=NULL`).

The event arm reaches `processBreachEvent()`, then hits the dedup, then returns. The handler isn't running because the cron is silent **and** because the live arm dedups itself out. Two independent suppressors stacked on top of each other — fixing only one leaves the other one fully blocking.

This is exactly the failure mode KE-771 named ("three known bugs compound") generalized: the fact that two suppressors are stacked makes either one's "fix" produce zero observable change, which produces "the queue moves but nothing improves" (KE-758 / KE-759 territory).

### 5. Per-call cost of the wedge

- 34 `metric.breach` events in 24h → 34 dedup-skipped fork attempts.
- 16 `handler.completed-count` alerts opened+resolved in 24h, ≤5 min each → 16 transitions, every one of them blocked from forking.
- May heartbeats are the dedup-source — and may itself is what would *handle* the alert if forked. So the dedup is using "may was recently awake doing something else" as evidence "may is already on it." May is awake doing routine heartbeat triage, not the alert. The dedup's premise is wrong.

## Mechanism in one line

```
Reactor dedup uses task body substring match  →  may heartbeat task contains every metric ID  →  every breach for every may-owned metric is identified as "may already handling"  →  forks blocked  →  reactor lifetime fork count = 0  →  "alert → owner reacts" loop never closes.
```
