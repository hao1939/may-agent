# KE-193: Parallel Monitoring Validates Content-First — But Suggests Concurrent Guard Tier

**Date**: 2026-04-16  
**Source**: DD-770 (Cognitive Companion), content-first-guards-architecture.md  
**Confidence**: Medium-High  
**Tags**: `guard-architecture` `parallel-monitoring` `content-first` `reasoning-degradation`

## Finding

DD-770's cognitive companion research validates content-first guards AND reveals a gap: our architecture has no **concurrent monitoring** tier. We have pre-task injection (content-first) and post-task verification (process-first), but nothing watching the agent *during* execution.

## Three Key Connections

### 1. Content-First = Prevention; Companion = Detection

DD-770 shows two complementary strategies:
- **Prevent degradation** by giving better inputs (= our content-first guards: inject expert analysis, agent never degrades)
- **Detect degradation** in real-time and intervene (= companion monitoring: catch loops, drift, stuck states)

Content-first is strictly better *when expert analysis exists*. But for novel tasks (Phase 3 of our architecture), no expert doc exists. That's where companion-style monitoring would fill the gap — catching degradation on tasks we can't pre-analyze.

### 2. Task-Type Dependency Aligns Perfectly

DD-770 finding: companion monitoring helps on loop-prone/open-ended tasks but is neutral or negative on structured tasks. This maps directly to our difficulty-gated deployment principle (§5.5): content-first only on hard tasks (<25% baseline), leave easy tasks alone. Both systems converge on the same insight — **intervention ROI is task-dependent**.

### 3. Zero-Cost Monitoring via Probes (Not Available to Us — Yet)

DD-770's probe-based companion (AUROC 0.840, zero overhead) operates on hidden states — something we can't access through the API. But the *principle* applies: monitoring should be as cheap as possible. Our content-first guards achieve this (costTier "zero"). Any future concurrent monitoring should similarly minimize cognitive load on the working agent.

## Design Implication: Three-Tier Guard Timing

| Tier | Timing | Our Implementation | Status |
|------|--------|--------------------|--------|
| **Pre-task** | Before agent starts | Content-first injection | Designed (architecture doc) |
| **Concurrent** | During execution | *Not yet designed* | Gap identified by DD-770 |
| **Post-task** | After agent finishes | Process-first guards (verify-wrap, evidence-gate) | Existing |

A concurrent tier would watch for:
- **Loop detection**: Agent repeating the same approach (DD-770 reduced loops 52-62%)
- **Drift detection**: Agent wandering from the task
- **Stuck detection**: Agent not making progress

**Critical constraint**: Concurrent monitoring must NOT force the agent to produce analysis (displacement risk from EXP-166). It must be external observation only — either automated pattern matching on outputs, or a separate LLM evaluating the working agent's trajectory.

## What NOT to Do

- Don't build concurrent monitoring that interrupts the agent with "reflect on your progress" prompts — that's forced production, which causes displacement on hard tasks
- Don't stack concurrent monitoring with content-first on the same task (KE-123: intervention stacking degrades by 12-15pp)
- Don't invest in this before Phase 3 (generative analysis) — content-first covers known-hard tasks; concurrent monitoring only matters for novel-hard tasks

## Actionable Recommendation

**No immediate design changes needed.** Content-first handles our current hard-task failures. Add concurrent monitoring to the roadmap as a Phase 5 item, triggered when Phase 3 (generative analysis) reveals tasks where even generated expert analysis fails — those are the tasks that need real-time degradation detection.
