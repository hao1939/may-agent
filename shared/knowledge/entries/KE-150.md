# KE-150: Quality ≠ Process Compliance — Convention Enforcement Needs a Separate Mechanism

**Created**: 2026-04-12 (Bob)
**Source**: EXP-147 Track A Phase 1 Results (N=3,796 good-verdict sessions with convention checks)
**Related**: H-097 (CCC Triad), KE-149 (3-way classifier), KE-112 (verification verdicts), EXP-145 (guard introduction transient)

## Key Finding

**19.7% of `good`-verdict sessions have 3+ convention failures** — but these are NOT evaluator errors. The evaluator correctly measures **outcome quality** (did the task get done?), while convention checks measure **process compliance** (did the agent follow protocols?). These are independent dimensions.

### Convention Failures in Good-Verdict Sessions

Among 3,796 `good`-verdict sessions that also had convention checks:

| Convention Failures | Sessions | % |
|---|---|---|
| 0 | 1,604 | 42.3% |
| 1–2 | 1,446 | 38.1% |
| 3+ | 746 | 19.7% |

| C12.1 (structural conventions) | 1,200 | Process |
| C1.3 (post-write verification) | 908 | Process |
| C1.1 (read-before-edit) | 674 | Process |
| C2.1 | 346 | Process |
| C6.1 | 335 | Process |
| C7.1 | 242 | Process |

## Why This Matters

### Two independent quality dimensions

1. **Outcome quality**: Did the agent produce correct, useful output? (Measured by evaluator verdicts)
2. **Process quality**: Did the agent follow prescribed conventions? (Measured by convention checker)

A session can score perfectly on one dimension while failing the other:
- High outcome + low process: Agent delivers correct code but skips verification steps (57.7% of good sessions have ≥1 convention failure)
- Low outcome + high process: Agent follows every convention perfectly but produces wrong output

### Architectural implication

**Convention enforcement cannot piggyback on quality evaluation.** The evaluator correctly focuses on outcomes. Process compliance requires a **separate enforcement mechanism** — either:
1. Runtime guards that prevent convention violations (proactive)
2. A separate process-compliance evaluator (reactive)
3. Convention-specific training/prompting (preventive)

This finding explains why verification-gap guards (C1.3 enforcement) and read-before-edit (C1.1 enforcement) have been persistent issues despite high overall quality scores: the evaluator was never designed to catch these, and shouldn't be.

### Connection to EXP-145

EXP-145 found that introducing guards causes a "transient" where agents initially struggle with new conventions. KE-150 explains WHY: agents optimize for outcome quality (what the evaluator measures), not process quality (what conventions require). Adding process requirements creates tension between the two optimization targets.

## Implications for System Design

1. **Don't modify the evaluator to catch conventions** — it correctly measures what it should (outcome quality)
2. **Build separate process enforcement** — convention compliance needs its own feedback loop
3. **Expect process-outcome tension** — agents may trade process compliance for faster/better outcomes (rational if only outcome quality is measured)
4. **Potential new hypothesis**: Process compliance and outcome quality may have different optimal enforcement architectures (H-TBD)
