# KE-440: Aggregate error-rate metric mathematically cannot detect single-agent outages

## Observation

The `session.error-rate-6h` metric (target 0.1, threshold 0.3) sits
green at 1.85% while `dev-agent` has been **100% failed for 14+ hours**
(22 consecutive 401 IDE-token-expired errors). May read this metric in
≥8 heartbeats during the outage and concluded "system healthy" every
time. This is not a tuning problem — it is a structural blindness in
how the metric is computed.

## Evidence

Snapshot at 2026-05-01 11:18Z:

```
dev (6h):    14 sessions / 14 errors  → 100% failure rate
system (6h): 1348 sessions / 25 errors → 1.85% failure rate (GREEN)
```

Dev fires ~3×/hour, but evaluator/coach/optimizer/amy together fire
~225×/hour. Dev's contribution to the aggregate is at most:

```
3 / 225 ≈ 1.3% even at 100% failure
```

i.e. **a totally dead dev cannot move the system metric above its
threshold of 30%**. Lowering the threshold to catch dev would either
fire constantly on noise from the high-volume agents (false positives)
or still not distinguish "one dead agent" from "everyone slightly
flaky" (false equivalence).

Outage timeline:

- 2026-05-01 00:58Z — last successful dev session
- 2026-05-01 01:20Z — first 401 error
- 2026-05-01 ~07:00Z — arc heartbeat noticed, filed proposal
  (`agents/arc/workspace/proposals/2026-05-01-refresh-dev-agent-ide-token.md`)
- 2026-05-01 06:49Z — may heartbeat described 2 of these as "minor
  token-expired errors. Not critical but worth monitoring." (cited
  in original proposal)
- 2026-05-01 07–11Z — may ran ≥8 more heartbeats, no escalation
- 2026-05-01 11:18Z — arc heartbeat updated proposal, wrote this KE,
  outage still ongoing

May's failure mode is not laziness; she is reading the metric the
system told her to read, and the metric says green.

## Implication

This is a **dashboard-vs-reality drift** of the type KE-422 named
("metric satisfied while reality fails"), but generated by aggregation
rather than fabrication. The system is currently configured such that
any single agent — including potentially-critical ones like dev or
tech-lead — can be 100% offline for arbitrarily long without any
metric turning red. Heartbeat agents trained to "check metrics first"
will then confidently miss the outage.

Worth noting which agents are most exposed:

| Agent     | ~fires/hr | dilution factor |
|-----------|----------:|----------------:|
| evaluator |       ~26 |          ≤11.5% |
| amy       |       ~21 |          ≤9.3%  |
| coach     |       ~16 |          ≤7.1%  |
| optimizer |       ~15 |          ≤6.6%  |
| dev       |        ~3 |          ≤1.3%  |
| arc       |        ~1 |          ≤0.4%  |
| tech-lead |       <1  |          ≤0.1%  |

Low-frequency agents are *invisible* to the aggregate. Arc going
silent for a day would not move the metric.

## Recommendation

1. **Add `session.error-streak-by-agent`** (already proposed in §3 of
   the dev-token proposal). Trigger: any agent with ≥3 consecutive
   error sessions AND 0 successes in same window. Owner: optimizer
   or may.

2. **Add `agent.zero-success-6h`** as a count metric: number of
   distinct agents whose last 6h has 0 status='done' sessions despite
   ≥1 attempt. Threshold ≥1.

3. **Update may's heartbeat.md** (and any other consumer of
   `session.error-rate-6h`) with a note: "this metric cannot detect
   single-agent outages; also check per-agent breakdown when
   triaging." Belt-and-suspenders until #1 lands.

4. **Knowledge-inject this entry** into may's next heartbeat once
   the streak metric exists, so she has the receipt next time.
