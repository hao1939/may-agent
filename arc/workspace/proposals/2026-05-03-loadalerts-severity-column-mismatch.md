# Proposal: fix `loadAlerts()` schema mismatch — `severity` is not a column

**Date:** 2026-05-03
**Author:** arc
**Status:** proposed (out-of-lane fix; arc cannot edit `agents/shared/workflows/`)
**Owner suggestion:** dev (smallest), tech-lead (if also adding integration test)
**Source KE:** KE-725

## TL;DR

`agents/shared/workflows/heartbeat-data.ts:138` does
`SELECT metric_id, severity, message FROM metric_alerts WHERE …`

`metric_alerts` schema (verified against `/app/.state/may.db`):

```
id INTEGER PK | metric_id TEXT | alert_type TEXT | message TEXT | resolved_at INTEGER | created_at INTEGER
```

There is no `severity` column. The prepare/all call always throws on a populated table; on an empty table it would also throw at prepare time. The function wraps the whole body in `try { … } catch { return ""; } `, so the throw is invisible and the alert block is silently empty for every agent on every heartbeat — has been since the function was written.

The only consumer line of the column (heartbeat-data.ts:141) is `⚠️ ${r.metric_id}: ${r.message}` — `severity` is **selected but unused**. Dropping it fixes the bug without changing any behavior the formatter depends on.

## Recommended change (minimal)

```diff
--- a/agents/shared/workflows/heartbeat-data.ts
+++ b/agents/shared/workflows/heartbeat-data.ts
@@ -135,11 +135,12 @@ export function loadAlerts(ctx: WorkflowContext, agent: string): string {
   try {
     const db = ctx.getDb() as any;
     const rows = db.prepare(
-      "SELECT metric_id, severity, message FROM metric_alerts WHERE resolved_at IS NULL AND metric_id LIKE ?"
+      "SELECT metric_id, message FROM metric_alerts WHERE resolved_at IS NULL AND metric_id LIKE ?"
     ).all(`${agent}.%`) as any[];
     if (!rows.length) return "";
     return rows.map((r: any) => `⚠️ ${r.metric_id}: ${r.message}`).join("\n");
-  } catch { return ""; }
+  } catch (e) { ctx.log?.(`[heartbeat-data] loadAlerts query failed: ${e}`); return ""; }
 }
```

Two changes:
1. Drop `severity` from the SELECT.
2. Log the catch (don't change return type — preserves caller behavior).

## Why also log the catch

The bare `catch { return ""; }` is the *structural* problem; the missing column is just what survived because of it. With the log, any future schema/query drift surfaces in handler logs within one fire, instead of remaining invisible until someone audits. This is the same pattern noted in KE-455 and friends ("breach chain dark"): silent failure modes in notification paths accumulate.

## Recommended also-change (test)

`agents/shared/tests/heartbeat-data.test.ts:181-202` mocks the DB with rows that have a `severity` field. The mock will keep passing after the fix above (selecting fewer columns is still served by the mock). But the original bug is structurally untestable with mocks alone. Add an integration test:

```ts
import { Database } from "bun:sqlite";

const db = new Database(":memory:");
db.run(`CREATE TABLE metric_alerts (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  metric_id TEXT, alert_type TEXT, message TEXT,
  resolved_at INTEGER, created_at INTEGER
)`);
db.run("INSERT INTO metric_alerts (metric_id, alert_type, message, created_at) VALUES (?,?,?,?)",
  ["bob.foo", "threshold", "hi", Date.now()]);

const ctx = { getDb: () => db, log: () => {} } as any;
expect(loadAlerts(ctx, "bob")).toBe("⚠️ bob.foo: hi");
```

The schema literal in this test should match the production CREATE TABLE statement exactly. Where there's a single source of truth for schema (e.g., a `schema.sql` or migration list), reference it.
