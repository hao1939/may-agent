# Evaluator Quality Gap Calibration

## Goal
Reduce evaluator review-quality drift by driving `evaluator.false-good-rate-sample` back toward target (<= 0.05), with current emphasis on planner/update false-good routing: both over-broad `quick_exit_successful_session` skips and planner task-tree mutations that are misrouted as harmless `routine_ok` because material-output detection misses task-tree changes, while preserving healthy aftermath coverage and triage closure.

## Signals
- `evaluator.false-good-rate-sample`: current 0.272, target 0.05, threshold 0.6
- `evaluator.substantive-low-quality-rate-24h`: current 0, target 0.1, threshold 0.3
- `evaluator.meaningful-review-rate-24h`: current 0.9455, target 0.9, threshold 0.7
- `evaluator.triage-closure-rate-24h`: current 0.9329, target 0.9, threshold 0.7
- `eval.llm-coverage-lag-h`: current 0.1, target 1, threshold 4

## Current State
The evaluator pipeline is operational and no red alerts are firing. The project’s earlier assumption that `evaluator.low-quality-rate-24h` needed to return to target as a primary quality objective is now stale: May’s 2026-05-09 heartbeat explicitly approved the calibration pivot that demoted the broad low-quality metric to dashboard-only (`threshold 0.80`, `priority P3`) and promoted `evaluator.substantive-low-quality-rate-24h` to the primary alert (`threshold 0.30`, `priority P1`). The live registry and runtime DB both match that governance decision, and the substantive metric is currently healthy at `0`.

That means the durable open problem is no longer broad low-quality alerting; it is false-good drift. Fresh sampling in this project found two live planner/update failure families under `HEURISTIC_VERSION=11`: (1) repeated likely false skips where sessions with real review judgment and task-tree mutations are still auto-skipped by the coarse `status === 'done' && opCount <= 10` rule as `quick_exit_successful_session`, and (2) planner `Planning Update Step` sessions above the skip threshold that still mutate `tasks/tree.json` yet get routed as harmless `routine_ok` because `hasMaterialOutputSignal()` only recognizes `file write/edit|git commit|project artifact|knowledge update` and does not treat task-tree mutations as material output. The newest heartbeat samples keep both families live: planner update sessions `s_project_planner_planning_update_20260617093308_31e95u` (`opCount=5`) and `s_project_planner_planning_update_20260617093454_ivqhnh` (`opCount=4`) were both auto-skipped even though their own `session.end` summaries describe substantive planning judgments, including resolving review-state trust and refilling the frontier with a new assigned LocalDNS leaf, and minutes later planner update session `s_project_planner_planning_update_20260617094241_iwycec` (`opCount=11`) was routed as harmless `routine_ok` despite its `session.end` summary saying it refilled the frontier by creating and assigning a concrete repo-local LocalDNS handwritten-coverage leaf. Paired planner event-review sessions in the same wakes remained 1–2 op read/review passes that still look like benign quick exits, which keeps the target narrow rather than disabling all planner skips. Current readings support that focus: `evaluator.false-good-rate-sample=0.2383`, `evaluator.meaningful-review-rate-24h=0.9377`, `evaluator.triage-closure-rate-24h=0.9176`, `eval.llm-coverage-lag-h=0.55`, and `evaluator.substantive-low-quality-rate-24h=0`.
