# evaluator-aftermath reviewed-event delivery gap

## Goal
Restore trustworthy evaluator aftermath completion by ensuring each non-routine `evaluation.routed` session reliably produces the expected downstream `evaluation.reviewed` event (and companion success/learning events when applicable).

## Signals
- The prior routed-vs-reviewed census overstated the issue by counting `routine_ok` routes that are intentionally not reviewed. The workflow code returns early for `routine_ok` before spawning a review session.
- Fresh canonical counts since `1781492570000` now show `175` distinct `evaluation.routed` sessions split as `74 needs_triage`, `71 success_candidate`, and `30 routine_ok`, versus `134` distinct `evaluation.reviewed` sessions.
- After excluding the designed `routine_ok` skip lane, the live gap is `145` non-routine routed sessions versus `134` reviewed sessions: `11` missing outcomes total.
- Two earlier success-candidate gaps are now healthy: `s_1781501245983_31` has `evaluation.reviewed/success_candidate/learning_created` `1416154-1416156`, and `s_task_private-cluster-none-private-dns-zone-v3-staging-20260615` has `1416146-1416148`.
- The remaining `success_candidate` misses are now `s_task_virtualmachines-autoscale-upgrade-survival-staging-20260615` and the new done sample `s_task_gpu-operator-default-install-staging-20260615`, while the other open misses remain concentrated in `needs_triage` (`9` sessions).

## Current State
The creative-audit comment was directionally correct: the project was measuring the wrong denominator. `routine_ok` sessions are designed to stop after `evaluation.routed`, so they should not be counted as missing reviewed outcomes.

A smaller but real non-routine delivery gap still exists in live data. The oldest success-candidate case remains open, a new done success-candidate miss has appeared, and a cluster of `needs_triage` sessions still show `evaluation.routed` without any canonical `evaluation.reviewed` follow-through.

The newest revalidation still points at completed-session delivery rather than mere lag: of the `11` non-routine misses in the fresh window, `9` are already-completed source sessions while the other `2` source sessions are `interrupted`/`error`. The newest completed miss (`s_task_gpu-operator-default-install-staging-20260615`) ended seconds before this heartbeat, so it may still be transient; the older misses are not.

Evidence from the current pass:
1. `projects/evaluation.app/workflows/evaluator-aftermath.ts` returns immediately for `normalized.route.lane === "routine_ok"`, proving that lane is intentionally excluded from review emission.
2. Live canonical counts since `1781492570000` show `175` routed sessions overall, but only `145` of them are non-routine (`needs_triage`/`success_candidate`).
3. Live canonical counts for the same window show `134` distinct `evaluation.reviewed` sessions, leaving `11` non-routine routes without reviewed outcomes.
4. Breaking those `11` misses by lane/status gives `9` `needs_triage` + `2` `success_candidate`; by source status that is `9` done + `1` interrupted + `1` error, with `0` still running.
5. `s_1781501245983_31` and `s_task_private-cluster-none-private-dns-zone-v3-staging-20260615` are now fully recovered with reviewed/success/learning events, so the issue is not a total pipeline outage.
6. The old success-candidate sample `s_task_virtualmachines-autoscale-upgrade-survival-staging-20260615` still has only `evaluation.routed` event `1413956` and no downstream reviewed/success/learning event, even though both the source session and spawned evaluator review session `s_1781499184523_32` are `done`.
7. The new success-candidate sample `s_task_gpu-operator-default-install-staging-20260615` is currently another done source session with routed-but-no-reviewed follow-through, so the defect may still reproduce on fresh traffic.

## Plan
1. Keep the project waiting on owner/runtime action because the remaining gap is now clearly scoped to non-routine aftermath delivery, not routine-ok design behavior.
2. Revalidate after an owner/runtime change or explicit May request, focusing only on `needs_triage` and `success_candidate` routes; verify the old target `s_task_virtualmachines-autoscale-upgrade-survival-staging-20260615` and the current `needs_triage` misses.
3. If the gap persists after a claimed fix, reopen with fresh sample IDs and isolate where the non-routine path drops: review-session dispatch, post-finish event emission, or downstream event write filtering.
