# Evaluator False-Good Alignment

## Goal
Align `evaluator.false-good-rate-sample` with the real evaluator quality question so the metric only flags meaningful heuristic over-credit, not passing-grade `good -> acceptable` review outcomes.

## Signals
- `evaluator.false-good-rate-sample` target `< 0.05`; current metric row `0.1642` on 2026-06-19 heartbeat
- Snapshot-aligned 24h recompute for that metric row shows `11` `evaluation.false_good` events over `67` reviewed-good `evaluation.reviewed` events, while the live metric remains below its `0.6` alert threshold
- That snapshot-window `evaluation.false_good` mix is `10` `good -> acceptable` plus `1` `good -> needs_improvement`, so acceptable-only vocabulary mismatches still dominate the numerator even more strongly than the prior sample
- Shared work queue still has an open proposal to exclude `good -> acceptable` vocabulary mismatches from this metric

## Current State

- Live metrics now show `evaluator.false-good-rate-sample = 0.1644`, above the `0.05` target but still far below the `0.6` alert threshold.
- The latest owner message from May (`message.created` event `1605110`) explicitly says `good -> acceptable` is a vocabulary/passing-grade mismatch, not a real evaluator quality miss.
- That same owner judgment approved the concrete fix path: exclude `good -> acceptable` from the `evaluation.false_good` emission path in `projects/evaluation.app/workflows/evaluator-aftermath.ts`, and only emit `evaluation.false_good` when a heuristic `good` is later reviewed as `needs_improvement` or worse.

- May also clarified that the stale DB `projects` read-model row is a known platform limitation, not a project-state mistake in `project.md`; file-backed status is the source of truth for this project.
- Because a concrete next action is now ready, the project is correctly `active` until the implementation lands and the next fresh metric window confirms the expected drop.
