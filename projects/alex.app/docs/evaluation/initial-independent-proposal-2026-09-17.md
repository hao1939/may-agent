PROPOSED DESIGN — not implemented or approved for activation.

1. Smallest coherent architecture
Use Evaluation's ordinary App Tasks, one bounded evidence-review workflow and small helpers for subject resolution, evidence collection, result admission and publication. A goal input covers explicit review, report questions and follow-up; procedure preferences belong in context. A bounded scheduled selector can attach/create review work through existing Task admission, not a private queue. Keep existing explicit actions only as compatibility adapters into the same guarded review path. Do not retain separate shallow/deep/project scoring engines merely because they already exist. Agent chooses the useful review procedure; code enforces identity, bounds and artifact integrity.

Reuse canonical Task generation/input correlation, retained attempt evidence, schema-backed awaited agent calls, task-emission identity, read-back practices and the good evidence/attribution criteria. Keep historical reports and evaluations readable. Replace the fixed watchedProjectTargets, per-session fan-out, self-health scoring loop and agent-directory feedback writes. Evaluation operational failures remain its own ordinary Task evidence, not evaluations of Evaluation.

2. Subject and evidence identity
Make the primary subject an App's requested outcome at an exact Task/input/generation or accepted-result revision. Sessions and workflow runs are contributing evidence, not substitutes for the outcome. Support session-only history honestly when no Task linkage exists. Capture a bounded evidence manifest: authoritative App/Task identity, requested outcome and changes, acceptance, caller/worker links, attempts and recovery, accepted results, supplied transcript spans, artifact references and verification/publication receipts. Record unavailable and truncated evidence explicitly. Re-read mutable identity before publication; never grade a newer requirement using an older success.

Discover installed subjects using the existing App catalog/control capabilities, not directory-name inference or a May/Scout list. The inspected Workflow AppRead is scoped and has no global apps/SQL interface. Therefore first prove the available public control/tool read path and provenance fields in this installed Host; do not invent ctx.read.apps or import Host-private stores. A bounded public evidence adapter is preferable to a new Host schema or evaluator database. If provenance is unavailable, retain an unresolved-identity disposition instead of guessing.

Apply one exclusion function before model work AND before publication across automatic selection, explicit goal/session/deep/project actions, correction, replay and feedback. Resolve owning App and causal delegation/worker lineage; exclude Evaluation-owned work regardless of executor name or target App. Distinguish that causal lineage from an unrelated target Task that merely cites an evaluation. Historical ambiguous identity is not eligible by default. Test cross-App workers, nested calls, spoofed names and unresolved ancestry.

3. Judgment and honest accounting
Agent judges correctness, requested value, delegation quality, follow-up, recovery, verification, publication and delivery. A failed intermediate attempt can precede a good recovered outcome; correct reuse/no-op can be good; an operator-assisted success must credit the operator and not imply autonomous delivery. Use policy at the time of the reviewed work when available, not today's instructions retroactively.

Separate review dispositions: assessed, insufficient evidence, excluded, evaluator failure and reused unchanged review. Only assessed material enters quality aggregates. Reuse means no additional model assessment, not another quality sample. Coverage must expose eligible, selected, assessed, insufficient, excluded and failed counts with window and sampling limits. Empty or incomplete coverage is unknown/unsampled, never healthy. Preserve legacy rows but separate their semantics/version in metrics; avoid rewriting history or manufacturing low scores for missing evidence.

4. Publication, report use and follow-up
Code publishes an immutable, versioned report plus machine-readable facts beneath Evaluation's existing report/workspace conventions, reads both back, then returns exact artifact and Task/outcome references. Store evidence and report content hashes and evaluator execution/cost references. A correction explicitly supersedes an earlier report; retries reuse the exact admitted identity. Keep a disposable latest/index projection for discovery, not an issue lifecycle.

Provide a simple Evaluation goal for questions such as 'show recent May material issues and improvement status'. It reads published reports and linked canonical Task outcomes; May can use that existing App contract to answer the human with scope, material findings, evidence links, cost/coverage caveats and current improvement status. No automatic stream of every score. Prove a real report can be discovered from this interface, read, accurately explained and used for one follow-up.

Responsible Apps receive only useful findings through their current admitted input contract, with the report link and stable finding identity. Inspect actual consumer contracts; an emitted project.owner.requested event alone does not prove acceptance. Use existing Task/input correlation and public outcomes for delivery and follow-up; no private pending-findings queue. Distinguish report published, input accepted, owner acknowledged, remediation claimed and independently verified resolution. An unresolved delivery stays visible as such. A recheck reads the actual fix/output evidence and current acceptance; acknowledgement cannot close the finding. Avoid reflexively evaluating feedback-processing descendants. Align any generated agent feedback projection with the actual loaded reader convention, or omit that secondary channel until verified. Do not mutate other Apps' instruction files as report delivery.

5. Bounded cost and rollout
Suggested initial configuration, to calibrate rather than hard-code as universal policy: automatic selection disabled during trials; then one review per tick, one concurrent evaluator, at most four automatic model reviews per day, bounded lookback and candidate pages, one judgment call with roughly 30 tool operations and a five-minute timeout. Budget explicit trials separately and cap their total calls. Record actual model/provider cost, tokens, elapsed time and operations; unavailable cost stays unknown. No model call for deterministic exclusion or unchanged reuse. On unchanged provider/evidence failure use an exact wait/visible gap rather than an automatic retry storm. Preserve all failures for calibration.

6. Acceptance evidence and deployment
First freeze and report May's independent proposal, then compare it with the reviewer proposal without rewriting the original. Document common Task/workflow/discovery principles in may-agent.app and Evaluation selection, report schema, criteria, consumption, metrics and runbook in evaluation.app. Label proposals versus source-verified versus deployed facts.

Add tests for every entry-point exclusion, dynamic third-App discovery, identity mismatch, evidence truncation, stale generation, unchanged replay, correction, malformed output, provider error, failed publication/read-back, consumer rejection and acknowledgement without resolution. Replace old tests that require self-review or count every evaluation as coverage. The exact required argv currently fails because root bunfig.toml scopes discovery to shared: fix test discovery narrowly or have the workflow verification configuration corrected; do not present the explicit-glob pass as an exact-argv pass. Run package syntax/type/format/tests and relevant common-doc checks on the eventual candidate.

Use several small real-history/model batches and retain counterexamples. The Scout history provides exact positive controls: Task goal/app_8d1253ce-7fdc-45f2-96c6-8365379ed023 recovered on its second attempt and published commit 460ab58792b68dc8d41b9ed7877365dd24116a12; Task goal/app_517fa190-1325-496f-bf23-10fc96d6cac2 reused the report in one attempt without a commit. Expand their primary Task/session receipts, not just these summaries. Include May's delegated contribution versus operator-owned integration, an actual failure/correction, missing evidence and excluded Evaluation delegation. For every run show source Task/input/session identities, evaluation Task/model session, report/read-back, coverage, cost and expected versus observed attribution. Deterministic mocks are a separate evidence column.

This design judgment does not assert implementation, full acceptance, deployment or integration.
