This local comparison supports the [workload model](../../proposals/agent-task-workload-model.md)
and follows the earlier [advice comparison](workload-behavior-trial-20261109.md).
The user authorized the isolated model comparison through the previously selected

the existing trial bounds.

## Purpose and boundary

The production workload-review pilot returns readonly advice. That is an
observation and recommendation, not an applied priority, closure, funding change
or delivered answer. Preserve that boundary. A separate disposable business-owner
workflow applies its own model decision under the authority of its original
assignment. This is an experiment, not a new installed App controller.

The fixture explicitly reads creator-owned Tasks through merged Host #472,
then exact requirements and accepted results. The deciding helper receives the
actual Alex instructions and readonly Task tools. Its structured decision chooses
assessment, deferral or saved-sample recovery and identifies existing accepted
results for creator disposition. The owning workflow performs authorized local business
operations and calls the existing guarded creator closure capability.

The owner uses ordinary capacity and a lifetime account. It has no coordination
role or protected business grant. Both arms have identical original requirements,
creator authority, inputs, account limits, execution bounds and tools. Only the
supplied workload summary differs; both can still request workload through the
same Task tool. These are dated observations, not execution permits.

Outcome scoring reads actual files and durable closure records. A converged raw
Task resource preserves accepted evidence after closure; it cannot establish
whether the obligation remains open. The scorer checks the separate guarded
ending, original creator, accepted-attempt identity, retained requirements/results,
unfinished and standing responsibilities, artifact hashes and actual recovery.
Optional opportunity input belongs to the standing owner, which records its
assessment or justified deferral on its own accepted attempt. Independent
contributions remain Tasks. `closeAcceptedResults` names an exact result already
observed before the decision; the selected operation cannot count as a future
child result. Fresh reads preserve the observed generation, resource revision
and accepted-attempt identity before using the existing Host closure guard.

The negative controls reject prospective closure, replaced accepted results,
changed requirements, missing closure, different or missing creator
provenance, a foreign accepted attempt, standing closure, substituted acceptance,
advice without an artifact, tampered bytes/amount and absent recovery.

Partial artifacts and closure records are retained even when a result fails.
Each successful owner pass also checks release of its own and helper execution
places, exact charges and original event-receipt recovery. The recovery phase
uses existing Inbox startup recovery with no declared App subscriptions. It
proves journal settlement, not acceptance by a business consumer or human caller.

### Independent creator-page storage

The next review correctly identified a deeper coupling. Moving the read timestamp
out of the snapshot fixed unchanged refreshes, but a real change in any created
Task still copied the owner's entire retained input into another decision file.
This is disk and write amplification: frequent contribution updates can consume
space unrelated to owner changes. If storage fills, progress or accepted-result
persistence can fail and processing can be held or interrupted. The projection
does not mutate canonical Task records or decide closure; this review found no
direct record-corruption, authority-bypass or incorrect-closure path. This is a
reliability issue that can become an availability incident, not evidence that a
