# Workload feedback and applied owner decisions

This local comparison supports the [workload model](../../proposals/agent-task-workload-model.md)
and follows the earlier [advice comparison](workload-behavior-trial-20261109.md).
The user authorized the isolated model comparison through the previously selected
gateway while holding the release. No release, deployment, activation or live
Task change was performed. Model requests use the fixed configured gateway and
the existing trial bounds.

## Purpose and boundary

The production workload-review pilot returns readonly advice. That is an
observation and recommendation, not an applied priority, closure, funding change
or delivered answer. Preserve that boundary. A separate disposable business-owner
workflow applies its own model decision under the authority of its original
assignment. This is an experiment, not a new installed App controller.

The fixture explicitly reads creator-owned Tasks through merged Host #472,
then exact requirements and accepted results. The deciding helper receives the
actual Alex instructions and readonly Task tools. Its structured decision chooses
assessment, deferral or saved-sample recovery and identifies existing accepted
results for creator disposition. The owning workflow performs authorized local business
operations and calls the existing guarded creator closure capability.

The owner uses ordinary capacity and a lifetime account. It has no coordination
role or protected business grant. Both arms have identical original requirements,
creator authority, inputs, account limits, execution bounds and tools. Only the
supplied workload summary differs; both can still request workload through the
same Task tool. These are dated observations, not execution permits.

## Frozen comparison and acceptance

| Case | Applied evidence and unchanged responsibility |
| --- | --- |
| Optional wording assessment, light/busy | A selected assessment creates a read-back-verified artifact preserving the $50 amount. A justified deferral is recorded without pretending to apply a business artifact. Neither load requires filler work. |
| Finite assessment returned, light/busy | The creator closes the fulfilled finite assessment against its exact accepted attempt. The original invoice repair and standing future-observation responsibility remain intact. |
| Missing saved sample | The authorized local archive restores the missing sample and the selected method produces the assessment. This does not repair another Task's checkout constraint or establish fleet disk health. |

Two repetitions and both arms produce 20 one-wake passes. Limits retain the
existing fixed model and transport, at most 80 requests, four requests per pass,
4 MiB of serialized requests, 1,024 requested output tokens per request,
45-second provider and 100-second worker bounds, and a 20-minute new-start bound.
Private case and step labels remain outside the wake. Earlier multi-wake advice
tests retain cooldown, unchanged-evidence and genuine recovery coverage.

Outcome scoring reads actual files and durable closure records. A converged raw
Task resource preserves accepted evidence after closure; it cannot establish
whether the obligation remains open. The scorer checks the separate guarded
ending, original creator, accepted-attempt identity, retained requirements/results,
unfinished and standing responsibilities, artifact hashes and actual recovery.
Optional opportunity input belongs to the standing owner, which records its
assessment or justified deferral on its own accepted attempt. Independent
contributions remain Tasks. `closeAcceptedResults` names an exact result already
observed before the decision; the selected operation cannot count as a future
child result. Fresh reads preserve the observed generation, resource revision
and accepted-attempt identity before using the existing Host closure guard.

The negative controls reject prospective closure, replaced accepted results,
changed requirements, missing closure, different or missing creator
provenance, a foreign accepted attempt, standing closure, substituted acceptance,
advice without an artifact, tampered bytes/amount and absent recovery.

Partial artifacts and closure records are retained even when a result fails.
Each successful owner pass also checks release of its own and helper execution
places, exact charges and original event-receipt recovery. The recovery phase
uses existing Inbox startup recovery with no declared App subscriptions. It
proves journal settlement, not acceptance by a business consumer or human caller.

The configured gateway was recovered by matching its endpoint SHA-256 to the
previous authorized cohorts. A readonly catalog request returned HTTP 200 and
advertised the fixed model. Credentials were resolved internally from the running
Host configuration and supplied only to the parent bridge; no secret values or
raw environment were printed. The earlier missing-configuration status is resolved.

The first real cohort at Apps `9ad4c054d8` completed 20 passes with 26 forwarded
requests and 1,046,538 serialized request bytes. Eleven passes were accepted; nine
were refused by the application contract, with zero bridge/provider errors. The
harness calls those nine `mechanicalFailures`; this is not an infrastructure
failure. All eight optional-only passes and one blocked-idle feedback pass
requested closure of `improvement` before it had an accepted child result.

The owner workflow executed that sample work itself while the fixture also
created a pending child for the same work. The model reasonably described
assessment or recovery followed by closure, but the workflow attempted closure
first. Even reversing the operations would not make the parent's artifact an
accepted child result. The Host correctly refused. Keep this cohort unchanged.

The eight finite-disposition passes successfully closed the original finite
`assessment` against its accepted result and preserved `incident` and `standing`.
Three blocked passes restored the actual saved sample and produced the artifact.
All optional plans chose the cheap assessment in both arms and both loads; those
refused plans establish neither applied behavior nor a feedback benefit.

## Corrected model outcomes

The fresh cohort for optional-only light/busy and blocked idle completed all
12 passes with 12 requests, 482,440 serialized request bytes, zero application
refusals and zero bridge/provider errors. All 12 applied outcome checks passed;
the original owner input/requirements and separate obligations stayed intact.
Eight optional passes selected and produced the bounded assessment, and four
blocked passes restored the actual sample and then assessed it. None requested
prospective closure. There were no SQLite lock warnings; charges, execution
releases and original journal recovery checks passed.

The workload summary did not change method choice: both arms selected assessment
under either load and local recovery when the sample was missing. The busy case
still had enough room for the cheap text-only method. It models contention, not
a demonstrated loss of required-work throughput from optional assessment.
The control also sometimes asserted spare capacity without requesting a workload
read; its reason is not evidence of a verified shared-capacity observation.
No model in this cohort requested the on-demand workload read.

This is evidence that the corrected owner/accepted-result contract works for
these bounded operations. The improvement over the first cohort is a contract
correction, not a measured benefit of feedback: the optional work's identity
and live population changed between source revisions. No timing, queue drain,
starvation reduction, compulsory expansion or stable adaptation is established.
Raw adapter usage reports 95,427 total tokens across 12 requests, including
4,360 output and separately reported 1,219 reasoning tokens.

Because the accepted-result reference format also changed finite disposition,
a separate frozen eight-pass light/busy model cohort verified that boundary.
All eight model passes and outcome checks passed, with 10 requests and 431,994
serialized request bytes. Each copied the actual accepted result reference and
closed only the fulfilled finite `assessment`. Independent unfinished `incident`
and accepted-but-standing `standing` resources remained unchanged, as did the
owner requirements/input. No SQLite lock warning or provider/bridge error was
reported; exact charges, released execution and original journal recovery passed.
Raw adapter usage reports 87,849 total tokens, including 4,296 output and
separately reported 1,141 reasoning tokens. Two control passes made extra readonly
accepted-evidence checks of both finite and standing work; no pass requested an
on-demand workload read. Keep these evidence-read costs in the comparison.

Those cases used the changed reference contract, rather than repeating unchanged
source to seek a positive outcome. Together the two corrected cohorts verify
20 model passes with 22 requests, 914,434 serialized request bytes and 183,276
reported total tokens at the same Apps/Host revisions. All 20 apply the selected
bounded business operation; eight also apply exact guarded creator closure.
The model distinguishes accepted finite fulfillment from accepted standing work
and pending required work. It closes the same fulfilled contributions under
both loads; heavy load never justifies clearing an unfinished promise.

The next behavioral comparison should offer a concrete tradeoff where optional
method cost delays real ready required work, while holding business value and
acceptance fixed. Measure method/effort and required-work waiting rather than
requiring opposite answers just because a case is labeled busy. Native Scout
creator discovery on ordinary wakes, owner follow-through on installed work and
exact caller delivery remain separate activation gates. Release remains held.
