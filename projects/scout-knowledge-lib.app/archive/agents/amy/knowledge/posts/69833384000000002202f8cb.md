## 核心原理（作者读GitHub源码后总结）

### 第一步：对话全部存下来（持久化层）
```
用户对话 → 自动写入 memory/日期.md
文件改动 → Chokidar监听 → 1.5s去抖 → 触发重索引
处理流水线:
  步骤A: 分块 (400 tokens/块, 80 tokens重叠)
  步骤B: 哈希校验+缓存查询(embedding_cache表节省API成本)
  步骤C: 写入SQLite五张表
```

### SQLite五张表
| 表名 | 作用 |
|------|------|
| files | 追踪文件变更 (path+hash) |
| chunks | 主索引 (id+text+lines+hash) |
| chunks_vec | 语义检索 (embedding 1536维 6KB二进制) sqlite-vec扩展+SIMD加速 |
| chunks_fts | 关键字检索 (FTS5引擎+BM25算法) |
| embedding_cache | 缓存加速 (hash→embedding, 节省API调用) |

### 第二步：混合检索精准召回
```sql
-- 向量搜索（语义理解）
vec_distance_cosine(query, embed) ORDER BY dist ASC
-- 余弦距离: dist=0.15 → score=0.85

-- 关键字搜索（精确匹配）
FTS5 MATCH 'Alice' AND '负责' AND '项目' ORDER BY bm25 ASC
-- BM25 rank: -8.5 → 文本分: 0.94
```
加权合并: 0.85×0.7 + 0.94×0.3 = **0.877**（minScore=0.35通过）

## 上下文 vs 记忆的根本区别
```
上下文 = 系统提示词 + 对话历史 + 工具结果 + 附件
  → 临时的|有限的(20万token)|昂贵的(每token计费)

记忆 = MEMORY.md + memory/*.md + 会话转录文件
  → 持久的|无限的|低成本(存储不产生API费用)|可搜索

上下文结构（每次请求注入）:
  [0] 系统提示词 (静态指令+条件指令)
  [1] 项目上下文 (AGENTS.md/SOUL.md等引导文件)
  [2] 对话历史 (消息/工具调用/压缩摘要)
  [3] 当前消息
```

## 技术栈
```
存储: Markdown + SQLite
向量: OpenAI embedding (1536维)
检索: sqlite-vec + FTS5(BM25)
文件监听: Chokidar + 1.5s去抖
```
