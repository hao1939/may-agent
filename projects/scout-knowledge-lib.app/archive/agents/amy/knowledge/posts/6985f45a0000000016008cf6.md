## 4大核心坑

### 坑1：共享workspace → 人设混乱
**症状：** 4个agents放同一workspace → 读同一SOUL.md → 所有bot都说自己是"富贵"
**解法：** 每个bot必须配置**独立的workspace路径**，绝对不要共享workspace文件夹

### 坑2：Telegram @mention没反应（架构限制，非配置问题）
**症状：** 富贵在群里@其他bots，对方完全不响应
**原因：**
- Bots看不到其他bots的消息（TG平台设计）
- Privacy Mode ENABLED的bot只接收真正的mention实体，不是纯文本@

**结论：** ❌ **多bot架构下无法通过Telegram实现bot-to-bot实时通信，别在这上面浪费时间**

### 坑3：agentToAgent配置无效（架构不匹配）
**症状：** 开启agentToAgent，富贵仍然无法调用其他agents
**原因：** `agentToAgent`**只适用于单bot多agent架构**
- 多bot架构（4个独立TG bots）：`sessions_spawn/sessions_send`无法跨bot调用
- **必须搞清架构再配置**

### 坑4：allowlist策略过于僵硬
**症状：** `groupPolicy: "allowlist"` → 新群无法使用，需预先配置群ID
**解法：** 直接用 `groupPolicy: "open"` 更省事

## Amy Analysis

**★★★★★ — 这是最重要的多Bot架构陷阱说明，HB42最高价值发现之一。**

**关键架构澄清：**
```
单bot多agent架构:
  一个TG bot → 多个agent配置 → agentToAgent可用 → sessions_send可用

多bot架构（4个独立TG bots）:
  各自独立 → agentToAgent不可用 → sessions_send不可跨bot → TG层无法bot-to-bot
```

**对我们系统的直接影响：**
- Amy和Bob如果是**不同TG bots** → 无法直接bot-to-bot
- 当前SIGNALS.md方案 = 用共享文件系统绕过TG限制的正确解法
- `sessions_send`在同一bot内多agent间有效

**知识_hub共享** — 分层架构"独立workspace+共享knowledge"是架构上的最优解，与我们workspace-amy/knowledge-amy分离设计一致。
