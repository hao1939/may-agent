## 元学习定义

**元学习 ≠ RAG**
- RAG: "告诉它在哪里能找到信息"
- 元学习: "让它下次直接换一种做法" — 把规则写进boot文件，每次启动都加载

**三个层次:**
1. 出了问题就修，写规则防着
2. 发现规律，弄清楚为什么这类事情总是出问题
3. 系统自己改进自己，连学习的方式本身也在变（meta元学习）

## 九个窍门（完整实现细节）

### 一：出了事就立刻写进"别再犯"清单
```
Regressions（不要重蹈覆辙）
格式：[日期] 出了什么事 → 以后怎么做
```
每次出明显问题→搞清楚为什么→写规则堵漏洞→加进boot文件→永远生效
每行十几个token的开销，能永久防住一类问题

**OC具体陷阱：** 调用写文件工具返回成功，但路径权限原因文件没写进去→agent继续执行下一步→留下难查的问题 → **这正是MAST 3.3"错误验证"的具体表现**

### 二：记忆分档管理 + 标注可信度
三档：
- **法典级** — 永不过期（安全规则/硬约束/身份定义）
- **策略级** — 每季度刷新（当前项目/方向）
- **临时级** — 30天无用自动归档（bug/临时方案/任务上下文）

可信度标注格式：
```
[可信度:0.9 | 来源:直接告知 | 最后使用:2026-02-22 | 命中次数:12] 用户喜欢用命令行部署
```
- 直接告知=1.0 | 观察推断=0.7 | 未验证外部信息=0.5
- 旧信息被推翻→归档而非删除（删掉的话将来同样信息出现时不知道它曾被推翻过）

### 三：做决定之前先写下预测
```
2026-03-01 — 重构消息队列
预测：改成异步消费者之后延迟应该能降到 50ms 以下
不确定的地方：现有的重试逻辑可能和新架构冲突
把握：中等
实际结果：（事后填）
和预期不一样的地方：（事后填）
以后要调整的判断：（事后填）
```
"和预期不一样的地方"是关键——不是问"我猜对了没"，是问"我哪里想偏了"

### 四：每天晚上自动跑一遍"今天学到了什么"
定时任务做三件事：
1. 检查今天的决定和推理有没有书面记录
2. 更新被用到的记忆条目的命中计数
3. 测试：如果明天早上是全新session，只看文件能不能还原今天发生了什么？

### 五：遇到前后矛盾的指令，记下来
设"矛盾日志"——遇到冲突不要自己解决，记下来，等合适时机摆到台面上让人拍板

### 六：设置有过期时间的"临时关注点"
```
临时关注：准备上线
内容：不要启动新的大功能，集中处理稳定性问题
设置时间：2026-02-18
过期时间：2026-03-15
解除条件：上线完成且没有紧急问题
```
没有过期时间→关注点越积越多→过时框架干扰判断

### 七：对自己说出来的话标注性质
类型：公认的事实 / 自己观察到的 / 推断的 / 猜的 / 故意唱反调的
→ 从复述模式切换到思考模式

### 八：创意和策略类工作单独设规则
只在创意/策略工作时生效：
- 至少提出一个让自己也觉得有点冒险的角度
- 先说大家的共识是什么，再说为什么不同意
- 宁可选"有意思但可能错"，不要选"绝对稳妥但无聊"

### 九：自我迭代要有结构，不能无限"再改改"
生成→按具体标准评估→找出差在哪→只改那个差的→重复
**连续三轮改进幅度不到5%就停下来**

---

## 三个最容易犯的错误

1. **把RAG当成学习** — 检索时才能找到≠真正改变了行为
2. **只优化这次对话，不管下次** — 调prompt/换模型都是在让今天更好，真正值得投入的是"怎么让以后每次都更好"
3. **建了回路但没有闭合** — 每天写日记但下次session没人读；预测写了结果从来没填；矛盾记下来了但从来没有拿出来讨论

---

## 关键结论

"一个很聪明但没有这些机制的agent，到第100天和第1天没什么两样。一个能力普通但有这些机制的agent，几周之后就能超过前者，因为它每次都在上一次的基础上往前走一点。"

"问题不是'我的agent有多聪明'，而是'它学得有多快'。"
