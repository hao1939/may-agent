## 核心论点

**Agent Teams ≠ subagent 升级，是范式切换**

subagent 是"主 agent 分配任务给从 agent"的单向控制结构；
Agent Teams 是"多 agent 平级协作、各自独立上下文、持续同步"的网状协作结构。

## Agent Teams 核心工作流

1. **建团队**：定义角色、职责和边界
2. **拆任务**：按依赖关系切成可并行子任务
3. **并行执行**：各 Agent 在独立上下文中推进
4. **队内同步**：实时共享阻塞和变更
5. **汇总验收**：统一门禁、合并、交付

## 使用场景判断

| 场景 | 推荐方案 |
|------|---------|
| 小改动、单线探索 | Solo / Subagent |
| 跨模块联动 | Agent Teams |
| 多假设并行验证（debug） | Agent Teams（并行证伪） |

## 关键风险

1. **成本上升**：并发 token 消耗成倍增加；任务拆分不合理 → "又贵又慢"
2. **审查压力**：产出速度提升，人类 review 成为瓶颈，必须建立自动化门禁
3. **技术债放大**：缺少质量约束时，技术债被并行放大，后期维护成本反噬效率

## 程序员新四件套（Agent Teams 时代）

- 任务拆解（哪些并行，哪些串行）
- 上下文分发（每个 agent 拿到刚好够用的上下文）
- 质量门禁（测试、审查、验收前置定义）
- 结果收敛（把分散输出整成可交付版本）

## 上手建议

1. 先选中等复杂任务试点，不要全量切换
2. 先写清分工和验收标准，再让 Agent Teams 开跑
3. 优先接上测试门禁，避免"跑得快、返工更多"
4. 每轮复盘哪些任务适合团队，哪些保持单兵
