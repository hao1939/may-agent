当 Agent 会自己「写工具」，评测要重做一遍

当你的 Agent 在做 planning 时，需要调用工具——

但现有预置工具里没有合适的。

这时候你有两种选择：

1️⃣ 直接 fail / fallback
2️⃣ 让 LLM 基于 Prompt 现场生成一个工具（通常是 code），然后执行

第二种，其实可以称之为：planning with code execution

这已经不是简单的 tool calling 了，而是：

模型在 planning 阶段，具备「构造执行能力」的

[Slide 2]
能力。

如果你想系统化评估这类能力，评测标准必须升级。
否则你只是在测模型会不会写代码，而不是在测「规划能力」。

# 一、planning with code execution需要评什么？

很多人第一反应会说：

"那就测代码对不对呗。"

但这是不够的。

planning with code execution，本质包含 4 个层次：

1️⃣ 任务分解是否合理
2️⃣ 是否识别出"需要新工具"
3️⃣ 生成的代码是否满足功能
4️⃣ 执行结果是否被正确使用

它不是单点能力，而是一条链路能力。

[Slide 3]
二、可以怎么定评测标准?

建议从 5 个维度来设计：

① Tool Gap Recognition（工具缺口识别）

模型是否正确判断：

当前预置工具不够用
必须生成新工具

⚠️ 常见错误：

*　明明已有工具却重复造轮子

*　明明需要新工具却硬用已有工具拼凑

② Planning Rationality（规划合理性）

是否明确：

*　先生成代码

*　再执行

*　再消费结果

[Slide 4]
有没有顺序错乱、跳步、漏步。

## ③ Code Correctness（功能正确性）

不是只看是否能跑通，而是：

* 输入输出 schema 是否匹配

* 是否处理异常

* 是否考虑边界

## ④ Execution Stability（执行稳定性）

* 是否出现 runtime error

* 是否无限循环

* 是否污染上下文

这个维度很多团队忽略。

## ⑤ Result Integration（结果整合能力）

执行结果出来后：

[Slide 5]
* 是否正确读回结果

* 是否用于后续 reasoning

* 是否出现 hallucinated execution result

# 三、评测集应该怎么设计？

核心原则：
不要只测"算法题"，要测"工具缺失场景"。

可以分三类：

## A 类：轻量工具生成场景

例子：

* 计算一个特殊统计指标（已有 math 不支持）

* 转换某种特殊格式

* 解析自定义规则文本

目标：测基础 planning + 代码生成。

## B 类：跨步骤数据依赖场景

例子：

[Slide 6]
* 生成代码处理数据

* 再基于处理结果生成分析报告

目标： 测 execution 结果是否真实参与后续决策。

# C 类： 边界 & 失败场景

例子：

* 代码运行会抛异常

* 输入数据为空

* 数据量极大

目标：测模型是否具备 retry / 修复能力。

# 四、关键指标可以量化成什么？

你可以定义：

* Tool Gap 判断准确率

* 代码一次运行成功率

[Slide 7]
* 平均 retry 次数

* execution result hallucination rate

* 端到端成功率

其 中 个 人 最 看 重 的 是 ： execution result hallucination rate

很多模型会"假装执行成功"。

如果你不校验 stdout / file output，
它可以编出一个结果继续往下走。

这种系统，一上线就会翻车。

# 五、一个更底层的判断

planning with code execution，
本质是让模型：

从"调用已有能力"，
升级为"构造能力"。

这会让系统能力指数级上升，
同时风险也指数级上升。

所以评测的核心，不是：

[Slide 8]
"模型能不能写出代码"。

而是：

"系统在引入动态执行能力后，
是否仍然可控"。

如果你把它只当成 codegen 评测，
你会低估系统复杂度。

如果你把它当成系统级能力升级，
你就会知道评测必须覆盖：

规划 → 构造 → 执行 → 消费 → 纠错
整个闭环。
