# Commit Guard Window 2 Regression Analysis

**Date**: 2026-04-09  
**Question**: Why did auto-commit rate jump from 17% (Window 1) to 47% (Window 2)?

## TL;DR

**The regression is an artifact, not a real regression.** The apparent jump is caused by a new type of infrastructure commit (`chore(auto): commit before sync`) introduced by the federation sync redesign at 14:50 on Apr 8. These commits are not indicators of agent laziness — they're generated by the sync mechanism every 10 minutes to safely commit dirty state before pulling from the remote.

When infrastructure noise is excluded, the real auto-commit rate is **8% (W1) → 21% (W2)**, and the W2 "auto-commits" are entirely `shared/knowledge/` files arriving via cross-instance federation sync — not agents failing to commit.

## Detailed Findings

### 1. Is the guard still active?

**Yes.** The code in `agents/may/handlers/agents-auto-commit.ts` is unchanged. The `--no-verify` flag on "commit before sync" bypasses git hooks, but this is intentional — these are infrastructure commits, not agent work.

### 2. Two types of auto-commits

| Type | Source | Meaning |
|------|--------|---------|
| `chore(auto): commit before sync` | `tryPull()` in agents-auto-commit.ts | Commits dirty files before `git fetch + rebase`. Runs every 10min. **Infrastructure noise.** |
| `chore(auto): shared: knowledge updates` (descriptive) | Main handler body | Safety-net for orphaned changes. **This is what the guard targets.** |

### 3. Window breakdown

| Metric | Window 1 (24h) | Window 2 (9h) |
|--------|----------------|---------------|
| **Original metric** (all auto / total) | 25/147 = **17%** | 51/108 = **47%** |
| Commit-before-sync (infra) | 14 | 35 |
| Descriptive auto (safety-net) | 11 | 16 |
| Agent commits | 122 | 57 |
| **Corrected** (safety-net only / relevant) | 11/133 = **8%** | 16/73 = **21%** |

### 4. Why more "commit before sync" in Window 2?

The federation sync redesign was deployed at **2026-04-08 14:50**. It introduced:
- `writeInstanceHeartbeat()` — writes `shared/federation/heartbeats/local.json` every cycle
- `tryPull()` — commits any dirty files before fetching from remote
- Conflict resolution that creates `.conflict-k3s` files

This creates a **self-sustaining dirty-state loop**:
1. Handler runs → writes `local.json` heartbeat
2. Next handler run → `tryPull()` sees dirty `local.json` → creates "commit before sync"
3. Remote instance does the same → creates its own "commit before sync"
4. Both instances produce paired commits every ~10 minutes (visible as :X3/:X4 second patterns)

In the 16:00-17:30 period, commits came in **pairs** (~51s apart):
- `:X3:37` — one instance (this k3s pod)  
- `:X4:26-28` — the other instance (local/dell-laptop)

After the **2.5h outage** (17:30-20:20), only one instance was active, reducing to single commits.

### 5. Which agents account for Window 2 auto-commits?

**None.** All 16 descriptive auto-commits in Window 2 contain only `shared/` or `gym/` files — these are cross-instance synced files that arrive via federation pull but aren't committed by any agent (because they originate from the other instance). Zero agent-specific files (bob/, coach/, may/, etc.) appear in Window 2 descriptive auto-commits.

### 6. Session type correlation

Not applicable — the "commit before sync" commits are generated by the cron handler itself (every 10min cycle), not by any agent session. They occur regardless of whether agents are active.

### 7. Time-of-day pattern

The "commit before sync" pattern is constant (every 10 min) when both instances are running. It paused during the 2.5h outage (17:30-20:20 on Apr 8).

## Corrected Assessment

| Metric | Baseline | Window 1 | Window 2 |
|--------|----------|----------|----------|
| Original (all auto) | 62% | 17% | 47% |
| Corrected (safety-net only) | ~62%* | 8% | 21% |
| Agent-laziness auto-commits | ~62% | 1** | 0 |

\* Baseline was measured before "commit before sync" existed, so all auto-commits were safety-net type.  
\** Window 1 has 1 non-shared descriptive auto-commit; 10 are shared/ files from federation.

## Root Cause

The original metric (`chore(auto)` count / total) conflates two different things:
1. **Agent laziness** (the guard's target): agents not committing their own work → caught by safety-net
2. **Infrastructure** (not the guard's target): federation sync creating "commit before sync" commits

The federation redesign at 14:50 Apr 8 doubled the infrastructure commit rate.

## Recommendations

1. **The guard is working well.** Agent-laziness auto-commits dropped from ~62% (baseline) to near-zero. Agents are committing their own work.

2. **Fix the metric.** For future measurements, exclude `commit before sync` from the count. The meaningful metric is descriptive auto-commits containing agent-specific paths.

3. **Fix the heartbeat dirty-state loop.** The `writeInstanceHeartbeat()` function creates a constantly-dirty file that forces a "commit before sync" every cycle. Options:
   - Add `shared/federation/heartbeats/*.json` to `.gitignore`
   - Only write heartbeat if it's been >30min since last write
   - Move heartbeat to a non-git location (e.g., `.state/`)

4. **The shared/knowledge auto-commits are expected.** These are legitimate: changes made by agents on the other instance arrive via federation sync as unstaged files. The auto-commit handler correctly commits them. This is the safety net working as designed.

5. **Final measurement at 48h mark** should use the corrected metric to avoid misleading conclusions.
