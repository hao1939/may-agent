# Design: Telegram Channel

**Status**: implemented foundation, needs interaction refinement
**Updated**: 2026-06-14

## Purpose

Telegram is the mobile human-control surface for May-agent. It should feel like
talking to the system, not operating a separate bot UI.

The channel has three jobs:

1. Let the human ask questions and steer active work.
2. Notify the human only when attention is useful.
3. Turn every human reply into tracked input with enough context for the
   receiver to act.

The rule is:

> Telegram reply chains preserve local context. Human text stays plain;
> May-agent attaches the context and enriches the internal delivery message.

## Current Implementation

The current code path is:

```text
outbound event
  -> telegram-outbound formats message
  -> telegram-client sends message and stores notification_messages row
  -> human replies to that Telegram message
  -> telegram-reply-router reconstructs context
  -> telegram.ts acknowledges the reply and emits human.input.received
     with structured context
  -> command-router enriches the internal delivery message
  -> command-router routes to a target session, project comment, or May chat
```

What works now:

- Allowed-chat enforcement.
- Long-polling inbound messages.
- `message.created` to `human` is forwarded to Telegram.
- Root chat responses stream back to Telegram.
- Child-session completions are summarized.
- Telegram message IDs are stored in `notification_messages`.
- Replies to stored notifications carry notification/session context in
  `human.input.received.data.context`.
- Internal delivery to a worker/session can include a compact context block
  generated by May-agent; the human does not type or see that metadata.
- Bot acknowledgements can be sent as Telegram replies, preserving the visible
  message chain.

Observed weaknesses:

- Many notifications are too noisy or repetitive, especially recurring metric
  and handler-failure alerts.
- Some notification rows still miss `conversationId`, so May-agent may need to
  fall back to legacy notification/session context.
- Reply context is stored as a generic JSON blob. It works, but producers still
  need to converge on a stable shape for subject, severity, action hints, and
  resolution state.
- The bot still needs better final-result confirmations after May handles a
  human reply.
- Slash-command help advertises status-like flows, but `/status` currently
  becomes a normal chat request rather than a fast read-model response.
- Stale notifications remain actionable. A reply to an old message may wake the
  wrong session or reopen already-resolved work.

## Desired Interaction Model

Telegram messages should look like compact action cards:

```text
AKS RP E2E needs approval

Decision
Approve live staging execution for aad-rbac and ossku-migration?

Why now
Check-mode coverage is high, but evidence quality is missing live staging.

Current state
153/173 paths pass. 20 non-passing paths remain classified.

Reply
approve
adjust <changes>
hold

Open: /projects/aks-rp-e2e.app/ui/kanban/
```

The message should answer four questions without requiring a web UI:

- What happened?
- Why am I being notified?
- What can I say?
- What happens after I reply?

After May receives the enriched reply, May or the project owner may produce a
small typed event:

```json
{
  "type": "project.focus.approval.submitted",
  "source": "telegram",
  "owner": "agent:aks-explorer",
  "data": {
    "projectPath": "projects/aks-rp-e2e.app",
    "planId": "focus-proposal-live-staging-20260613",
    "decision": "approve",
    "reply": "approved",
    "author": "hao"
  }
}
```

The human-facing acknowledgement should describe the effect:

```text
Approved. aks-rp-e2e planner is reviewing the focus plan now.
```

Not:

```text
Approval sent to project event project.focus.approval.submitted.
```

## Reply Context Model

There are three separate layers. They must not be collapsed into one string.

```text
Human-visible Telegram text
  Plain language only. It describes the situation and the decision needed.

Received event metadata
  `human.input.received.data.context` stores channel context such as
  `conversationId`, `originalIssue`, `expectedClosure`, and notification
  summary fields.

Internal delivery message
  The command router combines the human reply with a compact context block
  before sending work to a May chat session, a target session, or another
  receiver.
```

Example:

```text
Human sees:
AKS RP E2E needs approval

Decision needed
Approve one bounded replay?

Human replies:
approve
```

The received event keeps the human reply and metadata separate:

```json
{
  "type": "human.input.received",
  "source": "telegram",
  "owner": "agent:may",
  "data": {
    "actor": "human",
    "text": "approve",
    "conversation": {
      "id": "approval:approval-123",
      "channel": "telegram",
      "channelMessageId": 511
    },
    "context": {
      "telegramReply": {
        "conversationId": "approval:approval-123",
        "originalIssue": {
          "eventType": "project.approval.requested",
          "approvalId": "approval-123"
        },
        "expectedClosure": ["project.approval.submitted"],
        "notification": {
          "requestedAction": "Approve one bounded replay",
          "reason": "Need exact owner decision"
        }
      }
    }
  }
}
```

The internal delivery message can then be enriched by May-agent:

```text
Human reply
approve

Attached context
Conversation: approval:approval-123
Original issue: project.approval.requested
Original ask: Approve one bounded replay
Reason: Need exact owner decision
Expected closure: project.approval.submitted

Use the human reply as the decision or missing input. Continue the tracked work
and emit the expected closure/update event when done.
```

This is not human-authored text. It is a system-generated work packet for the
receiver. The structured context must also remain attached to the routed event
so reports and health checks can track whether the loop closed.

## Priority 1: One May Human-Chat Session

The first priority is smooth communication and no lost replies:

> Human channels emit canonical input events. The command router uses attached
> context to pick the safest existing receiver and to enrich the delivered work
> packet.

Telegram, Web UI, and default terminal input should all connect to the same May
human-chat session. Telegram reply chains are still useful, but only as local
context attached to the message. They should not select or create separate May
sessions.

Terminal can be more flexible: by default it uses the canonical May chat
session, but operator/debug commands may attach to other sessions explicitly.

May owns the human-control channel by default. When a reply has a known live or
resumable session target, the command router may use the existing
`session.steer.requested` mechanism so the original worker can continue with the
enriched reply. Otherwise the reply goes to May with source and context
attached. May then decides how to handle it:

- fix the issue directly,
- delegate to another agent,
- resume the original session,
- emit a project or escalation event,
- ask the human a follow-up,
- or close the conversation with a result.

This keeps every user interface simple. The transport does not need to know
whether a reply should become a project event, an escalation resolution, or a
new investigation. It only needs to preserve local context and emit
`human.input.received`.

Transport boundary:

- Store the Telegram message id and compact conversation context.
- On reply, recover that context from `reply_to_message_id`.
- Attach conversation/session/notification context to `human.input.received`.
- Acknowledge delivery in the same Telegram reply chain.
- Do not execute project decisions, classify approvals, or repair blockers in
  transport code. May and project agents do that work.

May session rule:

```text
human input from Telegram/Web UI/default terminal
  -> canonical May human-chat session
  -> if the session is idle/running: send input to it
  -> if the session is cold/resumable: resume it
  -> if missing: create it
```

The local channel context needs an envelope:

```ts
interface TelegramConversationContext {
  conversationId: string;

  originalIssue?: {
    eventType?: string;
    eventId?: number;
    sourceAgent?: string;
    sourceSessionId?: string;
    projectPath?: string;
    taskId?: string;
    reason?: string;
    requestedAction?: string;
  };

  lastHandledBy?: {
    agent?: string;
    sessionId?: string;
  };

  expectedClosure?: string[]; // e.g. ["escalation.resolved", "project.owner.requested"]
  staleAfterMs?: number;
}
```

Human-visible text is not routing data. Prose like `From: aks-explorer` or
`Project: aks-rp-e2e` is useful to the human, but the router should use the
stored `conversationId` and `originalIssue` only to enrich May's input.

Recommended flow:

1. Human replies to a Telegram message.
2. Router looks up `reply_to_message_id` in `notification_messages`.
3. Telegram emits `human.input.received` with the human reply in `data.text`
   and recovered metadata in `data.context.telegramReply`.
4. Command router builds the internal delivery message by combining the human
   reply with a compact attached-context block.
5. If a known session target is present, command router emits
   `session.steer.requested` with the enriched delivery message and the same
   structured context.
6. Otherwise it sends the enriched delivery message to May's canonical
   human-chat path.
7. May or the target worker may answer through the originating channel, notify
   the human through another channel, delegate to a project owner, or emit a
   typed event.

This preserves natural conversation while avoiding per-channel May sessions.

### Conversation Examples

Message sent while May brokers a project escalation:

```json
{
  "conversationId": "tg_12345",
  "originalIssue": {
    "eventType": "escalation.created",
    "eventId": 100,
    "sourceAgent": "aks-explorer",
    "sourceSessionId": "s_blocked",
    "projectPath": "projects/aks-rp-e2e.app",
    "reason": "No ready work while gaps remain.",
    "requestedAction": "Ask human how to proceed."
  },
  "lastHandledBy": {
    "agent": "may",
    "sessionId": "s_may_broker_456"
  },
  "expectedClosure": ["escalation.resolved", "project.owner.requested"]
}
```

Plain May chat response:

```json
{
  "conversationId": "tg_67890",
  "lastHandledBy": {
    "agent": "may",
    "sessionId": "s_chat_789"
  }
}
```

### Message Responsibility

The component that sends a human-facing message should provide:

- `conversationId` when continuing a local Telegram reply chain
- `originalIssue` when the message is about an escalation, project, task, or
  blocked session
- `lastHandledBy` when May delegated or resumed work
- `expectedClosure` when the producer knows what event should eventually close
  the loop

Telegram transport should not infer ownership from prose. It may keep best
effort fallback for legacy messages, but new messages must carry conversation
context.

### Original Session Gone

If the original or last-handling session is gone, the reply is still not lost:

```text
reply to Telegram message
  -> read conversationId + originalIssue + lastHandledBy
  -> emit human.input.received with attached metadata
  -> command-router tries the existing session target when one is present
  -> if that target cannot be used, deliver the enriched message to May
  -> May decides whether to resume, delegate, replan, or ask follow-up
  -> May confirms what happened
```

The fallback prompt should be compact:

```text
Human replied in Telegram conversation tg_12345.

Original issue:
<structured issue summary>

Previous handling session: s_old
Human reply: <reply>

Handle the reply. Close or update the original issue when done.
```

Do not silently drop the reply if the previous worker/project session cannot be
resumed. The canonical May chat session should still receive the enriched input.

### May As Broker For Escalations

It is acceptable, and often desirable, for `escalation.created` to route to May
first. May is the human-facing broker and can decide whether the issue needs a
human, another agent, or an automatic repair.

When May reaches out to the human, the human reply returns to the canonical May
human-chat session with Telegram reply-chain context attached. May's
notification must include the original escalation as `originalIssue`, so May can
fix, delegate, resolve, or replan the real problem.

Current weak pattern:

```text
escalation.created
  -> May receives it
  -> May sends plain message to human:
       "[escalation] event #100 ... Reason: ..."
  -> human replies
  -> reply routes to May chat with only prose context
  -> original escalation may remain unresolved
```

Desired pattern:

```text
escalation.created
  -> May receives it
  -> May sends message.created to human with conversationId + originalIssue
  -> human replies to that Telegram message
  -> human.input.received stores originalIssue as metadata
  -> command-router delivers a compact attached-context message
  -> May or the target worker fixes/delegates/resolves/replans the original issue
  -> May confirms the result through the appropriate human channel
```

May should receive a packet like:

```json
{
  "conversationId": "tg_12345",
  "originalIssue": {
    "eventType": "escalation.created",
    "eventId": 100,
    "sourceAgent": "aks-explorer",
    "sourceSessionId": "s_blocked",
    "projectPath": "projects/aks-rp-e2e.app",
    "reason": "No ready work while gaps remain.",
    "requestedAction": "Ask human how to proceed."
  },
  "lastHandledBy": {
    "agent": "may",
    "sessionId": "s_may_broker_456"
  },
  "humanReply": "Investigate and push the project forward"
}
```

May does not have to emit `escalation.resolved` immediately. It may first
investigate and fix the issue. But the reply must stay attached to the original
issue until May emits one structured outcome: resolved, dismissed, routed to the
project owner, or converted into an exact follow-up wait.

Escalation replies have one extra routing rule:

> `sourceSessionId` is resume context, not the Telegram reply target.

For a human-owned escalation, the reply must go to May first. May is the
human-facing decision agent: it reads the human reply plus restored context,
decides the next event, and emits the structured closure or follow-up. Only
after a terminal event does the escalation lifecycle resume the original source
session.

Wrong path:

```text
human reply
  -> session.steer.requested(sourceSessionId)
  -> source session receives "approve"
  -> escalation.created remains open
```

Correct path:

```text
human reply
  -> human.input.received(context.originalIssue.eventType = "escalation.created")
  -> May receives one enriched reply-handling work item
  -> May emits escalation.resolved, escalation.dismissed, or an exact follow-up
  -> escalation-lifecycle resumes sourceSessionId/checkpointRef
```

The notification may store `sourceSessionId` inside `originalIssue` and
`resume`, but it should not store that value as the direct reply `sessionId`.
If legacy rows do contain it, command-router should prefer the
`expectedClosure`/`originalIssue` rule and route the reply to May rather than
steering the source session directly.

## Notification Context

Keep the existing `notification_messages.data` JSON blob, but standardize its
shape. This avoids a schema migration while giving the router a reliable
contract.

```ts
interface TelegramNotificationData {
  text: string;
  summary?: string;

  subject?: string; // "AKS RP E2E focus approval"
  kind?: string; // "approval" | "blocker" | "failure" | "digest" | "session"
  severity?: "P0" | "P1" | "P2" | "P3";

  projectPath?: string;
  sessionId?: string;
  taskId?: string;
  eventId?: string;

  conversationId?: string;
  conversation?: TelegramConversationContext;
  actionHints?: string[]; // ["approve", "adjust <changes>", "hold"]

  staleAfterMs?: number;
  dedupKey?: string;
  supersedesKey?: string;
}
```

New producers should prefer trace metadata when the related event id is known.
`conversationId` plus `conversation.originalIssue` remains useful
transport context, but it should not become a second lifecycle identity.
Telegram transport should not execute the domain decision itself.

## Routing Rules

Reply routing should stay deterministic:

1. If the human message replies to a Telegram message with a stored
   `conversationId`, attach that id and its context to
   `human.input.received.data.context.telegramReply`. If the stored message has
   a source event id, set the received input event's `trace.parentEventId` to
   the message event id and preserve the same `trace.traceId`.
2. Else if it replies to a stored notification without `conversationId`, attach
   the stored notification/session context as legacy fallback.
3. Else if it replies to a Telegram quote with no DB row, build a quote fallback
   context from the quoted text.
4. Else if it is a bare Telegram message, send it as normal input to the
   canonical May human-chat session.
5. Legacy notifications without a conversation envelope should still be
   delivered with the stored notification/session context.
6. Command router is the boundary that turns the received event into an
   internal delivery message and target event.
7. Project-specific events, escalation resolution, session resume, and task
   steering beyond the direct session target are agent/owner decisions after the
   receiver sees the enriched delivery message. Those decisions should emit
   normal events linked back to the human input event.

If the notification is stale, do not silently execute it. Send a short message:

```text
That request is stale. I opened a fresh status check instead.
```

Then emit normal May input with the stale context attached.

## Human Channel Adapters

For now, do not introduce a new built-in service concept. The simpler rule is:

> Human channels are platform adapters. They all feed the canonical May
> human-chat session.

Each adapter should stay small:

```text
Telegram adapter
  -> inbound Telegram messages
  -> outbound Telegram replies/notifications
  -> Telegram message id context store

Web UI adapter
  -> browser chat input
  -> May chat stream
  -> links to project/task/event pages

Terminal adapter
  -> default input to canonical May chat
  -> explicit attach/debug commands for other sessions

Read-model command adapter
  -> /status, /projects, /tasks, /sessions
  -> fast deterministic responses without starting extra LLM work
```

Adapter responsibilities:

- Accept human input from one channel.
- Add channel-local context, such as Telegram reply-chain context.
- Send input to the canonical May human-chat session.
- Deliver May output or acknowledgements back to the human when appropriate.
- Provide fast read-only commands where a full May turn is unnecessary.

Adapter non-responsibilities:

- Do not decide project plans.
- Do not classify approvals.
- Do not repair blockers.
- Do not own project task trees.
- Do not replace project/domain UIs.

This keeps the current architecture simple:

```text
human channel adapter
  -> canonical May human-chat session
  -> May decides/delegates/emits events
  -> adapter delivers visible result when needed
```

Projects may still provide their own domain UI under project routes, but that UI
should call stable project actions or emit project events. It should not reach
into human-channel adapter internals.

If Telegram, Web UI, and terminal later duplicate too much code, we can factor
shared mechanics into a built-in human-interface module. That should be a
refactor after the adapter boundaries are clear, not a design requirement now.

## No Silent Drops

Every Telegram reply must produce a human-visible confirmation.

There are two levels:

1. **Delivery confirmation**: sent immediately after the router accepts the
   reply.
2. **Result confirmation**: sent when May finishes handling the reply or records
   a closure/update event.

Examples:

```text
Received. I attached the reply context and May is handling it.
```

```text
Received. I found the original issue and May is checking it now.
```

```text
Received. The previous worker session is gone, so May is handling it in the
human-chat session with the original issue attached.
```

```text
Done. May classified the blocker as stale and updated the project status.
```

If routing fails, Telegram must say so:

```text
I could not resume the previous worker session. I sent the reply to May with
the original issue attached.
```

Current implementation gap: `telegram.ts` sends delivery acknowledgements when
it accepts a reply, but final result confirmation still depends on May sending a
follow-up. The human-chat design requires that closure to be explicit.

## Noise Control

Telegram should be attention-first, not event-log-first.

Recommended policy:

- `P0`: immediate, always send.
- `P1`: immediate, dedupe by `dedupKey` with cooldown.
- `P2`: batch into a digest unless it asks for human input.
- `P3`: do not push by default; visible in web/console.

Repeated notifications with the same `dedupKey` should update or collapse:

```text
AKS RP E2E still blocked

Same blocker repeated 5 times in 42m.
Latest: task not found: network-acns-cilium-network-policy...

Reply: investigate / mute 2h / show details
```

Telegram supports editing messages. When practical, store the message ID and
edit the existing notification instead of sending a new one for the same
dedupKey. If editing is unavailable or fails, send a collapsed follow-up.

## Status And Control Commands

Natural language should remain primary. Slash commands are for fast mobile
read-models and safety controls:

- `/status` - compact system/project status, no LLM session required.
- `/projects` - list project health: active, blocked, backlog, last progress.
- `/project <id>` - focused project status and useful links.
- `/tasks <id>` - project task summary / current active leaves.
- `/sessions` - active sessions and what they are doing.
- `/quiet <duration>` - mute P2/P3 notifications.
- `/watch <project>` - raise attention level for one project.
- `/cancel <session>` and `/cancel all` - explicit cancellation.
- `/help` - show the above plus examples.

These commands should query read models directly where possible. They should not
spawn a general chat session unless the command asks for analysis.

## Convenience Features

High-value refinements:

- **Reply examples**: every actionable notification includes the exact replies
  it understands.
- **Human acknowledgements**: confirmations describe the outcome, not internal
  event names.
- **Project links**: include web links for kanban, task, event trace, or feature
  page when relevant.
- **Digest mode**: grouped summary for repeated low-priority events.
- **Stale reply detection**: avoid applying old approvals or steering to
  terminal work.
- **Context health metric**: track percentage of Telegram notifications with
  `conversationId` and useful `originalIssue`.
- **Reply-actionable metric**: track replies that reach May with conversation
  context and produce a delivery/result confirmation without needing a
  clarification turn.

## Implementation Plan

1. Tighten notification formatting.
   - Add a small formatter for `message.created` to human.
   - Preserve `subject`, `kind`, `severity`, `conversationId`,
     `conversation.originalIssue`, and `actionHints` in
     `notification_messages.data`.

2. Improve reply acknowledgement.
   - Confirm delivery to May immediately.
   - Confirm final result or closure when May finishes handling the reply.
   - Keep internal event names in logs, not the chat message.

3. Add direct read-model commands.
   - Implement `/status`, `/projects`, `/project`, `/tasks`, `/sessions`.
   - Keep them fast and deterministic.

4. Add notification lifecycle controls.
   - Dedupe by `dedupKey`.
   - Support quiet mode.
   - Detect stale replies using `staleAfterMs`.

5. Add metrics.
   - `telegram.notification-context-rate`
   - `telegram.reply-actionable-rate`
   - `telegram.notification-dedupe-suppressed`

## Non-Goals

- Telegram should not become the full web UI.
- The channel should not require buttons or custom clients to be useful.
- The router should not hide state changes in free-form chat when a typed event
  exists.
