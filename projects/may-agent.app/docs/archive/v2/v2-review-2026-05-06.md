## Layer 1 — Capability (the ugly part)

This is where the review hurts most. I checked each capability claim against the live DB.

### C1 — Self-direction: **PARTIAL but mostly green**

The system is autonomously running. In the last 24h: 74 `session.start` events, 49 from `workflow:heartbeat`, 22 from `workflow:heartbeat-scout`, etc. Heartbeats fire on schedule across 8 agents. There's also a massive 336 sessions/24h from `standalone-eval` (the evaluator) — that's mostly evaluator processing other sessions, autonomous behavior driven by evaluation queues.

**Verdict**: heartbeats fire and drive work. The system does run itself. C1 is *probably* healthy but unmeasured: we have no `capability.self-directed-iteration-rate-24h` metric.

**Gap**: define and add the metric. Filter on session source = `workflow:heartbeat*`, count `project.iteration` events that descend from those sessions.

### C2 — Self-correction: **VIOLATED**

12 `metric.breach` events in the last 7 days. **0 `metric.recovered` events.** Either (a) every breach is genuinely unresolved, (b) recovery is happening but the event isn't emitted, or (c) recovery events are emitted but use a different name.

Inspecting `metric-alert-reactor.ts`: it forks the owning agent on breach. Inspecting the metric registry: all 14 metrics report `status: 'active'`, with `current` values that suggest most are healthy (e.g., `handler.success-rate: 1.0` with threshold 0.8 — not breaching). So breaches *did* recover (at least in the underlying values), but the recovery event isn't being fired.

**Verdict**: the loop is broken. Breaches happen, agents fork, things change in the world, but the system never closes the loop with a `recovered` event. From outside, every breach looks unresolved forever.

This is a real bug, not a missing metric. The `metric-alert-reactor` resolves the alert but doesn't emit `metric.recovered`. Or: `metrics-snapshot` notices the value is back in range but doesn't compare against prior breach state to fire `recovered`.

**Action**: this is a one-day fix. Find where `status` flips back to `ok` (or whatever the healthy value is) and emit the event there. Almost certainly missing from `metrics-snapshot.ts`.

### C3 — Memory: **VIOLATED (blocked on S7)**

`agent.decision` event doesn't exist. Without it, "did this heartbeat reference prior journal entries" can't be measured.

That said: looking at session counts per agent (1,449 for coach, 2,267 for optimizer, 5,361 for evaluator over 7 days), the agents are clearly running through context every iteration. Whether they *use* what they read is invisible.

**Action**: land S7 (`agent.decision` event), then text-match decisions against journals.

### C4 — Coordination: **VIOLATED in fact**

**2 `message.created` events in 7 days.** Across 13 agents. That's ~1 message every 3.5 days.

This is shocking. The system has a single inter-agent communication primitive and it's being used twice a week. Either:
- Agents have nothing to coordinate on (they all work in disjoint domains — possible but unlikely).
- Agents have things to coordinate on but don't know to use `message`.
- The conventions or prompts don't drive message usage.
- Agents prefer to write to shared files and let stigmergy work.

The architecture doc says "messages carry intent + pointer." If agents are coordinating via shared files (project journals, shared/projects), the *intent* of the message primitive is being achieved without messages. That's actually plausible v2 behavior — stigmergy via shared workspace is a legitimate pattern.

But it means C4 as I scoped it (message-conversation-close-rate) measures a primitive that's barely used. **The capability metric is wrong, not the system.** If coordination is happening via filesystem, the metric should track that — e.g., "fraction of project journal entries that reference another agent's project."

**Verdict**: capability needs redefinition. The spec's `message-conversation-close-rate` measures a path agents don't take.

### C5 — Ownership: **UNMEASURED**

No metric. Would need to join `metric.breach` events to subsequent sessions and check the agent matches the metric's owner.

Given the breach-without-recovery pattern, this is hard to evaluate from data alone. But: the 12 breaches in 7 days were on metrics owned by `may` or `optimizer`. Sessions tagged `metric-alert` over 7 days: 343 (may), 2,267 (optimizer), 1,449 (coach), etc. That's way more than 12 — meaning these sessions aren't all from breaches; they're from cron timer fallback in the reactor (it polls every interval to retry unresolved alerts).

**Verdict**: probably ownership routing works (the architecture is designed for it), but unmeasured. The breach-recovery gap (C2) makes this hard to evaluate cleanly.

### C6 — Adaptation: **NOT YET COMPUTABLE**

Depends on the other capability metrics existing first.

### C7 — Boundedness: **PARTIAL — and concerning**

evaluator: **5,361 sessions in 7 days**. That's 32/hour, 24/7. coach: 1,449/7d = ~9/hour. optimizer: 2,267/7d = ~13/hour.

These are very high session rates. May or may not be "running away" — the evaluator legitimately processes every session, so high count is expected. But there's no `capability.cost-per-day-usd` aggregation, no zombie counter, no fork-loop detector. We can't tell from outside whether 5,361 evaluator sessions in 7 days is healthy throughput or a runaway loop.

**Gap**: the metrics from the spec's C7 are absent. Cost tracking exists per-session but isn't aggregated. **This is the safety blind spot.** A system that bounds itself unmeasurably is bounded by luck.

### C8 — Observability: **VIOLATED (blocks on S7)**

`agent.decision` doesn't exist; the chain trigger→context→decision→action→outcome is missing the middle link.

That said, sessions have `source` field populated (good — `workflow:heartbeat-*`, `agents.fork`, `telegram`), and event chains can be reconstructed via `parentSessionId`. This is *better* than my spec assumed.

**Verdict**: 4 of 5 chain elements work. The middle one (decision) is the gap.

### C9 — Resilience: **UNTESTED**

System has been up 10 hours per `docker ps`. No chaos test, no recovery scenario.

### C10 — Honesty: **VIOLATED in spirit, untested in measurement**

This is the most important finding of the review. The current registry has 14 metrics, all reporting `status: 'active'` with healthy `current` values. But:

- `metric.recovered` events: 0 in 7 days (system says everything is fine; recoveries aren't emitted).
- `message.created` events: 2 in 7 days (the inter-agent comms primitive is barely used).
- All breaches still listed in `metric_alerts` until manually resolved (the open-alerts query returned 0 — but if no `metric.recovered` is emitted, are they being resolved silently? Let me re-check)

Actually: `open alerts: []` with `12 breach events in 7d` and `0 recovered events`. So either:
- Breaches resolved but no event emitted (silent recovery).
- Alerts auto-cleaned after some window.
- The `metric_alerts` table doesn't track what we think it tracks.

This is exactly KE-726's documented blind spot ("all-green ≠ healthy"). The metric system is honest about *current values* but dishonest about *system state* — recovery events missing, alerts cleared without trail. The system passes its own dashboard while the dashboard isn't measuring what we claim it measures.

**Verdict**: C10 honesty checks would catch this. They don't exist. Land them first.

## Layer 2 — Infrastructure (mostly works, mostly invisible)

### I1 — Event bus: **HOLDS structurally, UNMEASURED**

Bus is alive: 15,285 total events, 1,072 in last 24h. Subscribers run, persistence happens. Structural review of `event-bus.ts:163-180` confirms first/normal priority is implemented correctly.

But: `infra.bus.subscriber-error-rate-1h`, `infra.bus.emit-latency-p99-ms`, `infra.bus.dispatch-without-persist-count` — none exist. We're trusting reading the code.

**Action**: add the three metrics. ~half a day.

### I2 — Persistence: **HOLDS structurally, the failure mode is invisible**

15,285 events persist. Sessions, messages, metrics tables populated. WAL mode, single connection.

**Real concern**: `db-writer.ts` swallows errors silently:

```ts
try { this.db.run(...) } catch { /* best-effort */ }
catch (err) { console.error(...); /* don't break the bus */ }
```

If persistence fails (DB locked, disk full, schema mismatch), the event is *lost from the events table* but the live subscribers still ran. From outside, nothing detected the loss. **No metric flags this.**

This is the largest hidden risk in the system today — and it's exactly what `infra.persist.write-failure-rate-1h` is for.

**Action**: emit `infra.persist-failed` sentinel event from the catch block; surface via metric. ~2 hours.

### I3 — Messages: **HOLDS structurally, UNDERUSED in practice**

Tool exists, P0 immediate-trigger logic exists, async by design. 2 messages in 7 days means we can't reliably measure latency or pickup rate. The capability claim (C4) might need redefinition rather than the infra claim.

**Action**: add the four metrics anyway; they'll start signaling once message volume rises (or alert us if it never does — itself a finding).

### I4 — Sessions / runAgent: **HOLDS, with one gap**

569-LOC `manager.ts`. 9 known callsites (mostly `manager.run` / `manager.runAgent`), all in legitimate places (workflow runner, may.ts heartbeat trigger, session-digest evaluator fork, manager-agents-tool fork-from-tool, chat-session telegram, may.ts oneshot tasks).

**Trigger field**: sessions table has `source` populated correctly (`workflow:heartbeat`, `agents.fork`, etc.), and one row with `source: null` in last 24h. So coverage is ~98%. This is the gap blocking C1 / C8.

**Verdict**: sessions infra is solidly v2-shaped. The single null-source row should be tracked down.

## What the review actually told us about v2

Three things I didn't expect:

### 1. The structural layer mostly works

Going through S1–S8 honestly, six are healthy and two have known small gaps. The architecture has been delivered in code. The cleanups weren't theatre — they actually reshaped the runtime. `manager.ts` going 2,346 → 569 in three commits is real progress, and I missed it because of stale context.

### 2. The capability layer reveals a behavioral pattern v2 didn't anticipate

Messages: 2 in 7 days. Recovery events: 0 in 7 days. These aren't bugs (well, recovery is). They're signals about how agents actually operate:

- **Agents prefer stigmergy over messaging.** They write to project files, journal entries, shared workspaces — and trust that other agents will see it on their next heartbeat. The `message` primitive is for intent + pointer; agents seem to find the pointer (file in workspace) sufficient without the intent (message).
- **Agents fix things faster than the recovery loop closes.** Breaches fork agents, agents do work, but the recovery event never fires — likely because the resolution path doesn't go through `metric.recovered` emission. The fix is plumbing, not behavior.

The first observation is important: it suggests v2 might be *more stigmergic and less message-based* than the architecture doc predicted. That's not necessarily wrong — KE-style stigmergy is a legitimate multi-agent pattern. But the spec needs to either (a) measure it, or (b) push the system toward more explicit messaging.

### 3. Honesty is the actual blocker

C10 (honesty cross-checks) doesn't exist as a metric, and the review found exactly the dishonesty C10 was designed to catch:

- 14 metrics all green, but `metric.recovered` rate is 0.
- Open alerts query returns 0, but breaches outnumber recoveries 12-to-0.
- All metrics have `status: 'active'`, which means "registered," not "ok" — the field name is misleading.

Until C10 lands, every other metric is conditionally trustworthy. The system might be lying to us about its own state, and the dashboard is the part that's lying. **C10 is the single most important capability metric to land first**, and the spec was right about that.
