# Evidence-to-improvement pilot

The pilot is a composition of small ordinary Task stages, not one improvement
controller. Evaluation findings and observed execution failures share owner
judgment and the later improvement stages; they keep different evidence readers.
Normal execution recovery remains in the original work.

1. **Source evidence:** Evaluation's immutable `evaluation.task_report_published` names subject App/Task, evidence hash, execution, report/facts paths and both content hashes. Publication can race its durable marker; May retries the same ordinary work and never trusts staged bytes. A supported execution failure instead returns through its exact caller relationship and is read from the accepted Task result plus its Task/attempt/operation identity and retained receipts. It is not converted into a synthetic Evaluation publication.
2. **Disposition (owner/May):** May uses Evaluation's published reader for Evaluation evidence and current Task/execution evidence for execution failures. Model identity does not change this intake boundary. Routine DeepSeek screening reports are leads: May rereads current outcomes, recovery and exact linked corrections, classifies material claims as confirmed, rejected, or uncertain, and never treats no-finding as certified health. She records impact, accountable owner, disposition, action or genuine wait, next step and evidence/repair links in the accepted Task result. During a bounded screening rollout she also records useful impact and total verification cost/latency, so attempt allowance is not mislabeled as effective capacity. Expected failures and ordinary recovery create no repair. Duplicate transport reuses accepted work; semantic repair reuse remains owner judgment, and changed evidence is reconsidered without inheriting stale approval. A separate repair Task exists only for an independent outcome or lifetime.
3. **Candidate (responsible App):** existing isolated development prepares and commits one candidate with diff and verification receipts. Evaluation does not own this decision; Gym does not build it. A new error never selects a workflow automatically.
4. **Comparison (when useful):** an ordinary Gym goal carries a bounded `context.comparison`; Gym freezes exact baseline/candidate/benchmark/scorer/model/scenario/trial scope and returns a content-addressed receipt. Mechanical Host failures remain Host tests, not model training data. If Gym adds no value, retain a truthful comparison-decision artifact that says why it was not used, names the deterministic and local-agent evidence used instead, and states the limits. The approval packet hashes this artifact; it is not a fabricated Gym success receipt.
5. **Approval (human):** a packet binds baseline and candidate commits/tree, complete diff, verification and comparison hashes, activation scope and rollback. `prepare-improvement-approval` rereads the clean target and pinned evidence, applies May's necessity and candidate-value judgments, and returns an ordinary human-owned Condition containing the full readable proposal. An authenticated literal Telegram reply to that exact card is the primary decision path; it is bound to the provider message, Task generation, Condition and displayed bytes.
6. **Source application (May/operator fallback):** `scripts/apply-improvement.ts` rereads the trusted journal event, current owner Task/Condition, actual Git and evidence identities before fast-forwarding the exact source candidate. The retained receipt includes the authorizing event/proposal/Task and all input references. Missing, rejected, stale, superseded or mismatched approval makes zero mutation. The packet-hash operator route remains a fallback.
7. **Activation and outcome follow-up:** source approval is source-only unless the displayed packet separately includes the exact activation. For App-definition activation, `improvement-activation-follow-up` rereads the trusted journal decision, current owner Task/Condition and source receipt, then emits the existing `runtime.reload.requested` operation with the approved source commit pinned. The correlated result records the actual loaded source commit; drift, failure or an inconclusive identity remains open. Only after verified adoption and readable post-activation execution does the same owner request ordinary Evaluation of a concrete new subject Task. The Evaluation dependency is pinned to that generation/evidence; its result wakes the owner, which records the independent disposition without turning it into an automatic value claim. Reviewing the activation Task itself does not show that the intended improvement helped. Host-binary deployment and any scope not shown in the proposal remain separate explicit operator work.

Each stage has an explicit input/output and retained evidence naming its failure stage. Candidate readiness is not integration, approval, activation, or deployment. The accountable owner performs one reconciliation from current Task detail at each return: it reuses the retained selected subject and admitted `appdep_…` request rather than resampling or assuming the workflow-local dependency label is the public result identity. Outstanding activation, post-adoption subject selection, and Evaluation return remain visible through the same Task's Conditions and accepted result until the exact next fact arrives. Present that state using the common [current-first Task guidance](../../may-agent.app/docs/2a-design/human-control-surfaces.md#shared-resource-interface); the same document defines generic trusted-ingress, Condition, and operation-identity boundaries.
