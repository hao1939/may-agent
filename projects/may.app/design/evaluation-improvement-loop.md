# Evaluation-to-improvement pilot

The pilot is a composition of small ordinary Task stages, not one improvement controller.

1. **Publication (Evaluation):** immutable `evaluation.task_report_published` names subject App/Task, evidence hash, execution, report/facts paths and both content hashes. Publication can race its durable marker; May retries the same ordinary work and never trusts staged bytes.
2. **Disposition (May):** the explicit cross-target subscription normalizes the fact into a `message`. May uses Evaluation's published reader, rereads current subject outcomes/recovery/linked corrections, and records `invalid`, `retry-publication`, `recovered`, `no-op`, `reuse-linked-work`, or `candidate-needed` in the accepted Task result. Duplicate transport and unchanged semantic findings reuse accepted work.
3. **Candidate (responsible App):** existing isolated development prepares and commits one candidate with diff and verification receipts. Evaluation does not own this decision; Gym does not build it.
4. **Comparison (Gym):** an ordinary Gym goal carries a bounded `context.comparison`; Gym freezes exact baseline/candidate/benchmark/scorer/model/scenario/trial scope and returns a content-addressed receipt. Mechanical Host failures remain Host tests, not model training data.
5. **Approval (human):** a packet binds baseline and candidate commits/tree, complete diff, verification and comparison hashes, activation scope and rollback. `prepare-improvement-approval` rereads the clean target and pinned evidence, applies May's necessity and candidate-value judgments, and returns an ordinary human-owned Condition containing the full readable proposal. An authenticated literal Telegram reply to that exact card is the primary decision path; it is bound to the provider message, Task generation, Condition and displayed bytes.
6. **Source application (May/operator fallback):** `scripts/apply-improvement.ts` rereads the trusted journal event, current owner Task/Condition, actual Git and evidence identities before fast-forwarding the exact source candidate. The retained receipt includes the authorizing event/proposal/Task and all input references. Missing, rejected, stale, superseded or mismatched approval makes zero mutation. The packet-hash operator route remains a fallback.
7. **Activation and outcome follow-up:** source approval is source-only unless the displayed packet separately includes the exact activation. For App-definition activation, `improvement-activation-follow-up` rereads the trusted journal decision, current owner Task/Condition and source receipt, then emits the existing `runtime.reload.requested` operation with the approved source commit pinned. The correlated result records the actual loaded source commit; drift, failure or an inconclusive identity remains open. Only after verified adoption and readable post-activation execution does the same owner request ordinary Evaluation of a concrete new subject Task. The Evaluation dependency is pinned to that generation/evidence; its result wakes the owner, which records the independent disposition without turning it into an automatic value claim. Reviewing the activation Task itself does not show that the intended improvement helped. Host-binary deployment and any scope not shown in the proposal remain separate explicit operator work.

Each stage has an explicit input/output and retained evidence naming its failure stage. Candidate readiness is not integration, approval, activation, or deployment. The accountable owner performs one reconciliation from current Task detail at each return: it reuses the retained selected subject and admitted `appdep_…` request rather than resampling or assuming the workflow-local dependency label is the public result identity. Outstanding activation, post-adoption subject selection, and Evaluation return remain visible through the same Task's Conditions and accepted result until the exact next fact arrives. See the common [human control surfaces](../../may-agent.app/docs/2a-design/human-control-surfaces.md) for generic trusted-ingress, Task, Condition, and operation-identity boundaries.
