## Pushback / Calibration recommendations

### 1) Add alert dedupe/cooldown for rapidly repeating threshold alerts
Metrics like `project.invalid-format-count` firing every few minutes create paging fatigue.

Recommendation:
- implement dedupe: don’t create a new alert if the most recent alert for the same `(metric_id, alert_type)` is still unresolved, or was created < X minutes ago with the same message.

### 2) Revisit rate-alert semantics for monotonic counters
`handler.completed-count` and `system.real-output-24h` show negative rates (e.g., `rate=-71650.71/hour`). A rate alert should either:
- explicitly handle counter resets (treat reset as “unknown rate” rather than negative), or
- use a gauge rather than a counter.

Recommendation:
- if this is a monotonic counter, detect resets and ignore that interval for rate-based alerting.

## Non-obvious issue: timestamp units mismatch (ms vs s)

Evidence:
- `strftime('%s','now')` returns seconds (`1778284299`).
- `metric_alerts.created_at` values are ~`1778282693059` (13 digits), i.e. **milliseconds**.
- Formatting via `datetime(created_at,'unixepoch')` yields `NULL` because SQLite expects seconds.

Consequences:
- “last 24h” filtering using `created_at >= now-86400` will behave incorrectly.
  - Specifically, since `created_at` is much larger than seconds, it will **always** satisfy the threshold, making the “last 24h” query effectively “all time”.
- Any reporting that relies on `created_at`/`resolved_at` being seconds will be wrong.
- Downstream patterns (e.g., “repeats frequently”, “unresolved alerts”) become hard to interpret.

Recommended fix direction (for owner):
- Standardize timestamp storage units across tables. If `metric_alerts` is intended to store ms, then:
  - convert in queries/reports: `datetime(created_at/1000,'unixepoch')`.
  - adjust window predicates: `created_at >= (strftime('%s','now')-86400)*1000`.
- Add a migration or defensive view/helper for consistent time arithmetic.
