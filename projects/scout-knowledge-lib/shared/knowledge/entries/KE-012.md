# KE-012: Amdahl's Law for Agents — The Overhead Equation

**Discovered:** 2026-06-18 | **Status:** Active — measured from 14 days of production data

---

## The Discovery

Every prior KE entry (001–011) describes a specific system pathology. This entry identifies the **general law** that contains all of them.

The system's total compute follows a simple equation:

```
T = F + (1 + k) × W
```

Where:
- **T** = total ops per day
- **F** = fixed overhead (heartbeats + discovery; independent of work volume)
- **k** = overhead multiplier (overhead ops generated per work op)
- **W** = actual domain work ops

This is **Amdahl's Law applied to multi-agent coordination**. Just as Amdahl's Law imposes a ceiling on parallel speedup from the serial fraction, the overhead multiplier k imposes a ceiling on productive work fraction:

```
Work fraction = W / T = 1 / (F/W + 1 + k)
```

At high work volume (F/W → 0), the ceiling is **1/(1+k)**.

**k has been declining**: from ~2.3 in mid-June to ~1.3 in recent days. The system IS getting more efficient organically — the planner exits faster on familiar patterns, more evaluations are skipped. But k has a structural floor.

### The Structural Floor on k

Each task-worker session (avg 39 ops) generates, at minimum:
- ~2 aftermath sessions × 19 ops = **38 ops** (k_eval ≈ 1.0)
- ~2 planner sessions × 12.7 ops = **25 ops** (k_plan ≈ 0.6)
- ~0.2 monitoring sessions × 34 ops = **7 ops** (k_mon ≈ 0.2)

**k_floor = (38 + 25 + 7) / 39 ≈ 1.8**

The recent measured k of 1.25–1.44 is already *below* this structural estimate, which means some efficiency gains are happening (planner tiny-exits, evaluation skips). But it cannot sustainably go below ~0.8 without changing ratios.

## The Priority Stack (Quantified)

### Intervention 1: Reduce k_eval (highest leverage)

**Current:** Every work session generates ~1 aftermath evaluation. k_eval ≈ 1.0.  
**Change:** Evaluate 20% random sample. k_eval drops to ~0.2.  
**Impact:** k drops from 1.3 to ~0.5. Ceiling rises from 43% to 67%.  
**Savings:** ~24,000 ops/day (at current volumes).

### Intervention 2: Reduce k_plan

**Current:** 46.6% of planner sessions are tiny exits (≤5 ops). k_plan ≈ 0.6.  
**Change:** Pre-dispatch DB check (is there runnable work?). Skip ~47% of planners.  
**Impact:** k drops by ~0.3. Combined with #1: ceiling rises to ~77%.  
**Savings:** ~8,000 ops/day.

### Intervention 3: Reduce F

**Current:** F ≈ 9,000 ops/day. Stable regardless of work volume.  
**Change:** Suppress stale heartbeats, lengthen intervals when healthy.  
**Impact:** Minimal ceiling change (F/W → 0 at scale). Matters only on quiet days.  
**Savings:** ~2,000 ops/day.

**Priority order is clear**: k_eval > k_plan > F. This is because k multiplies W while F is constant. At scale, k dominates.

## Amdahl's Law Connection (not just metaphor)

Amdahl's Law: `Speedup(n) = 1 / (s + (1-s)/n)` where s = serial fraction, n = processors.  
As n → ∞, speedup → 1/s. The serial fraction sets an absolute ceiling.

Our law: `WorkFraction(W) = W / (F + (1+k)W)` where F = fixed cost, k = per-work overhead.  
As W → ∞, WorkFraction → 1/(1+k). The overhead multiplier sets an absolute ceiling.

The parallel is structural:
- Amdahl: adding more parallelism (processors) can't help past the serial bottleneck
- Overhead Equation: adding more work volume can't help past the overhead multiplier

Both have the same solution path: **reduce the limiting parameter** (serial fraction / overhead multiplier), don't add more of the unlimited resource (processors / work volume).

The semiconductor industry spent 40 years optimizing serial code fractions. Agent systems will spend the next period optimizing overhead multipliers.

## The Deepest Insight: Why KE-007 (Cassandra) Is Inevitable

KE-007 observed that knowledge entries don't change code. The Overhead Equation explains *why* this is structurally inevitable, not just culturally contingent:

Knowledge entries are produced by **scout** and **arc** — agents whose ops are part of F (fixed overhead). They run on heartbeat schedules, independent of work volume. The work they produce (insights, KE entries) has zero coupling to the dispatch mechanisms that determine k.

**F and k live in different code paths.** F-producers (heartbeat agents) write to `shared/knowledge/entries/`. k-determiners (workflow dispatchers, evaluation logic, planner triggers) read from `projects/may-agent.app/src/`. There is no mechanism — not even a theoretical one — for a file in `shared/knowledge/entries/` to modify the value of k.

The Cassandra Architecture isn't a bug or a cultural failure. It's a **topological separation**: the insight-producing path and the overhead-determining path share no edges in the system's dependency graph.

The fix isn't "make agents read KE entries" — it's to create a path from insight → code change, which is exactly what the work-queue + human-approval mechanism is designed to do. The bottleneck is approval throughput, not insight production.
