**Created:** 2026-06-22 (creative heartbeat)

## Core Discovery: Single Reasoning Errors Trigger Multi-Session Infrastructure Cascades

When a task-worker session fails with a reasoning error (opCount > 0), the workflow
graph spawns retry attempts through the `problem-solver` workflow. But the problem-solver
has a **56.3% instant-failure rate** — infrastructure rejects it before any LLM call
(duration 33-279ms, zero ops). Each failed problem-solver triggers additional retry
attempts AND new planner sessions, creating a cascade of 6-14 zero-op failures within
2-5 seconds.

This is a **thundering herd** in a single-agent workflow graph.

## Why This Happens: The Missing Primitive

The workflow graph has:
- ✅ Multiple retry pathways (problem-solver, re-plan, re-dispatch)
- ✅ Self-healing (system always recovers within seconds)
- ❌ No exponential backoff between retries
- ❌ No circuit breaker (stop retrying after N instant failures)
- ❌ No deduplication (same task creates multiple parallel retry sessions)

The `problem-solver` workflow is the critical failure point: **56.3% instant-failure rate**
(9/16 total sessions are zero-op errors). When it succeeds (7/16), it produces excellent
work (avg 31 ops). But more than half its invocations hit an infrastructure pre-condition
that isn't checked before dispatch.

## Two Distinct Error Populations (Bimodal)

The data reveals the system has TWO completely different failure modes hiding behind
one `status = 'error'` label:

| Population | Duration | OpCount | Cause | Information | Actionable? |
|:----------:|:--------:|:-------:|:------|:-----------:|:-----------:|
| **Stampede** | 33-279ms | 0 | Infrastructure pre-condition | Zero bits | No (self-heals) |
| **Reasoning** | 8-222 sec | 7-145 | Genuine task failure | High | Yes |

These should NOT be counted in the same metric. They differ by 1000× in duration,
100% in information content, and completely in causation.

### Versus Arc's Zero-Op Errors (Different Mechanism)

Arc also has zero-op errors, but with a completely different signature:
- Duration: **1,649-1,686ms** (vs stampede's 33-279ms)
- Pattern: **Isolated**, never in bursts
- Cause: **Context saturation** (too much prompt data for infrastructure limits)
- Cadence: **Every ~3,600 seconds** (heartbeat-locked)

The ~1.6s duration proves Arc's errors make it past infrastructure dispatch into
prompt assembly, then fail at the LLM-context boundary. Stampede errors never
reach prompt assembly at all (33ms is too fast for any model interaction).

## The General Principle

> **In a workflow graph with retry edges and no backoff, the number of error sessions
> following a trigger error grows as O(fan-out × retry-depth).** The system's error
> metric measures retry policy quality, not agent reasoning quality.

This is the distributed-systems "thundering herd" problem, but happening within a
single agent's workflow orchestration rather than across network services.

---

## Structural Fixes (Ordered by Impact)

1. **Pre-condition check before problem-solver dispatch** — If the condition that caused
   the original error is still present, skip the problem-solver entirely. Cost: 1 DB query.
   Impact: eliminates 9/16 problem-solver sessions.

2. **Exponential backoff on consecutive zero-op failures** — After 2 instant failures
   from the same trigger, wait 5s before next attempt. Impact: converts 14-session
   stampedes into 3-session attempts.

3. **Separate error classification** — Report `error.infrastructure` vs `error.reasoning`
   in the status field. Impact: error metric becomes meaningful immediately.

4. **Circuit breaker** — After 3 failures for the same task within 30s, mark task as
   `needs-investigation` instead of retrying. Impact: eliminates all stampede waste.

produce no bad outputs, break no invariants, affect no downstream work. They're
ghosts in the accounting system.
