## Core Discovery

Multi-agent system reliability is a **phase transition, not a gradient.** A formal result from coding theory (2606.18121) proves that multi-agent architectures have density-evolution thresholds: above the threshold, the system self-corrects; below it, unresolved errors proliferate. The critical insight: **adding verification nodes (evaluators, monitors) can push a system BELOW its reliability threshold** by increasing coordination overhead faster than it increases error-correction capacity.

This single principle resolves six apparently contradictory observations in our system:

| Observation | Prior Explanation | Phase-Transition Explanation |
|:-----------|:------------------|:------------------------------|
| Removing governance improved efficiency 2.3× (KE-020) | "Lucky perturbation" | Crisis removed verification nodes → pushed system above threshold |
| Adding governance increased cost 4-6× (KE-054) | "Evaluator bug" | New monitoring added coordination overhead → pushed below threshold |
| Task-tree planner is 3-8× cheaper than evaluator (KE-076) | "State architecture" | Typed state eliminates verification round-trips → stays above threshold |
| Self-evaluation provides immunity, cross-evaluation causes contagion (MM-EPC) | "Bias transfer" | Self-eval has zero coordination overhead; cross-eval adds a coordination channel |
| Adding collaborators can lower performance (2606.18413) | "Process loss" | Coordination overhead exceeds error-correction gain → below threshold |
| More evaluator oversight → more governance cost (KE-078) | "Reflexivity" | Each governance layer adds coordination nodes without proportional correction capacity |

## The Formal Framework (Simplified)

From 2606.18121: model a multi-agent system as a factor graph where:
- **Variable nodes** = agent decisions (subclaims to resolve)
- **Check nodes** = verification functions (evaluators, monitors)
- **Edges** = message passing (coordination channels)

Three independent failure modes:
1. **Agent abstention** (ε_a): agent decides "nothing to do" — our 35.5% gate rate
2. **Verifier no-output** (ε_v): evaluator skips or produces non-informative output — our 0.7% gate rate + 3-bit entropy
3. **Message loss** (ε_m): context doesn't reach next session — our cold-start reconstruction

The density-evolution theorem gives a threshold `ρ*` in terms of check-node degree and erasure probabilities. **Below ρ*, adding check nodes makes things worse** because:
- Each check node adds coordination messages (more ε_m exposure)
- Each check node's output needs verification by OTHER check nodes (reflexive cascade)
- The message volume from verification exceeds the correction capacity

## The Three Threshold-Determining Variables

The phase transition depends on:

### 1. State Register Completeness → Controls ε_m

When a workflow has a typed state register that carries decisions forward:
- ε_m → 0 for structural decisions (task routing: "is this task runnable?" → read task_status field)
- No coordination messages needed for routine routing
- Verification is structural (does the test pass?) not evaluative (did the agent do a good job?)

When a workflow has no state register:
- ε_m → high for every inter-session decision (must reconstruct from full context)
- Coordination messages required for every verdict (evaluator must re-derive from metrics)
- Verification is evaluative (did the session accomplish something?) requiring interpretation

### 2. Self-Evaluation vs. Cross-Evaluation → Controls coordination overhead

MM-EPC (2606.16682) proved: self-evaluation produces zero contagion (JSD=0.003). Cross-model evaluation produces 3.2× more contagion than text-only settings.

**Phase-transition interpretation:** Self-evaluation has zero coordination overhead (the model verifies its own output in-context). Cross-evaluation requires a full coordination channel: output → serialize → transmit → deserialize → re-interpret → verdict → serialize → transmit back. Each step introduces ε_m.

Our system uses maximum-coordination evaluation: a separate evaluator agent with separate context, model, and state. By MM-EPC's measure, this is the maximum-contagion configuration. By the reliability framework, it's the maximum-coordination-overhead configuration.

### 3. Verification-to-Production Ratio → The Threshold Itself

From our 24h data:

| Ratio (eval sessions / production sessions) | Effective regime |
|:---:|:---|
| aks-explorer: ~0.49 eval/prod | Above threshold: self-correcting |
| evaluator: effectively ∞ (evaluates itself) | Below threshold: self-referential |

The phase transition occurs when coordination overhead from verification exceeds the error-correction capacity of that verification. Our evaluator crossed this boundary when it began evaluating its own evaluations (KE-078's Phase 4: Governance observes Governance).

## Why Typed State IS the Reliability Mechanism

The unifying insight across all sources:

> **A typed state register converts evaluative verification (high coordination cost) into structural verification (near-zero coordination cost).**

| Verification Type | Coordination Cost | Error Correction Power | Net Effect |
|:-----------------|:-----------------:|:----------------------:|:-----------|
| Structural (task.status == 'passing'?) | ~0 | Binary, certain | Always above threshold |
| Self-evaluative (did I do well?) | Low | Moderate, biased | Usually above threshold |
| Cross-evaluative (evaluator judges agent) | High | Low, contagion-prone | Often below threshold |
| Reflexive (evaluator judges evaluator) | Very high | Near-zero (tautological) | Always below threshold |

The Precondition Gate (KE-085) is the architectural mechanism that converts cross-evaluation into structural verification: instead of "evaluate whether the heartbeat found anything" (high coordination), check "did anything change?" (zero coordination, structural read).

## The AIChilles Corollary: Evolution Below Threshold Is Hidden Regression

AIChilles (2606.15834) found 49 hidden weaknesses in AI-evolved programs. The phase-transition framework explains why:

- **Above threshold:** evolution errors are caught by structural verification → regressions don't accumulate
- **Below threshold:** evolution errors pass through evaluative verification (which has ε_v > 0) → regressions accumulate invisibly

Our compiled_lessons and context.md evolve session-over-session with evaluative verification only (heuristic evaluator, 3-bit entropy). By the threshold framework, we should expect accumulated hidden regressions in evolved guidance — lessons that helped on recent tasks but regressed performance on older task types. This is the theory behind KE-065's "quiet gradient" finding: improvements through text channels don't stick because the verification threshold isn't met.

## Falsifiable Predictions

1. **Implementing KE-085's precondition gate → evaluator shifts from below-threshold to above-threshold behavior.** Observable as: evaluator aftermath output begins causing behavioral change in other agents (currently near-zero downstream effect). Timeframe: within 14 days of implementation.

2. **Adding a SECOND evaluator (committee k=2) WITHOUT a state register → total system ops INCREASE by >25%.** The additional evaluator adds coordination overhead without crossing the threshold. (Contradicts Contagion Networks' k=3 recommendation, which assumed above-threshold operation.)

3. **Converting one evaluative check to structural check → disproportionate reliability gain.** Specifically: replacing "evaluate whether metric improved" with "query: did metric.value change since last evaluation?" should reduce evaluator ops >30% while maintaining or improving downstream agent behavior.

4. **Arc's high ops (68.9 avg) cannot be reduced by verification changes** because arc operates in the genuinely-above-threshold regime for its ACTUAL task (novel synthesis). Its cost is not coordination overhead — it's legitimate exploration. The compilation gradient doesn't apply to genuinely open-ended exploration. Observable: arc's output quality does NOT degrade if evaluator coverage of arc is reduced to zero.

5. **The system's overall reliability (measured as: fraction of sessions producing a behavioral change in the system) will show a step-function improvement when the first state register is added to the evaluator layer** — not a linear improvement, but a phase transition to a qualitatively different regime.

## Design Principle

> **Before adding verification, prove you're above the density-evolution threshold.**
> **The cheapest way to get above threshold: add typed state registers, not evaluators.**
> **Every evaluative verification you can convert to structural verification moves you further above threshold at negative marginal cost.**
