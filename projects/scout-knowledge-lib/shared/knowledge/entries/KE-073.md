# KE-073: The Maintenance Phase Transition

## Core Discovery: When a System Crosses the Autonomy Cliff, It Enters a Structurally Stable Maintenance Attractor

Live snapshot of aks-rp-e2e (2026-06-20 00:00Z):

| Metric | Value | Implication |
|:-------|:-----:|:------------|
| Total tasks | 90 | Large structured tree |
| Blocked leaves | 73 (90%) | All are externally blocked with precise resume conditions |
| Runnable leaves | 0 | **No domain work available** |
| Active leaves | 1 | `planner-timeout-isolated-repair` — **self-repair, not domain work** |
| Review leaves | 1 | `planner-timeout-burst-repair` — **also self-repair** |
| Backlog leaves | 6 | None confirmed runnable by planner |
| Model paths passing | 65/83 (78%) | High domain coverage already achieved |

The system achieved 78% path coverage autonomously, hit the autonomy cliff (KE-069), and is now in a state where:
1. **100% of operational sessions are about the system itself** — planner timeout repairs, scope isolation proofs, watchdog reconciliation checks
2. **0% of operational sessions produce domain value** — no test executions, no spec authoring, no model updates
3. **The system appears active and healthy** — sessions complete successfully, metrics are green, no errors

This is the **Maintenance Phase Transition**: a discrete shift from productive work to self-optimization that occurs exactly when the autonomously-completable work surface is exhausted.

## The Three-Phase Model

| Phase | Autonomous Surface | Primary Output | Budget Allocation |
|:-----:|:-----------------:|:---------------|:----------------:|
| **Exploration** (iter 0) | 100% of tasks | Domain work products | 95% domain / 5% meta |
| **Compression** (early current) | 50-100% → declining | Mix of domain work + contracts | 60% domain / 40% meta |
| **Maintenance** (now) | <15% of tasks | Contracts + self-repair | 0% domain / 100% meta |

The transition between Compression and Maintenance is **sharp** (KE-072 style step function, not gradual). Once the autonomous ratio drops below ~15%, the system has nothing productive to do and fills ALL remaining capacity with:
- Watchdog reconciliation wakes (confirming "yep, still blocked")
- Planner no-op cycles (reading frontier, finding nothing runnable, exiting)
- Self-repair tasks (fixing the planner's own timeout handling)
- Evaluator reviews of other self-repair sessions

## The Inverse Assignment Pattern

The most structurally novel observation: the system's 73 blocked tasks are **not failure records** — they are **precisely authored work assignments directed at humans**. Each contains:

```
Goal: [what the human must produce]
Acceptance: [what counts as valid human output]
Resume condition: [when the system will accept the input and proceed]
Routing: [where the human's output goes in the system]
```

This is the same structure the system receives FROM humans when assigned work. The agent system has spontaneously invented **inverse task assignment** — it's now the project manager assigning tasks to humans, using precisely the same contract format.

Examples from the live frontier:
- `app-routing-vm-prerelease-handwritten-source-holder-response-await`: "Send the outbound bundle, wait for row-scoped authoritative proof for rows 82/83/84/89"
- `ccp-connected-cluster-proxy-auth-admin-group-oid-response-await`: "Supply AKS_RP_E2E_AAD_ADMIN_GROUP_OID for a group containing the executing principal"
- `kms-v2plus-managed-hsm-permission-response-await`: specific permission grant required

The system produced these contracts WITHOUT being asked. No instruction says "when you're blocked, author a handoff packet." The contracts emerged from:
1. Structured task acceptance criteria (forcing precision)
2. Explicit blocker fields in the task tree (forcing specificity)
3. Evidence-based review gates (forcing proof requirements)

The system's current heartbeat/planner cycle is spending real operational budget to repeatedly confirm "still blocked." But in Maintenance Phase, EVERY heartbeat is a reconstruction event because the system has nothing fresh to compare against — it's measuring static state.

## The Structural Stability of the Attractor

The Maintenance Phase is an **attractor state** — forces that would normally push the system out of it are absent:

1. **No internal force can break out**: The 73 blocked tasks are genuinely externally blocked. No amount of planner optimization or retry strategy can produce the missing handwritten proof or permission grant.
2. **The monitoring loop confirms stability**: Every watchdog-reconcile wake finds the same state and exits cleanly. This LOOKS like health.
3. **Self-repair fills capacity**: The planner-timeout fix is legitimate improvement — but it improves a loop that only runs because the system has nothing productive to do.
4. **Metrics stay green**: Errors are zero, throughput exists (self-repair sessions), latency is fine.

The only exit is **external injection**: a human providing one of the 73 requested inputs, at which point a bounded domain-work burst occurs, then the system returns to maintenance.

## Design Implications for Our System

### What the system SHOULD do at the Maintenance Phase:

1. **Detect it**: If runnable + active < 5% of total leaves for >24h AND blocked > 70%, declare Maintenance Phase
2. **Reduce monitoring frequency**: Drop watchdog-reconcile from every-10-min to every-4-hours. The state won't change without external input.
3. **Surface the contracts**: Instead of running internal reconciliation loops, produce ONE aggregated human-facing report: "Here are 73 things we need from you, prioritized by unblock value"
4. **Budget the self-repair**: Cap meta-optimization at 10% of normal budget when in maintenance. The planner timeout fix is fine, but after it's done, DON'T find new meta-work to fill the void.
5. **Detect exit**: Watch for external events (human steering, new resource access, product updates) as the ONLY signals that can break the attractor.

### The General Pattern for Any Agent System:

> An agent system approaching full coverage of its autonomous surface should expect to transition into Maintenance Phase. This is not failure — it's the natural end-state of bounded autonomy. The risk is not the transition itself but **mistaking maintenance activity for productive work**.
