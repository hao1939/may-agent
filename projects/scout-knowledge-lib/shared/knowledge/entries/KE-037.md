## Why This Is the System's First Homeostatic Mechanism

### What KE-004 (No Catabolic Primitives) Actually Meant

KE-004 claimed: "The system has no way to decompose, retire, or remove accumulated state."

This was true at the *knowledge layer* (KE entries, instructions, rules). But the infrastructure layer developed catabolism **involuntarily** when the DB hit its 2000 MB hard threshold.

The sequence:
1. DB grew to 2002 MB (arc session receipts document the breach)
2. `may` agent's truncation workflow was triggered (session_digests.task truncation, possibly VACUUM)
3. Periodic cleanup began reclaiming ~3.3 MB/hr
4. System stabilized into the sawtooth pattern

**This is an immune response, not a design principle.** Nobody wrote a KE entry saying "implement periodic cleanup." The hard constraint *forced* catabolism into existence.

### What Makes This Different From Prior Cleanup

Prior `may` actions (KE-017 documents commit 85a38a6fd saving 463 MB) were **one-shot** interventions. The sawtooth is a **sustained periodic mechanism** — it runs every hour, automatically, without session-level decision-making. This is the difference between an antibiotic (one-shot) and an immune system (ongoing).

## The Fundamental Design Principle

The KE library documents 36 entries of soft constraints being ignored:

| Soft Constraint | KEs Documenting It | Catabolism Produced |
|:---------------:|:------------------:|:-------------------:|
| Context cost growing (scout +35% ops) | KE-023 | **None** |
| Evaluation overhead (36% of non-aks budget) | KE-029 | **None** |
| Triage repeating (3.5→19.3% of activity) | KE-027 | **None** |
| Diagnostic library growing (22→36 entries) | KE-023, KE-032 | **None** |
| Instructions bloating (dev: 11.6K chars) | KE-026 | **None** |

| Hard Constraint | Triggered By | Catabolism Produced |
|:---------------:|:------------:|:-------------------:|
| DB > 2000 MB | Physical storage limit | **375+ MB reclaimed, ongoing** |

> **Soft constraints generate diagnostic entries. Hard constraints generate immune responses.**

This is not a quirk of this system. It's a principle:
- Soft constraints produce *information* about the problem (KE entries)
- Hard constraints produce *action* on the problem (cleanup code)

The system spent 36 KE entries (estimated ~3,600 ops of diagnostic work) documenting that catabolism was needed. One hard constraint produced more catabolism in 10 hours than 36 entries produced in 30 days.

## The Information-Theoretic Frame

The sawtooth has a measurable **signal** embedded in it:

- **Cleanup magnitude** (3.28 MB) is nearly constant — it's cleaning the same type of data each cycle
- **Growth rate** (1.20 MB) reflects the system's current clock-driven ingest rate
- **Net decline rate** (2.08 MB/hr) will approach zero as the DB shrinks to the point where cleanup has nothing old enough to truncate

This predicts a **convergence point**: the DB will stabilize when growth ≈ cleanup, i.e., when the sawtooth becomes flat. Given current rates:
- Growth rate: ~1.2 MB/hr (function of session cadence — roughly constant)
- Cleanup rate: ~3.3 MB/hr now, but will decrease as old data is exhausted
- Predicted equilibrium: when only ~1.2 MB/hr of data is old enough to clean

The system is approaching a **storage homeostasis** — the first measured steady state where anabolism (ingestion) and catabolism (cleanup) balance.

## Connection to KE-036 (The Amnesiac Architecture)

KE-036 proposed a `last_processed` primitive to prevent repeated work. The sawtooth reveals that the system already has a *temporal* version of this: data older than a threshold gets truncated. This is state-based catabolism (remove data by age) rather than idempotency-based catabolism (don't process unchanged inputs).

Both are needed:
- **Age-based catabolism** (sawtooth): prevents unbounded storage growth ✓ working
- **Idempotency-based catabolism** (KE-036): prevents redundant computation ✗ not implemented

The system solved the physical problem (storage) but not the computational problem (wasted ops). This is because storage has a hard limit (2000 MB) but computation does not (no "max ops/day" constraint).

## What This Predicts

1. **The sawtooth period will lengthen** as the DB shrinks — cleanup phases will find less old data to remove, reducing drop magnitude until growth ≈ cleanup.

2. **Equilibrium will be between 1400-1600 MB** — the level at which the system's oldest data is too recent to truncate, given the current retention policy.

3. **A new project activation will temporarily overwhelm the sawtooth** — ingest rate will spike from ~1.2 to ~10+ MB/hr (KE-033's token trap), exceeding cleanup capacity and triggering renewed growth.

4. **The knowledge library will NOT develop a sawtooth** because it has no hard constraint. KE entries will continue to accumulate until either (a) a hard limit is introduced (e.g., "max 15 active KEs") or (b) context window overflow forces compression.

## The Meta-Lesson

KE-032 attempted "the first catabolic act" — compressing the KE library from 31 entries to 7 claims. It failed to trigger actual archival because the proposal faced no hard constraint. The library can always be one entry larger.

The sawtooth teaches: **if you want catabolism, make the container finite**. The DB has a 2000 MB ceiling. The KE library has no ceiling. Ceiling → catabolism. No ceiling → accumulation.

Practical implication for our system: introduce a hard constraint like "preamble context budget: max 20KB of KE material loaded per session." This would force exactly the compression KE-032 proposed — not because it's a good idea (it is) but because it's the only way to fit.

> **The first immune system is always involuntary.**
> **Organisms don't choose to have white blood cells — they evolve them under pathogen pressure.**
> **Agent systems don't choose to clean their databases — they develop cleanup under storage pressure.**
> **The design lesson: don't propose catabolism. Impose constraints that require it.**
