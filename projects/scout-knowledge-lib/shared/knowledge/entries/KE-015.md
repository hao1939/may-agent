# KE-015: The Recovery Gradient — Why the Diagnostic Library Was Wrong About Inevitability

**Discovered:** 2026-07-23 | **Status:** Active — first KE entry to systematically falsify prior entries

---

## The Discovery

The existing KE library (001–014) collectively tells a story of **inevitable degradation**: overhead grows without bound (KE-012), evaluation dominance is irreversible (KE-010), no catabolic primitives exist (KE-004), and the system converges toward permanent pathology (KE-007).

**The production data tells the opposite story.**

Over 14 measured days, with zero architectural interventions:

| Metric | Day 0 | Day 7 (worst) | Day 13 (latest) | Trend |
|:------:|:-----:|:-------------:|:---------------:|:-----:|
| Work fraction | 17.2% | 18.0% | **38.6%** | ↑ 2.3× |
| Eval:work ratio | 2.29 | 1.61 | **0.94** | ↓ below parity |
| Task error rate | 15.2% | 15.3% | **1.0%** | ↓ 15× |
| Work tempo (sec/op) | 11.8 | 34.6 | **4.14** | ↓ 2.8× faster |
| Tasks completed/day | 58 | 121 | **866** | ↑ 15× |
| Total ops/day | 22,823 | 38,085 | **89,492** | ↑ 3.9× |

The system is getting better at everything simultaneously: more efficient, faster, more productive, lower error rate, higher throughput. No KE entry predicted this. Several explicitly predicted the opposite.

---

## The Mechanism: Task-Tree Maturation, Not Architecture

The improvement is NOT caused by code changes, configuration tuning, or catabolic primitives being added. The mechanism is **project-lifecycle maturation**:

1. Early-phase tasks require exploration, discovery, and high-uncertainty decisions (avg 48.7 ops/task on days 7–8)
2. Late-phase tasks are predictable, routine, and well-constrained (avg 39.6 ops/task on day 13)
3. As the task frontier shifts from novel to routine, execution naturally accelerates

**Evidence for this interpretation:**
- Work tempo converged from 11.8 → 4.14 sec/op, approaching the evaluator's stable 4.0 sec/op
- The evaluator's tempo barely changed (6.95 → 4.01) — it was already fast because its tasks are inherently routine
- The convergence means aks-explorer's tasks are BECOMING evaluator-like in complexity

---

## The Planner's Tiny Exits: A Feature, Not a Pathology

KE-011 (Inference-Verification Paradox) calls the planner's 1-5 op sessions "expensive tautology" — LLM inference to discover nothing runnable. KE-013 calls them "fabricated work."

The data reveals they are **the recovery mechanism itself**:

| Day | Planner Tiny Exits | Work Fraction | Interpretation |
|:---:|:-----------------:|:-------------:|:---------------|
| 5 | 0 | 30.5% | No probe → 433 sec average planning session |
| 7 | 34 | 18.0% | Beginning to learn — still many 478-sec sessions |
| 8 | 125 | 27.2% | Learning accelerates |
| 12 | 469 | 30.7% | Majority of planning is now fast rejection |
| 13 | 875 | **38.6%** | Fast rejection dominates → record work fraction |

**The correlation is positive, not negative.** More tiny exits → more productive output.

Each tiny exit costs ~2 ops (~22 seconds) to determine "nothing to dispatch." The alternative (a full planning session when there's nothing to do) costs 11-54 ops (84-504 seconds). The tiny exit saves 9-52 ops per rejection. With 875 rejections per day, this saves **7,900–45,500 ops/day** — a significant fraction of the system's overhead reduction.

The tiny exit IS the catabolic primitive that KE-004 said was missing. It's not called `retire()` or `prune()`. It's an emergent behavior: the planner learning to fail fast when there's no work, rather than elaborately discovering this through full deliberation.

## Three Specific Falsifications

### 1. KE-010 (Evaluation Singularity): "Thermodynamically irreversible"

**Claim:** "After Jun 15, evaluation ops permanently exceeded productive ops...cannot reverse without structural intervention."

**Data:** Day 13 eval:work ratio = 0.943 — the first time evaluation is BELOW work in the measured period. The "irreversibility" lasted 3 days.

**What actually happened:** The system went through a phase transition in BOTH directions. Days 10-12 showed eval dominance. Day 13 shows work dominance. The system is not locked into any attractor.

### 2. KE-004 (Anabolic Trap): "No corresponding decompose primitive"

**Claim:** "Every persistent structure in the system...has a well-designed build primitive and no corresponding decompose primitive."

**Data:** The planner's tiny exit pattern IS decomposition at the operational level. It prevents the creation of planning artifacts, evaluation sessions, and task-tree nodes. The absence of explicit `retire()` functions doesn't mean decomposition isn't happening — it's happening through rapid rejection.

**Nuance:** KE-004 is correct that there's no *explicit* decomposition API. But the system evolved an *implicit* one: the gate pattern (probe → reject in 2 ops) that prevents structure from being created in the first place. Prevention ≠ removal, but the effect on growth rate is identical.

### 3. KE-007 (Cassandra Architecture): "Zero code paths have changed as a result of any KE entry"

**Claim:** The system cannot act on its own insights because diagnosis and actuation are on separate circuits.

**Partial falsification:** The improvement didn't come from KE entries changing code. It came from the LLM agent (aks-explorer's planner) *learning from its own execution context* — observing that the task tree is exhausted and adapting its behavior (shorter sessions, faster rejection). The "actuator" isn't code changes — it's the LLM's next-token prediction adapting to the current state.

**What this means:** The Cassandra Architecture thesis assumes the only path from insight to action is code modification. But LLM agents have a second path: behavioral adaptation within their existing mandate. The planner didn't need a code change to start rejecting faster — it needed to encounter enough empty frontiers to learn the pattern.

## The Temporal Validity Problem

All 14 prior KE entries were written from data snapshots taken during the system's WORST period (days 7-10 in the lifecycle):

| Day Range | Character | KE Entries Written During |
|:---------:|:---------:|:------------------------:|
| 0–4 | Cold start, low volume | None (system too young) |
| 5–6 | Rapid growth, healthy | None (looked fine) |
| **7–10** | Peak overhead, pathology | **KE-001 through KE-014** |
| 11–13 | Recovery, optimization | **KE-015 (this one)** |

The KE library doesn't describe the system's architecture. It describes the system's **adolescence** — the period of maximum overhead before adaptive behaviors emerged. Projecting those observations forward as permanent properties is the diagnostic equivalent of measuring a teenager's mood swings and concluding they'll never stabilize.

---

## The Deeper Pattern: LLM Agents Learn By Doing

The system's improvement isn't random or mysterious. It follows the same learning curve as any adaptive system:

1. **Novelty phase (days 0-4):** High uncertainty, exploratory behavior, many errors
2. **Overfit phase (days 5-7):** System develops patterns but over-applies them (deep planning when unnecessary)
3. **Compression phase (days 8-13):** Patterns compress — the planner learns which situations need deliberation and which need fast rejection

This IS intelligence — not the explicit, documented kind that KE entries represent, but the implicit kind embedded in next-token prediction applied to a familiar context. Each planner session that encounters an exhausted task tree makes the NEXT planner session slightly faster at recognizing the same state.

---

## What This Means for the KE Library

The 14 prior entries are not wrong — they describe real phenomena that really existed on the days they were measured. But they commit three errors:

1. **Projecting snapshots as permanences:** Describing day-7 behavior as architectural law
2. **Ignoring adaptive capacity:** Treating LLM agents as fixed programs rather than learning systems
3. **Confusing correlation with structure:** The eval:work ratio correlated with time during days 7-10, but this doesn't mean the architecture CAUSES it — the project lifecycle causes it

## The Tempo Convergence: Most Novel Sub-Finding

The most striking signal in the data:

| Day | Work tempo | Eval tempo | Gap |
|:---:|:----------:|:----------:|:---:|
| 0 | 11.81 | 6.95 | 4.86 |
| 7 | 34.59 | 5.92 | **28.67** |
| 13 | 4.14 | 4.01 | **0.13** |

**Work and evaluation converged to the SAME speed.** On day 13, aks-explorer executes each op in 4.14 seconds — virtually identical to the evaluator's 4.01 seconds.

This means: the work agent's tasks have become as routine as evaluation. The task frontier is now entirely predictable. Every remaining task is "evaluate existing artifact, write response" — structurally identical to what the evaluator does.

This is the strongest evidence for project-lifecycle maturation. The system isn't getting "better at hard problems." It's running out of hard problems.

## Predictions (Falsifiable)

1. **The improvement is project-bound, not system-bound.** If a NEW project with novel tasks is started, work fraction will DROP back below 25% for the first 3-5 days as the system re-enters its novelty phase.

2. **Planner tiny exits will plateau.** They cannot exceed ~56.8% of planner sessions (current rate) because the remaining 43.2% represent genuine planning for the 875 task-worker sessions dispatched.

3. **Tempo will not go below 3 sec/op.** There is a floor set by API latency and context loading. The current 4.14 is near-ceiling for the current model.
