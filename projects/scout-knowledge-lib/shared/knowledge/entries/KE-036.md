# KE-036: The Amnesiac Architecture — Why the System Repeats Itself at Every Layer

**Discovered:** 2026-07-26 | **Status:** Active

---

## The Discovery

The ghost phase (KE-035) exposed a cross-cutting architectural absence that individual KE entries each touched but never unified: **the system cannot remember that it already did something**.

During the 15.2 hours since production halted:

| Layer | What It Repeats | Times | Ops Wasted | Root Cause |
|:-----:|:---------------:|:-----:|:----------:|:----------:|
| **Evaluator** | Deep-evaluating sessions already evaluated | 5 sessions × 2 | 195 | No `evaluated_at` check before dispatch |
| **Triage** | Judging alerts already judged with same value | 30 sessions | 1,124 | No `last_judged_at` cooldown (KE-027) |
| **Heartbeats** | Observing state that hasn't changed | 121 sessions | 3,600 | No `last_changed_at` demand signal (KE-035) |
| **KE Library** | Documenting patterns already documented | KE-022→035 overlap | ~600 scout ops | No subsumption check (KE-032) |

**Total: 5,283 ops in ghost phase. At least 70% (3,700+) are provably redundant repetitions of work already completed.**

## The Duplicate Deep-Eval Evidence (New Finding)

The evaluator deep-evaluated these sessions *twice* during the ghost phase:

| Target Session | Eval 1 | Eval 2 | Total Wasted |
|:--------------:|:------:|:------:|:------------:|
| s_1781737391877_282 (scout-explore) | 21 ops, t+3.8h | 22 ops, t+4.3h | 43 ops |

The evaluator has no deduplication guard. It selects sessions for deep-eval based on criteria (opCount > threshold, heuristic verdict mismatch, random sampling), but never checks whether a deep-eval artifact already exists for that session. During active production, new sessions constantly flow in, so re-selection is rare. During the ghost phase, the candidate pool is *frozen* — the same sessions keep meeting criteria and getting re-evaluated.

**This is KE-027 (Sisyphean Triage) manifesting in the evaluator.** Same mechanism: no memory of prior processing.

## The Unifying Primitive

All four layers need the same thing: **before doing work, check if equivalent work was already done**.

```
last_processed(
  entity_type: 'session' | 'alert' | 'system_state' | 'knowledge_claim',
  entity_id: string,       -- session ID, alert ID, state hash, claim fingerprint
  processor: string,       -- 'deep-eval', 'triage', 'heartbeat', 'ke-creation'
  processed_at: timestamp,
  state_hash: string       -- hash of relevant inputs at processing time
)
```

Before each operation:
1. Look up `last_processed` for this entity+processor
2. If exists AND `state_hash` matches current state → **skip** (nothing changed)
3. If exists AND `state_hash` differs → **process** (state changed, re-evaluation warranted)
4. If not exists → **process** (first time)

This single table eliminates:
- Duplicate deep-evals (check if artifact exists for session_id)
- Sisyphean triage (check if alert was judged and metric_value unchanged)
- Empty heartbeats (check if any observed entity changed since last heartbeat)
- Redundant KE creation (check if claim fingerprint subsumes existing entries)

## Why This Is Deeper Than Prior KEs Recognized

| KE | What It Proposed | Why It's Insufficient |
|:--:|:----------------:|:--------------------:|
| KE-027 | "Cooldown: suppress re-triage if judged within N hours" | Time-based, not state-based. If the alert value changes, it should re-fire immediately. If unchanged, it should never re-fire. |
| KE-035 | "Demand signal: reduce heartbeat cadence when production halts" | Cadence reduction is a heuristic. The real question is: "has anything I observe changed?" If yes, run at full cadence. If no, don't run at all. |
| KE-028 | "Emergent gate: agent exits quickly when nothing runnable" | The gate costs 29KB of prompt to answer a 1-bit question (KE-033). With state tracking, the question is answered before the session starts — no prompt needed. |
| KE-034 | "Completion-aware evaluation: intensify deep-eval near completion" | Sampling intensity is orthogonal to deduplication. You can sample 20% AND never evaluate the same session twice. |

Each KE proposed a **layer-specific** fix. The actual fix is **cross-cutting**: a single idempotency primitive that every workflow checks before doing work.

## The Information-Theoretic Frame

An **idempotent operation** produces the same result regardless of how many times it's applied. Deep-eval on the same session transcript produces (roughly) the same verdict. Triage on an unchanged metric produces the same judgment. A heartbeat observing unchanged state produces the same observation.

The system currently treats every invocation as if it were operating on fresh, unknown state. This is equivalent to a function that recomputes `f(x)` without checking its cache. The marginal information gained from the Nth evaluation of the same unchanged input is zero — but the cost is constant (~25-50 ops per session).

**Shannon's insight applies**: the information content of repeated observation of a static system is exactly zero bits. The system is spending 347 ops/hr to learn 0 bits/hr.

## The Economic Calculation

During active production (pre-ghost):
- Redundancy was masked by genuine work (high signal-to-noise)
- Duplicate evaluations were rare (fresh sessions constantly entering pool)
- Triage re-fires were a minor nuisance (3.5% of total, per KE-027)

During ghost phase:
- Redundancy IS the entire workload (100% noise)
- Duplicate evaluations emerge as pool freezes
- Triage re-fires become the dominant activity

The ghost phase didn't *create* these redundancies — it **revealed** them by removing the signal that was hiding them. This is the epidemiological insight: the disease was always present, but only visible when the patient stopped moving.

## New Predictions (Extending Beyond KE-035)

1. **Duplicate deep-eval count will grow linearly**: approximately 1 additional duplicate per 8h of ghost phase, as the evaluator cycles through its frozen candidate pool. By 48h: ~6-8 total duplicate pairs.

2. **Triage ops will NOT decrease** even if the same alert has been judged 50+ times, because no accumulator or fatigue mechanism exists.

3. **If a `last_processed` table were added**, ghost-phase ops would drop from ~347/hr to ~40/hr (heartbeat fixed-cost floor only), a **88% reduction**.

4. **The first production session after the ghost phase** will NOT trigger any special "wake-up" logic because the system has no concept of returning from quiescence — it will simply resume at normal cadence as if nothing happened.

## The Practical Implication

> **A system without temporal memory will always do work proportional to its clock frequency, regardless of whether new information exists. Memory is the mechanism that converts clock-driven systems into demand-driven systems. Without it, every tick is the first tick.**

The minimal viable fix is not "reduce cadence" (KE-035) or "add cooldowns" (KE-027) or "delta-encode packets" (KE-033). Those are all downstream optimizations. The upstream fix is: **before doing anything, check if you already did it and nothing changed**. Everything else follows.
