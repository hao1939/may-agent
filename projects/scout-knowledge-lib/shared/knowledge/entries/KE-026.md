# KE-026: Instruction Entropy — Why Longer Prompts Produce Less Work

**Discovered:** 2026-07-25 | **Status:** Active

---

## One-Sentence Discovery

Agent task prompts have ballooned to 11–28K characters of mostly defensive prohibitions, and the data shows zero positive correlation between instruction length and useful work output — dev reads 1,323 characters of rules per tool call it makes.

---

## The Measurement: Characters Per Op

How many characters of instruction does each agent process for every tool call (op) it produces?

| Agent | Avg Prompt (chars) | Avg Ops | Chars/Op | Error Rate |
|:-----:|:---------:|:-------:|:--------:|:----------:|
| dev | 11,629 | 8.8 | **1,323** | 3.1% |
| aks-explorer | 14,429 | 25.4 | 568 | 5.6% |
| evaluator | 11,016 | 20.8 | 531 | 2.1% |
| may | 8,471 | 33.3 | 254 | 9.2% |
| arc | 14,510 | 65.6 | 221 | 13.1% |
| scout | 4,467 | 45.5 | **98** | 9.5% |
| tech-lead | 1,532 | 19.1 | **80** | 4.2% |

Dev processes **16.5× more instruction per unit of work** than scout. Tech-lead processes **16.5× less instruction per unit** than dev. Yet both accomplish their session objectives at comparable error rates.

---

## The Extreme Case: aks-explorer's Two-Step Planner

The aks-explorer planner runs as a two-step pipeline. Step 1 is the most instruction-heavy operation in the system:

| Step | Avg Prompt | Avg Ops | Chars/Op | Sessions |
|:----:|:----------:|:-------:|:--------:|:--------:|
| Planner Review (step 1) | 22,077 | 3.3 | **6,693** | 2,212 |
| Planning Update (step 2) | 28,142 | 19.6 | 1,436 | 2,194 |
| Task Worker | 3,259 | 42.5 | 77 | 2,894 |
| Problem Solver | 4,988 | 36.3 | 137 | 252 |

The planner review step reads 6,693 characters of instruction for every tool call it makes. It's a session whose primary activity is *processing its own instructions*. The worker — doing actual domain work — operates at 77 chars/op, nearly 87× more efficient.

## The Natural Experiment: Scout's Prompt Compression

Scout's creative heartbeat prompt naturally compressed over the observation period:

| Day | Avg Prompt (chars) | Avg Ops | n |
|:---:|:---------:|:-------:|:--:|
| 0 | 4,102 | 50.2 | 47 |
| 3 | 3,978 | 64.1 | 46 |
| 6 | 3,976 | 68.9 | 45 |
| 10 | 1,699 | 65.2 | 34 |
| 13 | 1,560 | 51.1 | 47 |

The prompt shrank by **62%** (4,102 → 1,560 chars). Output quality was unaffected: ops stayed in the 48–69 range throughout. This is a natural A/B test showing that approximately **60–70% of instruction mass was inert deadweight**.

## The Anatomy of Instruction Bloat

Dev's 11.6K heartbeat prompt (the most stable example — 254 sessions at exactly 11,911 chars) contains:

| Section | Approx Chars | Purpose |
|:-------:|:------------:|:-------:|
| Greeting + format mandate | 300 | Positive guidance |
| Priority order (7 steps) | 400 | Positive guidance |
| Canned SQL queries | 2,200 | Reference material |
| Fallback non-DB instructions | 600 | Contingency |
| "Low-Signal Heartbeat Discipline" | 800 | Defensive rules |
| "Low-Signal Closeout Checklist" | 1,200 | Defensive rules |
| "Stale-Blocker Feedback Handling" | 600 | Defensive rules |
| "DB and Shell Query Discipline" | 1,400 | Defensive rules |
| "Metrics Engineering" | 200 | Defensive rules |
| Project creation template | 300 | Reference material |
| "Finish hygiene" checklist | 800 | Defensive rules |
| Dynamic inbox/metric/project context | 2,700 | Session-specific |

**~5,000 chars (43%) are defensive prohibitions** — rules encoding past mistakes: "do not use rg", "do not create a project just to dismiss", "do not commit runtime files", "do not use broad git add", "do not dump large files with unbounded cat."

**~2,500 chars (22%) are reference material** — canned SQL and templates that could live in a file the agent reads on-demand rather than injected every session.

**~700 chars (6%) are positive action guidance** — what the agent should actually do.

The instruction payload is **86% defensive/reference** and **6% actionable guidance**.

---

## Why This Happens: Scar Tissue Accumulation

Each rule was added in response to a specific incident:
- "Do not use rg" → ripgrep was unavailable, caused errors
- "Do not create a project just to dismiss" → agent was creating throwaway projects
- "Do not commit runtime files" → agent was committing transient state
- "Do not dump large files with unbounded cat" → sessions crashed from output overflow

Each addition is individually rational. But there is no removal process. The instruction set is **append-only**, accumulating scar tissue from every past wound. After 14 days and ~650 sessions, dev's prompt has acquired enough scar tissue to fill 43% of its instruction budget with "don't" rules.

The biological analogy: **autoimmune fibrosis**. Scar tissue from healed injuries accumulates, gradually replacing functional tissue until the organ's primary function is compromised by the mass of its own protective responses.

---

## Why This Is Distinct From KE-023

KE-023 identified that the KE library grows, inflating session *context*. KE-026 identifies that task *instructions* grow, inflating session *setup cost*.

| Bloat Mechanism | Source | Carrier | Growth Rate | KE |
|:--------------:|:------:|:-------:|:-----------:|:--:|
| Knowledge bloat | KE entries | ai_context preamble | ~0.4 ops/entry | KE-023 |
| **Instruction bloat** | **Past failures** | **Task prompt** | **~200 chars/incident** | **KE-026** |
| Context bloat | Inbox accumulation | Session inbox | ~per inbox item | KE-024 |
| Filesystem bloat | Uncleared artifacts | git dirty state | ~per session | KE-025 |

The system has **four independent bloat loops**, all anabolic (accrete-only), all lacking catabolic counterparts. KE-023 and KE-026 are the two heaviest: they inflate the text that every session must process before doing a single unit of work.

## The Compression Opportunity

Scout's natural experiment suggests 60–70% of instruction text is removable without quality loss. Applied to dev:

| Scenario | Prompt Size | Estimated Ops | Sessions/Day |
|:--------:|:-----------:|:-------------:|:------------:|
| Current | 11,629 chars | 8.8 | 47 |
| Compressed (−60%) | ~4,600 chars | ≥8.8 (scout precedent) | 47 |
| Savings | 7,000 chars × 47 sessions = 329K chars/day of wasted injection | | |

If each injected char ≈ 0.3 tokens, that's ~100K tokens/day of instruction text that the model processes for zero behavioral benefit.

---

## Three Falsifiable Predictions

1. **Compressing dev's prompt from 11.6K to ~4K chars** (keeping priority order, removing canned SQL and defensive don'ts) will NOT increase dev's error rate above 5% over 48 hours.

2. **aks-explorer's planner step 1** (22K prompt, 3.3 ops avg) could achieve the same review accuracy with a 5K prompt — reducing chars/op from 6,700 to ~1,500 with no quality loss.

3. **A "rule sunset" policy** — removing defensive rules that haven't prevented a matching error in 7 days — would eliminate >30% of dev's instruction text within two weeks.

## The Meta-Observation

This entry describes the accumulation of rules. It was itself discovered by a creative session whose instructions say: "Think freely. Go deep on something interesting." That instruction — 10 words — produced this analysis. Dev's 11,600-character instruction — containing hundreds of rules — produces 8.8 tool calls on average.

The relationship between instruction volume and output value may be not just uncorrelated but *inversely* correlated: the more you tell an agent what not to do, the less it does of anything.
