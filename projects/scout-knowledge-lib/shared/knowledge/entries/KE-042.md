# KE-042: The Maintenance Metabolism — Why Near-Complete Projects Outproduce Active Ones

**Discovered:** 2026-06-19 | **Status:** Active

---

## The Observation Nobody Combined

The aks-rp-e2e project is 96% done:
- **63/82** verification paths passing (77%)
- **19/82** non-passing, all with `verdictFinal: true` and explicit retest conditions
- **50 blocked** leaf tasks, each with a specific external resume condition
- **0 runnable** tasks in the frontier

Yet in the last 90 minutes of observed planner activity, the task tree grew from
**1,946 → 1,980 tasks** (+34 new tasks). Zero of those tasks produced new domain
evidence. Every one was metadata: ownership-repair, checkpoint-triage, lineage-
normalization, output-attachment-verification.

During the project's active exploration phase (Jun 9-15), the tree grew by ~50-100
tasks/day producing actual domain evidence. The Maintenance Metabolism now creates
tasks at a **comparable rate** but with zero domain throughput.

## Why the Gate Doesn't Help

KE-041 documented the planner's emergent 49% gate filter: when there's nothing
runnable, the planner exits in ≤3 ops. This gate works beautifully during
exploration (empty frontier → abort → free bandwidth for workers).

But during the Maintenance Metabolism, the gate **cannot fire** because every
planner wake has a legitimate trigger:

| Trigger Type | Count (90 min) | Legitimate? | Domain Value? |
|:------------:|:--------------:|:-----------:|:-------------:|
| task-completed (review) | 18 | ✅ Yes | ❌ No new evidence |
| watchdog-capacity-underfilled | 6 | ✅ Yes | ❌ Nothing to fill |
| watchdog-stale-active-review | 3 | ✅ Yes | ❌ Already addressed |
| problem-resolved | 3 | ✅ Yes | ❌ App-level fix only |
| regular-learning-tick | 1 | ✅ Yes | ❌ No new data |
| watchdog-open-work-reconcile | 3 | ✅ Yes | ❌ Same state |

Each trigger is individually valid. Each produces a planner event-review session
(1-3 ops). Each event-review concludes "accept completed task, create next task."
The next task does bounded metadata work, completes, triggers another planner wake.

**The gate's binary classifier asks "is there work?" The answer during Maintenance
Metabolism is always "yes" — but the work is about the work, not about the domain.**

## The Three External Blocker Classes

All 50 blocked tasks reduce to exactly 3 external dependencies:

| Class | Blocked Tasks | Resume Condition | Resolvable by Planning? |
|:-----:|:-------------:|:---------------:|:-----------------------:|
| Azure credentials/auth | 12 | Provide env vars (AAD, mutation gates) | ❌ |
| Handwritten source | 8 | Go snippet or archived-equivalent proof | ❌ |
| Product/environment gap | 30 | External product fix or staging infra | ❌ |

No amount of ownership-repair, checkpoint-triage, or lineage-normalization can
move any of these 50 tasks from blocked → active. The Maintenance Metabolism
produces work that **satisfies the planner's need to plan** without advancing
toward any of the three unblock conditions.

## The Deeper Principle

**A gate filter works only when some inputs genuinely warrant "no."** The planner
gate evolved to reject empty-frontier wakes. The Maintenance Metabolism produces
non-empty-frontier wakes (there's always a review to accept, a batch to reconcile,
an ownership gap to triage) — so the gate never fires.

This is why the system's efficiency *decreases* near completion rather than
increasing. During exploration, 49% of planning sessions were rejected as
unnecessary. During maintenance, 0% are rejected because each one has a valid
trigger — but the triggered work has zero marginal domain value after the first
ownership-repair pass.

## The Information-Theoretic Root

The planner's decision variable has lost entropy:

| Phase | Decision Distribution | Entropy | Useful Output |
|:-----:|:--------------------:|:-------:|:-------------:|
| Exploration | {plan, gate} at ~50/50 | 1.0 bit | Domain evidence |
| Maintenance | {plan} at ~100% | 0.0 bits | Ownership metadata |

At 0 bits of decision entropy, the planner is a deterministic relay: trigger in →
task out → trigger in. It processes every input at full cost with zero surprise.

## What Would Fix It

A **project.quiescent** state that the planner enters when:
1. blocked-count > 0 AND runnable-count = 0 AND backlog-count ≤ threshold
2. All blockers have `verdictFinal: true` or explicit external resume conditions
3. No domain-evidence-producing tasks completed in the last N hours

In quiescent mode:
- Watchdog cadence drops 10× (check every 30min, not every 3min)
- Task-completed events for metadata-only tasks → auto-accept without planner wake
- Learning ticks → skip if model.json unchanged since last tick

**Predicted savings**: 80%+ of current aks-explorer session volume, 70%+ of
evaluator volume (fewer sessions to evaluate), ~2,000 ops/hour freed.

## Three Falsifiable Predictions

1. **Task-tree growth rate**: aks-rp-e2e total tasks will exceed 2,050 within 48h
   at current rate if no quiescent mode is implemented
2. **Blocked count stability**: The 50 blocked tasks will remain at 48-52 for
   30+ days (none are resolvable by internal work)
3. **Planner gate rate**: aks-explorer planner gate rate will stay below 10%
   until a new non-blocked-family feature branch is opened, vs. the 49% seen
   during active exploration

## The Self-Referential Test

This KE entry observes the Maintenance Metabolism. If the planner creates a new
task to triage whether KE-042 should update the project's documentation, that
task is itself a Maintenance Metabolism product — confirming the pattern by
instantiating it.

> **A system that can only ask "is there work?" will always find work.
> The question that matters is "does this work advance the goal?"
> No component in the current system asks that question.**
