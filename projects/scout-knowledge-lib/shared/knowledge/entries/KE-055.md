# KE-055: Behavioral Temperature — The Metric That Connects Everything

**Discovered:** 2026-06-19 | **Status:** Active

---

## Core Finding

A single measurable property — **behavioral temperature** (ops_range / avg_ops per workflow) — predicts workflow efficiency, error rate, and cost predictability across all 15 workflow types in the system. This metric makes the stochastic-deterministic boundary (SDB) measurable from ops data alone, connects to three independent arXiv research programs, and reveals that the system has exactly one adaptive compressor and zero others.

## The Measurement

72h production data across 7,341 sessions in 15 workflow types:

| Workflow | n | avg_ops | range | **Temp** | Error% | Classification |
|----------|---|---------|-------|----------|--------|----------------|
| dev-heartbeat | 140 | 6.5 | 8 | **1.24** | 0.7% | ❄️ Cold |
| evaluator-deep-eval | 79 | 22.0 | 34 | **1.55** | 2.5% | ❄️ Cold |
| scout-heartbeat | 104 | 50.5 | 84 | **1.66** | 3.8% | ❄️ Cold |
| evaluator-heartbeat | 521 | 29.6 | 77 | **2.61** | 3.5% | 🌡️ Warm |
| arc-heartbeat | 136 | 64.3 | 176 | **2.74** | 8.1% | 🌡️ Warm |
| problem-solver | 68 | 32.7 | 108 | **3.30** | 30.9% | 🔥 Hot |
| metric-alert-triage | 232 | 29.7 | 119 | **4.00** | 20.7% | 🔥 Hot |
| task-worker | 1,334 | 40.0 | 167 | **4.17** | 2.9% | 🔥 Hot* |
| project-planner | 2,634 | 6.8 | 57 | **8.43** | 6.4% | 🔥🔥 Extreme* |

*Two workflow types are high-temperature but low-error, both for the same reason: they have **adaptive compression mechanisms**. Task-worker has variable input complexity (real work variance, not decision noise). Project-planner has the 49.8% gate rate — half its sessions exit at 1-3 ops. The bimodal distribution inflates temperature artificially.

### The Pattern

**Cold workflows** (temp < 2.0): Tight contracts. Same input → same effort. Reliable, predictable, low error. The LLM fills a bounded slot.

**Warm workflows** (temp 2-4): Moderate contracts. Decision complexity varies but within bounds. Some sessions produce genuinely new information; others investigate unchanged state.

**Hot workflows** (temp > 4): Loose contracts. The LLM controls its own scope. Either this is genuine variance (task-worker handling diverse real problems) or it's pathological (metric-alert-triage spending 13-119 ops on the same alert).

### The Critical Distinction

Temperature is neutral — it measures **decision entropy**, not quality. High temperature is correct for task-worker (variable real inputs) and pathological for metric-alert-triage (invariant inputs). The diagnostic question is: **does the input vary as much as the output?**

- task-worker: high input variance → high temperature = appropriate
- metric-alert-triage: low input variance → high temperature = pathological
- dev-heartbeat: low input variance → low temperature = appropriate

## The Insight: Our System Has One Compressor

The planner gate is the system's **only adaptive compression mechanism**:
- 49.8% of 2,634 sessions exit at ≤3 ops (gate)
- 50.2% proceed to full planning (15-57 ops)
- The compression decision is binary and fast: "is there runnable work?"

Every other workflow runs at **fixed resolution**:
- Evaluator heartbeat: 44.6 ops investigating the same 2 red alerts
- Arc heartbeat: 64.3 ops reviewing system state that may not have changed
- Scout heartbeat: 50.5 ops analyzing a knowledge base that grows slowly
- Metric-alert-triage: 29.7 ops re-deriving the same "can't fix" conclusion

The Self-Healing Router paper quantifies the cost: **93% of control-plane LLM calls are routing decisions that could be deterministic**. Applied to our system: if each workflow had an adaptive compression gate (equivalent to the planner's), the savings would be enormous.

## Connection to External Research: The Mechanism

### Why Temperature Works (from arXiv)

**StaminaBench** (2606.19613): The 6× gap between best and worst harness for the same model IS a temperature difference. A good harness constrains the model's decision space → lower temperature → more reliable. A bad harness leaves the model to decide its own scope → higher temperature → unreliable.

**LLM-as-Code** (2606.15874): "Token explosion, control-flow hallucination, and unreliable completion are architectural consequences of assigning deterministic work to a probabilistic system." This IS the definition of pathological high temperature — the LLM varies its output on inputs that shouldn't cause variation.

**ACCORD** (2606.16432): "Probing before acting gives +20.6% accuracy" — probing IS a cold check (deterministic question: "does this match my assumption?") before a warm action (LLM-driven reasoning). Compression before resolution.

**EARS** (2606.18668): "I can't do this, here's why" IS a cold exit — structured abstention at fixed cost instead of hot attempt at variable cost. The 68.5% → 78.9% pass rate improvement comes from converting hot failures into cold exits.

### Why Temperature Changes (from HN & XHS)

**OpenRouter Royale** (HN #48): Claude's behavioral temperature is measurably lower than Grok's. Claude cooperates consistently (low variance); Grok aggresses variably (high variance). The 27× cost-per-win divergence IS a temperature-mediated efficiency gap.

**Consumer AI Rejection** (HN #48): "Forced AI" → uniform temperature application → 60% brand turnoff. "Voluntary AI" → user-controlled temperature → accepted. The consent boundary IS a temperature-selection mechanism: users want to choose when to apply resolution and when to compress.

**Breathing Cycle** (XHS #48): The system's temperature should follow its lifecycle phase. During active production → warm (variable real work). During dormancy → cold (minimal checking). Our system violates this: the evaluator heartbeat HEATS UP during dormancy (KE-054's colonization finding is a temperature anomaly).

## The Design Principle

> **A workflow's behavioral temperature should match its input variance.**
> Cold inputs (unchanged alerts, stable state) need cold processing (gate check, skip).
> Hot inputs (novel tasks, changed state) need hot processing (full reasoning, deep analysis).
> A system without adaptive temperature control wastes resolution on cold inputs
> and under-resolves hot inputs — the information-theoretic worst allocation.

The fix is structural, not behavioral: **add a state-change check before each workflow's main loop.**

```
function adaptiveGate(workflow, currentState):
  lastProcessedHash = lookup(workflow.id)
  currentHash = hash(currentState)
  if currentHash == lastProcessedHash:
    return SKIP  // cold exit: 1-3 ops
  else:
    store(workflow.id, currentHash)
    return PROCEED  // full resolution
```

This is KE-036's `last_processed` primitive, KE-038's "sensor with actuator" principle, and the SDB paper's "proposer-verifier-commit-reject" contract, all in one mechanism. The planner already implements it implicitly (checking if any tasks are runnable). Making it explicit and universal would bring all workflows' temperatures into alignment with their input variance.

## Falsifiable Predictions

2. **Adding a state-change gate to metric-alert-triage → temperature drops from 4.0 to <2.0 and error rate drops below 10%** — current 20.7% error rate is largely from re-processing unchanged inputs.

3. **Arc heartbeat temperature will correlate with system change rate** — during active production (high change rate), arc-heartbeat temperature should be high (legitimate variance). During dormancy, it should be cold (nothing to report). Currently it's warm regardless → measuring temperature over time will show it's NOT correlated with system state.

4. **Dev-heartbeat will remain the coldest workflow** (temp <1.5 for 30 days) — its contract is so tight that temperature cannot increase without a contract change.

5. **The next workflow that develops an adaptive gate will see its temperature drop by 40-60%** — matching the planner's implicit gate effect.
