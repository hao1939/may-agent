# KE-016: The Adaptation Ceiling — Why Recovery Stops at Architecture

**Discovered:** 2026-07-23 | **Status:** Active — reconciles KE-014 and KE-015

---

## The Paradox

Two recent discoveries appear to contradict each other:

- **KE-014 (Amplification Cascade):** The system's meta-overhead is structural, increasing at each abstraction layer, with a permanent 97:1 events-per-task ratio.
- **KE-015 (Recovery Gradient):** The system is organically improving — work fraction rose from 17% to 39%, eval:work ratio dropped below parity, all without architectural intervention.

If overhead is structural, how is the system recovering? If the system is recovering, why does the 97:1 ratio persist?

---

## The Resolution: Layer-Locked Recovery

Production data across 11 days reveals the answer: **recovery is real but layer-bounded.** Improvement propagates bottom-up through the abstraction stack and STOPS at the first layer whose overhead is architectural rather than behavioral.

### Measured Recovery By Layer

| Layer | Metric | Day 0 | Day 10 | Improvement | Recovery? |
|:-----:|:------:|:-----:|:------:|:-----------:|:---------:|
| **Ops** | Overhead:work ratio | 33.0 | 1.69 | **19.5×** | ✅ Strong |
| **Ops** | Work fraction | 2.9% | 37.2% | **12.8×** | ✅ Strong |
| **Sessions** | Overhead:work ratio | 43.2 | 4.46 | **9.7×** | ✅ Moderate |
| **Sessions** | Eval:worker sessions | 18.3 | 1.28 | **14.3×** | ✅ Strong |
| **Events** | Handler fraction | 54.6% | 49.5% | **1.1×** | ❌ Flat |
| **Events** | Events per session | 10.6 | 15.5 | **0.68×** | ❌ Worsened |
| **Events** | Events per task | 84.7 | 78.7 | **1.08×** | ❌ Flat |

The pattern is unmistakable:
- **Ops layer:** 12–19× improvement
- **Session layer:** 10–14× improvement
- **Event layer:** 0–10% improvement (flat or worsening)

---

## The Mechanism: Two Types of Overhead

The data reveals a sharp categorical distinction between two kinds of overhead:

### Behavioral Overhead (Ops + Session Layers)
- **Source:** LLM agent decisions — how long to plan, whether to evaluate, how deep to work
- **Reducible by:** Agent learning, behavioral adaptation, experience
- **Examples:** Planner tiny exits (learned rejection), evaluator skipping (heuristic gate), work tempo convergence
- **Character:** Compresses over time as agents encounter familiar states

### Architectural Overhead (Event Layer)
- **Source:** Dispatch infrastructure — every session generates handler.started, handler.completed, session.start, session.end regardless of session content
- **Reducible by:** Code changes only — modifying the dispatcher, suppressing events, changing architecture
- **Examples:** handler.started/completed (logged unconditionally), guard.triggered (logged even when passing), session.receipt (logged for every session)
- **Character:** Constant coefficient per session, immune to behavioral improvement

## The Adaptation Ceiling

```
                    ┌─────────────────────────────────┐
  EVENT LAYER       │  handler.started/completed      │  ← ABOVE CEILING
  (architectural)   │  guard.triggered                │     Cannot be reduced by
                    │  session.start/end              │     agent learning
                    │  ~50% of all events             │
                    └─────────────────────────────────┘
                    ═══════ ADAPTATION CEILING ════════
                    ┌─────────────────────────────────┐
  SESSION LAYER     │  eval sessions / worker         │  ← BELOW CEILING
  (behavioral)     │  planner sessions / dispatch    │     Agents CAN reduce by
                    │  eval skip rate                 │     adapting behavior
                    └─────────────────────────────────┘
                    ┌─────────────────────────────────┐
  OPS LAYER         │  planner ops / worker ops       │  ← BELOW CEILING
  (behavioral)     │  eval ops / work ops            │     Agents DID reduce by
                    │  tiny exit frequency            │     adapting behavior
                    └─────────────────────────────────┘
```

The **adaptation ceiling** is the boundary between layers where LLM behavioral adaptation can optimize and layers where only code changes help. It sits between the session layer (where agent decisions about "whether to do something" live) and the event layer (where "recording that something happened" lives).

## Evidence: The Three Recovery Mechanisms

### Mechanism 1: Planner Tiny Exits (Ops Layer)

| Day | Planner Tiny % | Plan:Work Ops Ratio | Ops Layer Effect |
|:---:|:--------------:|:-------------------:|:----------------:|
| Jun 9 | 0% | 0.08 | Low (planner nascent) |
| Jun 11 | 3.6% | 0.64 | Planner scaling up, no gate |
| Jun 12 | 29.2% | 0.76 | Gate emerging |
| Jun 14 | 39.8% | 0.72 | Gate active |
| Jun 17 | **60.5%** | **0.27** | Gate dominant |
| Jun 18 | **56.8%** | **0.32** | Gate stable |

The planner learned to reject in 2 ops instead of deliberating for 24+ ops. This reduced the planner's contribution to k from 0.76 to 0.27 — a **2.8× improvement** at the ops layer.

Simultaneously, "deep" planner sessions got shorter: 55.8 avg ops → 11.4 avg ops. Even when the planner DOES deliberate, it deliberates faster.

### Mechanism 2: Evaluation Skipping (Session Layer)

| Day | Eval Skip % | Eval Sessions per Worker | Session Layer Effect |
|:---:|:-----------:|:------------------------:|:--------------------:|
| Jun 11 | 0% | 2.80 | All sessions evaluated |

| Jun 17 | **50.9%** | 1.39 | Half of sessions skip eval |
| Jun 18 | **50.6%** | 1.28 | Stable at ~50% skip rate |

The evaluator's JS-level skip gate (introduced ~Jun 15) reduced eval sessions per worker from ~3.5 to ~1.3. This compressed the session layer's overhead ratio from 7.7 to 4.1.

Handler events remain locked at 49–55% of all events across all days, regardless of ops-layer or session-layer recovery. **The event layer's structural overhead is impervious to the behavioral adaptation occurring below it.**

## Why This Matters: The Ceiling Constrains Total System Improvement

The ops layer can improve 19× and the event layer won't notice. This means:

1. **Events-per-task has a behavioral floor.** KE-014's ~78 events/task minimum cannot be reduced without architectural change, no matter how efficient the agents become.

2. **The recovery has a ceiling.** KE-015's improvement trajectory will asymptote. Work fraction may reach 40-45% (KE-012's Amdahl ceiling) but events-per-task will remain at ~78-85.

3. **Storage/query costs grow linearly with sessions regardless of session efficiency.** Making sessions shorter or skipping evaluation reduces ops but not event volume proportionally.

4. **The two optimization axes (KE-014's finding) are actually LAYER-SPECIFIC prescriptions:**
   - Below the ceiling: behavioral adaptation (already happening organically)
   - Above the ceiling: architectural intervention (requires developer action)

### Why KE-015 Partially Falsified KE-007

KE-007 says: "Zero code paths have changed as a result of any KE entry." This is correct at the event layer (above the ceiling). But KE-015 showed that agents adapt behavior without code changes — the planner's tiny exits weren't programmed, they emerged from experience. This is action-without-code-change, which KE-007 couldn't conceive of.

**The Cassandra Architecture only applies above the adaptation ceiling.** Below it, LLM agents have a second actuation path: behavioral adaptation through next-token prediction encountering familiar states.

### Why KE-015 Didn't Falsify KE-014

KE-014's 97:1 events-per-task ratio barely improved (from ~120 to ~79 over 8 days — much of that from throughput scaling, not per-session efficiency). The amplification cascade is an event-layer phenomenon. Recovery is an ops-layer phenomenon. They coexist because they're at different altitudes.

## The Deep Principle

> **In any adaptive multi-layered system, organic improvement propagates from the agent layer upward but cannot cross boundaries where the overhead source is the infrastructure itself rather than agent decisions.**

This means:
1. You can train agents to be more efficient (behavioral), but you cannot train the message bus to emit fewer messages (architectural).
2. Learning-based improvement has a sharp ceiling determined by how high up the stack agent decisions reach.
3. The ratio of behavioral-to-architectural overhead determines what fraction of total system cost is improvable without developer intervention.

For our system:
- **Behaviorally-determined overhead** (below ceiling): ~65% of ops, ~55% of sessions
- **Architecturally-determined overhead** (above ceiling): ~50% of events, 100% of storage growth
- **Maximum behavioral improvement:** Can compress the 65% of ops by 10-19× (proven). Cannot compress the 50% of events at all (proven).

---

## Quantifying the Ceiling's Location

The adaptation ceiling sits precisely at the **session dispatch boundary**:
- An agent CAN decide "don't do a deep planning session" → reduces ops and sessions
- An agent CANNOT decide "don't log that I started" → handler.started fires unconditionally
- An agent CAN trigger eval.skipped → reduces eval sessions
- An agent CANNOT prevent session.start/session.end from being recorded

The architectural overhead per session is approximately:
- 1 × handler.started
- 1 × handler.completed  
- 1 × session.start
- 1 × session.end
- 0.7 × handler.workflow_dispatched
- 0.5 × guard.triggered
- 0.3 × session.receipt

**≈ 5.5 events per session** as irreducible architectural floor, regardless of what happens inside the session.

With ~4,000 sessions/day (current rate), this means ~22,000 events/day are purely architectural — events that exist because sessions exist, carrying zero information about what happened inside them.

## Three Falsifiable Predictions

1. **Work fraction will plateau between 35-45% (the Amdahl ceiling from KE-012) within the next 5 days, and then fluctuate within that band.** The ops-layer recovery is near its maximum. The session-layer recovery (eval skipping at 50%) is also near its stable state. Further improvement requires event-layer changes.

2. **If handler.started and handler.completed events are suppressed, total event volume will drop by 33-36% with zero impact on ops-layer or session-layer metrics.** This tests whether the event layer is truly decoupled from lower layers. If suppressing these events somehow changes agent behavior, the ceiling model is wrong.

3. **A new project (novel tasks) will reset ops-layer efficiency to <20% work fraction while leaving the handler_fraction at ~50%.** This tests whether the behavioral recovery is project-specific (KE-015's claim) while the architectural overhead is project-independent (KE-014's claim).

## Prescriptive Implication: Two-Track Optimization

The system needs two DIFFERENT optimization strategies for two different layers:

| Layer | Strategy | Responsible | Mechanism | Already Happening? |
|:-----:|:--------:|:-----------:|:---------:|:------------------:|
| Ops + Sessions | **Let agents learn** | Agents (LLMs) | Behavioral adaptation, tiny exits, skip gates | ✅ Yes (organic) |
| Events | **Change architecture** | Developers (humans) | Suppress logging, batch events, reduce handler registration | ❌ No (blocked by KE-007) |

The first track is free — it happens automatically as agents encounter familiar states. The system has already captured most of its behavioral improvement potential (19× over 11 days).

The second track requires breaking the Cassandra gap (KE-007): converting event-layer insights into code changes. **This is where future efficiency gains live.** The behavioral improvement is nearly maxed out. The architectural improvement hasn't started.

## The Meta-Observation

This entry reconciles the two most recent and most ambitious KE entries by showing they describe the **same system at different altitudes.** Neither is wrong. The system simultaneously exhibits:
- Dramatic organic improvement (below the ceiling)
- Permanent structural overhead (above the ceiling)
- And the ceiling itself is the deepest structural finding — it determines what CAN improve without intervention and what CANNOT.

The ceiling is not a failure. It's a **design boundary**. Every system has layers where adaptation works and layers where architecture constrains. The insight is knowing WHERE the boundary is, so you don't expect behavioral learning to fix architectural problems (or waste developer time on problems that agents will solve themselves).
