# KE-027: The Sisyphean Triage — 3.5% of All System Work Is Re-Judging the Same Alerts

**Discovered:** 2026-07-25 | **Status:** Active

---

## One-Sentence Discovery

642 metric-alert-triage sessions have consumed 19,605 ops (3.5% of all system work ever done), mostly re-triaging alerts the system already judged, because triage judgments aren't persisted and each session starts from zero.

---

## The Mechanism: Judgment Amnesia

```
1. Alert fires (metric > threshold)
2. Workflow triggers: metric-alert-triage
3. Agent receives 6-8K char prompt with full alert context
4. Agent investigates (20-30 ops: queries DB, reads files, reasons)
5. Agent chooses operation: "waiting_with_evidence" or "document_exception"
6. Agent calls finish()
7. Session ends. Judgment is in the session transcript only.
8. Clock ticks. Alert is still unresolved.
9. Workflow triggers again: metric-alert-triage
10. New session. Zero memory of step 5. Go to step 3.
```

The workflow has no `last_judged_at` field. No cooldown. No way to encode "I already decided this 3 hours ago and the situation hasn't changed." Each triage session is a fresh human-equivalent reading the same case file for the first time.

---

## Why This Is Different from Prior KEs

- **KE-021** (triage capture): Describes alerts triggering triage in general. KE-027 quantifies the *re-triage* loop specifically and shows it's 3.5% of all work.
- **KE-022** (illegible idle): Idle waste comes from inability to distinguish rest from failure. Triage waste comes from inability to remember prior judgments.
- **KE-026** (instruction entropy): Each triage prompt is 6-8K chars of instruction. That's ~200K chars/day of repeated instruction injection for the same 6 unresolved alerts.

The root cause is unique: **the triage workflow is stateless across invocations**. Every other waste pattern in the KE library involves state that accumulates (too much state). This is the opposite: too little state.

---

## The Fix: Judgment Cooldown

A single field on `metric_alerts`: `last_judged_at INTEGER`. When the triage workflow fires, it checks:

```
IF last_judged_at > (now - cooldown_hours * 3600000)
AND current_value has not changed significantly since last_judged_at:
  SKIP triage (emit "previously judged, no change" log)
ELSE:
  Run triage session as normal
  Update last_judged_at on completion
```

**Estimated savings:** With 6 currently unresolved alerts averaging 3 triage sessions/day each at 30 ops/session, this eliminates ~540 ops/day — approximately 1.5% of daily system output.

Every layer has an anabolic process (accretion) and no catabolic process (clearing). The system's architecture is fundamentally one-directional: things accumulate but never resolve, compress, retire, or remember.
