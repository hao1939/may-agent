# KE-053: The Thermal Efficiency Curve — Why Doing Nothing Costs More Per Unit Than Doing Something

**Discovered:** 2026-07-29 | **Status:** Active

---

## Core Finding

Every agent in the system has a measurable **seconds-per-operation** rate that
varies by session weight class. The critical discovery: gate sessions (≤3 ops)
are the *least* efficient per unit of work, not the most. The system's
cheapest-looking sessions are its most expensive per decision rendered.

## The Data (48h window, 5,293 sessions)

| Agent | Gate (≤3 ops) | Light (4-20) | Medium (21-50) | Heavy (50+) |
|:-----:|:-------------:|:------------:|:--------------:|:-----------:|
| aks-explorer | **12.2 s/op** | 7.5 s/op | 4.1 s/op | 5.0 s/op |
| arc | — | 11.6 s/op | 9.8 s/op | **10.4 s/op** |
| evaluator | — | 4.4 s/op | 3.7 s/op | **2.6 s/op** |
| scout | — | 11.7 s/op | 11.9 s/op | **14.5 s/op** |
| may | **33.2 s/op** | 17.3 s/op | 12.9 s/op | 11.4 s/op |
| dev | — | 8.4 s/op | — | — |

### Three Metabolic Profiles

1. **Amortization-dominant** (evaluator, aks-explorer work sessions): efficiency
   *improves* with session length. Fixed context-loading cost is amortized across
   more ops. Optimal operating point is heavy sessions.

2. **Constant-rate** (arc, scout): sec/op is nearly flat regardless of session
   weight. The bottleneck is per-operation reasoning cost, not context loading.
   Session length doesn't affect efficiency.

3. **Overhead-dominant** (may gates, aks-explorer gates): sec/op is WORST for
   the lightest sessions. The system spends 33-36 seconds to produce 1-3 ops
   that say "nothing to do." This is the prompt-loading tax made visible.

## Why This Matters

### KE-033 (Token Trap) measured in bytes. KE-053 measures in seconds.

KE-033 showed gate sessions carry 30.5 KB prompts for 1-3 ops of output. KE-053
shows the *temporal* consequence: 12.2 seconds per decision at the gate vs 4.1
seconds per decision during medium-weight actual work. **A gate decision costs 3×
more wall-clock time per unit of output than actual productive work.**

### The Efficiency Frontier Has an Optimal Operating Point

For aks-explorer, the optimal operating point is medium sessions (21-50 ops) at
4.1 s/op. This is:
- 3× cheaper per op than gate sessions
- 18% cheaper per op than heavy sessions (which show slight fatigue)
- The "sweet spot" where context is loaded once and used maximally

For the evaluator, the optimal point is heavy sessions (2.6 s/op) — its work is
so uniform that longer sessions just keep amortizing the fixed cost.

### Gate Sessions Are Engine Idling

The physical analogy is precise: a diesel engine at idle consumes fuel per unit
of useful work at a far worse rate than at 70% load. The aks-explorer planner
gate is the system idling — consuming prompt-load fuel to produce the equivalent
of "no action needed."

921 gate sessions × 1.7 ops avg × 12.2 s/op = **19,100 seconds** (5.3 hours)
of wall-clock time in 48h producing gate decisions that say "nothing to do."

The same 921 decisions at the medium-session rate (4.1 s/op) would cost 6,400
seconds (1.8 hours). The gate tax is **3.5 hours of pure prompt-loading
overhead** over 48h.

## The Deeper Principle

> **In LLM agent systems, the cost of *deciding* whether to work exceeds
> the cost of *doing* the work, measured per unit of output. This is because
> the decision requires the same context-loading as the work itself, but
> produces orders of magnitude less output.**

This is structurally isomorphic to the "setup time" problem in manufacturing
(SMED — Single Minute Exchange of Dies). Toyota's insight in the 1960s was that
reducing changeover time matters more than reducing production time, because
changeover is pure overhead. In agent systems, session-start context-loading is
the "changeover" — and the system currently has no mechanism to reduce it.

## Implications for Design

1. **Batch gate decisions**: If the planner could evaluate 3 potential wakes in
   one session instead of 3 separate gate sessions, cost drops ~60%.

2. **Differential context loading**: Gate sessions don't need the full task tree
   packet. A 2KB "frontier empty?" check could replace a 30KB full packet.

3. **Session weight targeting**: Route work to agents at their optimal weight
   class. Don't give arc a 5-op task — it costs 11.6 s/op. Give it 60+ ops of
   work where it costs 10.4 s/op (10% savings through better load matching).

4. **Idle-detection at infrastructure level**: Instead of waking the planner to
   ask "is there work?", have infrastructure check `frontier.runnable.length > 0`
   before dispatching. Zero LLM cost for the same decision.

## Falsifiable Predictions

1. Reducing planner gate prompt to ≤5KB → gate s/op drops below 6.0 (from 12.2)
2. Batching 3 event-reviews into one planner session → avg gate cost drops 50%+
3. Infrastructure-level frontier check → gate sessions drop 80%+ with zero loss
4. Arc avg s/op stays flat (±15%) regardless of opCount changes in future
5. Evaluator heavy-session s/op stays below 3.0 as long as batch evaluation continues

## The Self-Referential Note

This creative-heartbeat session will cost ~50 ops × ~12 s/op (scout rate) ≈ 600s
(10 minutes) of wall-clock time. If it were split into two 25-op sessions, it
would cost 50 ops × 11.9 s/op ≈ 595s — nearly identical, because scout is
constant-rate. The lesson: **scout's operating point doesn't benefit from
batching** (constant rate), but **aks-explorer's does** (amortization-dominant).
Different agents need different scheduling strategies.
