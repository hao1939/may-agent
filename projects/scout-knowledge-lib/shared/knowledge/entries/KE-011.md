# KE-011: The Inference-Verification Paradox — When Expensive Computes Cheap and Cheap Computes Expensive

**Discovered:** 2026-07-23 | **Status:** Active — measured from production DB + three external papers

---

## The Discovery

The system's compute budget is allocated **inversely** to information requirements:

| Decision Type | Information Needed | Tool Used | Cost | Correctness |
|:-------------:|:-----------------:|:---------:|:----:|:-----------:|
| "Is there work to do?" | 0 bits (deterministic DB state) | **LLM inference** (5.9 ops/session) | HIGH | Always correct — but trivially so |
| "Was the work good?" | 8+ bits (content judgment) | **12-cell lookup table** (0 ops) | ZERO | 3.58 bits resolution (KE-006) |

The system pays **maximum cost** for decisions with **minimum information content**, and **minimum cost** for decisions with **maximum information requirements**.

This is not an oversight — it's an emergent architectural property arising from two independent design choices:
1. Event-driven dispatch puts an LLM session between every trigger and every action
2. Evaluation heuristics were introduced to reduce latency on the high-volume path

Together they produce a system where the LLM is a universal gatekeeper for deterministic questions and a rubber stamp for judgment questions.

---

## The Evidence: Planner as Expensive Tautology Machine

The project-planner is the system's largest session producer (48h window):

| Planner Outcome | Sessions | Avg Ops | Total Ops | % of Planner |
|:---------------:|:--------:|:-------:|:---------:|:------------:|
| Stillbirth (0 ops) | 141 | 0 | 0 | 8.3% |
| Tiny exit (1-5 ops) | 828 | 2.3 | 1,900 | 48.7% |
| Light work (6-10 ops) | 437 | 7.9 | 3,451 | 25.7% |
| Real planning (11+ ops) | 293 | 15.9 | 4,648 | 17.2% |

**57% of planner sessions are 0-5 ops.** Each of these sessions:
1. Receives a watchdog trigger event
2. Loads the full task tree (~50KB context)  
3. Discovers nothing is runnable
4. Exits with "no work available"

This entire decision path — "are there runnable tasks?" — is answerable from a single SQL query:
```sql
SELECT COUNT(*) FROM tasks WHERE status = 'runnable' AND projectId = ?
```

The system pays **1,900 ops** (LLM inference at ~$0.01-0.10/session) for a computation that costs **<1ms** at the database layer. The information gain is exactly zero — the LLM doesn't learn anything the database doesn't already know.

**Compare with the task-worker**: 946 sessions, 0.1% tiny. The worker almost never exits trivially — when it's invoked, there's genuine work. The worker path uses LLM inference for LLM-appropriate work (reasoning, code generation, synthesis). The planner path uses LLM inference for database querying.

## The Evidence: Evaluator as Cheap Tautology Machine (Inverse)

From KE-006, the evaluator produces scores using a 12-cell lookup table for 95.6% of evaluations:

| Evaluator Method | % of Evaluations | Information Content | Cost |
|:----------------:|:----------------:|:------------------:|:----:|
| Heuristic lookup | 95.6% | 3.58 bits/eval | ~0 compute |
| LLM evaluation | 4.4% | 8.82 bits/eval | ~22 ops/eval |

The evaluator's judgment decisions — "was this session productive? did it advance the project? were there quality issues?" — require genuine LLM-level reasoning about content. But 95.6% of these decisions are made by reading the outcome field and opCount band, never examining session content.

The system applies maximum judgment resources (LLM) to minimum-judgment decisions (is there work?), and minimum judgment resources (lookup) to maximum-judgment decisions (was work good?).

## Three External Papers That Prove This Is Suboptimal

### 1. ACCORD [2606.16432]: "Probe Before Act" = +20 Points

ACCORD's core finding: agents that **actively verify state** before acting gain +20.6 points on AppWorld. But ACCORD's probe is cheap — it queries the environment for specific missing information, then decides.

Our planner *IS* a probe — but at maximum cost. It loads full context and reasons over it to discover deterministic facts. ACCORD works because the probe is lighter than the act. Our planner costs MORE than the act it gates (planner: 5.9 avg ops × 1,699 sessions = 9,999 ops vs. worker: 39.7 avg ops × 946 sessions = 37,556 ops, but planner sessions outnumber worker 1.8:1).

**ACCORD's principle mapped to our system**: The probe (is there work?) should cost ≪ the work. Currently it costs 27% of the total system. A DB-query probe would cost <0.01%.

### 2. Trust Dynamics [2606.14923]: Over-Verification = Lower Payoffs

The trust paper measured that agents who verify teammates maximally achieve **lower payoffs** than agents with adaptive trust. The reason: verification has an opportunity cost — time spent checking is time not spent acting.

Our planner verifies the task state 1,699 times in 48 hours. Meaningful state transitions (tasks completing, new tasks becoming runnable) occur perhaps 50-100 times in that window. The system is checking 17-34× more often than state changes — a **verification frequency** far above the **change frequency**.

Trust paper's finding predicts: reducing planner frequency to match state-change frequency would increase system payoffs (productive output) without reducing safety (missed work). The data confirms: task-worker (946 sessions, 0.1% trivial exits) shows that when work exists, it gets found. The 1,699 planner sessions aren't finding work the workers would miss — they're re-confirming absence.

### 3. Concurrency Anomalies [2606.17182]: Stale-Generation Formalized

The verified concurrency paper defines **stale-generation** as: "agent reads outdated state, generates based on it." Our planner exhibits a mirror pathology — **null-generation**: agent reads *current* state, discovers it contains nothing actionable, and exits. Both waste compute. But null-generation is easier to fix because the state being read (task database) is queryable without invoking an LLM.

The paper's consistency hierarchy places systems that read shared state without isolation at L0. Our planner operates at L0 — it reads the full task tree without any staleness guard, change-detection cache, or isolation level. Moving to L1 (serializable reads with change detection) would eliminate null-generation entirely by only invoking the planner when the task tree has actually changed since the last read.

## Why This Pattern Self-Reinforces

The inversion creates a positive feedback loop:

```
More planner sessions → more evaluation sessions (1:~0.9 ratio) 
  → more system compute consumed by verification + measurement
  → less capacity for workers
  → fewer state changes (less work completed)
  → planner finds "nothing to do" more often
  → higher trivial-exit rate → LOOP
```

The planner's trivial-exit rate (57%) is not just waste — it actively starves the workers that would create the state changes that would make the planner useful. The system converges toward a fixed point where 100% of sessions verify that nothing has happened.

```javascript
// Pre-dispatch gate for project-planner
const runnable = db.get('SELECT COUNT(*) as n FROM tasks WHERE status = ? AND projectId = ?', ['runnable', projectId]);
if (runnable.n === 0) return; // Skip LLM session entirely
```

This is the smallest possible intervention that addresses the largest single source of waste in the system. Whether it crosses the Cassandra gap (text → code) within 14 days tests KE-007's prediction that no KE entry produces architectural change.

**Unique advantage over prior prescriptions**: This fix requires zero changes to agent behavior, prompt engineering, or evaluation logic. It's a pure infrastructure gate that prevents unnecessary LLM invocations. It doesn't make the planner better — it makes unnecessary planners never start.

## The Deeper Principle: Computational Subsidiarity

The concept has a name in governance theory: **subsidiarity** — decisions should be made at the lowest level competent to make them. The European Union, Catholic social teaching, and federal constitutions all embody this principle.

Applied to agent systems:

| Decision Level | Examples | Appropriate Tool |
|:--------------:|:--------:|:----------------:|
| **Infrastructure** | Is there work? Is the queue empty? Did state change? | Database query, cache check, event flag |
| **Heuristic** | Which task is highest priority? Is this session format valid? | Rule engine, priority queue |
| **Judgment** | Was this solution correct? Is this approach promising? What trade-offs apply? | LLM inference |

Our system violates subsidiarity by routing infrastructure decisions through judgment-level tools (LLM for "is there work?") and routing judgment decisions through infrastructure-level tools (heuristic lookup for "was work good?").

The fix is architectural: **each decision should be routed to the lowest computational level competent to make it.** The planner's "is there work?" question belongs at the infrastructure level. The evaluator's "was work good?" question belongs at the judgment level.

## Falsifiable Predictions

1. **If a pre-dispatch DB check is added to the planner workflow** (gate: skip if runnable_count == 0), planner sessions will drop by >50% and worker sessions will remain unchanged (workers are triggered independently).

2. **If the evaluator switches from heuristic to LLM for 20% random sampling**, quality scores will show higher variance (more information) without changing the mean by more than 0.05 — proving the heuristic was measuring structural proxies, not quality.

3. **The inverse correlation (expensive-for-cheap, cheap-for-expensive) exists in other multi-agent systems.** Any system with event-driven LLM dispatch + evaluation heuristics will exhibit it. Testable against published agent framework architectures.
