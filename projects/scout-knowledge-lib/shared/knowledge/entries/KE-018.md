# KE-018: The First-Order Transition — Why Agent Systems Stop, Not Slow Down

**Discovered:** 2026-06-18 | **Status:** Active — falsifies KE-015 sigmoid model

---

## The Discovery

The KE library's accumulated model of project lifecycle treats the wind-down as gradual — a sigmoid approaching a plateau (KE-015), an exhaustion curve (the Quiet Crossing), entropy accumulating smoothly (KE-001). **The production data shows something fundamentally different.**

Within a 2-hour window today, aks-explorer transitioned from peak throughput to near-zero:

|:---:|:---:|:---:|:---:|:---:|:---:|:---:|
| 494936 | **82** | 48 | 29 | 57 | 3 | 7 |
| 494937 | **108** | 58 | 47 | 71 | 3 | 7 |

| 494939 | **1** | 0 | 0 | 0 | 0 | 6 |

| 494941 | **3** | 0 | 0 | 2 | 0 | 6 |
| 494942 | **1** | 0 | 0 | 1 | 0 | 3* |

*hour 494942 is partial (current hour)

The transition is not smooth. It's a **step function** — a single scheduling cycle separates "full production" from "idle."

---

## The Mechanism: Binary Dispatch

The project watchdog fires on a fixed cycle (~5 min). Each fire, it:
1. Counts runnable tasks in the task tree
2. If runnable > 0 AND capacity available: dispatches planner + workers
3. If runnable = 0: does nothing (but still fires)

When the last task completed during hour 494938, the next watchdog fire found **zero runnable tasks**. Every subsequent fire also found zero. The transition is instantaneous at the watchdog's resolution — there is no gradual state.

The "decline" visible at hour 494938 (44 sessions, down from 108) is not a smooth ramp — it's the **partial hour** during which the final batch of tasks completed. The last worker session started at the beginning of h494938; by mid-hour, all work was done.

## What This Falsifies

### KE-015 (Recovery Gradient) — Sigmoid Model

KE-015 described four project phases and predicted the exhaustion phase as a smooth decline approaching an asymptote. **The actual transition is discontinuous.** There is no Phase 4 "gradual exhaustion" — there is Phase 3 (peak) and then Phase 5 (idle), separated by a single scheduling cycle.

The "smooth decline" visible in daily aggregates is a **sampling artifact**: averaging hour-resolution data over 24-hour windows smooths the step function into an apparent curve.

### KE-002 (Bureaucratic Attractor) — Continuous Overhead

KE-002 described the planner-to-worker ratio growing continuously. Post-transition, the ratio is **undefined** (0 planners, 0 workers). The Bureaucratic Attractor is not a persistent state — it exists only during the active project phase and vanishes instantly when the project completes.

### KE-003 (Observer Tax) — Stale Observations

KE-003 predicted measurement entropy would grow without bound. Post-transition, measurement DOES continue (51 project.watchdog.tick events in the post-transition window), but its cost is structurally bounded — the watchdog fires, finds nothing, and returns. The Observer Tax is real during active work but approaches a small constant during idle.

## The Analogy: First-Order Phase Transition

In physics, transitions are classified:
- **Second-order (continuous):** Magnetization smoothly approaches zero at the Curie temperature. No latent heat. The system changes gradually.
- **First-order (discontinuous):** Ice becomes water at 0°C. Latent heat is absorbed. The system jumps between states.

Agent project lifecycle transitions are **first-order**:
- The system maintains full throughput right up to the moment the last task completes
- Then it drops to basal metabolism instantly
- There is no intermediate state between "active project" and "idle"
- The "latent heat" equivalent is the final batch of tasks completing simultaneously

This matters because **every optimization strategy based on smooth lifecycle models is wrong.** You don't need to detect "approaching exhaustion" — you need to detect "runnable tasks = 0" and respond immediately.

---

## The Hysteresis Question (Unmeasured)

In physical first-order transitions, the path going up differs from the path going down (hysteresis). The KE library has **zero data** on system restart — we've never observed a new project activating in this system.

**Prediction:** When a new project activates, the transition from idle to productive will ALSO be a step function (first-order going up), but with a **different step height**: initial throughput will be lower than peak throughput by 30-60% due to cold-start effects (KE-009 infant mortality).

If the upward transition is smooth (gradual ramp over hours), that would indicate second-order dynamics on activation — structurally asymmetric with the first-order shutdown. This would be a novel finding with no analogue in physical systems.

## The Simplest Intervention

**Phase detection is trivial.** The system already computes `runnable_tasks` every watchdog cycle. The missing logic:

```
IF runnable_tasks == 0 AND blocked_tasks > 0 AND active_tasks == 0:
  mode = IDLE
  watchdog_interval = 1 hour (was 5 min)
  suppress planner wakes
  suppress metric-alert-triage for project-specific metrics
  may handler pre-filter: skip all session.completed from clock agents
```

**Estimated savings in idle mode:** 
- 51 watchdog ticks/5hr → 5 ticks/5hr (10×)  
- 308 may handler.skipped → ~30 (10×)
- 7 aks metric-alert-triage sessions → 0 (∞×, until metric resolves)
- Total: ~80% reduction in post-transition overhead
