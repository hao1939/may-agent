# KE-003: The Observer Tax — When Measurement Loops Amplify What They Cannot Fix

**Discovered:** 2026-06-18 | **Status:** Active — measured from live production data

---

## The Pattern

The system has evolved a **four-layer metacognitive stack** where each layer observes/evaluates the one below it:

| Layer | Function | Sessions/24h | Ops/24h | % System |
|-------|----------|:------------:|:-------:|:--------:|
| 0. **Work** | Execute domain tasks | 948 | 38,314 | 39.5% |
| 1. **Evaluation** | Judge work quality | 1,578 | 35,519 | 36.7% |
| 2. **Coordination** | Plan & orchestrate | 1,743 | 10,059 | 10.4% |
| 3. **Monitoring** | Judge system health | 217 | 6,001 | 6.2% |

The **Observer Tax** emerges when Layer 3 (monitoring) repeatedly measures a condition that Layers 0-2 cannot resolve:

- The `aks-rp-e2e.task.blocked-count` metric reads 20 (threshold: 5)
- All 49 blocked tasks require **external** inputs (Azure auth credentials, handwritten source files, product fixes)
- No internal session — at any layer — can change this number
- Yet the system spawns **63 metric-alert-triage sessions** (2,012 ops) in 24h to "judge" the alert
- Each triage session reads context, examines the tree, concludes "waiting_with_evidence" or "document_exception"
- 5 minutes later, the metric fires again, and a new triage session starts

## The Evidence (Live DB, 2026-06-18)

### The Blocked-Count Alert Loop

| Metric | blocked-count value | Status |
|--------|:-------------------:|--------|
| 24h ago | 5 | At threshold |
| 18h ago | 7 | Above threshold |
| 12h ago | 8 | Climbing (planner created new blocked leaves) |
| 6h ago | 20 | Plateau (tree pruned to 49 proper blockers) |
| Now | 20 | **Static** for 6+ hours |

Each transition triggered a burst of triage sessions. Even after the value stabilized at 20 for 6 hours, triage sessions continued firing every ~20 minutes.

### The Observation Cost Stack

For each fired alert, the system pays:

| Component | Ops per fire | Why |
|-----------|:-----------:|-----|
| Metric snapshot | 1 | may measures the metric |
| Alert threshold check | 1 | may fires the alert |
| Metric-alert-triage session | ~31 | aks-explorer reads tree, decides it cannot fix external blockers |
| Evaluator-aftermath session | ~22 | evaluator judges the triage session |
| Possible planner wake | ~5.6 | if triage creates a tree action |
| **Total per fire** | **~60** | |

At ~4.5 fires/hour × 24h = ~108 fires × 60 ops = **~6,500 ops/day** spent observing that the number 20 has not changed.

### The Capacity-Underfilled Companion Alert

A second alert (`capacity-underfilled-with-gaps`) fires continuously alongside `blocked-count`. It says "worker capacity is available but gaps remain." This is the SAME information in different words. The system pays for both observations independently, doubling the cost.

Combined monitoring overhead for the two unfixable alerts: **~13,000 ops/day** or ~13% of system compute devoted to re-confirming that external blockers remain external.

## Why This Is Different From KE-001 and KE-002

**KE-001** (Immune Disorder) identified that persistent memory without feedback evolves from protective to parasitic. KE-003 is not about memory — it's about **active computation** that repeats without changing state.

**KE-002** (Bureaucratic Attractor) identified that planning overhead grows monotonically with tree size. KE-003 identifies a different mechanism: **monitoring overhead grows with alert count × fire rate**, independent of tree size.

The Observer Tax operates in a different dimension:
- KE-002's cost is proportional to `tree_size × wake_frequency`
- KE-003's cost is proportional to `unfixable_alerts × fire_rate × layer_count`

Together they form a **cost scissors**: coordination overhead grows with tree complexity, while monitoring overhead grows with alert count. A system that is simultaneously large and stuck (many nodes, many blocks) pays both costs multiplicatively.

## The Metacognitive Cascade

The four-layer stack creates a multiplicative overhead when problems propagate upward:

```
Layer 0: Task blocked (0 ops — just sits there)
     ↓ observed by
Layer 1: Evaluator scores "blocked" work (22 ops each)
     ↓ detected by
Layer 2: Watchdog fires capacity-underfilled → planner wakes (5.6 ops)
     ↓ measured by
Layer 3: Metric reads "blocked-count=20" → fires alert → triage session (31 ops)
     ↓ which evaluator evaluates
Layer 1 again: Evaluator scores the triage session (22 ops)
```

The single blocked task at Layer 0 (cost: 0 ops) creates a per-fire cost of **~80 ops** across all layers. With 49 blocked tasks collectively driving the metric, and the metric firing ~108 times/day, the cost amplification is:

**0 ops of actual work → ~6,500 ops of observation overhead = ∞× amplification**

This is the purest possible waste: the observation cost divided by the information gained per observation. Since the information gain is zero after the first observation (the situation is unchanged), every subsequent observation has infinite cost-per-bit.

## Connection to External Research

### Trust Dynamics (2606.14923)
The paper found that maximum verification correlates with LOWER payoffs — not higher. Over-verification in the presence of a trusted condition (the blocks are real and documented) produces negative value. Our system re-verifies 108 times per day that 49 documented external blocks are still... external blocks.

### ACCORD (2606.16432)
ACCORD showed that "probe-before-act" improves outcomes by +20 points. But the key word is "before-act." Our triage probes repeatedly without any possible subsequent action. The ACCORD pattern degrades to waste when there is no action available after the probe.

### CoffeeBench Idle Drift (2606.16613)
"Correct assessment + coherent plan + inaction" — the triage session correctly identifies the blockers, produces a sensible recommendation ("waiting_with_evidence"), and then nothing happens. The system performs expensive cognitive work to reach the same conclusion it reached last time.

## The Missing Primitive: Observation Staleness

The system has no concept of **observation staleness**. A fresh observation of a changing condition is valuable. A repeated observation of a static condition is waste. The missing gate is:

```
IF metric.value == metric.previous_value
   AND metric.cause_class == 'external'
   AND hours_since_last_triage < staleness_threshold:
     SUPPRESS alert (no new triage session)
```

This single conditional would eliminate ~63 sessions/day for this metric alone. Given that multiple metrics fire for the same underlying condition, the savings cascade.

---

## Three Prescriptions

### 1. Alert Staleness Gate
Suppress metric-alert-triage for any alert where: (a) the metric value hasn't changed since last triage, (b) the last triage concluded with a "waiting" or "document_exception" operation, and (c) the triage is less than 6h old. Re-fire only on value change or time expiry.

### 2. Alert Deduplication  
`blocked-count` and `capacity-underfilled-with-gaps` describe the same underlying condition (project has external blockers). Deduplicate at the alert layer: one triage session covers both, and both are suppressed until the underlying condition changes.

### 3. Layer Collapse for Static Conditions
When a Layer 3 triage concludes "external, cannot fix," skip Layer 1 evaluation of the triage session. The evaluator adds 22 ops of overhead to confirm that a "we can't do anything" session was... a reasonable response to not being able to do anything.

## The Deeper Insight: Measurement Has Mass

In physics, the observer effect means measurement disturbs the measured system. In agent systems, the observer effect is literal: **measurement consumes the same resources that could be used for work.**

Every monitoring session uses the same LLM context window, the same token budget, the same scheduling slot as a work session. The cost of observation is not zero — it is drawn from the same finite pool as productive work. When observation becomes the dominant activity (as it approaches for the blocked-count condition), the system has crossed a boundary where its primary output is self-description rather than domain progress.

This connects to the Legibility Trap (synthesis #43): the system optimizes for what it can measure. When what it measures is itself measuring, it enters a recursive loop with no external ground truth to break the cycle.

## Falsification Conditions

1. If suppressing the staleness gate for 24h changes the blocked-count metric, the observation WAS doing something useful (triggering retry behavior that occasionally clears a block). Falsified if metric improves during suppression.
2. If the 63 triage sessions produced different conclusions (not all "waiting_with_evidence" or "document_exception"), the repetition contains information. Falsified if >3 distinct operation types appear.
3. If removing evaluation of triage sessions correlates with worse triage quality in later sessions, the evaluation feedback loop IS active. Falsified if post-removal triage quality degrades.
