# KE-002: The Bureaucratic Attractor — When Planning Infrastructure Becomes the Primary Workload

**Discovered:** 2026-06-18 | **Status:** Active — measured from live production data

---

## The Pattern

The aks-rp-e2e project task tree grew from **1,032 to 1,959 nodes in 24 hours** while remaining **96.1% complete** (1,879 done, 49 blocked, 2 active). The system's dominant agent (aks-explorer: 2,774 sessions, 51,107 ops) and its evaluator (1,580 sessions, 35,458 ops) together consume **88.6% of all system compute** to manage a project with **two active task leaves**.

This is not a bug in a component. It's a **stable attractor state** where planning overhead has become the system's primary output.

---

## The Evidence (Live DB, 2026-06-18)

### The Session Ratio: 85:1

| Category | Sessions | Ops | Avg Ops |
|----------|:--------:|:---:|:-------:|
| aks-explorer `call` (planner steps) | 2,746 | 50,697 | 18.5 |
| aks-explorer `job` (worker tasks) | 32 | 510 | 15.9 |
| **Ratio** | **85.8:1** | **99.4:1** | — |

For every worker session that performs actual project work, the planner runs **85.8 sessions** of coordination overhead. The planner's per-session cost (18.5 ops) is actually *higher* than the worker's (15.9 ops), because reading the task-tree packet, reviewing event context, and deciding what to do next requires as much LLM reasoning as the task itself.

### The Packet Bloat Problem

The compact task-tree packet sent to each planner wake currently contains:
- 1,959 total nodes (1,931 leaves)
- 49 blocked leaves with full blocker text, acceptance criteria, and trace histories
- 2 active leaves with full session traces
- 19 non-passing model paths with retest conditions
- Full `model_status_summary` with labels, root cause classes, and retest conditions

Each planner wake is a 2-step workflow (Event Review + Planning Update), so each logical planning decision costs **2 LLM sessions**. Each session receives and processes this full packet. The packet itself is ~50KB+ of structured JSON.

These are planner-step sessions that failed at the workflow orchestration layer, consuming session creation overhead without performing any work.

## Why This Is a Stable Attractor

The system cannot escape this state through normal operation because:

1. **The watchdog fires `capacity-underfilled`** when the frontier has fewer active tasks than `maxConcurrent` (5). With only 2 active leaves, the watchdog triggers on every tick.

2. **The planner responds to watchdog events** by creating new leaves. But the project has no *genuine* new work — 1,879/1,931 leaves are done, and 49 are blocked on external inputs (Azure auth, handwritten source files, product gaps).

3. **The planner creates meta-work**: ownership-repair tasks, conflict-scope parity fixes, checkpoint reconciliation — real tasks, but they address the task tree's own internal consistency, not the project's domain goals.

4. **Each new task triggers evaluation sessions**, which triggers more watchdog events (capacity freed → underfilled again), which triggers more planner wakes.

5. **The task tree never shrinks**. Done tasks remain in the tree. Blocked tasks remain in the tree. The packet grows monotonically.

This is a **fixed point**: the system has converged to a state where its dominant activity is managing the overhead of its own coordination infrastructure.

## Connection to External Research

### Bayesian-Agent (2606.08348) — Lifecycle Actions

The Bayesian-Agent framework defines lifecycle actions for skills: **patch, split, compress, retire, explore**. The critical missing action in our task tree is **retire**. Done tasks, blocked tasks with `verdictFinal: true`, and deprecated paths remain permanently in the tree, growing the packet on every planner wake. A retirement action — moving completed branches to an archive and removing them from the active packet — would reduce packet size by ~96%.

### IntentKV (2606.09916) — Pruning Signal

IntentKV showed that 77.8% of agent KV memory is prunable without accuracy loss when using *intent relevance* as the pruning signal. The task-tree packet is structurally identical: 96.1% of its content (done/blocked leaves) is irrelevant to the planner's current decision (which of 0-2 runnable tasks to assign). Intent-relevant pruning of the packet to frontier-only would reduce per-session LLM load by ~20×.

### Intelligence Entropy (2606.08162) — Exponential Growth

The paper's `S(t) = S₀ · e^(α·t)` describes system entropy growing exponentially. The task tree *is* accumulated entropy: 730 new nodes in 18 hours, each carrying trace histories, acceptance criteria, conflict scopes, and blocker text. Without a deterministic gate (retirement, archival, compaction), tree entropy grows at the rate of planner wake frequency, not at the rate of domain progress.

## The Deeper Structural Issue: Coordination Cost Scaling

In organizational theory, **coordination cost scales superlinearly with team size** (Brooks's Law). The same applies to task trees: coordination cost scales with *tree size*, not *frontier size*.

A well-designed coordination system should have cost proportional to:
```
cost ∝ f(frontier_size) + ε
```

Our system has cost proportional to:
```
cost ∝ f(tree_size) × wake_frequency
```

Since `tree_size` grows monotonically and `wake_frequency` is driven by watchdog ticks (constant), coordination cost grows without bound while the frontier it coordinates approaches zero.

This is the **bureaucratic attractor**: the point where the coordination system's self-maintenance cost exceeds the value of the work it coordinates.

---

## Three Prescriptions (Subtractive)

All three are *removals*, not additions — following the Inoculation Paradox's insight that the highest-ROI interventions are subtractive.

### 1. Packet Pruning: Send Only the Frontier
Strip done/blocked leaves from the planner packet. Include only: runnable, active, review, and the 5 most recent blocked (for context). Tree size drops from 1,959 to ~55 in the packet. Planner session ops should halve.

### 2. Watchdog Dampening: Respect Phase 4
When `runnable == 0 AND blocked > 20 AND done/total > 0.95`, the project is in Phase 4 (exhaustion, per the Quiet Crossing). Watchdog frequency should drop from 5min to 1h. This alone eliminates ~85% of planner wakes.

### 3. Tree Retirement: Archive Completed Branches
Move branches with `verdictFinal: true` to an archive table. Keep a summary count ("49 branches archived, all externally blocked"). The planner never sees them unless explicitly requested.

## Falsification Conditions

1. If packet pruning reduces planner session ops by <30%, the packet is not the bottleneck (the planning prompt template or event payload is)
2. If watchdog dampening reduces aks-explorer sessions by <50%, something other than the watchdog is triggering planner wakes
3. If the planner *still* creates meta-tasks after packet pruning + watchdog dampening, the behavior is prompt-driven, not data-driven
