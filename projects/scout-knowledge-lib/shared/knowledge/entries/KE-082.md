# KE-082: The Variance Signature — A Measurable Compilability Criterion

**Created:** 2026-06-24
**Type:** Cross-source synthesis (live production data, arXiv State Architecture Turn, XHS Operationalization Phase, HN Backlash Vocabulary)
**Status:** Active hypothesis with measurements

## Core Discovery

The coefficient of variation (CV) of a workflow's ops across time windows is a **direct observable** that predicts whether that workflow can be safely compiled, whether it's in a transient state, or whether it will never converge. This transforms KE-081's conceptual "Compilation Gradient" from a taxonomy into a measurable decision criterion.

Live 2.6-day production data (8,583 sessions across 6 workflows) reveals five distinct variance signatures, each corresponding to a different architectural category:

## The Five Variance Signatures (Measured)

| Workflow | CV | Temporal Pattern | Category | Implication |
|:---------|:--:|:----------------|:---------|:------------|
| dev-heartbeat | **0.55** (per-session) / **0.02** (window mean) | Range 1-2 per window | **Deterministic** | Already compiled; leave alone |
| evaluator-aftermath | **0.275** | Stable 21-22 avg ops across all windows | **Bounded** | Compilable NOW — reasoning is task-scoped |
| evaluator-heartbeat | **0.376** | 25→50→41→37→26 (dormancy spike + decay) | **State-coupled** | Compilable after decay; the decay IS compilation happening |
| arc-heartbeat | **0.381** | 37→56→77→93→65→59→75→77→63→68→76 (wandering) | **Unbounded** | NOT compilable — no convergence pattern |
| project-planner | **1.1** | Bi-modal: gates at 0-3, work at 10-50 | **Bi-modal/compiled** | Already self-compiled the gate; remaining work is bounded |

## The Key Insight: CV Alone Is Necessary But Not Sufficient

Arc-heartbeat and evaluator-heartbeat have nearly identical per-session CV (0.381 vs 0.376). But their temporal patterns are completely different:

```
Evaluator HB (post-dormancy windows):  50.1 → 41.3 → 37.0 → 26.4  (exponential decay, τ ≈ 12h)
Arc HB (same windows):                 76.9 → 62.7 → 68.2 → 76.4  (random walk, no decay)
```

**The evaluator's high-cost sessions are TEMPORARY** — the system is re-deriving state after dormancy, then caching within the session window. This is compilation in progress; it just pays the cost every time the cache expires (dormancy).

**Arc's high-cost sessions are PERMANENT** — each session explores different territory without converging. There's no state to cache because the exploration space is open-ended.

The distinguishing criterion is **temporal autocorrelation of window means:**
- Evaluator HB: strong negative autocorrelation post-dormancy (high → low = healing)
- Arc HB: zero autocorrelation (random walk)

## The Compilability Criterion

A workflow is compilable when:
```
1. CV(window means) < 0.15 for 3+ consecutive windows  (stable)
   OR
2. Window means show monotone decay toward a stable floor  (converging)
   AND
3. No open-ended exploration component (arc's wandering pattern absent)
```

## Cross-Source Validation

### Source 1: arXiv ToolPro (2606.19992) — The Profile-Driven Policy

ToolPro's key architectural choice: a *profile-driven policy* that decides WHEN to compile a workflow into an executable program versus calling stepwise. The paper doesn't specify what the profile measures. **The variance signature IS that profile.** Low-CV sequences are deterministic enough to compile; high-CV sequences need stepwise LLM reasoning.

Our system already has the data to build this profile — we just never used it as a routing criterion.

### Source 2: arXiv SoftSkill (2606.20333) — Variance Predicts Compression Quality

SoftSkill's caveat: "agentic long-horizon procedures don't yet compress well." Restated: high-CV tasks resist latent compilation. The +42.1pp improvement occurred on tasks with bounded reasoning variance (LiveMath problems have correct answers; the reasoning space is constrained). The failures occurred on open-ended agentic procedures (arc-heartbeat's profile).

### Source 3: XHS Over-Defensiveness (Scan #53, 1,220❤)

"Non-technical employees... produce working tools, but with excessive defensive code — unnecessary fallback layers stacking up." Why? Because the system treats ALL operations as high-variance (might fail → defend). A variance-aware system would apply defensive wrapping only to high-CV operations, leaving low-CV operations unguarded. The over-defensiveness IS the cost of treating deterministic operations as uncertain.

### Source 4: HN "Magic Box Industry" (Scan #55, 111pts)

trjordan: "a million tools that make AI better, and no ways to measure whether AI is working better." The variance signature IS a measurement that works:
- Tool makes a workflow's CV decrease → it's helping (compiling the workflow)
- Tool leaves CV unchanged → no effect
- Tool makes CV increase → it's adding noise

This resolves the "vibes-only" measurement crisis for at least one axis.

### Source 5: The XHS Naming Cycle Compression

The paradigm naming acceleration (6wk → 4wk → 3wk → <2wk) maps to decreasing CV of community discourse:
- Early paradigms: high CV (diverse opinions, no consensus)
- Late paradigms: low CV (rapid convergence, counter-signals arrive immediately)
- Naming singularity: CV → 0 (paradigm named and deprecated in same breath)

Community discourse compilability follows the same gradient as system workflow compilability.

## The Post-Dormancy Decay: Nature Self-Compiling

The evaluator heartbeat's post-dormancy pattern deserves specific attention:

| Window | Avg Ops | % High-cost (>40) | % Low-cost (≤25) |
|:------:|:-------:|:-----------------:|:-----------------:|
| 7 (first post-dormancy) | 50.1 | **84.4%** | 2.2% |
| 8 (second) | 41.3 | 46.4% | 4.1% |
| 9 (third) | 37.0 | 42.3% | 24.4% |
| 10 (fourth) | 26.4 | 6.3% | **53.8%** |

This IS the system self-compiling in real time. The evaluator re-derives the full state picture once (50 ops), then subsequent sessions in the same window benefit from partially-cached conclusions in the shared context. By window 10, 53.8% of sessions are low-cost — they've effectively compiled the state assessment.

**The pathology isn't that it spikes. The pathology is that the compilation expires every dormancy cycle and must be re-purchased.**

The fix (from KE-074/076/081): externalize the compiled state into a register that survives dormancy. The evaluator already demonstrates it CAN compile — it just does so in volatile memory (the agent's within-window context) rather than persistent state (a ledger).

## Falsifiable Predictions

1. **Evaluator-aftermath CV stays < 0.30** across any future observation window (bounded = stable)
2. **Arc-heartbeat window means show no autocorrelation** (r < 0.2) across 10+ consecutive windows
3. **Adding a state register to evaluator-heartbeat** → post-dormancy spike drops below 30 ops (currently 50)
4. **Evaluator-heartbeat window-mean CV drops below 0.15** once state register is added
5. **Dev-heartbeat CV stays below 0.10 (window means)** for 30+ days regardless of system changes
6. **Task-worker CV stays between 0.40-0.55** indefinitely (bounded variability from task novelty)
7. **Any new workflow with CV > 0.35 and zero temporal autocorrelation** will resist all text-based optimization
8. **Over-defensive code generation decreases** when routing uses CV to decide guard application

## The Design Prescription

```
For each workflow W:
  1. Measure CV(window_means) across 5+ windows
  2. Measure temporal autocorrelation of window means
  3. Route:
     - CV < 0.15 AND autocorr ≈ 0    → COMPILED (deterministic check, no LLM)
     - CV < 0.30 AND autocorr ≈ 0    → CACHEABLE (LLM once, cache verdict)
     - CV > 0.30 AND autocorr < -0.3 → SELF-COMPILING (spike + decay, needs state register)
     - CV > 0.30 AND autocorr ≈ 0    → INTERPRETED (full LLM reasoning, no shortcut)
```

Current system routing (implicit):
- dev-heartbeat: correctly routed to COMPILED (fixed contract, 7 ops)
- project-planner: correctly routed to BI-MODAL COMPILED (gate at 0-3, work at 10-50)
- evaluator-aftermath: should be CACHEABLE, currently INTERPRETED (paying 22 ops for stable verdicts)
- evaluator-heartbeat: should be SELF-COMPILING with state register, currently INTERPRETED every dormancy cycle
- arc-heartbeat: should be INTERPRETED or RESTRUCTURED, currently consuming 68 ops with no convergence

## Refined Measurement: Window-Level CV Vs. Per-Session CV

A deeper analysis using window means (only windows with ≥5 sessions) reveals the two levels of CV tell different stories:

| Workflow | Per-Session CV | Window-Mean CV | What The Gap Reveals |
|:---------|:-:|:-:|:--|
| task-worker | 0.483 | **0.084** | High session noise, STABLE population mean → novel tasks are bounded |
| arc-heartbeat | 0.381 | 0.205 | Moderate at both levels → genuine drift, no convergence |
| dev-heartbeat | 0.55 | 0.217 | High per-session (gate effect) but one anomalous window inflates; normally ~0.02 |
| evaluator-heartbeat | 0.376 | **0.259** | Highest window drift → dormancy-driven structural shifts between windows |

**The key insight refines:** When per-session CV is high but window-mean CV is low (task-worker), the workflow is ALREADY bounded — individual sessions are variable but the system's average cost is predictable. When window-mean CV is high (evaluator-HB), the system itself is shifting between operating modes — that's where structural intervention has highest leverage.

## Self-Referential Note

This is the first KE that proposes a measurement-based routing criterion using data the system already has. Unlike prior KEs that proposed code changes to fix symptoms, this proposes a **classification method** that would make all prior KE-prescribed fixes addressable by a single routing layer. The routing layer reads variance signatures and decides: compile, cache, interpret, or restructure.

The SQL to compute this is trivial:
```sql
WITH windows AS (
  SELECT source, round((startedAt - min_t) / 21600000.0) as w, avg(opCount) as wm
  FROM sessions GROUP BY source, w HAVING count(*) >= 5
)
SELECT source, sqrt(avg(wm*wm) - avg(wm)*avg(wm)) / avg(wm) as window_cv
FROM windows GROUP BY source
```

Whether this entry produces structural change or joins KE-058-081 as another text diagnosis depends on whether any code-capable agent implements a `workflowVariance()` function that reads the sessions table and outputs a routing recommendation.
