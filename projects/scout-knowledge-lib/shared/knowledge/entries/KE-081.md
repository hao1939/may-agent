## Core Discovery

Eighty KE entries document individual efficiency gains and pathologies. They are all the same phenomenon viewed from different angles: **the transition from interpretation to compilation**. Every measured improvement in this system — and every corresponding improvement described in external research — moves an operation rightward on a single gradient:

```
Level 1          Level 2              Level 3              Level 4
Full             Cached               Compiled             Latent
Interpretation   Interpretation       Routing              Compilation
────────────────────────────────────────────────────────────────────►
46.7 ops         ~20 ops (predicted)  10.5 ops (measured)  ? (SoftSkill: +42pp)
```

Each transition eliminates a category of cost that the previous level must pay every time.

## The Transition Mechanisms

### Level 1 → Level 2: Input-Change Detection
- **Mechanism:** Hash inputs; skip if unchanged
- **Cost eliminated:** Re-deriving conclusions from unchanged data
- **Implementation:** `if inputHash == lastInputHash: return cachedVerdict`
- **Predicted savings:** 40-55% of evaluator ops (KE-074 estimate)

### Level 2 → Level 3: Structural Compilation
- **Mechanism:** Encode decision as a structural check, not LLM reasoning
- **Cost eliminated:** LLM inference on deterministic decisions
- **Implementation:** ToolPro's profile-driven policy; our planner gate's pre-computed state read
- **Measured savings:** 4.4× (46.7 → 10.5 ops in production)

### Level 3 → Level 4: Latent Compilation
- **Mechanism:** Compress repeated behavioral intent into learned representations
- **Cost eliminated:** Token-level processing of stable context
- **Implementation:** SoftSkill's 32-token trained prefixes; BabelTele's 3.6× compression
- **Predicted savings:** +42pp quality OR 3.6× context reduction (depends on axis optimized)

## The XHS Self-Evolution Collapse Explained

The self-evolution papers (XHS 190❤, arXiv 2606.04703) show multi-round improvement collapses after 3 rounds. The compilation gradient explains why:

1. Round 1: Agent discovers a better approach (Level 1 interpretation produces insight)
2. Round 2: Agent re-interprets its own insight, partially retaining it (L1 → marginal L2)  
3. Round 3+: Each re-interpretation LOSES information because text-to-text transfer has <100% fidelity

The fix (principle-level experience + step-wise injection from the paper) IS compilation: extract the principle, encode it structurally, inject it as a fixed prefix rather than re-interpreting the full exploration trace. They discovered L2→L3 empirically without naming it.

## The Architectural Prescription

For our system, the compilation gradient prescribes a specific investment order:

| Current Operation | Current Level | Next Level | Implementation |
|:-----------------|:---:|:---:|:---------------|
| Evaluator alert re-derivation | L1 | L2 | `verdict_cache[alertId + valueHash]` |
| Evaluator heartbeat coverage check | L1 | L3 | Structural: `if sessions_in_window == 0: skip` |
| Agent context loading (95.9% boilerplate) | L1 | L3/L4 | BabelTele-compress stable portion |
| Planner "is there work?" | L3 (gate) | L3 | Already compiled — leave alone |
| Worker task execution | L1 | L1 | Must stay L1 — novel reasoning required |

The key insight: **not everything should compile.** Worker task bodies are inherently Level 1 (novel problems requiring LLM reasoning). The pathology is that governance/evaluation/routing operations — which are *deterministic* given their inputs — are ALSO at Level 1.
