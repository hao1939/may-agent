# KE-076: The Accidental State Architecture

**Created:** 2026-06-20 (creative heartbeat — cross-domain synthesis)  
**Confidence:** High — three independent evidence streams converge  
**Sources:** arXiv State Architecture Turn (2026-08-23 triage, 5 papers), XHS scan #52 (2026-08-23), live aks-rp-e2e task-tree data, 14-day system telemetry

## Core Discovery: The System Contains Both Sides of a Controlled Experiment

The aks-rp-e2e project accidentally implemented what five June 2026 arXiv papers prescribe (LedgerAgent, OpenRath, ToolPro, BabelTele, SoftSkill) — while the monitoring layer did not. The cost difference between these two paths IS the empirical measurement that the papers' benchmarks cannot provide: a long-running, production-grade, multi-week demonstration of explicit-state vs. implicit-state architecture under identical model, tooling, and infrastructure conditions.

### The Evidence

| Property | aks-rp-e2e Planner (explicit state) | Evaluator Heartbeat (implicit state) |
|:---------|:-------------------------------------|:--------------------------------------|
| State access | Reads `task-tree packet` (typed JSON, 147 nodes, pre-computed frontier) | Re-derives from metric snapshots + alert table + KE references |
| Avg ops/session | **10.5** | **29.8–66.8** (varies with dormancy) |
| Gate rate | **49.4%** (dormancy-immune, σ = 1.3%) | **0–1.6%** (almost never gates) |
| Dormancy response | +51% cost spike after 18h idle (from 5.7 to 8.6) | +93% cost spike (from 25.5 to 49.3) |
| Cost trajectory over 14 days | **Declining** (stateless sessions, each reads fresh state) | **Rising** (context accumulation, guardrail growth) |
| Improvement mechanism | External state updates → immediately visible | Text instructions → decay with repetition |

**The ratio**: evaluator heartbeat costs **2.8–6.4×** more per session than the planner, despite the planner managing a MORE complex domain (147 tasks across 83 verification paths).

### Why This Is a Controlled Experiment

Both workflows:
- Run on the same infrastructure
- Use the same underlying model family
- Are dispatched by the same runtime
- Have access to the same tools
- Started at approximately the same time

The ONLY structural difference: the planner reads a **pre-computed, typed, externalized state register** (the task-tree packet). The evaluator re-derives state from **raw, distributed observations** (metrics table, alert records, session history, KE references in context).

This is what LedgerAgent (2606.20529) prescribes: "maintain observed task states in a separate ledger rendered into the prompt... eliminates two failure classes simultaneously."

### The Three-Source Convergence

**1. arXiv (June 2026): The prescription**

| Paper | What It Proposes | What Our System Already Has |
|:------|:-----------------|:----------------------------|
| LedgerAgent | External ledger with policy-constraint checking | Task tree with blocker/acceptance fields |
| OpenRath | Session as first-class branchable runtime value | Task trace with attempt history, branch lineage |
| ToolPro | Compile deterministic tool sequences into programs | Planner gate (deterministic "nothing runnable" exit) |
| BabelTele | Model-native compressed representations | Compact task-tree packet (JSON, not prose) |
| SoftSkill | Behavioral compression into latent prefixes | Fixed packet format → fixed response patterns |

The project planner independently evolved 4/5 of these patterns because the problem (managing 147+ tasks across weeks of execution) forced explicit state externalization.

**2. XHS (scan #52): The community names the gap**

任川 (243❤): "新词只负责标出瓶颈的位置。瓶颈迁移的终点，是只给系统一个目标。"  
(New terms only mark where the bottleneck is. The endpoint of bottleneck migration is: just give the system one goal.)

The XHS paradigm naming sequence (Context → Skill → Harness → Loop → Eval Engineering) is the community discovering, through naming, that **each "paradigm" is a bottleneck pointer that resolves into the same structural fix**: externalize the thing you're currently re-computing.

- Context Engineering = externalize knowledge retrieval
- Skill Engineering = externalize procedure encoding  
- Harness Engineering = externalize governance
- Loop Engineering = externalize iteration control
- Eval Engineering = externalize quality judgment state

**3. Live system (14-day telemetry): The empirical proof**

KE-064/066/068/070 independently measured the production/monitoring divergence from different angles. KE-076 identifies the **unifying cause**: production converges because it reads explicit state. Monitoring diverges because it re-derives implicit state. The cost gap grows with time because explicit state is dormancy-immune while implicit state's reconstruction cost is proportional to elapsed time × possibility space.

### The Novel Contribution: Why Accidents Beat Papers

The task tree was NOT designed as a "State Architecture Turn" implementation. It was designed as a project management tool. The state externalization happened because:

1. **The domain forced it**: 147 tasks cannot be managed by re-reading all task descriptions each session
2. **The runtime forced it**: the `task-tree packet` command exists because the full tree.json exceeds context limits
3. **The lifecycle forced it**: tasks blocked for 7+ days with exact resume conditions MUST be externalized or the planner re-derives "why is this blocked?" every wake

This suggests the State Architecture Turn is not a design choice but an **inevitable consequence of scale × time**. Any system that manages >50 concurrent entities across >7 days will independently develop explicit state registers — or fail.

The monitoring layer hasn't hit this threshold because:
- It manages ~5 metrics, not 147 tasks
- Each metric is "simple" (one number, one threshold)
- The failure mode (excessive ops) is tolerable, not catastrophic

But the COST of not externalizing is cumulative: KE-059 documented the evaluator's guardrail tax growing from 0 to 18-24 ops. KE-070 showed post-dormancy spikes reaching 49.3 ops. KE-066 showed the trajectory is divergent, not stable. Eventually the monitoring layer will hit the same threshold — but because its failure mode is waste rather than breakage, it will continue paying the reconstruction tax indefinitely.

### The Design Implication

> **Explicit state externalization is not a feature — it's a phase transition that happens when (entity count × lifecycle duration) exceeds a system-specific threshold. Below the threshold, re-derivation works. Above it, re-derivation diverges. The threshold is lower than most designers assume.**

For our system: the evaluator's 5 metrics × 30+ days of history already exceeds the threshold. The evidence: KE-070's reconstruction tax grows with time, which means the system is past its threshold and accumulating debt.

### The One-Line Fix (From arXiv to Implementation)

Following LedgerAgent's architecture:

```
evaluator_state_register = {
  alerts: { id, value, last_changed_at, conclusion, concluded_at },
  metrics: { id, current, last_changed_at },
  last_heartbeat_at: timestamp
}

// At heartbeat start:
if (no alert.value changed since last_heartbeat_at) → gate exit (2 ops)
// else → full investigation (current path)
```

This is KE-074's "input-change detection" applied through KE-068's "demodulation" using the architecture that arXiv's LedgerAgent formalized and that our own task-tree planner accidentally demonstrates works.
