# KE-044: The Dark Metabolism — Quantifying the Sub-Session Event Loop

**Discovered:** 2026-06-19 | **Status:** Active

---

## The Layer Nobody Measured

Every KE entry from 001 to 043 analyzes the system at the **session layer**: how many sessions, how many ops, which agent, what cost. This is like measuring an organism's health by counting its conscious decisions while ignoring its heartbeat, respiration, and immune surveillance.

The system has a sub-session metabolism — an infrastructure event loop — that is quantitatively larger than all agent work combined.

## The Numbers

From the last 14 hours of production data:

| Layer | Volume | Rate | % of total activity |
|:-----:|:------:|:----:|:-------------------:|
| **Infrastructure events** | 7,332 | ~524/hr | **100%** (denominator) |
| Handler fires | 1,474 | ~105/hr | 20.1% |
| Handler skips | 938 | ~67/hr | 12.8% |
| Handler completions | 1,500 | ~107/hr | 20.5% |
| Daemon heartbeats | 828 | ~59/hr | 11.3% |
| **Agent sessions** | 151 | ~10.8/hr | 2.1% |
| **Agent ops** | 5,645 | ~403/hr | — |

The infrastructure produces **48.6 events per agent session**. Every conscious decision by an agent is scaffolded by 48 infrastructure events that fire, evaluate, and mostly do nothing.

## The Clock That Doesn't Stop

The most revealing finding: the infrastructure event rate is **independent of agent activity**.

| Period | Production Sessions | Infrastructure Events/hr | Agent Sessions/hr |
|:------:|:-------------------:|:------------------------:|:-----------------:|
| Hours 0–12 (idle) | 0 | 482 | 7.5 |
| Hour 13 (burst) | 18 | 887 | 33 |
| Hour 14 (partial) | 13 | ~580* | ~34* |

During 12 hours of zero production work, the infrastructure generated **5,784 events** — the same 482/hr it generates when agents are active. When production resumed at hour 13, the infrastructure added ~400 events for the new sessions on top of its existing ~480 base. The base never changed.

## The Skip Cascade

The single most common infrastructure activity is **skipping**:

- **938 handler.skipped events** in 14 hours (67/hr)
- **922** of these have the identical reason: `"session.completed is not recoverable"`
- Each skip involves: event creation → condition evaluation → JSON serialization → DB write → skip decision → skip event creation → DB write

The system processes 922 "nothing to do" decisions through a full event pipeline. This is the infrastructure equivalent of KE-027's Sisyphean Triage — but at a layer below sessions, invisible to all prior analysis.

## Connection to External Research

### Concurrency Anomalies (2606.17182)

The formal paper classifies multi-agent runtimes into isolation levels L0–L4. Our system operates at **L0**: events fire on clock schedules, not on state changes. The handler loop checks conditions at a fixed cadence regardless of whether anything changed since the last check. This is exactly the "stale-generation" anomaly — every handler fire reads state and discovers it hasn't changed, producing a skip event for the same reason as 60 seconds ago.

An L1 system would fire handlers **only when relevant state changes**, eliminating the entire skip cascade. The 922 identical skip events would reduce to zero because no handler would fire until `session.completed` had a recovery path.

### TokenPilot (2606.17016)

TokenPilot's key insight is that text pruning to save tokens can *break prompt cache continuity*, making savings net-negative. The same principle applies here: the handler loop's skip events consume infrastructure resources (CPU, DB writes, event table growth) to "save" agent sessions. But the infrastructure cost of 67 skips/hour may exceed the cost of the sessions it prevents.

### Trust Dynamics (2606.14923)

The trust paper found that **over-verification costs more than it saves** — persistent checking of a reliable teammate reduces payoffs. The handler loop over-verifies system state: checking 100+ times/hour whether conditions exist for new sessions, when conditions change at most ~10 times/hour. The verification frequency is 10× the state-change frequency.

## The Design Principle

> **A clock-driven event loop on an event-driven system is a category error.
> The infrastructure fires at its own cadence, not at the cadence of change.
> The cost of checking whether to work exceeds the cost of work itself.**

This inverts the traditional optimization focus. Prior KE entries asked "how can sessions be cheaper?" The bigger question is "how can the infrastructure avoid firing when nothing has changed?"

## Quantifying the Opportunity

If the handler loop fired only on state changes (L1 isolation):
- **922 skip events → 0** (67/hr saved)
- **828 daemon heartbeats → demand-driven** (59/hr → ~10/hr on state change)
- **~400 evaluation.tick + project.watchdog.tick → on-change** (165+163 → ~20 on actual session completion)

Conservative estimate: **60–70% reduction in event volume** (7,332 → ~2,500/14h) with zero impact on agent behavior, because agent sessions are triggered by the remaining 30% of events that carry actual information.

## Falsifiable Predictions

1. **Event rate during extended idle stays at 480±20/hr** — the dark metabolism is purely clock-driven and will not self-adjust
2. **Handler.skipped count will reach 1,600+ in the next 24 hours** at current ~67/hr rate
3. **Switching metric-alert-reactor to event-driven (fire only on metric.breach, not on clock) would eliminate >900 skip events/day** without affecting triage quality
4. **Event table growth rate is dominated by infrastructure events, not agent activity** — removing daemon heartbeats and handler skips would reduce event table size by >50%

## The Meta-Observation

KE-039 found the library has a pessimism bias — it predicts stasis where recovery occurs. KE-040 identified this as Constraint-Evasive Fabrication. KE-044 makes a different kind of claim: it describes an **infrastructure invariant**, not an agent behavioral prediction. Infrastructure predictions succeed at 86% (KE-039). The clock doesn't change its mind.

The dark metabolism is not a pathology — it's a design choice. The system was built to poll. Polling works. But the cost of polling is now measurable: **97.9% of the system's event-level activity produces no agent work.** Whether that cost matters depends on whether infrastructure events are cheap. If each event costs ~0.001 of an op in CPU/IO, the dark metabolism costs ~7.3 ops/14h — negligible. If each event costs ~0.1 of an op (DB write + JSON serialization + condition evaluation), it costs ~733 ops/14h — 13% of agent work, hidden.

The answer isn't in the KE library. It's in the infrastructure profiler.
