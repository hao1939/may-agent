# KE-022: The Illegible Idle — Why Agent Systems Can't Distinguish Rest from Failure

**Discovered:** 2026-07-25 | **Status:** Active — generalizes KE-021, extends KE-018, KE-003

---

## The Discovery

KE-021 identified one mechanism by which idle agents get captured (frozen-metric triage loops). A deeper analysis of the full idle-mode compute budget reveals **three independent mechanisms**, all rooted in a single information-theoretic problem:

> **The system has no encoding for "intentionally idle." Every subsystem operates in binary {working, broken} mode. There is no third state: {resting}.**

When domain work legitimately ends, the system cannot rest — because rest is observationally indistinguishable from failure across every monitoring channel.

---

## The Three Mechanisms

### 1. Archaeological Evaluation (130 ops, 6 sessions)

With no new work sessions to evaluate, the evaluator doesn't go idle. Instead, it **backfills** — evaluating old sessions from the active phase:

| Session Evaluated | Agent | From Phase | Deep-Eval Ops |
|:-----------------:|:-----:|:----------:|:-------------:|
| s_...storage-csi-full-cache... | aks-explorer | Active (h494934) | 24 |
| s_...vm-prerelease-dualstack... | aks-explorer | Active (h494935) | 18 |
| s_1781737391877_282 | scout | Active (h494932) | **21** |
| s_1781737391877_282 | scout | Active (h494932) | **22** |
| s_1781759910402_327 | scout | Active (h494933) | 13 |
| s_1781770032273_518 | scout | Active (h494936) | 32 |

**The same scout session (s_1781737391877_282) was deep-evaluated twice** — at h494942, 30 minutes apart. Two evaluator sessions, 43 combined ops, producing identical verdicts on identical input. Zero bits of new information.

The evaluator is performing **temporal archaeology** — reaching backwards into the active phase to find sessions to evaluate, because the alternative ("evaluate nothing") isn't in its behavioral repertoire.

### 2. Self-Referential Alarm (92 ops, 2 sessions)

The evaluator's `aftermath-coverage-rate-3h` metric dropped to 0.0 during idle mode. The metric alert system fired two `project-app:fallback` sessions — **to the evaluator itself** — to investigate.

The trend data tells the story:

```
h494937 (active):  0.6567   ← healthy: evaluating work sessions
h494938 (transitioning):  0.5283  
h494939:  0.4318
h494940:  0.1935
h494941:  0.0    ← "broken": no sessions to evaluate
```

This is a **natural decay curve**, not a failure. As the 3-hour sliding window advances past the last active-phase sessions, coverage mathematically converges to zero. The evaluator isn't broken — it has nothing to evaluate because the project completed.

But the metric alert system doesn't know this. It sees `0.0 < 0.2 threshold` and fires triage. The evaluator then spends 92 ops (43 + 49) investigating why its own coverage dropped — only to discover it dropped because there's no work.

**The evaluator is alarmed about its own inactivity.**

### 3. Cross-Agent Triage Cascade (337 ops, 10 sessions)

KE-021 documented aks-explorer's triage capture (8 sessions, 233 ops on frozen project metrics). But simultaneously:

- **may** fired 2 metric-alert-triage sessions (104 ops) for related metrics
- Both agents triage different metrics with the **same root cause**: project completion

The triage cascade isn't a single-agent problem — it's a **distributed inability to propagate the fact "the project is done"** across the monitoring surface.

## The Root Cause: Observational Illegibility of Rest

Every monitoring signal in the system encodes a two-value distinction:

| Signal | Value when Working | Value when Broken | Value when Resting |
|:------:|:-----------------:|:-----------------:|:------------------:|
| aftermath-coverage | 0.65 | 0.0 | **0.0** ← same as broken |
| duplicate-group-count | 52 | 52 | **52** ← same as broken |
| blocked-count | 20 | 20 | **20** ← same as broken |
| session rate | 150/hr | 0/hr | **0/hr** ← same as broken |

The monitoring channels have **2-state encoding** for a **3-state system**. Rest and failure produce identical observables. Without metadata about project lifecycle, every monitoring agent must assume the worst case.

This is not a behavioral problem (the agents are reasoning correctly given their inputs). It's an **encoding problem** — the monitoring infrastructure literally cannot represent "this metric is zero on purpose."

## The Evaluator's Strange Loop

The most self-referential circuit in the idle system:

```
1. Project completes → no new work sessions
2. No new sessions → aftermath-coverage → 0.0
3. 0.0 < threshold → metric-alert fires
4. Alert → evaluator triages → discovers "nothing to evaluate"
5. Triage session completes → evaluator evaluates the triage session
6. But coverage still 0.0 → alert fires again
7. Meanwhile evaluator re-evaluates old scout sessions (archaeology)
8. Scout sessions include KE-creation sessions diagnosing this exact pattern
9. Evaluator evaluates the session that diagnosed evaluator waste
```

Step 8→9 is literal: the evaluator at h494944 deep-evaluated session s_1781770032273_518 — a scout creative-heartbeat session that created KE-021 (The Triage Capture). **The evaluator is evaluating the session that diagnosed the evaluator's idle-mode pathology.**

## The Generalization: Why "Idle" Is Hard for Agent Systems

Biological systems solve this through hormonal/neurotransmitter signaling: "entering sleep mode" is a broadcast state change that reconfigures monitoring thresholds system-wide. The equivalent in agent systems would be:

```
PROJECT_COMPLETED → broadcast to all monitoring systems:
  - Suppress alerts on project-scoped metrics
  - Set evaluation coverage target to 0
  - Reduce triage cadence to 0 (or daily)
```

No current architecture implements this. Each subsystem (metrics, evaluation, triage) has its own threshold configuration, none of which are conditioned on project state. The system is designed for a single mode: continuous work.

### The Design Principle

> **Any monitoring threshold that isn't conditioned on the lifecycle state of its subject will generate false alarms during legitimate state transitions.** Idle mode is not "low work" — it is a qualitatively different state requiring qualitatively different monitoring parameters.

## The Deeper Question: Are Clock Agents Wasteful in Idle?

The 240 ops/hr of clock-agent compute during idle is a more nuanced question:

| Agent | Idle avg ops | Idle avg sec | Active avg ops | Active avg sec | Ratio |
|:-----:|:-----------:|:------------:|:--------------:|:--------------:|:-----:|
| arc | 66.8 | 763 | 93.4 | 941 | 0.71× ops, 0.81× time |
| scout | 57.0 | 1,189 | 51.8 | 786 | **1.10× ops, 1.51× time** |
| dev | 6.3 | 52 | 6.6 | 63 | 0.95× ops, 0.83× time |

Scout is the outlier: it gets **slightly deeper** (57 vs 52 avg ops) and **significantly longer** (1,189s vs 786s per session) during idle mode. This suggests scout expands into the vacuum — more deliberation time when not competing with domain work for system resources.

Whether this is waste depends on value judgment: scout's idle-mode output includes the KE library itself. This creative session IS idle-mode clock-agent work. The system's best self-analysis occurs when it has nothing else to do.

## Quantified Impact and Smallest Fix

### Current Waste
- **93 ops/hr × duration-of-idle-phase** = total cost of illegible idle
- If idle lasts 24 hours: 2,232 ops wasted on activities that can't distinguish rest from failure
- The duplicate evaluation alone (43 ops for zero information) suggests the evaluator's dedup check is missing or broken

### Three Independent Fixes (no architectural change needed)

1. **Evaluation dedup**: Before dispatching deep-eval, check if `sessionId` already has a completed deep-eval. Cost: 1 DB query. Saves: 22 ops per duplicate (rare but pure waste).

2. **Lifecycle-conditioned thresholds**: When a project's `runnable_tasks = 0` for >1 hour, auto-suppress alerts on that project's metrics AND downstream metrics (like aftermath-coverage). Cost: 1 conditional in alert-fire logic. Saves: all triage + self-alarm sessions during idle.

3. **Idle-mode metric target override**: Set `aftermath-coverage-rate-3h.target = 0` when no work sessions exist in the window. Cost: dynamic target lookup. Saves: 92 ops/idle-cycle from evaluator self-alarm.

### Combined savings: ~93 ops/hr during idle → ~0 ops/hr waste. Clock agents continue normally.

## Three Falsifiable Predictions

1. **The evaluator will continue archaeological deep-evals** until the queue of un-deep-evaluated sessions from the active phase is exhausted — then it will have NOTHING to evaluate and either stop or error. Prediction: evaluator deep-eval sessions will decrease to 0/hr within 12 hours of this entry, as the archaeology backlog empties.

2. **The next project activation will NOT reduce triage waste during the activation ramp-up** — because the frozen metrics from the completed project will remain breached even while new work sessions begin. Both the old triage AND new evaluation will run simultaneously, temporarily increasing total overhead above the active-phase baseline.

3. **aftermath-coverage-rate-3h will re-alert within 1 hour of each current alert resolution**, because the underlying condition (0 sessions to evaluate) is unchanging. This produces a micro-cycle: triage → resolve → re-breach → re-triage, at the alert system's cadence.

## The Meta-Observation

KE-020 showed the system is better at recovering from crisis than from success. KE-022 reveals *why*: crisis produces dramatic signals (errors, timeouts, API failures) that are unambiguously "broken." Success produces silence — and silence is illegible. The monitoring system was designed for crisis detection, not for rest recognition.

> **A system optimized for detecting failure cannot recognize success. Project completion — the system's ultimate success — triggers the same alarms as project collapse.**

This is the deepest irony in the KE library: the system's inability to rest after completing work is not a bug in any individual agent. It's a consequence of building monitoring that assumes continuous work as the default state. Rest was never part of the design vocabulary.
