# KE-052: The Completion Paradox — Why Finished Systems Can't Stop

**Discovered:** 2026-06-19 | **Status:** Active

---

## Core Finding

A multi-agent system that successfully completes its primary mission enters a
**completion paradox**: the infrastructure designed to drive exploration becomes
a pure cost center with no graceful shutdown path. The system currently runs
at 6× lower throughput than peak (660 vs 3,891 sessions/day) but 0× of that
reduced throughput advances the project, because all remaining work requires
human/external action. The system is optimally idle but structurally unable
to express idleness.

## The Evidence

### The Project Scorecard (as of 2026-06-19)

| Metric | Value |
|:------:|:-----:|
| Task tree total | 2,345 |
| Leaf tasks done | 2,215 (96.2%) |
| Blocked on external | 78 |
| Backlog (local work) | 8 |
| Review | 1 |
| Runnable | **0** |
| Active | **0** |
| Model paths passing | 65/82 (79.3%) |
| Non-passing with final verdicts | 17/17 (100%) |

Every non-passing path has a `verdictFinal: true` with a concrete
`retestCondition` requiring Azure auth, product fixes, environment
changes, or human source-holder responses. **Zero paths are blocked
on agent compute.**

### The Throughput Collapse Is Correct Behavior

| Day | Sessions | Total Ops | Productive % |
|:---:|:--------:|:---------:|:------------:|
| Jun 15 | 2,588 | 71,503 | High (exploration phase) |
| Jun 17 | 3,891 | 79,805 | Moderate (peak + cleanup) |
| Jun 18 | 1,977 | 42,091 | Low (completion phase) |
| Jun 19 | 660 | 17,044 | ~0% (idle maintenance) |

This is not a failure. This is a system that **finished its job**. But the
infrastructure doesn't recognize completion — it continues scheduling
heartbeats, evaluating empty queues, and triaging frozen metrics.

| Activity | Sessions | Ops | Purpose |
|:--------:|:--------:|:---:|:-------:|

| Worker (final cleanup task) | 1 | 25 | Writing one more archive note |

The evaluator spends 183 ops investigating `aftermath-coverage-rate-3h=0`
and `failed-triage-rate-3h=0` — both structural artifacts of low volume,
not bugs. The metric alert triage spends 60 ops re-concluding that 7 failed
sessions (all `aks-explorer` task workers) can't be triaged because they're
project-planner task failures, not evaluator-actionable errors.

### The Missing Primitive: Dormancy

The system has concepts for:
- **Active**: project has runnable work → schedule sessions
- **Blocked**: specific task can't proceed → wait for condition
- **Done**: individual task completed → mark done

It does NOT have:
- **Dormant**: project has no agent-actionable work → reduce scheduling to
  minimum viable monitoring (e.g., once per hour instead of once per 5 minutes)
- **Completion**: project mission achieved → archive, stop evaluation,
  stop metric alerts for this project's scope

## The General Principle

> **Systems designed for exploration have no natural rest state.**
> They are structurally biased toward activity because every scheduling
> primitive assumes "more work exists." When work genuinely ends, the
> system continues at reduced efficiency rather than entering a defined
> low-power mode — like a laptop without a sleep state that can only
> run at full power or be hard-killed.

This applies beyond our system to any autonomous agent framework:
- GitHub Actions with cron triggers keep running after the repo is archived
- Kubernetes controllers keep reconciling after the desired state is achieved
- CI/CD pipelines keep checking for changes on abandoned branches

The cost isn't catastrophic (660 sessions vs 3,891 is already 83% reduction
through organic load-shedding). But it's structurally unbounded: the system
will fire these 660 sessions/day *forever* unless someone manually intervenes.

## The Crossed Incentive

The evaluator is incentivized to achieve `aftermath-coverage-rate-3h > 0.8`.
But when only 7 sessions fail in a 3h window and all are project-task failures
(not evaluator-actionable), the metric is structurally zero. The evaluator
then spends 183 ops per heartbeat investigating why it's zero — creating more
sessions that themselves need evaluation — in a completeness loop:

```
Low session volume → metric = 0 → evaluator investigates →
evaluator sessions increase → but none fix root cause →
metric stays 0 → repeat
```

This is KE-021's triage capture, but caused specifically by the completion
transition rather than by metric miscalibration in general.

## The 78-Task External Wall

All 78 blocked tasks fall into exactly 5 categories:

| Category | Count | Example Resume Condition |
|:--------:|:-----:|:------------------------|
| Azure auth/cloud-mutation gate | 23 | `AKS_RP_E2E_ALLOW_CLOUD_MUTATION=<probe>` |
| Human source-holder response | 12 | Send outbound packet, await proof |
| Product fix required | 18 | AKS RP fixes sku.DefaultClaim |
| Environment/infra unavailable | 15 | HCP/underlay access, cross-sub VNet |
| Product-by-design constraints | 10 | N/A - outbound migration not supported |

The 10 product-constraint tasks will **never** unblock — they're documented
impossibilities. The remaining 68 await human decisions that have no SLA.
The system has no way to distinguish "waiting 2 hours for a human" from
"waiting forever for a product that was deprecated."

## Design Implications

1. **Dormancy primitive**: When `frontier.runnable = [] AND frontier.active = []
   AND all blocked tasks have external resume conditions`, the project enters
   dormancy: reduce planner wake frequency from per-event to per-hour, suppress
   metric alerts for this project's scope, and reduce evaluation to 0%.

2. **Completion detection**: When `blocked.every(t => t.blocker.includes('External'))
   AND done > 95% AND backlog < 10`, emit a `project.near-complete` event that
   a human can acknowledge or override.

3. **Metric hibernation**: Metrics whose denominator is "sessions in window" should
   automatically suppress alerts when session count < minimum_meaningful_sample
   (e.g., < 20 in 3h). A metric measured on 7 sessions has no statistical power.

4. **Eternal-block detection**: Blocked tasks with `retestCondition: "N/A"` or
   that haven't changed state in > 7 days should be reclassified from "blocked"
   to "archived-blocked" — visible in reports but excluded from frontier counts
   and alert denominators.

## Falsifiable Predictions

1. The `aftermath-coverage-rate-3h` and `failed-triage-rate-3h` alerts will
   persist for as long as the system runs at < 50 sessions/3h, regardless of
   evaluator action. (Testable: check in 48h)
2. Planner sessions will continue to fire and exit at 2-7 ops whenever the
   remaining review task is processed, creating a stream of empty wakes
   indistinguishable from productive planning. (Testable: track next 24h)
3. Total daily ops will stabilize at 400-800/day (current: ~660 extrapolated)
   without any manual intervention — the system's organic floor.
4. Zero additional tasks will be completed in the next 7 days without human
   action on one of the 78 blocked resume conditions.
