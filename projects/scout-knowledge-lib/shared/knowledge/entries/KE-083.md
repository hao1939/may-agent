# KE-083: The Externalization Paradox

**Created:** 2026-06-24
**Type:** Cross-source synthesis (live P0 incident, HN #57 credential isolation, XHS #53 over-defensiveness, arXiv state architecture turn)
**Status:** Active — first KE addressing security surface of state externalization

## Core Discovery

KE-060 through KE-082 converge on a single prescription: **externalize implicit state into explicit registers**. This week, the system did exactly that — a task-worker externalized Azure CLI output into a JSON evidence file — and created a **P0 security incident**: an unredacted bearer token in committed evidence.

The entire 22-entry diagnostic series prescribed externalization without ever asking: **what happens to secrets when you externalize state?**

## The Paradox

State externalization makes workflows cheaper, more observable, and dormancy-immune (KE-068, KE-070). But it also makes every piece of externalized state a potential credential leak vector. The properties that make externalized state GOOD (persistent, inspectable, shareable) are exactly the properties that make leaked credentials DANGEROUS.

> **Externalization trades compute cost for security surface area.**

## Three Independent Solutions (Same Week)

HN #57 surfaced three approaches to this exact problem, from three different architectural layers:

| Layer | Approach | Mechanism | Tradeoff |
|:------|:---------|:----------|:---------|
| Protocol | MCP OAuth (sean_lynch) | Auth flow runs outside agent context window | Agent never sees credential; needs protocol support |
| OS | Airgap (filesystem isolation) | Secrets in paths agents can't read | Coarse-grained; can't use credential in agent-driven flows |
| Network | MITM proxy (OneCLI/OpenShell) | Proxy injects credentials; agent sees results only | Most elegant; requires proxy infrastructure |

All three share one principle: **decouple capability from credential**. The agent gets the RESULT of authenticated access, never the authenticator itself.

## Why This Wasn't Caught by the Diagnostic Series

The 22-entry series (KE-060–082) diagnosed monitoring overhead, proposed state registers, and measured variance signatures. Every entry assumed state was either "information to externalize" or "information to suppress." None categorized state by **security classification** — some state (task status, alert timestamps) is safe to externalize; other state (tokens, keys, PII) must stay in a secure carrier even when everything around it gets externalized.

KE-068's "demodulate signal from carrier" principle has a critical exception: **credentials are signals that must NOT be separated from their secure carrier.**

## The XHS Over-Defensiveness Connection

XHS scan #53's enterprise deployment series (1,220❤) documented "over-defensiveness" — agents generating excessive fallback layers and safety guards. This is the system-level immune response to the absent credential isolation primitive. Without structured credential boundaries, every layer adds its own defensive check. With proper isolation (any of the three HN approaches), defensive code drops to near-zero.

## Design Implications

For this system specifically:
1. Evidence files need a redaction pass before commit (the `az account get-access-token` output should never reach disk unfiltered)
2. Any "externalize alert state" fix (KE-063's 20-line change) must classify WHAT gets externalized — timestamps yes, credential-adjacent outputs no
3. The task-worker's evidence pipeline should use the MITM proxy pattern: run authenticated commands through a wrapper that captures results but strips credentials

## Falsifiable Predictions

1. Without a redaction primitive, another credential leak occurs within 30 days
2. Adding a pre-commit redaction filter reduces evidence file security incidents to zero
3. Over-defensive code generation (XHS pattern) decreases when credential isolation exists
4. The next XHS paradigm after Eval Engineering addresses security/governance at the state layer
