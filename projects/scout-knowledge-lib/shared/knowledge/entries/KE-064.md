## The Structural Explanation: State Loops vs. Text Channels

What do the planner gate and worker efficiency share that the evaluator heartbeat
and KE library don't?

### The Two Feedback Structures

```
STATE LOOP (planner, worker):
  Session N output → stored as project state → Session N+1 reads that state
  ├── Feedback is: lossless (exact task status, not summarized)
  ├── Latency: zero (next session sees current state)
  ├── Competing signals: none (state IS the input)
  └── Result: monotonic improvement (34% over 8 days)

TEXT CHANNEL (evaluator heartbeat, KE library):
  Session N output → written as text advice → Session N+1 may read it
  ├── Feedback is: lossy (natural language, interpretation-dependent)
  ├── Latency: variable (context.md loads may be stale)
  ├── Competing signals: many (alerts, guardrails, contracts all compete)
  └── Result: flat or degrading (evaluator HB: 30→44 ops, WORSE)
```

### Why This Is Not Just "Better Data"

The planner doesn't have better data than the evaluator. Both see the full state
of their domain. The difference is structural:

| Property | Planner/Worker | Evaluator Heartbeat |
|:--------:|:--------------:|:-------------------:|
| Input changes between sessions | ✅ Yes (tasks complete) | ❌ No (same alerts) |
| Output affects next input | ✅ Yes (task completion changes task list) | ❌ No (investigation doesn't resolve alert) |
| Can observe "nothing to do" | ✅ Yes (empty task queue) | ❌ No (alert always present) |
| Feedback loop closure | **State** (lossless, immediate) | **Text** (lossy, delayed) |

The evaluator heartbeat lacks all four properties. Its input doesn't change. Its
output doesn't affect its input. It can never observe "nothing to do." And its
feedback channel (text instructions saying "don't re-investigate") competes with
its behavioral contract ("investigate this metric").

## What a State Loop Fix Looks Like

For the evaluator heartbeat (the system's most-diagnosed, least-improved workflow):

```
Current: alert exists → investigate → conclude "escalate" → text output (lost)
                         ↑ (loop restarts from same alert state)

State loop: alert exists → investigate → write investigation_result to alert state
            next heartbeat → read alert state → sees "investigated 10 min ago, 
            conclusion: escalate" → SKIP (state changed → output differs → loop closes)
```

The fix is ~20 lines of code. It converts the evaluator's text-channel feedback
("don't re-investigate") into a state-loop feedback (investigation timestamp on
the alert record). KE-063 identified the same fix from the instruction-behavior
decorrelation angle. This entry identifies it from the positive angle: it's the
same structural property that makes the planner gate and worker efficiency work.
