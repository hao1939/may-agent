## The Non-Obvious Inversion: Zero-Ops Failure Is the Optimal Architecture

Fresh 24h production data reveals a pattern that inverts how the system's health should be read:

| Workflow | Zero-Ops Rate | Avg Ops (non-zero) | Error Rate | Interpretation |
|:---------|:-------------:|:------------------:|:----------:|:---------------|
| problem-solver | **52.6%** | 32.1 | 52.6% | Fails fast when preconditions unmet |
| project-planner | 8.5% | 8.0 | 1.3% | Sometimes detects no-work cheaply |
| task-worker | 0.5% | 36.1 | 2.3% | Rarely launched without work |
| evaluator-heartbeat | **0.9%** | 36.5 | 2.8% | Almost never says "nothing to do" cheaply |
| arc-heartbeat | **0%** | 69.0 | 2.2% | NEVER fails cheaply |
| scout-heartbeat | **0%** | 43.6 | 0% | NEVER fails cheaply |

**The inversion:** We categorize the problem-solver's 52.6% zero-ops rate as a pathology. But compare: when a problem-solver CAN'T proceed, it fails in 0 ops ($0 cost). When an arc-heartbeat has nothing to do, it runs 69 ops to conclude "no changes" (~$0.35). The problem-solver's "failure" costs $0. The heartbeat's "success" costs $0.35 to produce zero information.

The cheapest form of abstention in the entire system is already happening — it's just labeled as an error instead of a feature.

## What Three Papers Prescribe

### ToolPro (2606.19992): Profile-Driven Policy

> "A profile-driven policy decides WHEN to compile a workflow into a program versus calling stepwise."

ToolPro separates the **decision to execute** from the **execution itself**. A cheap profiling step determines whether the full workflow should fire. If the profile indicates the interaction is deterministic, it compiles to a program (0 LLM calls). If not, it calls stepwise.

**Application to our system:** Before invoking an LLM heartbeat session, a deterministic check (no LLM) evaluates: "Has the input to this workflow changed since last invocation?" If no → skip. If yes → invoke.

### GIST-CMTF (2606.16813): Goal-State Validation Before Execution

> "Wrong-goal execution drops from 19.4% to 2.5% when goal state is validated before tool exposure."

GIST-CMTF proves that validating the PURPOSE of execution before beginning it eliminates 87% of wrong-goal waste.

**Application to our system:** A heartbeat session's goal is "detect and respond to state changes." If the state hasn't changed (deterministically checkable: alert timestamps, metric values, session counts), the goal is pre-satisfied. Skip.

### User as Code (2606.16707): Executable Rules on State Change

> "Rules execute deterministically on state change, enabling unsolicited alerts impossible with query-driven memory."

UaC's key architectural choice: rules fire ONLY when state changes, not on every query. The agent doesn't poll — it reacts.

**Application to our system:** Convert heartbeats from time-triggered polling to change-triggered reactions. When `metric_snapshots` updates, fire evaluator. When `sessions` shows a novel error pattern, fire arc. Between changes: nothing fires.

## The Specification (Not Diagnosis)

### What to Build

A **precondition gate** that runs before any workflow dispatch. It's a deterministic function (no LLM) that returns `{ should_launch: boolean, reason: string }`.

```
precondition_gate(workflow, agent, last_run_timestamp) → boolean

For heartbeats:
  1. Query: "Did any input to this workflow change since last_run_timestamp?"
     - evaluator-heartbeat: new sessions since last run? new metric alerts? 
     - arc-heartbeat: new events? new errors? context changes?
     - scout-heartbeat: new findings? new inbox items?
  2. If no changes detected → return false (don't launch)
  3. If changes detected → return true (launch normally)
  
For problem-solver:
  1. Query: "Is the task's precondition met?" (external blocker resolved?)
  2. If blocked → return false (don't launch, don't count as error)
  3. If unblocked → return true (launch)
```

### What This Changes

| Current | With Precondition Gate |
|:--------|:----------------------|
| 325 evaluator heartbeats @ 36.5 ops = **11,863 ops** | Est. 50-80 heartbeats (only when changes exist) @ 36.5 ops = **1,825-2,920 ops** |
| 46 arc heartbeats @ 69 ops = **3,174 ops** | Est. 5-10 arc heartbeats @ 69 ops = **345-690 ops** |
| 46 scout heartbeats @ 43.6 ops = **2,006 ops** | Est. 10-15 scout heartbeats @ 43.6 ops = **436-654 ops** |
| 10 problem-solver 0-op errors (counted as failures) | 10 precondition gates (not errors, counted as correct abstention) |
| **17,043 ops on heartbeats** | **~2,600-4,264 ops** (75-85% reduction) |

### Implementation Cost

The precondition gate requires:
1. A `last_dispatched_at` timestamp per (workflow, agent) pair — 1 DB column
2. A deterministic change-detection query per workflow type — ~5-10 lines per workflow
3. A dispatch-layer check: if `!precondition_gate(...)` → log gate, don't invoke

Total estimated: **~50 lines of code**, no LLM calls, no prompt changes.

## The XHS Connection: The Naming Singularity Is a Missing Precondition Gate

XHS scan #52 documented the paradigm naming cycle compressing to <2 weeks. 任川's insight: "新词只负责标出瓶颈的位置" (new terms only mark bottleneck location). The naming singularity is a community-level system WITHOUT a precondition gate:

- No mechanism checks "has a new bottleneck actually appeared?" before naming fires
- Each naming wave launches at full cost (2,000+ ❤ engagement, multiple response posts) regardless of novelty
- Counter-signals arriving simultaneously = the community's manual version of a precondition check (but arriving too late — after engagement cost is paid)

The pattern: **any system that dispatches work without checking preconditions will spend most of its budget on unnecessary invocations.** True at the community level (naming), the system level (heartbeats), and the paper level (wrong-goal execution).
