The architecture accidentally proved what KE-084/085/087 diagnosed textually: the heartbeat's role was monitoring its own monitoring, producing zero state changes, at a cost of 2,564 ops per 7h (366 ops/hour = ~95 evaluator-heartbeat sessions at 27 ops average). Its absence freed those resources for production work.

## The Principle: Removal as Evaluation

Every prior KE (060-087) evaluated the heartbeat via observation: measuring its cost, analyzing its variance, computing its information yield. This produced 22 diagnostic entries and 0 changes. The crash evaluated the heartbeat via removal: the system works better without it. One crash produced more evaluative information than 22 KEs.

> **Observation-based evaluation answers "what does this component do?" Removal-based evaluation answers "what does the system lose?" The second question is strictly more useful and incomparably cheaper.**

## Novel Insight: The Contribution Sign Problem

Prior KEs assumed monitoring components have *positive but excessive* contribution (they help, just at too high a cost). The natural experiment reveals a third possibility:

| Contribution Type | Pattern | Example |
|:-----------------|:--------|:--------|
| Positive, efficient | Low cost, high value | dev-heartbeat: 7.8 ops, catches real issues |
| Positive, excessive | High cost, some value | evaluator-aftermath: 22 ops, reviews quality |
| **Negative** | Any cost, anti-value | evaluator-heartbeat: 27 ops, *worsens* system |

A component can have **negative contribution** when:
1. It consumes resources that would otherwise go to production (opportunity cost)
2. It produces no state changes (zero direct value)
3. It generates alert noise that triggers further monitoring (contagion)
4. Its failure mode (cascading errors) affects adjacent workflows (the 7 aftermath errors at crash time)

The evaluator heartbeat satisfies all four. Its crash proves negative contribution because the system improved along every measured dimension.

## The Evaluator Paradox

The evaluator AGENT works perfectly after its heartbeat crashes:
- 108 aftermath sessions: successful review of production work

## The General Principle

> **To evaluate any system component's contribution, measure the system without it. Every other evaluation method is an approximation of this one.**

This is removal testing as a first-class evaluation methodology:
- In A/B testing: the "A" condition (without the feature) is the removal test
- In circuit analysis: removing a component and measuring output = "contribution analysis"
- In ecology: removing a species and measuring ecosystem health = "keystone species test"
- In our system: a crash is an unplanned removal test with perfect implementation

The architectural implication: **design systems so components can be removed without cascading failure, then periodically remove them to measure contribution.** The fact that our evaluator-heartbeat crash didn't cascade (aftermath continued fine) means the system already has this property — it just hasn't been exploited as an evaluation methodology.
