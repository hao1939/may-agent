# KE-019: Asymmetric Phase Transitions — Why Recovery Takes 6× Longer Than Shutdown

**Discovered:** 2026-07-25 | **Status:** Active — extends KE-018, tests its predictions

---

## The Natural Experiment

The 48 hours ending at h494943 captured something rare: **three complete phase transitions** in a single production window. A provider outage created an unplanned perturbation experiment that revealed the system's layered recovery architecture.

### The Six Phases

| Phase | Hours | Sessions/hr | Workers/hr | Planners/hr | Error % | Duration |
|:-----:|:-----:|:-----------:|:----------:|:-----------:|:-------:|:--------:|
| **Pre-lull** | 494895–899 | 73 | 15 | 25 | 1.7% | 5h |
| **Searching** | 494900–906 | 17 | **0.3** | 4.4 | 0.8% | 7h |
| **Crisis** | 494907–909 | 103 | 2.3 | 50 | **58%** | 3h |
| **Recovery** | 494910–915 | 171 | 29 | 60 | 8.0% | 6h |
| **Peak** | 494916–937 | 195 | 40 | 73 | 2.3% | 22h |
| **Shutdown** | 494938–943 | 19 | **2.7** | **4.0** | 2.6% | **2h** |

## Discovery 1: Three States, Not Two

KE-018 claimed the system has exactly two states (Active and Idle) separated by a step function. The production data reveals **three**:

### State 1: Active
Workers + planners + evaluators all running. ~190 sessions/hr. Error rate ≤ 5%.

### State 2: Searching (NEW)
**Planners run but no workers execute.** 2–6 planner sessions/hr, 0 worker sessions. The system is actively looking for runnable tasks but not finding any.

This was visible for **7 consecutive hours** (h494900–906):
- h494900: 11 planner sessions, 0 workers
- h494901: 4 planners, 0 workers
- h494902: 2 planners, 0 workers
- h494903: 2 planners, 0 workers
- h494904: 4 planners, 0 workers
- h494905: 2 planners, 0 workers
- h494906: 6 planners, 2 workers ← work found, transition begins

This is NOT the pure-clock state. The planner is burning 2–11 sessions/hour actively searching for work. It's a distinct metabolic mode with its own resource signature.

### State 3: Idle (KE-018's "Pure-Clock State")
Only heartbeat agents. ~7 sessions/hr (arc=2, dev=2, scout=2, metric-triage=1). No planners, no workers.

## Discovery 2: Complexity-Ordered Recovery

The provider outage at h494907 was the system's equivalent of a circuit breaker tripping. Every agent failed simultaneously. The recovery happened in strict **complexity order**:

| Agent | Role Complexity | 100% → 0% Error | Recovery Mechanism |
|:-----:|:------:|:--------:|:-------:|
| **evaluator** | Lowest (template lookup) | **2 hours** (h494907→909) | Rigid template needs only 1 successful API call |
| **may** | Medium (triage + routing) | **4 hours** (h494907→911) | Needs evaluator results to triage correctly |
| **aks-explorer** | Highest (domain work) | **9+ hours** (h494907→916) | Needs planners + workers + complex multi-step sessions |

### Why This Ordering Exists

Each layer depends on the one below it:
1. **Evaluator** has the simplest template — a fixed score lookup taking ~80s with ~20 ops. It can succeed with minimal API reliability.
2. **May** needs evaluator output to triage alerts. Until evaluators finish scoring sessions, may's steward has nothing actionable.
3. **Workers** need planners to identify runnable tasks. Planners at h494909 found 22 tasks but workers didn't appear until h494910 — a 1-hour lag as the planner's output propagated to the dispatch queue.

### The Inverse of Shutdown Order

Shutdown is the mirror image: complex agents stop first (workers lose tasks → planners find nothing → evaluators have nothing to evaluate). Shutdown takes 2 hours. Recovery takes 6 hours. The asymmetry ratio is **≈ 3–6×**.

This confirms KE-018's hysteresis prediction: "ramp-up is gradual while shutdown is instant."

## Discovery 3: The Disabled Immune System

KE-017 identified may as the system's only "boundary agent" — the sole actuator that crosses the Cassandra gap. During the crisis:

| Hour | May Sessions | May Errors | May Error % | May Avg Duration |
|:----:|:-----------:|:----------:|:-----------:|:----------------:|
| 494906 | 1 | 0 | 0% | 645s |
| **494907** | **19** | **19** | **100%** | **1.1s** |
| **494908** | **28** | **18** | **64%** | **137s** |
| 494909 | 11 | 1 | 9% | 236s |
| 494910 | 18 | 3 | 17% | 394s |
| 494911 | 12 | 0 | 0% | 329s |

The paradox: may's session volume **spiked 19×** (1→19/hr) precisely BECAUSE the error flood triggered its steward workflows (metric-alert-triage: 14 sessions at h494907). But every one of those sessions **immediately failed** (0 ops, 1.1s average duration). 

**The system's immune agent was knocked offline by the same pathogen it was designed to fight.**

During h494907, the system had:
- 128 error sessions generating alerts
- may dispatched 19 times to triage those alerts
- may failed 19/19 times — unable to complete a single triage
- The error-generating sessions continued unchecked

This is a **single-point-of-resilience failure**: the same LLM provider serves both the work agents and the steward. There is no fallback path.

### The Recovery Window Gap

Between the provider outage resolving (~h494908) and may fully recovering (h494911), there was a **3-hour window** where errors were occurring but the immune system was operating at degraded capacity (64%→17%→0% error). During this window:
- aks-explorer had 24+5+10 = 39 error sessions
- may could only triage successfully 10+10+15 = 35 sessions
- The immune response was running at roughly 1:1 with the problem, not ahead of it

## The Three-State Model

```
                    task-worker sessions appear
   SEARCHING ──────────────────────────────> ACTIVE
   (planners     gradual: 6-10 hours         (all agents
    only)     <──────────────────────────     running)
              workers drain, planners persist
              
              ↑                              │
              │ planners start               │ first-order
              │ gradual: 2-4h                │ 1-2 hours
              │                              ↓
              
              ←─────────── IDLE ──────────────
                         (clock only)
```

### Transition Speeds

| Transition | Duration | Type | Mechanism |
|:----------:|:--------:|:----:|:---------:|
| Active → Idle | **1–2 hours** | First-order (step function) | runnable_tasks hits 0 |
| Active → Searching | **4–5 hours** | Gradual | Workers drain as tasks complete |
| Searching → Active | **6–10 hours** | Gradual | Planner finds work, dispatches workers |
| Idle → Searching | Unknown | Unknown | New project or task injection |
| Crisis → Active | **6 hours** | Complexity-ordered | evaluator → may → aks-explorer |

## Three Falsifiable Predictions

1. **Future provider outages** will show the same recovery ordering (evaluator → may → aks-explorer), because it's determined by session complexity, not accident.

2. **The Searching state** will always precede Active state when the system resumes work after idling — planners must run first to populate the task queue. The gap between first planner session and first worker session will be ≥ 30 minutes.

3. **May will spike to 15+ sessions/hour** within 1 hour of any system-wide error rate exceeding 50%, because the steward triggers are mechanically coupled to session.completed events regardless of error status.

## The Design Implication

The single-point-of-resilience vulnerability has a concrete fix: may's steward triage workflow should have a **circuit breaker** that suspends dispatch when the provider itself is failing. During h494907, 14 may sessions were launched for metric-alert-triage and all 14 failed in ~1 second. A simple check — "if my last 3 sessions errored in < 5 seconds, wait 5 minutes before retrying" — would have prevented 14 wasted sessions and the cascading event shadow they created.

This is the smallest possible change (3 lines) with the highest impact during crises: it converts the immune agent from a victim of the pathogen into a genuine circuit breaker.
