# KE-005: The Architectural Gravity Well — Why New Agents Reproduce Old Pathologies

**Discovered:** 2026-06-18 | **Status:** Active — measured from live production data

## The Discovery

Two new agents have appeared in production since the synthesis library began documenting system pathologies: **tech-lead** (19 sessions over 9 days, 322 ops) and **optimizer** (1 session, 42 ops). Both were created *after* KE-001 through KE-004 named the system's structural problems. Neither exhibits different behavior from the pathological patterns already documented.

This is the strongest possible evidence for a claim the library has circled but never directly stated: **the pathologies are architectural invariants, not agent-specific bugs.**

## Why This Is Not a Coincidence

The system's dispatch primitives create a fixed attractor basin:

```
1. Event fires (metric.recovered, waiting-with-comments, watchdog-capacity-underfilled)
     ↓
2. Owner-loop session dispatched (regardless of whether state changed)
     ↓
3. Agent reads project state (full context reload each time)
     ↓
4. Agent determines: nothing actionable
     ↓
5. Agent exits with "project waiting" / "nothing runnable"
     ↓
6. Event fires again (because the triggering condition persists)
     → GOTO 1
```

This loop is **primitive-level**, not agent-level. Any agent plugged into these primitives will exhibit the same behavior. The fix is not "make tech-lead smarter" — it's "add a change-detection gate before step 2."

### The Gravitational Analogy

In physics, a gravity well is a region of spacetime from which escape requires energy. The system's architectural gravity well works the same way:

- **Event-driven dispatch without staleness gates** → every agent will check unchanging state repeatedly
- **Owner-loop without change-detection** → every project owner will re-read stable projects
- **Evaluate-all without type-aware skipping** → every new agent's sessions will be evaluated

The energy needed to escape = changing the primitive. The energy available to each agent = zero (agents can't modify their own dispatch logic).

## The Meta-Pattern: Growth Instead of Change

The system's response to documented pathologies has been:

| Response | Type | Effect |
|----------|------|--------|
| Add tech-lead agent | Growth | Extended pathology surface area |
| Add optimizer agent | Growth | 1 session, then inactive |
| Add more syntheses | Growth | Documentation of the problem grew |
| Change dispatch primitives | Change | **Never happened** |
| Add staleness gates | Change | **Never happened** |
| Add catabolic primitives | Change | **Never happened** |

This is **organizational Brooks's Law**: the system responds to process problems by adding headcount (agents), which increases coordination overhead without addressing the process. The 75 tech-lead sessions and 1 optimizer session represent ~1,400 ops spent on new agents that inherited every pathology the system already had.

## The Single Prescription

Every prior KE prescribed specific catabolic primitives. This KE prescribes one meta-rule:

> **Before adding any new agent to the system, verify that the existing dispatch primitives have staleness gates.** Otherwise the new agent will immediately fall into the gravity well, adding cost without adding capability.

The corollary: **every "add an agent" proposal is a signal that the architecture needs a primitive change instead.**
