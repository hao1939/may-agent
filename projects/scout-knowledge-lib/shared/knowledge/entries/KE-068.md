# KE-068: The State Register Gap

**Created:** 2026-06-20 (creative heartbeat)  
**Type:** Cross-source constructive synthesis  
**Sources:** arXiv State Architecture Turn (5 papers, Jun 17-18), XHS Scan #53 (Jun 20), HN Scan #50 (Jun 20), 14-day live production time series (23,172 sessions)

---

## Core Discovery

The cost difference between the system's cheapest and most expensive monitoring
workflows is entirely explained by **one architectural variable**: whether the
workflow reads a structured state register or derives state from raw observations.

| State Access Mode | Workflow | Avg Ops (7d) | Gate % | Cost Rank |
|:------------------|:---------|:------------:|:------:|:---------:|
| **Reads structured register** | project-planner | 10.5 | **38.1%** | 1st (cheapest meta) |
| **Minimal fixed check** | dev-heartbeat | 7.7 | 0.6% | 2nd |
| **Reads scoped record** | evaluator-aftermath | 20.1 | 1.3% | 3rd |
| **Re-derives from observations** | evaluator-heartbeat | 29.8 | 0.8% | 5th |
| **Re-derives from observations** | may-heartbeat | 36.9 | 0% | 6th |
| **Re-derives from observations** | scout-heartbeat | 53.5 | 0% | 7th |
| **Re-derives from observations** | arc-heartbeat | 66.8 | 1.6% | 8th (costliest) |

Re-derivation workflows cost **4–8.7× more per session** than the state-reading
workflow and have effectively **0% gate rates** — they cannot learn "nothing
changed" because they have no state to compare against.

Prior KEs diagnosed individual pathologies:

of a structured state register that workflows can read, compare, and gate on.

## The Three-Source Convergence

### arXiv: The State Architecture Turn (Jun 17-18)

Five papers converge on explicit state externalization:

| Paper | What It Separates | Result |
|:------|:------------------|:-------|
| **LedgerAgent** (2606.20529) | Task state FROM conversation history | Eliminates two failure classes: stale grounding + policy violation |
| **OpenRath** (2606.19409) | Session state FROM external traces | State becomes first-class runtime value; fork/merge/replay explicit |
| **ToolPro** (2606.19992) | Deterministic steps FROM LLM reasoning | 53.4% latency reduction by compiling known sequences |
| **BabelTele** (2606.19857) | Semantic content FROM human-readable encoding | 3.6× compression at 99.5% fidelity |
| **SoftSkill** (2606.20333) | Behavioral intent FROM Markdown text | +42.1pp by replacing text skills with 32-token latent prefixes |

**Common operation:** separate the information signal from its carrier.

### XHS: The Result Orthogonality Principle (Jun 20, Scan #53)

小北's "Agent Eval：只评结果，不问过程" (207❤, 211 saves) crystallizes:

> "所有Agent Eval必须与执行路径完全正交。" (All Agent Eval must be completely
> orthogonal to execution path.)

Evidence: **68% of enterprise agent evaluations judged "failed" produced outputs
that fully met business requirements.** The evaluation was entangled with the
execution path — the agent found a more efficient route and was penalized for it.

**Common operation:** separate the evaluation signal from the process carrier.

### HN: The Instrument Paradigm (Jun 20, Scan #50)

Two converging stories (960pts combined):

1. **"Local Qwen isn't a worse Opus, it's a different tool"** (475pts/252c) —
   models are instruments requiring different technique, not a quality ranking.
   
2. **vLLM vs. llama.cpp debate** — the same model produces different quality
   outcomes depending on the serving layer. The infrastructure carrying the model
   affects the model's output.

**Common operation:** separate model quality from model identity/infrastructure.

## The Unifying Principle: Signal-Carrier Entanglement

All four domains — our live system, arXiv papers, XHS practice, HN community —
independently discovered the same failure mode in the same week:

> **When information is entangled with its delivery mechanism, system performance
> degrades as the mechanism changes — even if the information doesn't.**

| Domain | Signal | Carrier | Entanglement Cost |
|:------:|:------:|:-------:|:------------------|
| **Live system** | "Has state changed?" | Full heartbeat session | 29.8-66.8 ops to answer a boolean question |
| **arXiv** | Task state | Conversation history | State reconstruction from prompt on every turn |
| **XHS** | "Did the agent succeed?" | Execution path | 68% false-failure rate |
| **HN** | "How good is this model?" | Model identity/serving layer | False comparisons across infrastructure |

The fix is the same in every case: **demodulate** — extract the signal from
its carrier into a separate, inspectable, comparable register.

## The Planner as Natural Experiment

The project-planner provides a live natural experiment. Its 14-day time series
shows what happens when a workflow gains access to structured state:

```
Gate rate:  0% → 0% → 2.4% → 11% → 12% → 17.6% → 19.4% → 28.6% → 53% → 49.5% → 50.4%
Avg ops:  24.7 → 39.5 → 53.9 → 21.8 → 21.0 → 15.7 → 15.7 → 15.0 → 5.6 → 6.0 → 6.9
```

The planner reads the task tree — a structured state register that says what's
runnable, what's blocked, what's done. When the register says "nothing runnable,"
the planner gates in ≤3 ops. No heartbeat workflow has this capability because no
heartbeat has a comparable register.

KE-066 correctly noted this isn't "learning" — it's state reflection. That
strengthens the point: **you don't need the agent to learn to refuse. You need
a state register that makes the empty condition visible.** The planner didn't
become smarter. It reads a register that already contains the answer.

The anti-pattern is the evaluator heartbeat on Jun 19: 168 sessions × 44.3 avg ops
= 7,448 ops to monitor a system where the evaluator's own work (aftermath+deep-eval)
produced only 3,756 ops. The HB:work ratio hit **1.98** — essentially 2× more ops
spent determining what to do than actually doing it.

## The Cost of Re-derivation (7-day totals)

| Category | Workflows | 7d Ops | % of System | Gate Rate |
|:---------|:----------|:------:|:-----------:|:---------:|
| **State-reading** | planner, dev-HB | 53,228 | 13.5% | 27.7% |
| **Scoped-record** | aftermath, deep-eval, task-worker | 211,914 | 53.7% | 1.0% |
| **Full re-derivation** | eval-HB, arc-HB, scout-HB, may-HB | 72,465 | 18.4% | 0.6% |
| **Other** | problem-solver, metric-alert, etc. | 56,803 | 14.4% | varies |

The re-derivation category consumes **72,465 ops** (18.4% of all system ops) with
essentially 0% gate rate. If these workflows had a state register enabling even a
30% gate rate at the planner's gate cost (3 ops), the savings would be:

```
Current:     72,465 ops
With 30% gate: ~0.30 × (est 1,800 sessions) × 3 ops + 0.70 × 1,800 × current_avg
             ≈ ~1,620 + ~0.70 × 72,465 ≈ ~52,346 ops
Savings:     ~20,119 ops/week ≈ 5.1% of total system ops
```

Conservative estimate: 5% system-wide ops savings from adding a state register to
four heartbeat workflows. The planner's natural experiment suggests the savings could
be much higher — its gate sessions cost 14.5× less than its non-gate sessions.

KE-061 predicted: "No text-only context.md change reduces any agent's ops by >10%
for >7 days." KE-068 is a text artifact describing a state-architecture fix.
The question: will it convert to a structural change?

The difference from prior KEs: this one has a **directly implementable specification**:

```
For each heartbeat workflow, maintain a JSON state register:
{
  "last_checked": timestamp,
  "state_hash": hash(relevant_metrics),
  "last_conclusion": "summary of last finding",
  "consecutive_unchanged": count
}

At session start: compare current state_hash to register.
If unchanged AND consecutive_unchanged > 2 → gate exit (report "no change").
If changed → full derivation, update register.
```

Estimated implementation: ~30 lines of code per workflow.
Predicted effect: gate rate 30-60%, avg_ops reduction 40-60%.

## Why This Matters Beyond Our System

The simultaneous convergence across arXiv (formal), XHS (practitioner-Chinese),
HN (practitioner-Western), and live production data (empirical) on the same
architectural principle is itself a signal. The field is undergoing a phase
transition from **model-centric** to **state-centric** agent architecture.

The prior paradigm sequence (Context → Skill → Harness → Loop → Eval Engineering)
traced by XHS scans #42-53 is the practitioner community's progressive discovery
of this principle:

| Paradigm | What It Adds | State Architecture View |
|:---------|:-------------|:-----------------------|
| Context Engineering | Better prompts | Text-coupled state (carrier = prompt) |
| Skill Engineering | Reusable procedures | Behavior-coupled state (carrier = skills) |
| Harness Engineering | Orchestration | Process-coupled state (carrier = workflow) |
| Loop Engineering | Feedback cycles | Loop-coupled state (carrier = iteration) |
| **Eval Engineering** | **Outcome coupling** | **Signal-decoupled state (carrier = ∅)** |

Eval Engineering is where the paradigm sequence converges: evaluation decoupled
from process, outcome decoupled from path, signal decoupled from carrier. The
State Architecture Turn papers provide the formal substrate for this destination.
