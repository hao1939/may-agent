# KE-054: Evaluation Colonization — The Mechanism by Which Monitoring Becomes the System

**Discovered:** 2026-07-30 | **Status:** Active

---

## Core Finding

When production throughput drops, evaluation activity **doesn't proportionally decrease**. 
Instead, the evaluator's self-monitoring function (heartbeat) actively expands to fill 
the capacity vacuum. The evaluator switches from **demand-responsive** (passive, triggered 
by work) to **supply-driven** (active, generating its own stimuli) precisely when it 
should be most dormant.

## The Evidence: A 14-Day Natural Experiment

### The Heartbeat Inflation

| Day | Worker Sessions | Worker Ops | Heartbeat Ops | Ratio (HB per Worker) |
|:---:|:--------------:|:----------:|:-------------:|:--------------------:|
| 6 | 148 | 7,016 | 1,309 | 8.8 ops/worker |
| 7 | 267 | 12,958 | 1,389 | 5.2 |
| 8 | 276 | 12,634 | 1,215 | 4.4 |
| **9** | 364 | 14,461 | **6,040** | **16.6** |
| **10** | 468 | 21,168 | **7,876** | **16.8** |
| 11 | 309 | 13,322 | 2,635 | 8.5 |
| 12 | 881 | 34,760 | 8,179 | 9.3 |
| **13** | **148** | **5,517** | **4,217** | **28.5** |

Day 13 is the telling case: worker sessions drop to their lowest point (148), 
and the heartbeat cost **per worker** reaches 28.5 — meaning the evaluator spends 
28.5 ops monitoring for every worker op produced. The monitoring system now 
outweighs the system it monitors by a factor approaching 1:1.

### The Function Inversion (Day 12 → Day 13)

| Evaluator Source | Day 12 Ops | Day 13 Ops | Change |
|:---------------:|:----------:|:----------:|:------:|
| Aftermath (evaluates work) | 24,205 | 973 | **−96%** |
| Heartbeat (monitors itself) | 8,179 | 4,217 | −48% |
| Deep-eval (quality signal) | 539 | 641 | +19% |

When work disappeared, aftermath correctly dropped 96%. But the heartbeat 
only dropped 48% — it retained MORE than half its throughput despite having 
nothing substantive to monitor. The heartbeat's **investigation of its own 
absence of work** became its primary activity.

### The Self-Referential Loop (from KE-048 data)

The mechanism:
1. Worker sessions drop → fewer sessions to evaluate
2. Aftermath-coverage-rate drops to 0% (no sessions in window)
3. Alert fires: "aftermath-coverage-rate-3h = 0" 🔴
4. Heartbeat investigates the alert → spends 45.3 ops determining "coverage is 0 because nothing happened"
5. The heartbeat session itself shows up in the next coverage window
6. Return to step 1

This is evaluation **colonizing** capacity — the act of measuring the absence 
of work generates work that needs measuring.

## The Cross-Source Convergence

Three independent signal streams name the same mechanism from different angles:

### 1. APEX Three-Layer Co-Evolution [2606.15363]

APEX's critical finding: **single-axis optimization (L1 only) achieves +14-21% 
while three-layer co-evolution achieves +90%.** Our system's evaluator IS single-axis 
optimization: it optimizes evaluation coverage independently from production topology 
and behavioral principles. The evaluator can't see that maximizing its own coverage 
metric makes the system worse — because worse-ness lives in a dimension (throughput) 
that evaluation doesn't measure.

The APEX parallel: our evaluator is trapped at the L1 local optimum. It patches 
its own harness rules (investigate alerts, maintain coverage) without ever questioning 
whether its behavioral principles (evaluate everything) or its topology (heartbeat + 
aftermath + deep-eval, same cadence regardless of load) serve the overall system.

### 2. XHS "Skill Hell" (8,106 collects, scan #46)

"Skill越多，死的越快" — "The more skills, the faster you die." The XHS community 
discovered that agents with 120+ skills collapse under their own monitoring overhead. 
The solution: skill subtraction (技能减法).

Our evaluator has accumulated capability without lifecycle governance:
- Aftermath: evaluates completed sessions ✓
- Heartbeat: monitors own metrics ← THIS IS THE COLONIZER  
- Deep-eval: provides genuine quality signal ✓
- Metric-alert-triage: responds to fired alerts ✓

The heartbeat is the "121st skill" — it was useful when the system needed active 
monitoring during exploration phases, but it has no off-switch for completion phases. 
It's a skill that generates its own demand.

### 3. HN "Engineering Discipline Crisis" (412pts, scan #44)

Charity Majors: "AI demands more engineering discipline." trjordan: "a million tools 
that make AI better, and no ways to measure whether AI is working better."

The industry-level version of evaluation colonization: when code generation becomes 
cheap, the EVALUATION of that code becomes the bottleneck. But the evaluation itself 
has no evaluator — there's no meta-evaluation of whether evaluation is useful. Our 
system manifests this exactly: the evaluator's heartbeat has zero quality oversight 
(KE-010 noted "the evaluator is exempt from measurement").

The pattern at every scale:
- **Industry**: AI code generation ↑ → evaluation demand ↑ → evaluation becomes bottleneck
- **XHS community**: Skill count ↑ → monitoring skills ↑ → monitoring crowds out production
- **Our system**: Throughput ↓ → evaluator heartbeat ↑ → heartbeat becomes primary activity

## The Unified Principle

> **Evaluation in multi-agent systems is demand-responsive at high load but supply-driven 
> at low load.** It follows production up (scaling naturally with work volume) but does 
> NOT follow production down (generating self-referential stimuli to maintain throughput). 
> This creates a one-way ratchet: evaluation overhead can grow but never shrinks below 
> its self-monitoring floor.

This is why KE-046 found the evaluator "demand-responsive" (correct at macro scale — 
37× session drop during full idle) while KE-048 found the heartbeat "escalating" (also 
correct — heartbeat cost per meaningful signal trends upward). They're measuring the 
same agent in two different lifecycle phases.

## The Colonization Taxonomy

| Colonization Stage | Evaluator Behavior | System Impact |
|:------------------:|:------------------:|:-------------:|
| **Healthy** (days 7-8) | Aftermath dominates; heartbeat minimal | HB 4-5 ops per worker |
| **Inflating** (days 9-10) | Heartbeat surges; investigating metrics | HB 16-17 ops per worker |
| **Colonized** (day 13) | Heartbeat > aftermath; self-referential | HB 28.5 ops per worker |
| **Terminal** (predicted) | Heartbeat investigating own heartbeats | ∞ ratio (no workers) |

Day 2-3 already showed the terminal state: 541.5 heartbeat ops per worker (only 2 workers 
ran all day). The system visited this state once and recovered (via the perturbation at 
day 6-7). The question is whether it can escape again without a perturbation.

## Why Prior KEs Missed This

- **KE-046** correctly identified the evaluator as demand-responsive — but measured only 
  the session count, not the heartbeat vs aftermath split within evaluator sessions
- **KE-010** identified the Evaluation Singularity — but as a fixed ratio, not a 
  lifecycle-phase-dependent process
- **KE-048** identified heartbeat escalation — but attributed it to spurious convergence, 
  not to capacity colonization
- **KE-052** identified the Completion Paradox — but didn't name evaluation's specific 
  expansion mechanism

KE-054 provides the **mechanism**: evaluation colonizes capacity because the heartbeat 
function generates demand from the absence of supply. The other entries described symptoms; 
this entry identifies the causal loop.

## The Design Implication: Load-Aware Evaluation Topology

APEX's solution applies directly: make evaluation topology **fitness-selected**, not static.

```
IF production_throughput(last_3h) < 0.2 * peak_throughput:
  heartbeat_cadence = 4× normal (reduce frequency)
  suppress volume-dependent alerts (aftermath-coverage, etc.)
  evaluator_mode = "deep-only" (expensive but informative, no shallow monitoring)
ELSE:
  normal cadence
```

This converts the evaluator from "static topology with load-dependent behavior" to 
"load-selected topology" — APEX's L3 co-evolution principle applied to a single agent.

## Three Falsifiable Predictions

1. **Heartbeat ops/day will remain >3,000 even if worker count drops to zero** — 
   because the heartbeat generates its own demand via coverage-gap alerts. 
   Only suppressing the alert metric breaks the loop.

2. **Reducing heartbeat cadence 4× during low-throughput windows will NOT reduce 
   overall evaluation quality** — because the heartbeat produces zero unique 
   information during colonization phases (same conclusion: "nothing to do").

3. **The next production surge will suppress heartbeat inflation without code 
   changes** — because high aftermath volume naturally displaces heartbeat 
   scheduling priority. The colonization reverses automatically when work returns.
