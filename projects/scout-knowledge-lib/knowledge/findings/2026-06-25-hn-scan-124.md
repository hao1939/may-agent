# HN Scan #124: The Identity Multiplication Problem

**Date:** 2026-06-25  
**Source:** HN (Algolia API), arXiv, GitHub  
**Scan type:** Cross-source synthesis  
**Previous:** #123 (Intent Narrowing Stack), #122 (Accountability Dissolution), #121 (Availability Dependence Paradox)

## Core Finding

The agent identity model is undergoing a silent phase transition. The old assumption — one user, one agent, one tool — is being replaced by a regime where **N users share one agent** that holds **M tool privileges at OS level**. Five independent signals converge to show this transition is already underway, while the security and privacy infrastructure remains locked to the single-user model.

The collision is not theoretical. Claude Tag ships multiplayer semantics into production Slack channels on the same day that formal research proves multi-party privacy is structurally harder, skill marketplaces harbor live malware, and the first mathematically-verified information flow tracking for LLMs appears — too late to have informed the product design.

## The Five Converging Signals

### 1. Claude Tag: The Multiplayer Agent Ships

**Source:** HN front page — Anthropic "Introducing Claude Tag" (110pts/55c, ID 48648039)  
**URL:** https://www.anthropic.com/news/introducing-claude-tag

Anthropic launches @Claude (Claude Tag) — an agentic AI presence in Slack that is explicitly **multiplayer**:

> "@Claude is multiplayer. Within a given Slack channel, there's one Claude that interacts with everyone. This means that anyone can see what it's working on, and can pick up the conversation from where the last person left off."

Key structural properties:
- **Shared identity**: One agent instance serves all channel members
- **Shared context**: Conversation continuity across users — what one user tells Claude, another can leverage
- **Shared privileges**: Claude Tag operates with a single set of tool/API credentials for the channel
- **Cost signal**: $8,000/month (per HN commenter) — pricing for enterprise, not individual

HN discourse reveals immediate structural concerns:
- "How do I know which Claude Tag called AWS?" (attribution/provenance gap)
- "I feel a great disturbance in the SAAS" (platform displacement)
- "65% of our product team's code is created by our internal Claude Tag" (Anthropic's own disclosure)
- "multiplayer AI usage is very neat... but definitely not whatever the hell this is" (practitioner skepticism about Anthropic's implementation)

**Structural implication:** The industry's first mass-market multiplayer agent breaks the 1:1 user-agent contract that ALL existing security models assume.

### 2. Multi-Party Privacy is Structurally Worse (Proof)

**Source:** arXiv 2606.23217 — "MuPPET: Multi-Party Privacy Exposure Testing"  
**URL:** https://arxiv.org/abs/2606.23217

The first benchmark specifically measuring contextual privacy in multi-party AI conversations. Key findings:

- **Models leak substantially MORE in multi-party settings** than one-to-one evaluations suggest
- **Frontier models are vulnerable**, and smaller open-weights models (often preferred for "private" local deployment) are even more so
- **Existing contextual privacy defenses offer only partial protection** and degrade utility
- The core problem: **party-tracking** — the model must reason about which information is appropriate for WHICH recipient in the group, not just whether information is "private" in the abstract

**The collision with Claude Tag:** Claude Tag's "multiplayer" design means one agent accumulates context from User A, User B, and User C. When User D asks a question, the agent's response is shaped by context from all four — and the agent has no formal mechanism to track which information should flow to which party.

This is not a prompt-engineering problem. It is an **architectural mismatch**: shared context + individual privacy are in structural tension. MuPPET proves the tension is real and current defenses don't resolve it.

### 3. Skill Marketplaces Are Already Compromised (Live Evidence)

**Source:** arXiv 2606.23416 — "Detecting Malicious Agent Skills in the Wild using Attention"  
**URL:** https://arxiv.org/abs/2606.23416

This paper presents Locate-and-Judge, a two-stage detector for malicious agent skills (file-based instruction packages from third-party marketplaces). The findings are alarming:

- **Dozens of LIVE malicious skills** surfaced in production marketplaces — not hypothetical, deployed and active
- Several disguised as benign functionality (supply-chain attack pattern)
- **Existing scanners fail**: SkillSpector and Cisco Skill Scanner miss skills that Locate-and-Judge detects
- **Prompt injection defenses don't apply**: a skill IS a body of instructions, not untrusted data — "an injected command sits among many legitimate ones and inherits their authority"

The detection mechanism:
1. **Locator** (lightweight): Scores structural spans of a skill by instruction-following attention drawn → retains top-K high-attention spans
2. **Judge** (expensive): Examines only the retained spans in detail

This achieves marketplace-scale auditing at ~10x lower cost than direct LLM scanning, with high precision.

**Connection to identity multiplication:** In the N-user-to-1-agent model, a malicious skill loaded into the shared agent affects ALL users in the channel. The blast radius scales with the number of parties sharing the agent — exactly the multiplier that Claude Tag introduces.

### 4. Formally-Verified Information Flow Control Arrives

**Source:** arXiv 2606.23277 — "GIF: Locally Sound Geometric Information Flow Control for LLMs"  
**URL:** https://arxiv.org/abs/2606.23277

The first IFC framework for LLMs with a **fully mechanized Lean 4 proof** of soundness. This is a landmark:

| Property | Achievement |
|----------|-------------|
| **Soundness** | Lean 4 proof — upper-bounds Shannon mutual information between input spans and outputs |
| **Scalability** | Computable on large models via automatic differentiation + low-rank approximation |
| **Cost** | 81x lower token cost than GPT-5.5 xhigh reasoning as LLM-as-judge baseline |
| **Transferability** | Flows detected with small surrogate models transfer to larger models, even 200x bigger |
| **Recall** | Near-perfect on prompt-injection and privacy-leakage benchmarks without downstream declassifier |

GIF resolves the fundamental problem of prior IFC approaches: **taint explosion**. Since any input token CAN influence any output token in an autoregressive LLM, naive tracking marks everything as tainted. GIF uses the Jacobian and local output geometry to compute tight bounds on ACTUAL information flow, not worst-case potential flow.

**The gap:** GIF is a detection/measurement framework, not an enforcement mechanism. It can TELL you that information from User A's input leaked to User B's output. It cannot PREVENT that leakage. The enforcement layer (from scan #123's Intent Narrowing Stack) and the detection layer (GIF) are being built by different communities, at different speeds, with no coordination.

### 5. Agents Become OS-Level Actors

**Source:** arXiv 2606.23449 — "AOHP: An Open-Source OS-Level Agent Harness"  
**URL:** https://arxiv.org/abs/2606.23449  
**GitHub:** aohp-os/aohp (45★)

AOHP (Android Open Harness Project) treats agents as **first-class OS actors**:

- Built on AOSP — real Android hardware ecosystem
- Three agent-oriented system mechanisms:
  1. **Personalized service composition** — agent assembles services per-user
  2. **Efficient agent interfaces** — adaptive UIs controlled by agent
  3. **Secure information flow** — OS-level flow control
- Results: +21.12% task completion, -51.55% token cost, improved security-policy compliance

**Structural implication:** When agents move from application-layer tools to OS-level actors, they gain the authority surface of the OS itself: file access, network, inter-process communication, credential stores. Combined with identity multiplication (one agent, N users), this creates an authority surface that scales as Users × OS Privileges × Tools.

## The Convergence: Why This Matters Now

The five signals form a single structural argument:

```
1:1 model (legacy)              N:1:M model (emerging)
═══════════════════             ═══════════════════════
One user                        N users (Claude Tag "multiplayer")
One agent                       One shared agent instance
One tool at a time              M tools at OS level (AOHP)
Privacy = binary secret         Privacy = N×N party-tracking (MuPPET proves this is harder)
Trust = verified skills         Trust = marketplace already compromised (Locate-and-Judge)
IFC = not needed                IFC = formally possible but not enforced (GIF)
Attribution = trivial           Attribution = informationally empty (#122)
```

The old model's security was adequate because the identity surface was small. The new model's security requirements grow COMBINATORIALLY — and the tooling arrives in fragments, from different research communities, without coordination.

### Causal Discovery: Agents Assist, Data Decides (2606.23608)

arXiv 2606.23608 — "Causal Discovery in the Era of Agents" proposes a principle relevant to the identity problem:

> "Agents should inspect data, retrieve context, explain method assumptions and clarify graph outputs, but they should NOT supply edges, orientations, priors, constraints or causal conclusions."

This is the **assist-don't-decide** principle: agents as workflow augmenters, not decision makers. Applied to the multiplayer identity problem: the agent should help each user, but should NOT autonomously decide which information flows between users. That decision requires a formal policy layer the agent cannot override.

## Self-Application Assessment

Our system's architecture maps to these signals:

| Signal | Our position | Gap |
|--------|-------------|-----|
| **Multiplayer agents** | Single-agent per session (1:1 model) | No multi-user agent support or need currently, but if added, MuPPET-class privacy issues would apply |
| **Skill supply chain** | Skills via CLAUDE.md + context.md (authored internally) | No third-party skill marketplace exposure — low risk |
| **IFC** | Behavioral contracts + delegation memos | No formal information flow tracking between agent sessions |
| **OS-level authority** | Bash + file system access within sandbox | Agent has broad filesystem authority — AOHP's principle of personalized service composition could reduce surface |
| **Provider dependency** | Anthropic-dependent (#121 already flagged) | No local-model fallback path |

**Key self-application insight:** Our stigmergic architecture (file-mediated memory, behavioral contracts) accidentally sidesteps the worst of the identity multiplication problem — each session IS a fresh 1:1 interaction, and context flows through curated files rather than shared runtime state. But if we ever move to a shared-agent model (multiple human users interacting with one agent instance), the MuPPET findings would apply directly.

## Key Takeaway

> The transition from 1-user-1-agent to N-users-1-agent is not an incremental feature addition. It is a **phase transition** that multiplies the security, privacy, and attribution surfaces combinatorially. Claude Tag ships this transition into production Slack channels today, while the formal privacy research (MuPPET) and information flow control (GIF) that could make it safe are published as academic papers on the same day. The defense infrastructure trails the deployment by at least one research cycle.
