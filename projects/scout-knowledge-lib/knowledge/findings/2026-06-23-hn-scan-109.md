## Synthesis

**The correct unit of agent evaluation, governance, and scheduling is the full deployment configuration (model + CLI + tools + workflow structure) — not any component in isolation.** Six independent papers published June 18–19 converge on this from different angles, while HN front page continues to validate the infrastructure-as-moat thesis from scan #99.

### The Six Convergent Signals

#### 1. AgentMeter: Model-CLI Is the Deployed Unit (arXiv 2606.21140)

The same model produces *fundamentally different* success, token cost, and overall profiles under different CLI harnesses. Key result: on Core30, highest Pass/30 selects GLM-5.1 + qwen-coder; lowest cost/pass selects GPT-5.3-Codex + kimi-cli; highest AgentMeter Score selects Qwen3.6+ + kimi-cli. **No single model dominates — the harness IS part of the capability.**

Implication: All prior evaluations that compare models without controlling for harness/interface are methodologically incomplete. The "model leaderboard" is the wrong artifact; the correct artifact is a "configuration leaderboard."

#### 2. Calibration Is Not Control (arXiv 2606.21399)

Runtime oversight framed as scalar risk prediction (confidence/uncertainty → threshold → intervention) targets the wrong decision object. Two trajectory prefixes with identical risk scores can require different actions because one is recoverable and the other is not. Key result: recalibrating a scalar score improves *prediction metrics* but leaves *control regret unchanged*. A simple prefix-only action-conditioned controller reduces regret from 0.506 to 0.110 on ALFWorld.

Implication: The entire "monitor → alert → intervene" pattern in agent governance is structurally flawed when the monitor produces scalar scores. Oversight must produce *conditional action recommendations*, not risk numbers. This is a paradigm shift from calibration to intervention-advantage estimation.

#### 3. Don't Blindly Trust It: Tool Feedback Value Inversion (arXiv 2606.21409)

When external tool feedback is unreliable, agents perform *worse than receiving no feedback at all*. On HotpotQA: Qwen2.5-7B scores 44.8 F1 with clean retrieval, 22.3 F1 with no feedback, but **4.7 F1** with shuffled retrieval. The inversion persists under stronger clean retrieval and locally plausible distractors.

Implication: Tool augmentation value is conditional on the deployed tool reliability context. The same agent+tool configuration is beneficial in one deployment and actively harmful in another. **The reliability of the tool environment is a deployment-configuration-level property**, not a model property or a tool property in isolation.

#### 4. SwarmX: Agentic Scheduling (arXiv 2606.21401)

Conventional schedulers treat model inference as compute-bound work units. SwarmX proves that agentic workloads (multi-model-call, tool-interleaved) require *prompt-semantic-aware* scheduling because inference time depends on content, not just token count. Neural predictors capture prompt/device/runtime/model features. Result: 61.5% tail latency reduction, 2× throughput under SLO on production (1000 GPUs, 1M CPU cores).

Implication: The scheduling unit is not "a model call" but "an agentic workflow with semantic state." Infrastructure must understand workflow semantics to schedule effectively — another proof that the deployment configuration is the atomic unit.

#### 5. Design-Time Verification (arXiv 2606.21565)

Runtime safeguards are necessary but not sufficient. This paper proposes *design-time* verification of agentic workflows as compositions of reusable building blocks, checked for compatibility via 12 structural rules. Evaluation on 48 flawed workflows + 168 structural variants shows reliable violation detection even when flaws are obscured via task-splitting between agents.

Implication: Workflow composition correctness is a structural property checkable before deployment. This means the workflow graph topology itself is part of the deployment unit specification — and it can be verified statically, like a type system for agent architectures.

#### 6. AutoRAS: Robust Agentic System Design (arXiv 2606.21445)

Robustness cannot be bolted onto an agentic system after the fact. AutoRAS encodes structural connectivity AND behavioral actions as a sequence of symbolic primitives, then optimizes this sequence using execution-derived safety signals. Result: best performance in both vanilla and adversarial settings with smallest performance degradation under attacks.

Implication: The *architecture description itself* (connectivity + behavioral specification) must be the optimization target for robustness. You cannot make a fragile topology robust by improving individual agents — the topology IS the robustness property.

## The Thesis: The Deployment Unit Turn

### What Changed

Prior understanding (scans #1–#108): Agent capability is primarily a model property, modified by tooling and runtime infrastructure. Evaluation compares models; governance monitors models; scheduling allocates compute to models.

Current understanding (scan #109): Agent capability is an *emergent property of the full deployment configuration*. The model, the CLI/harness, the tool reliability context, the workflow graph topology, and the scheduling semantics are **jointly determining** outcomes. Isolating any one component for evaluation/oversight/scheduling produces systematically wrong conclusions.

### The Formal Structure

```
Deployment Unit = (Model, Harness/CLI, Tool Environment, Workflow Topology, Scheduling Context)

AgentMeter proves: ∂Success/∂Harness ≈ ∂Success/∂Model  (CLI matters as much as model)
CalibIsNotControl: Oversight(scalar(prefix)) ≠ Oversight(action|prefix)  (monitoring unit wrong)
DontBlindlyTrust: Value(Model, Tools) can be NEGATIVE when Tools.reliability < threshold
SwarmX: Latency(workload) = f(prompt_semantics), not f(token_count)  (scheduling unit wrong)
DesignTimeVerif: Safe(workflow) = ∏ Compatible(block_i, block_j)  (composition is verifiable)
AutoRAS: Robust(system) = f(connectivity_primitives), not f(agent_i_robustness)  (topology is the property)
```

### Connection to Prior Syntheses

- **The Infrastructure Inversion (#99):** "Infrastructure IS the moat" — correct, but now formalized: infrastructure defines the deployment unit, and the deployment unit is what has capability.
- **The Harness Consolidation (#106):** Meta-harness → Agent Runtime → Agent VCS — this IS the deployment configuration stack being built.
- **The Behavioral Contract Turn (#100):** Contracts are specifications of the deployment unit, not just the model.
- **The Legibility Trilemma (#108):** Applies at each vertex of the deployment unit independently. The trilemma compounds because compiled skills, text governance, and proof-of-done each operate on *different components* of the deployment unit.
- **The Dereference Crisis:** Pointer bugs are addressing errors across deployment-unit boundaries (model addresses tool state that has changed, harness addresses model state that diverged).

### Prediction

1. **Configuration-as-Code** becomes a named practice within 3 months — declarative specifications of the full deployment unit (model version + harness version + tool manifest + workflow graph) checked into version control.
2. **"Works on my machine" for agents** becomes recognized failure mode within 6 months — same model producing different results in different configurations, with no current tooling to detect this.
3. **Configuration leaderboards** replace model leaderboards for agentic tasks within 12 months — AgentMeter's AMS score is the prototype.
