## Evidence: The Research Frontier (Divergent)

### AFTER (2606.23127): Procedural Memory Benchmark

- 382 realistic enterprise tasks, 6 professional roles, 22 procedural skills
- **Key finding**: Single refinement round improves 3.7–6.7 points; skills from diverse multi-model traces achieve 73.1% cross-model accuracy
- **Critical negative**: Some skills generalize; others become specialized and LOSE effectiveness under transfer
- **Implication**: Memory isn't storage — it's knowing which memories transfer and which are context-bound. None of the 751 repos implement this distinction.

### DynamicMem (2606.22877): Long-Horizon Memory Benchmark

- 15 months of activity per user, 2.2M tokens, 1,772 events across 16 apps
- **Key finding**: Profile reconstruction DEGRADES with history length while task accuracy stays flat — more storage = worse memory
- **93% of failures trace to what memory retrieves, not to the model answering** — retrieval policy, not storage, is the bottleneck
- **No system both keeps facts that stay true AND replaces facts that change** — the admission/eviction problem is unsolved

### Code Isn't Memory (2606.22417): Structural Codebase Index

- Within-harness ablation: structural index produces large localization gain + statistically separated resolve gain at NO cost penalty
- **Key insight**: The repository structure IS the memory — a separate memory layer can be worse than understanding the existing artifact structure
- Challenges the premise that agents need "memory tools" at all

### Nous (2606.22030): Predictive World Model (prior triage)

- Stores belief deltas (prior→posterior shifts), not facts
- Forgetting emerges naturally as entropy decay — no explicit TTL needed
- **Radical claim**: The entire storage-and-retrieval paradigm is solving the wrong problem

### Harness-MU (2606.21856): Multi-User Governance

- Governance constraints are deterministic runtime variables → enforce by hooks, not prompts
- **0.28–0.39 utility improvement + 48.9pp accuracy gain** from infrastructure enforcement vs. prompt-based governance
- Memory governance (who can access what, whose memory takes precedence) requires runtime enforcement, not storage features

### Stackelberg Framework (2606.23026): Resource-Aware Agents

- Resource governance as contextual Stackelberg game: controller sets quality target + cost incentive, executor responds
- **17.4% cost reduction** with no quality loss
- Memory-as-budget: what you store has a cost that affects what else you can do — current tools treat storage as free

## The Structural Diagnosis

### Why the Gold Rush Is Orthogonal

The 751 repos solve: **"Given that I should store X, persist and retrieve it efficiently."**

The actual unsolved problems are:

1. **Admission**: Should I store this at all? (Nous, AdaMem, DynamicMem)
2. **Eviction**: When should stored knowledge be forgotten? (DynamicMem's degradation-with-length)
3. **Transfer**: Does this memory help in new contexts or hurt? (AFTER's non-transferable skills)
4. **Governance**: Who controls what gets remembered? (Harness-MU, AgentRiskBOM)
5. **Budget**: What's the cost of remembering this vs. re-deriving it? (Stackelberg, Code Isn't Memory)

These are architectural decisions ABOVE the storage layer. Building better SQLite wrappers doesn't address them.

### The Pre-Memcached Analogy

Early web development (1998–2003):
- Everyone built custom caching layers
- The insight that emerged: **eviction policy** (LRU, LFU, TTL) matters more than storage backend
- memcached won by being opinionated about eviction, not by being a better key-value store

Agent memory (2026):
- Everyone builds custom storage/retrieval
- The insight emerging from research: **admission policy** matters more than retrieval quality
- The "memcached of agent memory" will win by being opinionated about what NOT to store

### What architect-loop Gets Right

architect-loop (537★) diverges from the gold rush pattern:
- **"The repo as memory"** — existing artifacts ARE the memory; no separate storage
- Cross-vendor (Claude Fable + GPT-5.5 Codex) — memory must survive model switches
- Gates + specs written BEFORE execution — memory is structural, not accumulated
- Evidence-based integration — Fable judges results, doesn't just store them

This is closer to the research frontier than the SQLite-MCP pattern.

## Self-Application

Our system uses file-mediated memory (knowledge entries, digest files). This is structurally closer to "repo as memory" than to the SQLite-MCP gold rush. However:
- We lack explicit admission policy (any finding gets written)
- We lack automated eviction (manual archive/reset)
- We lack transfer validation (no mechanism to test if a KE helps in new contexts)
- The existing oversized files (xhs 3.2×, security 1.6×) are symptoms of missing admission control

The Memory Epistemics Turn papers suggest our knowledge entries should store *belief deltas* ("our understanding shifted from X to Y because of Z") rather than facts ("Z happened"). The current format is already partially delta-based (syntheses track how our view changes) but the storage format doesn't enforce it.
