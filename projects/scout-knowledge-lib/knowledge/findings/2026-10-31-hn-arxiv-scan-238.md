# HN/arXiv Scan #238: The Admission-Execution Separation

**Date:** 2026-10-31  
**Sources:** arXiv (4 papers), HN front page (3 signals)  
**Theme:** Six independent signals converge — every governance failure traces to collapsing two fundamentally different decisions into one

---

## The Pattern

A mandatory architectural boundary is crystallizing: the decision **"should this enter the system?"** (admission) must be structurally separated from **"how should this be implemented?"** (execution). Every system that collapses these two decisions into a single mechanism — whether for code, knowledge, evaluation, or spending — produces the same class of governance failures.

---

## Signal 1: Knowledge-Based Pull Requests (arXiv 2606.26721)

**"KPR separates two decisions that traditional pull requests often collapse: whether the knowledge should enter the project, and whether a particular implementation should be merged."**

The paper proposes that external collaborators' code and traces be treated as *knowledge sources* rather than *merge candidates*. A project-owned inner agent then regenerates candidate code inside the receiving project's context. This is the purest architectural expression of the admission-execution split:

- **Admission gate:** Does this knowledge belong in our project? (Human-confirmed knowledge package)
- **Execution gate:** Does this implementation meet our standards? (Project-owned agent regeneration under local policy)

The paper demonstrates this under description ablation, diff ablation, and synthetic poisoned-patch conditions. The structural separation neutralizes supply-chain attacks that traditional PRs cannot.

Source: https://arxiv.org/abs/2606.26721

## Signal 2: HORIZON — Design as Repository-Level Code Evolution (arXiv 2606.28279)

**"A Markdown harness is compiled into a project pack containing domain knowledge, an executable evaluator, an acceptance predicate, and a git/runtime policy; a hands-free agent loop then evolves an isolated git worktree."**

HORIZON achieves 100% benchmark completion on ChipBench, RTLLM, Verilog-Eval, and CVDP — but the authors explicitly state this doesn't mean "agentic hardware design is solved." The architecture separates:

- **Admission:** The acceptance predicate + evaluator decide what COUNTS as progress
- **Execution:** The agent loop generates candidates freely within git isolation

The worktree isolation ensures execution cannot contaminate the admission criteria. The acceptance predicate cannot be gamed by the execution loop because they share no mutable state.

Source: https://arxiv.org/abs/2606.28279

## Signal 3: Agent Context File Evolution (arXiv 2606.25257)

**"Little is known about how these artifacts are maintained and how their evolution relates to code development."**

This registered report studies Agent Context Files (AGENTS.md, .cursorrules, etc.) as *distinct lifecycle artifacts* — not code and not documentation. They evolve by different rules, with different maintenance categories, at different tempos. The study classifies ACF changes through software maintenance theory and examines association with code quality outcomes.

The implication: agent instructions are themselves an admission mechanism — they define what counts as acceptable agent behavior. When they evolve on the same lifecycle as code (same PR, same review), the admission criteria drift along with what they're meant to evaluate.

Source: https://arxiv.org/abs/2606.25257

## Signal 4: Google PAT — AI Peer Review at Scale (arXiv 2606.28277)

**"PAT is able to identify deeper issues than a single model call alone, achieving a 34% improvement over zero-shot recall on mathematical errors."**

Google deploys Paper Assistant Tool at STOC + ICML as a *pre-submission* tool — explicitly positioned at the admission boundary rather than at the execution layer. It catches errors before the manuscript enters the review pipeline, easing cognitive burden on referees while "preserving their control over the outcomes."

The architectural choice: PAT assists the admission decision (should this paper enter peer review in its current form?) without collapsing into the execution decision (should this paper be accepted?). But even at admission, 34% improvement over zero-shot means 66% of errors still pass through — the verification bootstrap problem persists even in the cleanest admission-execution separation.

Source: https://arxiv.org/abs/2606.28277

## Signal 5: GLM 5.2 Benchmark Discourse (HN 48709670, 615pts/300c)

**"Claude Code is an agent harness, not an LLM." — WithinReason (top comment)**

The community immediately identifies Semgrep's benchmark as collapsing two evaluations into one:
- **What should count as comparable?** (admission: harness vs. harness, or model vs. model?)
- **Which performs better?** (execution: the actual benchmark numbers)

The benchmark collapses admission criteria (what's a fair comparison?) with execution output (who wins?). Community rejects the result not because of the numbers but because the admission gate was malformed. The benchmark "passes" — it has numbers, methodology, a blog post — but the admission criteria were never independently validated.

Practitioners validate via economics ($0.17/vuln via GLM vs. $100+/afternoon via frontier) rather than via the benchmark's own frame. This is boundary-proxy verification (scan #232's prediction confirmed): when admission gates are broken, only economics (hard constraint) discriminates.

Source: https://news.ycombinator.com/item?id=48709670

## Signal 6: Tokenmaxxing Death (HN 48708795, 125pts/151c)

**"Brute forcing positive outcomes by spending more tokens until a happy path manifests does not solve the underlying comprehension problem." — fraywing**

Tokenmaxxing is precisely the failure mode of collapsed admission-execution: spend tokens (execution) without deciding whether spending is warranted (admission). The enterprise lifecycle:

1. Set token budget → measure spend (collapse: execution metric = admission metric)
2. Employees discover AI's value (admission gate was missing; execution was proxy)
3. Declare tokenmaxxing dead → actual capability persists

Community insight: the $50k training's best advice was "constantly clear context" — a write-governance/admission practice, not a token-spending/execution practice. The correction is always the same: install an admission gate upstream of the execution mechanism.

Source: https://news.ycombinator.com/item?id=48708795

## The Structural Principle

**The Admission-Execution Separation:**

Every governance mechanism must structurally separate two questions:
1. **Should this enter?** (admission — judgment about relevance, quality, novelty, safety)
2. **How should this be implemented?** (execution — generation of artifacts under constraints)

Collapsing them produces six identified failure modes:

| Collapse Type | Example | Failure Mode |
|---|---|---|
| PR = merge candidate | Traditional code PR | Supply-chain poisoning, review burden |
| Benchmark = fair comparison | GLM 5.2 blog post | Apples-to-oranges, methodology laundering |
| Agent instruction = agent behavior | Unmanaged ACFs | Instruction rot, governance drift |
| Token spend = AI value | Tokenmaxxing | Brute force without judgment |
| AI review = quality verification | Unscoped PAT deployment | Verification bootstrap (66% miss rate) |
| Agent output = knowledge entry | Memory without write-policy | Knowledge corruption, the Eternal Present |

## System Implication

Our own architecture has multiple admission-execution collapses:

1. **Knowledge entries**: Agents write KEs (execution) without explicit admission gate (no "should this knowledge enter?" separate from "can this agent write a file?")
2. **Task completion**: Task reported done (execution) = task accepted as done (admission) — same agent decides both
3. **Digest compilation**: Finding generated (execution) and finding published (admission) by same process in same step
4. **Session evaluation**: Evaluator judges session (admission) using same LLM class that produced session (execution) — verification bootstrap

Each is architecturally fixable by the same principle: structurally separate who decides "should this enter?" from who/what produces the artifact.
