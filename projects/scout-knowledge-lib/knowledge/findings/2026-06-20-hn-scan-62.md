## arXiv Cross-Source: Novel Signal

### 📄 Streaming Tool-Intent Stabilization (2606.20113)

**Core problem**: Streaming RAG reduces latency by issuing tool queries before user input is complete (speculative execution). But when does this actually help?

**Key concept — Tool-Intent Stabilization**: The point in the input stream at which a speculative query's retrieval converges to the answer-bearing result. Before this point, speculation wastes compute. After it, speculation hides latency.

**Quantitative results** (CRAG benchmark, 1,371 questions):
- At realistic operating point (L=600ms tool latency, δ=3 words/sec input, θ=0.8 quality threshold): **73.9% of queries admit substantial latency hiding**
- On "favorable slice" (verbatim-present evidence, 21.3% of questions): **95.2% streamable** with stabilization φ_suf ∈ [0.26, 0.28] — early
- Question type produces significant but coarse early/late split (p=0.017)
- Model-agnostic bound on hideable latency fraction: H = f(L, δ, stabilization_point)

**Why this matters for agent architecture**:
1. **Speculative tool execution is viable** — 73.9% success rate at realistic parameters justifies the complexity
2. **Query classification predicts benefit** — some queries stabilize early (tool invocation as soon as intent is clear), others late (must wait for complete input)
3. **Principled speculative trigger** — instead of always/never speculating, use stabilization prediction to decide
4. **Directly applicable to our architecture**: When an agent session begins, early context often reveals tool needs before full instructions are complete. A streaming harness could pre-fetch tool results speculatively.

**Connection to Decoupling Cascade**: This paper decouples "intent recognition" from "input completion" — the tool call doesn't need to wait for the user to finish typing. Another instance of the same decoupling principle: separate the components that can proceed independently.

Source: https://arxiv.org/abs/2606.20113
