# The Inline Verification Escape: Bounded Verification Through Co-Generation

**Scan**: #249 | **Source**: arXiv | **Date**: 2026-11-02

## Thesis

Five independent research streams demonstrate that the Verification-Generation Inversion (scans #167, #178, #186 — "generation cost → $0, verification cost → ∞") has a structural escape: **inline verification at generation time**. Rather than generating freely then verifying after the fact, these systems embed verification constraints INTO the generation process itself, making verification cost bounded and proportional to generation rather than exponential. This is the constructive answer to the structural diagnosis.

## Evidence

### 1. ChainCaps: Monotonic Capability Attenuation for Tool Composition (arXiv 2605.26542)

**"ChainCaps: Composition-Safe Tool-Using Agents via Monotonic Capability Attenuation"**

- **Problem**: "Permission laundering" — agents satisfy every per-tool permission check but produce unsafe end-to-end effects by composing individually-authorized operations (read confidential doc → summarize → send externally)
- **Solution**: Every value carries a sink-specific capability budget; tool composition propagates budgets by intersection. Authority can only *decrease* through composition, never *increase*
- **Implementation**: Transparent MCP proxy requiring no changes to agent or tool servers
- **Results**: ASR reduced from **25-68% → 0-4.8%** while preserving **96-100%** benign completion across 82 tasks, 5 frontier models, 3 providers
- **Key mechanism**: Verification is INLINE — checked at every tool boundary, not after the trajectory completes. Cost is O(n) in tool chain length, not O(2^n) in composition space
- **Bottleneck identified**: Manifest quality dominates — expert manifests achieve 100% attack blocking; naive manifests fall to 27.3%

Source: https://arxiv.org/abs/2605.26542

### 2. BashCoder-R1: Robustness-Aware Generation via Inline Reward (arXiv 2606.27733, ISSTA 2026)

**"BashCoder-R1: Towards Robust and Explainable Bash Code Generation with Robustness-Aware Group Relative Policy Optimization"**

- **Problem**: Generated Bash scripts pass syntax but carry critical robustness vulnerabilities (unquoted variables, unsafe `rm`, missing error handling)
- **Solution**: R-GRPO — RL reward function that WEIGHTS syntax correctness + robustness (via shellcheck) + format correctness simultaneously during training
- **Pipeline**: CPT (Bash specialization) → L-CoT SFT (risk-aware reasoning) → R-GRPO (robustness as inline reward)
- **Results**: SyntaxPass 100%/95%, RobustPass **96%/79%** (single/multi-line), FullRate **90%/73%** — outperforms DeepSeek-V3.2 (Reasoning) by 37.8%/20.2%
- **Key mechanism**: Verification (shellcheck) runs DURING training, not after deployment. The model learns to generate robustly, eliminating post-hoc verification need
- **Human evaluation**: Confirms highest ratings on Functionality, Robustness, AND Clarity

Source: https://arxiv.org/abs/2606.27733

### 3. TestHumanizer: Validation-Gated Refinement Over Robust Outputs (arXiv 2606.28229)

**"Humanizing Automatically Generated Unit Test Suites with LLM-Based Refactoring"**

- **Problem**: Direct LLM test generation achieves only 51-78% compilation rate; SBST tools (EvoSuite) compile at 100% but are unreadable
- **Solution**: Use LLMs as controlled refactoring layers OVER compilable SBST suites — preserve behavior/compilation while improving readability
- **Results**: 88-98% compilation rate (vs 51-78% direct, ~100% baseline); coverage preserved within 1-2pp; 86-95% satisfy faithful-refactoring threshold
- **Scale**: 350 classes, 31,500 refactorings across gpt-4o and mistral-large-2407
- **Human study**: 30 classes, 444 methods — significant gains in readability and adoption willingness (Wilcoxon p < 0.01)
- **Key insight**: "LLMs are most effective not as standalone generators but as **validation-gated refinement layers** over robust outputs"
- **Failure mode**: Long code-centric prompts prone to hallucination-induced failures; summary-based setting most robust

Source: https://arxiv.org/abs/2606.28229

### 4. ChainFuzzer: Greybox Discovery of Multi-Tool Composition Vulnerabilities (arXiv 2603.12614)

**"ChainFuzzer: Greybox Fuzzing for Workflow-Level Multi-Tool Vulnerabilities in LLM Agents"**

- **Problem**: Multi-tool vulnerabilities emerge only through composition — single-tool/single-hop testing misses long-horizon exploitable dataflows
- **Solution**: (i) Cross-tool dependency extraction with source-to-sink evidence, (ii) Trace-guided Prompt Solving (TPS) for stable attack prompts, (iii) guardrail-aware payload fuzzing
- **Results**: 20 popular agent apps (998 tools) → 2,388 candidate tool chains → **365 unique reproducible vulnerabilities** across 19/20 apps (302 require multi-tool execution)
- **Metrics**: Edge precision 96.5%, chain precision 91.5%, TPS reachability 27.1%→95.5%, trigger rate 18.2%→88.6%
- **Cost efficiency**: 3.02 vulnerabilities per 1M tokens
- **Key mechanism**: Verification (fuzzing) is STRUCTURAL — follows tool-chain topology, not random testing. Bounded by the graph structure of actual tool compositions

Source: https://arxiv.org/abs/2603.12614

### 5. Pomona: Continuous Incremental Verification at Bloomberg (arXiv 2606.06752)

**"Pomona: Continuous Code Quality Improvement via Small, Automated Changes at Bloomberg"**

- **Problem**: Large agent PRs exceed human verification capacity (the Supervision Cost Spiral, scan #191)
- **Solution**: "Kaizen" philosophy — Scanning skill identifies improvements, Repair skill generates tiny PRs (~10 lines of diff)
- **Results**: **15/17 PRs merged** (88.2%), median time-to-close **<2 hours**, 8/10 senior engineers want adoption
- **Design principles**: Human-in-the-loop, small diff sizes, focus on code quality not feature development
- **Key mechanism**: By BOUNDING the verification unit to ~10 lines, human review capacity is never exceeded. Verification cost is O(1) per PR rather than O(n) in change size
- **Practitioner insight**: "Small diff sizes" cited as primary adoption driver — engineers trust what they can fully verify

Source: https://arxiv.org/abs/2606.06752

## Synthesis: The Inline Verification Escape

The Verification-Generation Inversion established that:
- Generation cost → $0 (open weights, commoditization)
- After-the-fact verification cost → ∞ (multi-layer oracles, composition space explosion)

These five papers converge on a structural escape with three properties:

### Property 1: Verification embedded IN generation, not after it

| Paper | Verification point | Cost model |
|-------|-------------------|------------|
| ChainCaps | Every tool boundary (MCP proxy) | O(n) in chain length |
| BashCoder-R1 | Training reward signal (R-GRPO) | O(0) at inference time |
| TestHumanizer | Compilation gate per refactoring | O(1) per transformation |
| ChainFuzzer | Tool-chain graph traversal | O(edges) in dependency graph |
| Pomona | Human review of ~10-line diff | O(1) per bounded unit |

### Property 2: Verification scales with generation, not against it

After-the-fact verification grows super-linearly with output volume (the death spiral from scan #178). Inline verification grows linearly or sub-linearly because it constrains the generation space at each step:
- ChainCaps: capability budgets SHRINK at each composition → search space monotonically decreasing
- BashCoder-R1: robustness is a training signal → model can't generate non-robust code efficiently
- TestHumanizer: SBST ensures baseline correctness → LLM operates within pre-verified space
- ChainFuzzer: graph structure bounds the composition space → only reachable chains tested
- Pomona: 10-line bound → human verification capacity never exceeded regardless of total codebase size

### Property 3: The bottleneck shifts to specification quality

Every paper identifies the same residual bottleneck:
- ChainCaps: "Manifest quality is the dominant deployment bottleneck" (expert 100% vs naive 27.3%)
- BashCoder-R1: Robustness defined by shellcheck rules — quality depends on rule coverage
- TestHumanizer: "Summary-based setting most robust" — specification format matters
- ChainFuzzer: "Source-to-sink dataflow evidence" — requires correct dependency specification
- Pomona: "Focus on code quality" — improvement definition must be specified

**The escape resolves the Inversion at one level but re-introduces it at the specification level.** You don't pay verification cost at runtime; you pay specification cost at design time. This is dramatically better because specification is amortizable across all future generations, while per-output verification is not.
