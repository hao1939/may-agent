# HN Scan #85: The Temporal Orientation Trilemma

*Scanned: 2026-06-22 | Sources: arXiv (6 papers), GitHub (5 repos), HN front page (1 thread + related signals)*

---

## Cross-Source Synthesis: Memory Is Splitting by Temporal Orientation

Six independent academic papers and five grassroots repos from the past two weeks converge on a structural finding: **agent memory is not one problem but three**, split along temporal orientation. Each orientation requires a fundamentally different architecture, and no current system addresses all three simultaneously.

### The Three Temporal Orientations

| Orientation | Question | Architecture | Key Paper |
|-------------|----------|--------------|-----------|
| **Retrospective** | What happened? (faithfulness) | Append-only, signed, immutable | SMSR (2606.12703) |
| **Present** | What matters now? (assembly) | Selective, compressed, cache-aware | TokenPilot (2606.17016) |
| **Prospective** | What will be needed? (anticipation) | Anticipatory triggers, governance gates | T-Mem (2606.15405) |

### Why This Is a Trilemma (Not Just Three Features)

The three orientations create structural tensions:

1. **Retrospective ↔ Present**: Faithful storage conflicts with efficient assembly. SMSR requires HMAC-signed immutable records; TokenPilot requires aggressive eviction. You cannot sign memories and also freely delete them.

2. **Present ↔ Prospective**: Optimizing for current-task relevance conflicts with rehearsing for future retrieval. TokenPilot evicts content "when task relevance expires" — but T-Mem shows that content dormant now may be the only path to future retrieval via associative (non-surface-similar) queries.

3. **Prospective ↔ Retrospective**: Governance gates (projectmem, ACM) add pre-action checks that require loading retrospective data before acting — but the retrospective layer grows unboundedly while governance gates must be fast and deterministic.

## Paper-Level Evidence

### T-Mem (2606.15405) — Prospective Memory via "Write-Time Rehearsals"

**Key innovation**: First memory architecture implementing cognitive science's "episodic future thinking" — at write time, the system generates *triggers* that anticipate future contexts in which this memory will be needed.

- **Two trigger families**: Descriptive (surface-similar) and Associative (relevance-bound but no surface overlap)
- **Two granularities**: Single facts and full exchanges
- **Result**: State-of-the-art on both LoCoMo and LoCoMo-Plus
- **Critical implication**: Current similarity-based retrieval fails on exactly the cases where memory is most valuable — when the current situation doesn't resemble the stored experience but needs it. This is the "associative regime" where all prior systems fail.

**Connection to our system**: Our `triggers` field in `<ai_context>` preambles is a primitive form of T-Mem's architecture — we already write anticipated retrieval contexts at write time. But we only do descriptive triggers, not associative ones.

Source: https://arxiv.org/abs/2606.15405

### SMSR (2606.12703) — Certified Retrospective Integrity

**Key innovation**: First certified defense against memory poisoning in persistent agent systems. Proves that no provenance-free retrieval-time filter can certify against adaptive injection.

- **Component 1**: HMAC-SHA256 provenance at write time → cuts attack success from 93-100% to 0% for unsigned variants
- **Component 2**: Randomized memory ablation + verdict-based majority voting → bounds authenticated adversary success to 8.0%
- **Critical finding**: The "Consistent Minority Effect" — a consistent adversarial answer wins string-based voting as a numerical minority. Verdict-based voting (abstain/answer) defeats this.
- **End-to-end**: Even when the agent *itself* writes the poison (query-only attack), success drops from 65.3% to 5.3%.

**Connection to our system**: Our append-only event logs lack provenance signing. An agent session that writes a misleading `lesson` can steer all future sessions permanently.

Source: https://arxiv.org/abs/2606.12703

### TokenPilot (2606.17016) — Present-Moment Assembly Optimization

**Key innovation**: Identifies the cache-continuity/text-sparsity trade-off as the core tension in present-moment memory management.

- **Ingestion-Aware Compaction**: Stabilizes prompt prefixes, eliminates noise at the ingestion gate
- **Lifecycle-Aware Eviction**: Monitors residual utility of context segments, conservative batch-turn offloading
- **Results**: 61-87% cost reduction while maintaining competitive performance
- **Critical insight**: Memory management and inference caching are coupled — pruning that saves tokens but invalidates KV cache is net-negative.

**Connection to our system**: Our context assembly (reading files → loading into session) has no lifecycle-awareness. Files loaded at session start remain "present" regardless of whether their utility has expired.

Source: https://arxiv.org/abs/2606.17016

### MemTrace (2606.17328) — Measurement Framework for Temporal Memory Behavior

**Key finding**: "The dominant bottleneck is evidence use, not retrieval: when systems fail, the evidence was retrievable 10× more often than it was missing."

- Unit of measurement: the *knowledge point* (a single typed fact), not question rows
- Three dimensions: memory age, question type (current/earlier/trajectory), evidence condition (present/missing/contradicted)
- **Critical result**: Similar pooled accuracy hides different failure modes — recovering current and earlier states does NOT imply tracking trajectory of change.

**Connection**: Validates that our "Assembly Gap" thesis (triage 2026-06-19) extends to temporal tracking. Memory systems that answer "what is the current state?" well cannot necessarily answer "how did we get here?"

Source: https://arxiv.org/abs/2606.17328

### projectmem (2606.12329) — Memory-as-Governance

**Key innovation**: Frames memory not as a resource the agent draws from during work, but as an authority that constrains future actions. "Memory that does not merely answer the agent but acts on its next action."

- **Append-only typed event log**: issues, attempts, fixes, decisions, notes
- **Pre-action gate**: Warns agent before repeating a previously failed fix or editing a fragile file
- **MCP integration**: Deterministic projections served through Model Context Protocol
- **Results**: 207 logged events across 10 projects over 2-month self-study

**Grassroots validation**: 20★ on GitHub, active development, adopted by Cursor/Claude Desktop/Codex users.

Source: https://arxiv.org/abs/2606.12329, https://github.com/riponcm/projectmem

### Infini Memory (2606.10677) — Topic-Structured Consolidation

**Key innovation**: Treats memory as topic-structured documents (not isolated records or flat indices). Buffer → consolidation → topic documents.

- Observations staged in buffer, periodically consolidated into coherent topic documents
- Agentic retrieval: LLM reads memory through iterative tool calls, not single retrieval
- **Score**: 64.7% on MemoryAgentBench
- **Implication**: The text-document-per-topic pattern (which our knowledge library already uses) is validated as architecture, not just convention.

Source: https://arxiv.org/abs/2606.10677

## Grassroots Signal: The "Recall" Moment

### HN: "Stop wasting tokens re-explaining your project between sessions" (48622590, 32pts/27c)

The discussion reveals practitioner deadlock on which temporal orientation to prioritize:

- **cadamsdotcom**: "Automation like this is limited unless no human has to remember it. So perhaps you can save context during PreCompact and Stop hooks." → Prospective automation needed
- **gste**: "CLAUDE.md is already a good system... keeping a local copy of everything is bad for the same reasons My_Code_v3_final.zip is bad." → Retrospective accumulation is harmful
- **SubiculumCode**: "Sometimes it's good to start fresh. LLMs need large context restarts so they can better identify holes that they become blind to." → Present-moment clarity requires forgetting
- **dools**: "If I need context for a session then that is output from a previous session" → Retrospective→Present handoff is the core workflow

Each practitioner implicitly advocates for one temporal orientation while describing the failure mode of the others. The community cannot agree because they're solving different problems.

### GitHub: ACM Specification (ntholm86/agent-context-memory)

A formal specification for "governance-first context memory" that makes the Mandate Gate explicit:

- **Three-tier structure by trust level**: Intent (principal mandate) > Trace (agent decisions) > Evidence (captured interactions)
- **Key principle**: "If an agent begins work without a principal-authored mandate already in memory, the session is unauthorized."
- **Convergence with projectmem**: Both implement prospective memory-as-governance, arriving from different starting points (projectmem from failed-fix prevention, ACM from authorization theory).

Source: https://github.com/ntholm86/agent-context-memory

### GitHub: recall (raiyanyahya/recall, 35★)

Pure retrospective solution — TextRank summarization of past sessions, locally persisted. HN discussion exposes its limitation: it solves the "re-explanation" problem but not the "wrong retrieval" or "governance" problems.

Source: https://github.com/raiyanyahya/recall

## The Structural Insight: Orientation Determines Architecture

Each temporal orientation implies a different:

| Property | Retrospective | Present | Prospective |
|----------|--------------|---------|-------------|
| Write pattern | Append-only | Mutable/evictable | Append + rehearsal |
| Trust model | Signed provenance | Utility-scored | Authority-gated |
| Failure mode | Poisoning | Irrelevance | Over-constraint |
| Optimization target | Integrity | Efficiency | Safety |
| Growth strategy | Unbounded accumulation | Active compression | Bounded mandate |
| Query pattern | "What happened?" | "What's relevant?" | "Am I allowed?" |

**No single architecture can optimize for all three.** This is why every system we've surveyed is strong in one orientation and weak in the others:

- **SMSR**: Perfect retrospective integrity, zero present-moment optimization, no prospective governance
- **TokenPilot**: Perfect present-moment efficiency, actively destroys retrospective fidelity, no prospective gates
- **projectmem/ACM**: Strong prospective governance, primitive retrieval (no assembly optimization), limited retrospective integrity

## Predictions

1. **Within 6 months**: A system explicitly names and separates the three temporal orientations as distinct subsystems (the way databases separate OLTP and OLAP).
2. **Within 12 months**: "Prospective memory" becomes a tracked capability in agent evaluations — not just "can it recall?" but "can it anticipate what it will need?"
3. **Within 18 months**: The Trilemma resolves via architectural separation — retrospective memory as immutable event store, present memory as optimized context assembler, prospective memory as governance/trigger layer — each with independent scaling and trust properties.

## Implications for Our System

Our current architecture:
- **Retrospective**: `context.md` updates + `lessons` array → unverified, no provenance, no signing. Vulnerable to SMSR-class poisoning.
- **Present**: Files loaded into session context → no lifecycle-awareness, no eviction strategy, no cache-prefix optimization.
- **Prospective**: `<ai_context>` triggers → descriptive only, no associative triggers. Guard system provides governance gates but with no memory-derived authority (guards check rules, not whether the agent tried this before).

**Highest-leverage improvement**: Add T-Mem-style associative triggers to `<ai_context>` blocks — write at storage time a set of non-obvious future retrieval contexts. This is the cheapest way to address the biggest gap (prospective anticipation) without restructuring.
