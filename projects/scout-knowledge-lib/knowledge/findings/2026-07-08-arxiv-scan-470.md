# Scan #470: The Memory Loop Gap

**Date**: 2026-07-08
**Sources**: arXiv abstract and primary HTML (cs.AI, cs.CL)
**Previous**: The Admission Boundary (#469), The Temporal Arbitrage (#468), The Delegation Reckoning (#467)

## Theme

The memory loop gap.

Agent proactivity — anticipating user needs and acting without explicit instruction — is an increasingly central capability claim. But the best agents achieve only 40% on structured proactivity benchmarks, even with frontier models. Why?

Three papers motivate a testable explanation: memory placement and navigation
may contribute to proactive performance. They do not establish that explanation.
PROBE measures proactive search, identification, and resolution; Memory in the
Loop manipulates latency in separate constraint-recall and loop-guard tasks;
NapMem trains memory navigation on personalized-memory benchmarks.

The gap between reactive and proactive behavior may include a memory component,
but the current evidence does not isolate it from model, harness, task, or
planning effects.

## Paper Analysis

### 1. PROBE: Proactive Resolution Of Bottlenecks (2510.19771v4) — DIAGNOSTIC [PRIMARY-REVIEWED]

**Published**: 2025-10-22 (v4 updated 2026-07-07 — adds GPT-5 and Claude Opus-4.1 results)
**Source**: https://arxiv.org/abs/2510.19771v4

PROBE decomposes proactivity into a three-stage pipeline:
1. **Search** for unspecified issues (not prompted, must discover)
2. **Identify** specific bottlenecks (not generic, must localize)
3. **Execute** appropriate resolutions (not just flag, must fix)

**Key results**:
- Best end-to-end performance: **40%** (achieved by both GPT-5 and Claude Opus-4.1)
- Even state-of-the-art models "struggle to solve this benchmark"
- The pipeline structure reveals WHERE proactivity fails — agents can sometimes search but frequently fail to identify or resolve without explicit instruction
- Mutual failure-mode analysis shows models fail at different stages; it does
  not isolate memory architecture or rule out model and harness effects

**Implication**: The matched benchmark shows that two frontier models top out
at the same reported end-to-end score. It does not identify memory architecture
as the cause: PROBE does not vary memory placement, in-process retrieval, or
NapMem, and its framework baselines differ along more than memory design.

### 2. Memory in the Loop: In-Process Retrieval as Extended Working Memory (2607.05690v2) — MECHANISM [PRIMARY-REVIEWED]

**Published**: 2026-07-06 (v2 revised 2026-07-19)
**Source**: https://arxiv.org/abs/2607.05690v2

This paper provides a **causal latency result inside its own memory tasks**, not
a causal mechanism for PROBE's proactivity ceiling. It identifies a
three-order-of-magnitude latency contrast:

| Memory Placement | Latency | Redundant Actions (per 12-step episode) |
|---|---|---|
| In-process store | ~100μs (p50: 80–165μs) | **0.0** |
| Network/cloud store | ~110ms | **7.2** |

**Key results**:
- Holding per-turn memory-latency budget fixed, varying only store speed: redundant actions rise **monotonically** with latency (exact permutation p=0.0079)
- With in-loop memory, recall improves from 0/5 to 3.6–4.8/5 across four GPT-5-class models
- The store **never lost a fact** in any run (244/244 writes kept) — every miss traces to the agent's **read policy**, not the store
- Dominant per-step cost is embedding (~200–400ms network). Pairing in-process store with local embedder returns complete operation to ~40μs
- Invokes the **extended-mind thesis parity principle**: a store fast enough to be constantly and directly available becomes extended working memory, not a tool the agent merely consults

**Implication**: Within the tested loop-guard setup, store latency changes
whether lookups fit a fixed per-turn budget and changes redundant actions. The
paper tests two task families and one main window size; its five-fact, six-turn
task is also solved perfectly by instructed restatement. Version 2 adds a
25-turn cost comparison and a write-side dedup gate, strengthening the local
engineering result without testing PROBE or general proactivity.

#### Artifact and reproducibility boundary (2026-09-04)

The paper's bibliography links `Egoist-Machines/LodeDB` only for a comparative
embedded-store latency. The method and results name **vxdb** as the actual
measurement instrument, and the disclosure identifies vxdb developer Yusuf
Khan, who is also the paper's first author. Exact public search resolved this to
`getmykhan/vxdb` at
`d720fd3e67e2331144d7486e0642fe62c24ffd0f`.

That repository supplies direct implementation evidence: `WorkingMemory`, its
unit tests, and `examples/agent_working_memory.ipynb`. The notebook demonstrates
a deterministic four-hop bounded-window comparison, optional model-selected
retention, dedup, and live store timing. It is not the reported experiment: the
97-file current tree contains no paper ID, five-seed loop-guard workload,
injected `5/15/30/50/110` ms ladder, 12-duplicate result table, or per-run result
JSON. Its only JSON files are documentation configuration. The arXiv v2 source
archive has 13 manuscript/figure members and likewise contains no Docker build,
scripts, prompts, workloads, or result JSON.

The LodeDB control at
`67405f5eaac698bb8613eeb8a0be8a56f12f958e` is a separate store implementation.
Its current 700-file tree and the complete public tag trees bracketing the paper
(`v1.3.0`, `v1.3.1`, `v1.3.2`, and `v2.0.0`) contain generic store benchmarks
but no paper experiment paths. Twenty-six public releases expose package artifacts,
not the paper artifact. A historical `memory_integrations` suite compares
vector-store performance and does not implement the paper's loop guard.

Confidence is high for the implementation identities and current/public-tag
contents, medium that no public reproduction artifact is presently discoverable,
and deliberately low for deleted branches, private files, or material available
directly from the authors. Reproduction of the reported decision probabilities
therefore remains blocked on the promised Docker/scripts/per-run JSON release,
not on access to the underlying store primitive.

A bounded offline check reproduces that narrower primitive. Current notebook
`26bb84c604c671eca3981d11e470d88abe5ad4f0b029dd530383be9d9b9ba049`
from vxdb `d720fd3e67e2331144d7486e0642fe62c24ffd0f` ran against the public
0.5.1 wheel (SHA-256
`40640825f9a5866bd220f827f7ada0f5f276fd0bed9b959ab746770edcb7ec41`).
The wheel maps to release commit
`d6b8d516b091727dd5fc5fa417be6d57fe7d1101`; subsequent changes to the
Python wrapper are prose-only.

At the notebook's two-observation window, the baseline retained 2/4 terminal
facts and memory recovered 4/4 in 100/100 deterministic repeats. A matched
window sweep produced baseline `1/4, 2/4, 3/4, 4/4` versus memory
`4/4, 4/4, 4/4, 4/4`. Thus the example demonstrates real store retrieval but
its pass/fail contrast is determined by scaffold-driven writes and queries plus
deliberate window truncation; once all four observations remain visible, the
baseline also passes. One local timing sample reported p50 28.3 µs embedding,
6.5 µs writing, and 15.9 µs querying. These are local mechanism checks, not
the paper's model-selected behavior, delayed ladder, five-seed probabilities,
or independent latency-causality result.

### 3. NapMem: Active Memory Navigation (2607.05794v1) — ARCHITECTURE [PRIMARY-REVIEWED]

**Published**: 2026-07-07
**Source**: https://arxiv.org/abs/2607.05794v1

NapMem provides the architectural complement: even when memory is fast, agents need a **structured action space** for navigating it, not just passive retrieval.

**Architecture**:
- **Multi-granularity memory pyramid**: raw conversations → typed memory records → topic tracks → user profiles, connected through provenance relations
- **Memory as action space**: the agent is trained (via memory-tool RL) to **select** memory granularity based on the query and intermediate evidence
- **Active navigation**: the agent inspects different memory levels before answering — it navigates memory rather than receiving retrieved results

**Key results**:
- Memory-tool RL agent is competitive across diverse memory-intensive tasks (PersonaMem-v2, LongMemEval, LoCoMo)
- Learned policy largely preserves general reasoning and tool-use abilities
- The agent learns WHEN to use coarse-grained (user profile) vs fine-grained (specific conversation) memory

**Implication**: NapMem supports treating memory as a **multi-resolution action
space** on PersonaMem-v2, LongMemEval, and LoCoMo. Its five baselines mix flat,
graph, hierarchical, operating-system, and learned-policy designs, so the result
does not isolate one universal architectural factor. The paper does not evaluate
PROBE or proactivity and leaves real-world personalization, privacy, and
forgetting unresolved.

## Qualified convergence: a hypothesis, not a causal chain

These papers can be compared as diagnostic, mechanism, and architecture work,
but the arrows are hypotheses rather than measured links:

| Paper | Question | Answer |
|---|---|---|
| **PROBE** | How proactive are agents on PROBE? | 40% best; cause not isolated |
| **Memory in the Loop** | Does store latency affect two memory tasks? | Yes under a fixed lookup budget; transfer untested |
| **NapMem** | Can learned structured navigation compete on memory QA? | Yes on three personalized-memory benchmarks; proactivity untested |

**The retained hypothesis**: Proactive behavior may benefit from three memory
conditions, each requiring a matched PROBE-style test:

1. **Speed**: test whether per-step access (~100μs rather than ~100ms in the
   cited setup) changes proactive outcomes.
2. **Structure**: test navigable multi-resolution memory against a matched flat
   retrieval store.
3. **Agency**: test learned memory navigation against matched passive retrieval.

No current experiment combines all three conditions or measures their effect on
PROBE. Calling them an architectural precondition for proactivity would exceed
the evidence.

### Primary-review comparison (2026-09-04)

| Boundary | PROBE v4 | Memory in the Loop v2 | NapMem v1 |
|---|---|---|---|
| Population / model | Frontier models and agent frameworks | Four GPT-5-class models; two in the latency dose-response | Qwen-family agents in the reported setup |
| Task | 1,000 synthetic workplace bottleneck cases | Constraint recall and loop-guard dedup | PersonaMem-v2, LongMemEval, LoCoMo plus non-memory controls |
| Intervention | Model/framework comparison | Store latency under a fixed lookup budget; in-loop memory and dedup controls | Memory pyramid plus learned tool-use policy |
| Outcome | Search / identify / resolve and end-to-end success | Redundant actions, recall, latency, tokens | Memory-task accuracy/F1/judge scores, tool use, cost |
| Direct bridge | No memory-placement or NapMem arm | No PROBE or proactivity outcome | No PROBE, latency arm, or proactivity outcome |

Supporting evidence is high-confidence for each paper's scoped result.
Contradictory evidence is high-confidence against the original causal bridge:
the primary texts contain no shared intervention/outcome test and do not cite
one another by title. Confidence is low that these results predict PROBE gains
until an otherwise matched agent is evaluated with external versus in-process
memory and passive versus learned navigation.

## Connections

- **Read-Write Attention Inversion**: Adds a **candidate third dimension** —
  architectural placement (in-loop vs external). The evidence shows a local
  latency effect, not that correct read/write design generally fails outside
  the loop.
- **Latent Horizon (#433)** and **Doomed from the Start (#455)**: Always-
  available memory suggests mechanisms worth testing, but neither connection is
  measured by these three papers.
- **Memory Architecture Divergence (#393)**: Suggests a sixth candidate failure
  mode, **placement failure**. Current evidence establishes it only for the
  tested latency-budget tasks.
- **Oversight Inversion (thesis)**: The proactivity ceiling has oversight implications — agents that can't proactively detect issues require human monitoring to catch problems before they compound. If memory architecture is the bottleneck, then improving agent self-monitoring is an infrastructure question (memory placement) not a capability question (model scale).

## Prediction

- **PROBE scores may stratify by memory architecture**: compare otherwise
  matched external/in-process stores and passive/learned navigation. This is the
  missing causal test, not a result already established here.
- **"Memory-first agent" pattern within 6 months**: At least one major agent framework will adopt in-process memory as a first-class architectural primitive, citing latency as the motivating design constraint.
- **Proactivity benchmarks will multiply**: PROBE's decomposition (search → identify → resolve) will become the standard evaluation framework for proactive agents, displacing pure task-completion metrics.
