### Analysis — The Hidden Deployment Tax

This story is architecturally significant despite modest engagement (75pts) because it names a cost that's been growing silently:

**The problem**: In 2023-2024, "serve an LLM" was a relatively uniform operation. By mid-2026, model families have diverged:
- Different attention mechanisms (MHA, MQA, GQA, and newer variants)
- Different Flash Attention kernel paths per architecture
- Different KV-cache behaviors that affect throughput characteristics
- Different quantization-response curves

**The implication**: Multi-model agent systems that switch between model families (e.g., using GPT-5.5 for generation and GLM-5.2 for verification, as scan #54 suggested) will pay a **deployment complexity tax** — you can't treat models as interchangeable plugins; each requires its own inference optimization path.

**Connection to Scan #54 hallucination architecture**: The "big generates, small verifies" pattern is architecturally correct but operationally expensive if the models are from different families requiring different inference stacks.

## Finding 55-4: Relaymux — Anti-Overengineering in Agent Orchestration (8pts, early)

A Show HN presenting a deliberately minimal approach to multi-agent orchestration: tmux windows + Telegram/iMessage as the UI layer.

**Source:** https://github.com/mupt-ai/relaymux (id: 48573655)

### Design Philosophy (from Show HN text)

> "The orchestration layer tends to feel overengineered. I mostly wanted a simple local harness for running and tracking CLI agents with the ability to hop in (via tmux). Relaymux is my opinionated attempt."

Key design decisions:
- Frontend: Telegram / iMessage / CLI (no custom web UI)
- Agents: Normal interactive CLI agents running in tmux windows
- Task tracking: Each long task becomes a named tmux tab
- Oversight: Human can hop into any agent's tmux session at any time
- Subagents: Usually with their own worktrees

### Analysis — The Orchestration Simplicity Backlash

This is low engagement (8pts) but architecturally interesting as a data point in a broader trend. The developer explicitly names the phenomenon: orchestration frameworks feel *over-engineered* for what most people actually need.
