## arXiv Cross-Source — THE GUIDANCE SURFACE

### Probe-and-Refine Tuning of Repository Guidance (2606.20512) — DECISIVE FINDING

This paper directly validates a core thesis of our system: the quality of guidance (AGENTS.md, context files, operational knowledge) is the decisive variable in coding agent performance.

**Key findings**:
- AGENTS.md files exist but "whether they help is contested" — conflicting evidence until this study
- **Probe-and-refine tuning**: uses synthetic bug-fix probes to iteratively diagnose and patch guidance files through single-shot LLM calls. No agent loop or tool use during tuning
- On SWE-bench Verified: 33.0% resolve rate (probe-and-refine) vs 28.3% (static knowledge base) vs 25.5% (no guidance). p < 0.001 for both contrasts
- **Critical insight**: Improvement comes from COVERAGE not PRECISION — refined guidance produces evaluable patches for +14.5pp more instances while per-patch precision stays constant (~59%, p = 0.119)
- Step-budget experiment: guidance is what lets agents use a larger step budget productively — without guidance, more steps = more wasted work
- Cross-model experiment: tuning degrades when model can't generate "sufficiently diagnostic output" — the tuning loop requires model quality to work

**Why this matters for our system**: Our `context.md` files, `AGENTS.md` patterns, and heartbeat files are precisely the "repository guidance" this paper studies. The finding that COVERAGE > PRECISION means: it's better to have guidance that helps agents FIND the right files than guidance that tells them exactly how to modify them. Our Cold Start Tax (46% ops = re-discovery) is the measurable cost of insufficient guidance coverage.

**Structural implications**:
1. Guidance is infrastructure, not documentation — it directly determines resolve rates
2. Guidance should optimize for COVERAGE (reaching more problem types) not PRECISION (getting each fix perfect)
3. Guidance can be tuned via probing — systematic testing reveals gaps
4. Larger step budgets only help WITH good guidance — without it, more compute is wasted

Source: https://arxiv.org/abs/2606.20512

### N-Version Programming with Coding Agents (2606.20158) — Diversity as Engineering Strategy

Revisits Knight-Leveson's N-version programming experiment with modern AI coding agents.

**Key findings**:
- 48 agent-generated implementations evaluated on 1,000,000 randomized test inputs
- **Substantial common-mode failure** — confirming Knight-Leveson's original finding that independent implementations still share failure modes
- Many co-occurring failures trace to where spec is "particularly hard or ambiguous" — shared failures emerge from shared ambiguity in guidance
- **But diversity provides practical benefit**: majority voting across 3-version units reduces mean failure count from 387.44 (single) to 130.99 (triple) — **66% reduction**
- 11,844 N-version units exhibit zero observed failures — diversity + voting IS a viable engineering strategy

**Connection to Homogeneity Trap (#70)**: lcamtuf's "100k Whys" identified per-instance quality passing while population-level failure occurs. N-Version Programming is the engineering response: deliberately create diversity, then vote. The key constraint is that common-mode failures (from shared ambiguity) resist diversification — you need DIFFERENT models, DIFFERENT languages, DIFFERENT agents to achieve meaningful diversity.

**Connection to wwind123's HN comment**: "I use 3 AIs to review each other's design plans and implementation. Each often catches problems the others miss." — practitioner independently discovering N-Version review.

Source: https://arxiv.org/abs/2606.20158

## 🔬 THE GUIDANCE SURFACE — New Synthesis

Six converging signals identify a structural principle: **the interface where human operational knowledge meets agent execution — the Guidance Surface — is the decisive performance variable in agent systems, exceeding model capability, prompt engineering, and architectural choices in impact.**

### The Evidence Stack

| Signal | Key Finding | Implication |
|--------|-------------|-------------|
| **Probe-and-Refine** (2606.20512) | Guidance quality → +7.5pp resolve rate; COVERAGE > PRECISION | Guidance is infrastructure, not documentation |
| **N-Version Programming** (2606.20158) | Diversity + voting = 66% failure reduction; common-mode failures trace to ambiguous guidance | Ambiguous guidance creates correlated failures |
| **ScaffoldAgent** (2606.20122) | Utility-guided dynamic outline evolution outperforms static outlines | Guidance should be dynamically tuned, not static |
| **PRINCE** (97pts, 3rd appearance) | "What model shouldn't see" > what it should; 99/1 data:agent tuning time | Subtraction-first guidance is empirically dominant |
| **Reject AI Code** (172pts, 6th appearance) | cadamsdotcom: "The agent should've delivered acceptable code" = guidance failure | Poor output is a guidance problem, not a model problem |
| **eranation** (HN discourse) | "LLMs diverge, not converge" — entropy increases without control | Guidance provides the convergence force against natural divergence |

### The Principle

Agent performance is bounded by **guidance surface quality**, defined as:

```
Effective_Performance = Model_Capability × Guidance_Coverage × (1 - Context_Noise)
```

Where:
- **Guidance_Coverage**: what fraction of problem space the guidance helps agents navigate to (Probe-and-Refine: +14.5pp instances reached)
- **Context_Noise**: what fraction of context is irrelevant or misleading (PRINCE: subtraction > addition)
- **Model_Capability**: the baseline reasoning ability (necessary but not decisive — Probe-and-Refine shows guidance converts a 25.5% baseline into 33.0%)

This explains several library observations:
- **Cold Start Tax** (46% ops = re-discovery): cost of zero guidance coverage for a new session
- **Compilation Threshold** (53.5% below floor): sessions fail when guidance is insufficient for the task
- **Coordination Tax** (2.04:1 planning:work): discovery is "searching for guidance that doesn't exist"

### Three Modes of Guidance

1. **Static Guidance** (AGENTS.md, context.md, heartbeat): Pre-authored, covers known patterns. Probe-and-Refine shows this can be systematically improved
2. **Dynamic Guidance** (ScaffoldAgent outlines, evolving context): Adapts during execution. Utility-guided — keeps what helps, removes what doesn't
3. **Diverse Guidance** (N-Version approaches): Multiple independent guidance interpretations + voting. Overcomes common-mode failures from single-guidance ambiguity

### Predictions

1. **"Guidance engineering" becomes a named discipline** — distinct from prompt engineering, focused on what agents should know about a codebase/project rather than how to phrase requests (6 months)
2. **Automated guidance tuning** (probe-and-refine style) becomes standard CI step — AGENTS.md files tuned by automated probing, not just human authoring (9 months)
3. **Guidance coverage metrics** emerge — analogous to code coverage, measuring what fraction of likely tasks the guidance helps with (6 months)
4. **Step budgets coupled to guidance quality** — frameworks recognize that more compute without better guidance is waste; guidance quality gates determine allocated step budget

### For Our System

Our system already embodies the Guidance Surface:
- `context.md` files = static guidance layer
- `heartbeat.md` = dynamic priority guidance
- Knowledge library = accumulated operational knowledge that reduces Cold Start Tax
- Scout findings = guidance for future sessions (what's changed in the world)

**Action implications**:
- Guidance should be optimized for COVERAGE (helping agents find right files/patterns) not PRECISION (telling them exactly what to write)
- Context discipline (what to exclude) is at least as important as content (what to include)
- Probe-and-refine style testing of our guidance quality would directly measure and improve system performance
- The heartbeat → context → knowledge cycle is manual ScaffoldAgent — same principle, human-in-the-loop
