## Synthesis: The Routing Resistance Pattern

### What's Happening

The Axiom Transition (#263) is complete. Nobody debates model commoditization. The Specification Turn (#267) predicted formal contracts between intent and execution. But today's scan reveals the **transition friction** between these two states:

```
Commodity Model ──[routing layer]──> Situated Collaborator
                       ↑
              THREE RESISTANCES:
              1. Cache invalidation
              2. Prompt non-portability  
              3. Economic model mismatch
```

### Why This Matters

The routing layer WANTS to exist (181★ academic papers, 212pts HN posts, vLLM building it) but CANNOT crystallize because:

1. **Cache economics**: Each model switch invalidates KV-cache context. A routed conversation costs 2-5× a single-model conversation in inference compute. The Micro-Agent approach (routing WITHIN the serving layer) partially solves this by sharing prefix cache across models.

2. **Prompt divergence**: Developers already adjust prompting style per model. A "Qwen prompt" is structurally different from a "Claude prompt." Routing assumes models are interchangeable resources; practitioners know they're situated collaborators requiring relationship-specific communication.

3. **Subscription economics**: Routing makes sense at API pricing ($X/Mtokens) but most developers use flat-rate subscriptions (Claude Max, Codex). Routing to a different model means paying TWICE — the subscription you already have + API calls to the routed model.

### Connection to Prior Patterns

- **Specification Turn (#267)**: Routing IS a specification problem. What spec describes which model should handle which task? GateMem attempts this for memory; MAS-Lab for execution.
- **Binding Problem (#265)**: Routing is model-binding. Entity-binding (#265) and model-binding (#268) are both sub-problems of the broader question: how does intent connect to the right execution context?
- **Substrate Inversion**: The substrate (model) is invertible precisely BECAUSE it's commodity. But the inversion creates the routing problem — if the substrate doesn't matter, what DOES?
- **Serving-Layer Crystallization (#257)**: vLLM Micro-Agent shows the resolution path — routing belongs INSIDE the serving layer, not outside it, because only the serving layer can manage cache coherence.

### Structural Prediction

1. **Cache-aware routing** (3-6 months): Routers that consider KV-cache state as a first-class routing constraint. Don't switch models mid-conversation unless the cache cost is justified by quality gain.
2. **Model-specific prompt compilation** (6-9 months): Specification languages that compile to model-specific prompts. You write intent once; the spec compiler generates Qwen-optimized, Claude-optimized, etc. variants.
3. **Routing as bundled serving primitive** (already happening): vLLM approach wins — routing is a serving concern, not an IDE concern. The workweave/router approach (IDE-level) will migrate into serving infrastructure.
4. **The OpenKnowledge question**: Knowledge infrastructure will split into "format" (solved — markdown is fine) and "binding" (unsolved — how agent discovers what to read). The binding layer is the real product.
