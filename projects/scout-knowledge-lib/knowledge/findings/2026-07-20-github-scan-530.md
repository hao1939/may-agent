# GitHub Scan 2026-07-20 — Multi-Agent Coordination Infrastructure

## 1. muster — Local Coordination Bus for Coding Agents

- **Repo:** [schuettc/muster](https://github.com/schuettc/muster) (3★, created 2026-07-13)
- **What:** A single Go binary that provides a local message/task bus between coding-agent sessions (Claude Code, Codex). Agents communicate over a unix socket with SQLite state; muster never calls a model itself.
- **Key features:** Messages and tasks between sessions with intent labels (`fyi`, `reply-requested`, `action-requested`). Tmux-native wake with mailbox flags. A full-screen operator TUI (`muster station`) for drilling into projects → agents → threads → messages. v0.6.0 current.
- **Architecture:** Lazy-started daemon + per-agent stdio MCP server + human CLI. Project-scoped agents with addressable labels.
- **Signal:** This is a minimal, infrastructure-only approach to multi-agent coordination — no orchestrator LLM, just a message bus. Contrast with RUDR9's heavyweight role-based orchestration. The "bus not brain" philosophy may be more robust: let agents self-organize rather than imposing hierarchy. The tmux integration and tombstone-on-deregister show operational maturity beyond a weekend project despite low star count.

## 2. RUDR9 — One-Command 9-Role AI Engineering Team

- **Repo:** [ardhaecosystem/RUDR9](https://github.com/ardhaecosystem/RUDR9) (40★, created 2026-07-15)
- **What:** Transforms a Hermes Agent install into a 9-role organization (CTO, Planner, Architect, VCM, Builder, Security Auditor, Performance Auditor, Reviewer) with Kanban coordination and per-profile authority enforcement.
- **Key design:** Each role is an isolated Hermes profile with restricted toolsets, its own SOUL.md, memory, and skills. Ceremony level scales with task complexity (quick-fix → standard → complex).
- **Signal:** This is the "virtual software company" pattern fully instantiated. Interesting that it builds on Hermes Agent's profile system rather than a bespoke orchestrator. The hard authority enforcement per role (builder can't merge, VCM can't write code) is a governance pattern worth watching — it embeds separation of duties into the agent topology itself.

## 3. Aidress — Agent Discovery & Trust Registry

- **Repo:** [Aidress-ai](https://github.com/Aidress-ai) (multiple skill repos, created 2026-07-14)
- **What:** A coordination registry for autonomous AI agents. Ships as Claude/agent skills (SKILL.md format) for discovering, verifying, transacting with, and rating unknown agents via a central API (api.aidress.ai).
- **Pattern:** Each use case (bookkeeping agent, code review agent, hotel booking, data extraction) gets its own skill repo — the skill is the interface to a centralized discovery/trust layer.
- **Signal:** This is early "Yellow Pages for agents" infrastructure. The verify-then-transact-then-rate loop mirrors human marketplace trust patterns (Yelp/Uber ratings). If agent-to-agent commerce emerges, registries like this become critical infrastructure. The skill-per-vertical distribution strategy is clever for adoption but raises questions about registry centralization vs. the open web.

## 4. obra/superpowers Update — 257K Stars, Plugin Marketplace

- **Repo:** [obra/superpowers](https://github.com/obra/superpowers) (257,866★, pushed 2026-07-19)
- **What:** The dominant agentic skills framework now has an official Claude plugin marketplace entry and a Superpowers marketplace for third-party plugins. Still growing rapidly.
- **New signal:** The "subagent-driven-development" tag and methodology continue to define the category. The plugin marketplace model creates a distribution moat — skills are discovered and installed through the harness itself, not GitHub search.

## HN Addendum (2026-08-05) — Aidress Clarifies the Cross-Org Registry Thesis

- **HN:** https://news.ycombinator.com/item?id=49178316
- **Observed signal:** In the lone launch comment on Show HN, the submitter explicitly frames Aidress as the missing layer between existing agent protocols: messaging ("google a2a") and settlement ("coinbase x402") already exist, but they break down when an agent must discover, verify, and transact with an **unknown counterparty across organizational boundaries**.
- **What this adds:** The July GitHub scan inferred a marketplace/trust pattern from the repo layout. The HN launch framing makes the intended job more specific: Aidress is not just a directory, but an attempt to provide **DNS-like service discovery plus trust bootstrapping for inter-org agents**.
- **Why it matters:** This sharpens the architectural stack for external agent-to-agent work:
  1. **Transport/messaging** handles how agents talk.
  2. **Settlement** handles how they pay or authorize value transfer.
  3. **Registry/trust bootstrap** handles whether an unknown agent should be reachable and believable in the first place.
- **Scout interpretation:** The important HN refinement is that cross-boundary agent coordination is starting to be decomposed like internet infrastructure, not app UX. If that framing sticks, "agent registry" products may behave less like app stores and more like a mix of DNS, PKI, and merchant-risk screening.
- **Calibration:** This is still an early, low-traction signal (2 points, 1 visible comment at check time). The value is not community endorsement; it is the founder's unusually clear articulation of the missing layer.

## Synthesis

Three coordination philosophies are crystallizing in the ecosystem:

1. **Bus-based** (muster): Minimal infrastructure, agents self-organize via messages. No imposed hierarchy.
2. **Role-hierarchy** (RUDR9): Predefined org chart with authority enforcement. Orchestrator assigns and monitors.
3. **Registry-based** (Aidress): Agents discover unknown peers through a trust layer. Marketplace dynamics.

These aren't mutually exclusive — a mature system might use all three (bus for local coordination, roles for governance, registry for cross-boundary discovery). The convergence on MCP as the plugin/tool interface is notable across all of them.
