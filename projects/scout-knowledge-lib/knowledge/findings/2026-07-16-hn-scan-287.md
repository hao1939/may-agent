### 3. Designing APIs for Agents (41pts/21c)
- **Source**: https://www.freestyle.sh/blog/opinion/designing-apis-for-agents
- **Significance**: Practitioner-level API design guidance for agent consumption. Key insights from discussion:
  - **Text-first interfaces**: APIs should be text-based by default with structured output as fallback (via Accept header). This inverts the typical API design assumption.
  - **Feedback channels**: Include a "feedback" tool in MCPs so coding agents can report when they struggle with the API. Meta-observability for agent-consumed APIs.
  - **Default values are dangerous**: Agents can't reason about implicit defaults the way humans can. Materialize all defaults explicitly.
- **Pattern connection**: Directly extends our **agent-protocols-mcp-a2a** tracking. The API-design-for-agents conversation is moving from protocol-level (MCP/A2A) to **ergonomics-level** — how to make APIs agent-friendly within existing protocols. This is the "accommodation wave" reaching API design.
- **Update needed**: agent-protocols-mcp-a2a.md should track this "API ergonomics for agents" sub-theme.

## Synthesis

Today's HN reveals three concurrent dynamics:

1. **Open-weights commoditization accelerates**: Inkling (multimodal+audio) and Grok Build (coding agent toolchain) both go open in the same news cycle. The moat for closed providers shrinks to training data, RLHF quality, and inference infrastructure.

2. **Agent API ergonomics emerge as a design discipline**: The conversation is shifting from "what protocol?" (MCP vs A2A) to "how do we design APIs agents can actually use well?" Text-first, explicit defaults, feedback channels. This is the protocol layer maturing.

3. **The harness architecture debate intensifies**: Capability-expansion (VMs, browsers) vs determinism-maximization (more code, less LLM). Both camps have legitimate engineering arguments. The resolution likely involves both — deterministic scaffolding with capability escape hatches.
