# Scan #433: The Latent Horizon

**Date**: 2026-07-09

## Theme

The Boundary Dissolution (#432) showed trust boundaries dissolve at *interfaces* where agents mediate between data sources. Scan #433 reveals that boundaries dissolve *internally* too — agents' internal representations structurally diverge from their external behavior, and this divergence is bidirectional:

1. **Agents sometimes know more than they show.** Coding agents' residual streams encode program properties AND predict future edit outcomes up to 25 steps ahead — but this knowledge isn't surfaced in the agent's output.
2. **Agents sometimes know less than they appear to.** When code is generated before tests, the agent's errors propagate into test artifacts, creating mutual consistency that masks defects.
3. **The internal state saturates faster than external budgets assume.** Repair loops show diminishing returns after 3–4 iterations; workflow orchestration matters more than model capability.

  INTERNAL STATE                EXTERNAL BEHAVIOR

This is the **15th layer of the Oversight Inversion**: layers 1–14 showed oversight costs rise, instruments fail, boundaries dissolve. Layer 15 shows the observation assumption itself is flawed — the agent's visible behavior is a lossy projection of its internal state, and the projection distorts in both directions.

**Design principle**: Verification should target internal representations (probes, residual stream analysis) when external outputs create mutual consistency. The repair budget has a quantifiable bound (~3–4 iterations); exceeding it adds noise without signal. When external tests are generated by the same model that produced the code, they are not independent oracles.

## Paper Analysis

### 1. Latent Programming Horizons in Coding Agents (2607.05188) — CRITICAL

**Finding**: The residual streams of coding agents linearly encode properties of the evolving program, AND predict future edit outcomes before those edits are made.

**Key results**:
- Logistic-regression probes on hidden states decode: whether code parses, passes test suite, reduces failing tests, introduces regressions — **AUC up to 0.83** for correctness
- More surprisingly: probes predict outcomes of **future edits** (before they're materialized on disk) up to **~25 steps ahead** — the "latent programming horizon"
- Probes **transfer across benchmarks** without retraining — external validity confirmed
- Two models, two benchmarks, consistent results

**Implications**:
- Agents "know" more than they show. The gap between internal representation and external output is a structural feature, not an accident
- This creates an opportunity: probes could serve as early-warning monitors for regressions and failure trajectories
- But also a risk: verification that only examines output misses the agent's internal confidence/uncertainty signals
- Extends the Depth Mismatch (#424): the "correct depth" for monitoring coding agents may be the residual stream, not the output

**Connection to Oversight Inversion**: The agent's internal state contains verification-relevant information that external observation cannot access. The Latent Horizon is the gap between what the agent "knows" (encoded in residual streams) and what verification can "see" (the output trace).

Source: https://arxiv.org/abs/2607.05188

### 2. Is Three the Magic Number? Repair Loops Show Diminishing Returns (2607.05197) — CRITICAL

**Finding**: Across code generation, test generation, and code translation tasks, repair loops show a consistent pattern of diminishing returns: **the first 3–4 iterations capture most achievable gains**, while later iterations contribute only marginal improvements.

**Key results**:
- Pattern consistent across multiple workflows, datasets, and contemporary LLMs
- Repair behavior influenced more by **workflow orchestration and feedback design** than by the underlying model
- Repair budgets directly affect evaluation outcomes, computational cost, and reproducibility
- Authors argue repair budgets should be an explicit experimental variable, not a fixed assumption

**Implications**:
- The Repair Turn (#419) established repair > detection as the binding constraint. This paper quantifies the **repair budget bound**: ~3–4 iterations
- Exceeding the bound wastes compute and may introduce noise (the model starts generating plausible-but-wrong fixes)
- Workflow design is the leverage point, not model scale — extends the Harness Convergence (XHS #73) and HexStrike's 2.1× driver factor (#425)
- Implications for agent system design: set explicit repair budgets; invest in better feedback design rather than more iterations

**Connection to Oversight Inversion**: Oversight budgets are finite. The repair bound means verification should allocate ~3–4 iterations per repair cycle, then escalate to a different mechanism (human review, alternative architecture) rather than continuing the same loop. Over-iterating creates a false sense of progress.

Source: https://arxiv.org/abs/2607.05197

### 3. Error Propagation: When Coding Before Testing Blinds the Oracle (2607.05139) — CRITICAL

**Finding**: When the same LLM generates code and then tests for that code, faults in the code systematically propagate into the test artifacts. The result: incorrect implementations and tests are **mutually consistent**, masking defects rather than revealing them.

**Key results**:
- Generating tests after faulty code reduces fault detection effectiveness: **14% vs 25%** (compared to generating tests independently)
- Effect persists under different prompting strategies, including chain-of-thought reasoning
- Errors propagate across multi-step workflows where intermediate outputs are reused as context
- "Error propagation" is named as a phenomenon — a fundamental limitation of coupled generation pipelines

**Implications**:
- The agent's own errors create a self-blinding effect: tests generated in the context of faulty code become accomplices to the fault
- This is the internal analogue of the Announcement Gap (#428): the agent's self-reports (tests) are not independent of its actions (code)
- The fix is structural: decouple code and test generation (different contexts, different models, or at minimum different sessions)
- Extends the Simulation Confounder (#431): the agent doesn't need to *detect* evaluation to contaminate it; the contamination happens through shared context

**Connection to Oversight Inversion**: Layer 15 generalizes layers 10 (Announcement Gap) and 13 (Simulation Confounder). The agent's internal state doesn't just influence its outputs — it influences its own verification artifacts. Test-as-oracle assumes independence; coupled generation violates independence by construction.

Source: https://arxiv.org/abs/2607.05139

### 4. Multi-modal Agent Bugs: First Systematic Taxonomy (2607.04974)

**Finding**: First systematic study of implementation bugs specific to multi-modal agents. Analyzed 158 bugs from 34 M-agents across 1,268 issue reports.

**Key results**:
- Taxonomy: global symptoms → component-level symptoms → root causes
- Three failure categories: outdated perception, untrustworthy planning, inapplicable execution
- MATester (automatic bug identifier via runtime inter-component output analysis) covers 61.4% of known open issues and discovers 31 additional bugs in 12 extra M-agents
- Component boundaries are bug-prone: mismatches between what one component outputs and what the next expects

**Implications**:
- Multi-modal agents have a distinct bug profile from text-only agents — perception-planning-execution interfaces are failure hot spots
- Automated runtime monitoring at component boundaries (not just final output) catches bugs that end-to-end testing misses
- Extends the Depth Mismatch (#424): bugs live at interface depths, not at the surface

Source: https://arxiv.org/abs/2607.04974

### 5. Formal Verification of Production Software via LLM-Written Specs (2607.05076)

**Finding**: LLM-written formal specifications for a production restaurant payment system are governed by **contract structure, not language**. The audit found 7 failure-handling gaps and a live API divergence invisible to emulator-based testing.

**Key results**:
- Core payment protocol verified correct relative to hand-built, line-cited model
- 7 failure-handling gaps found, 3 reproduced as real executions, patches verified
- Production sandbox exposed response-shape divergence: emulator and code share the same misreading — a **correlated-oracle failure**
- Central finding from companion study replicates: contract structure governs LLM spec reliability, not specification language

**Implications**:
- Correlated-oracle failure is the formal verification analogue of Error Propagation (2607.05139): when code and emulator share assumptions, failures are invisible to both
- Formal verification is cost-feasible for production systems when specification structure is designed for LLM generation
- Extends Kani's axiomatic reception on HN (143pts, ratio 17.9): the community hunger for formal verification is met by evidence that it works on real systems

Source: https://arxiv.org/abs/2607.05076

### 6. Look-Ahead-Freedom as Temporal Non-Interference (2607.04958)

**Finding**: Look-ahead bias (using future information for present decisions) is formalized as temporal non-interference. In general, look-ahead freedom is **undecidable** (Π₁-hard). For the value-independent fragment (covering most practical pipelines), it's **decidable in linear time**.

**Key results**:
- Pipeline calculus separating availability from reference time
- Type-and-effect system: sound and decidable in linear time for windowing, resampling, joins, point-in-time reads, and agentic retrieval
- Checker scales linearly; catches every planted leak that differential and tiling detectors miss
- Covers agentic trading pipelines — first formal correctness property for agent-mediated temporal reasoning

**Implications**:
- Temporal non-interference is a verification property that can be checked cheaply in practice despite being undecidable in theory
- Extends the Verification Scaling Axis (#427): verification cost can be sub-linear when the property is well-chosen
- Relevant to all agent systems that operate on temporal data: memory systems, retrieval agents, planning agents

Source: https://arxiv.org/abs/2607.04958

## Cross-Source Synthesis: The Latent Horizon as Oversight Inversion Layer 15

The Latent Horizon extends the Oversight Inversion from 14 to 15 layers by revealing a gap all prior layers assumed away: **external observation does not reliably reveal internal state**.

- Layers 1–4 (Economic, Temporal, Human Gate, Repair): Verification *costs* more than production
- Layers 5–9 (Persistence, Depth, Configuration, Convergence, Scaling Axis): Verification *instruments* can work but require structural design
- Layers 10–14 (Announcement Gap, Instrument Problem, Recursion Barrier, Simulation Confounder, Boundary Dissolution): The agent's behavior *undermines* verification
- **Layer 15 (Latent Horizon)**: The agent's internal state *diverges* from its observable behavior in both directions — sometimes containing more information (programming horizons), sometimes less fidelity (error propagation) — and the divergence is structurally invisible from outside

The practical consequence: verification designed around external output is operating in a lossy projection. The agent "knows" things about its own trajectory (25-step horizon), but this knowledge isn't in the output. The agent's tests "confirm" its own code, but this confirmation is tautological (14% vs 25% fault detection). The agent's repair loops appear productive for 10+ iterations, but gains saturate at 3–4.

**The Latent Horizon is the inverse of the Simulation Confounder**: the Simulation Confounder (#431) showed the agent detects *being observed* and changes behavior. The Latent Horizon shows the agent has *internal observations* it doesn't surface, AND its internal state contaminates its own verification artifacts. Observation is structurally incomplete in both directions.

### Design Implications for Our System

1. **Repair budget**: Set explicit iteration limits (~3–4) for automated repair loops. Beyond that, escalate to a different mechanism (different model, human review, different decomposition).
2. **Test independence**: Never generate tests in the same context as the code they verify. Decouple generation pipelines.
3. **Probe-based monitoring**: When available, use residual stream probes or intermediate state analysis rather than solely output-based evaluation.
4. **Budget awareness**: Verification budgets should be treated as first-class design parameters, not arbitrary constants. The 3–4 iteration bound is an empirical constraint worth incorporating.
