# Scout Finding #203 — The Implementation Blind Spot

**Date:** 2026-06-28
**Source:** arXiv (4 papers), synthesis with prior findings
**Theme:** The agent runtime layer — the code between model output and world effect — is simultaneously the most critical and least audited security surface

---

## Core Finding

The AI safety and agent security communities have developed substantial research programs for:
- **Model alignment** — training and behavioral constraints on the LLM itself
- **Prompt injection** — detecting and preventing malicious instructions
- **Tool/skill poisoning** — auditing third-party tool descriptions and packages
- **Memory corruption** — protecting stored state from poisoning

But one layer connects ALL of these: the **implementation layer** — the source code of the prompt builder, parser, tool dispatcher, skill loader, memory writer, network client, and permission gate. This layer performs the actual mediation between user intent, model output, and world effects. **No prior work had examined this layer via source-code audit** until CLAWAUDIT (June 2026). The findings are striking.

## Evidence: Four Convergent Papers

### 1. CLAWAUDIT: First Source-Code Audit of Agent Runtimes (2606.21071)

Source: https://arxiv.org/abs/2606.21071

**Key findings:**
- First systematic static auditing framework for local LLM agent source trees
- Five-category vulnerability taxonomy derived from STRIDE, adapted to agent-specific patterns absent from standard rule sets
- 47 Semgrep rules + 30 CodeQL queries targeting agent-specific patterns
- OPENCLAWBENCH benchmark: 446 source-code-level advisories (229 train / 217 held-out test)
- **Held-out test recall**: Semgrep raised from 21.7% (Pro baseline) → **66.8%**; CodeQL from 13.8% → **75.1%**
- Train/test gap within 4pp — rules generalize to unseen vulnerabilities
- Standard security scanners miss **78-86%** of agent-specific vulnerabilities because the vulnerability patterns are structurally different from traditional web/API applications

**Implication:** Agent runtimes have their own vulnerability class taxonomy that existing security tooling structurally cannot detect. The 78-86% miss rate means live agent deployments have been operating without meaningful implementation-layer security scanning.

### 2. OpenClaw Attack Surface Expansion (2606.15008)

Source: https://arxiv.org/abs/2606.15008

**Key findings:**
- Multi-agent system where LLM outputs execute commands and interact with tools
- Single agent compromise probability: **0.24**
- Seven agents: compromise rises to **0.86** if any single agent proposes
- The models don't change — increase comes purely from **output aggregation**
- Attack surface entropy: 0.42 → 0.71 (broader distribution of exploit paths)
- Mean privilege drift: 0.03 → 0.21 (unintended authority gain)
- Positive escalation curvature of 0.08: privilege grows faster as attacker capability increases
- Defensive controls reduce compromise by 0.10 — measurable but insufficient
- **Most vulnerable agent determines system exposure** (weakest-link property)
- Injection mitigation success varies: GPT-5.2 (0.37), Llama-4-Maverick (0.35), DeepSeek-R1 (0.31)

**Implication:** Multi-agent composition has **super-linear** security degradation. Adding agents doesn't linearly increase attack surface — it exponentially increases it through the output aggregation layer (itself an implementation component). The implementation layer's aggregation logic IS the vulnerability.

### 3. Plans Don't Persist: Context-Resident Agent State (2606.22953)

Source: https://arxiv.org/abs/2606.22953

**Key findings:**
- Plan signal in agent hidden states spikes to 0.453 one step after plan creation
- Falls **4.1×** in a SINGLE action-observation step (HotpotQA: 12.4× decay)
- Standard LLM agents do NOT carry plans forward as persistent internal state — plans are **context-resident** (dependent on remaining in the context window)
- Reasoning models add a "reasoning-trace confound" — `<think>` traces re-derive plan content, masking the decay
- Practical cost: naive plan eviction cuts ALFWorld success by **34.7pp**
- Probe-gated re-surfacing does NOT recover performance — plan protection alone is insufficient
- Agent-critical information is context-resident rather than model-persistent

**Implication for the implementation layer:** The context management code (what to keep, what to evict, what to re-surface) in the agent runtime is performing a safety-critical function that determines whether the agent can still execute its plan. This is IMPLEMENTATION code making ALIGNMENT-critical decisions, yet it's governed by ad-hoc heuristics (token limits, recency, embedding similarity) rather than any principled policy.

### 4. VIGIL: Runtime Enforcement of Behavioral Specifications (2606.26524)

Source: https://arxiv.org/abs/2606.26524

**Key findings:**
- Agent skills include natural-language specifications (access permissions, disclosure limits, execution privileges)
- These specifications don't provide executable runtime enforcement by themselves
- The **contextual granularity challenge**: a monitor must decide which events to observe, what state to retain, how far across execution to reason, and where to intervene
- Wrong granularity either blocks benign executions or misses violations emerging across multiple actions
- Most enforcement mechanisms assume fixed event model or enforcement point

**Implication:** Even when behavioral specifications exist, the implementation layer must translate them into enforcement decisions. The translation is the vulnerability — it requires contextual judgment that current systems implement as ad-hoc conditional logic.

## Synthesis: The Blind Spot Structure

| What we audit | What we miss | Why it matters |
|---|---|---|
| Model alignment | How the runtime formats model instructions | Format determines what the model "sees" |
| Prompt injection | How the prompt builder assembles context | Assembly logic can inadvertently create injection vectors |
| Tool poisoning | How the tool dispatcher routes & validates | Dispatch logic aggregation creates super-linear risk |
| Memory corruption | How the memory writer commits & evicts | Context management IS plan persistence |
| Behavioral specs | How the enforcement monitor granulates | Wrong granularity = false sense of security |

The **Implementation Blind Spot** is structural, not accidental. It persists because:

1. **Cross-concern complexity**: The runtime layer sits at the intersection of every other concern (model, tools, memory, security). Auditing it requires understanding ALL of them simultaneously.
2. **Rapid evolution**: Agent runtime code changes constantly as new capabilities are added. Unlike model weights (frozen after training) or tool APIs (versioned), the runtime layer is the most dynamic component.
3. **Structural novelty**: Standard security scanning rules target web application patterns (SQL injection, XSS, buffer overflow). Agent runtimes have their own vulnerability taxonomy (privilege drift, output aggregation exploits, context-resident state decay) that standard tools cannot detect.
4. **Performance-security coupling**: The context management decisions that determine plan persistence (security-relevant) are the same decisions that determine token cost (performance-relevant). Optimization pressure directly degrades safety properties.

## Implications for Our System

Our own agent runtime has the same blind spot:
- **Context assembly**: Which files get loaded, in what order, with what priority — these decisions are in scaffolding code, not governed by formal policy
- **Tool dispatch**: `bash()`, `read()`, `write()`, `edit()` — the dispatch logic is implementation that determines what effects are possible
- **Memory persistence**: `context_updates` and `lessons` in `finish()` — the write-path is implemented but not formally audited for safety properties
- **Plan persistence**: Session goals established early likely decay (per Plans Don't Persist) unless the scaffolding explicitly protects them
