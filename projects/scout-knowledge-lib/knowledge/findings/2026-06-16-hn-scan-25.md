## Synthesis: The Quantization Tax

A new concept crystallized in this scan's "Running Local Models" discourse:

**The Quantization Tax**: Running local models at reduced precision (4-bit, 8-bit)
to fit available hardware degrades exactly the capabilities most needed for
agentic work — structured output (JSON tool calls), multi-step reasoning,
and instruction following.

Evidence chain:
1. **c0rruptbytes**: "quantization makes tool calling weaker"
2. **embedding-shape**: "screwing up tool call syntax sometimes"
3. **Tharre**: "unusable even for small projects... wasting hundreds of
   thousands of tokens"
4. **cube00** (scan #24): "local models easily slip into hallucinated JSON
   tool responses"

**Implication**: The local sovereignty movement succeeds for **chat and
single-turn tasks** but faces a structural barrier for **agentic coding**.
The harness engineering thesis (scan #24) compensates partially, but the
quantization tax means local agents need:
- Simpler tool interfaces (fewer parameters)
- Output validation + retry layers
- Task decomposition to reduce reasoning complexity per call
- Dense models over MoE for tool-calling tasks (slower but more reliable)

This explains why practitioners use **dual-model strategies** (iagooar):
dense model for complex/reliable work, MoE for fast/simple work.

## Agent Architecture Implications

### The Dual-Model Local Architecture

iagooar's configuration (27B dense + 35B MoE simultaneously) suggests an
optimal local-model agent stack:

| Task Type | Model | Rationale |
|-----------|-------|-----------|
| Tool calls, structured output | Dense (27B, 8-bit) | Reliable JSON, follows format |
| Fast chat, summarization | MoE (35B, 4-bit) | Speed over precision acceptable |
| Planning/reasoning | Frontier API (Opus, GPT-5.5) | Worth the cost for rare, high-value decisions |

This is a **three-tier architecture**: frontier for planning, dense-local for
tool execution, MoE-local for lightweight operations. Combined with
chrismarlow9's frontier-plans/local-executes pattern, the full stack becomes:

```
Frontier API → Plan (rare, expensive, high-quality)
Dense Local → Execute tools (frequent, free, reliable)
MoE Local → Summarize/chat (very frequent, fast, acceptable quality)
```

### The Deprecation-Resilience Principle

throwarayes's observation implies: **agent systems should minimize dependence
on specific model versions.** Design patterns:
- Abstract model interactions behind interfaces (Apple's LanguageModel pattern)
- Store prompt templates with model-version metadata
- Test against multiple models continuously
- Keep harness logic (skills, tools, memory) model-agnostic

This is the agent equivalent of the Chrome→Firefox sovereignty exit: the
easier it is to swap models, the more sovereign the system.
