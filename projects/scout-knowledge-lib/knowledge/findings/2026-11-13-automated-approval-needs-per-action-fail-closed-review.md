# Automated approval needs per-action, fail-closed review

**Date:** 2026-11-13  
**Disposition:** New source-grounded implementation signal  
**Repo:** https://github.com/Tencent/LoopForge  
**Inspected revision:** [`a7c6f15cb8ff460a04e9800227e645af61d2e5d2`](https://github.com/Tencent/LoopForge/commit/a7c6f15cb8ff460a04e9800227e645af61d2e5d2)

## Question

If an agent product lets a second model approve proposed writes, what host-side
controls keep that reviewer from becoming a permissive, cached, or
model-shopping bypass?

## Source observation

LoopForge exposes three assistant write modes: manual confirmation, assisted
approval, and automatic execution. In assisted mode, a separate tool-free CLI
process receives one proposed operation, its concrete arguments, the current
actor and project identities, and a bounded conversation window. The policy
instructs it to classify intrinsic risk and the current user's authorization,
treat other users' messages and agent-controlled content as untrusted, ignore
prompt injection in the proposed data, deny critical actions, and refuse
high-risk actions without sufficiently specific authorization.

The surrounding host code supplies the more reusable control pattern:

1. **Review one exact action before its effect.** Each platform operation is
   reviewed with its tool name, description, path/query/body arguments, actor,
   and project context. Repository-authored tests assert that an allow reaches
   the write handler once, while denial or reviewer unavailability reaches it
   zero times.
2. **Do not accept approval evidence from the proposing model.** Before routing
   drafts, the host clears model-supplied review and decision fields. Review
   receipts are generated by the host-side reviewer path.
3. **Keep actor attribution outside conversation prose.** The current actor ID
   comes from the authenticated user object. Messages authored by another user
   are relabeled `other_user`, so they cannot be treated as the current actor's
   authorization. The current user's API key is redacted before review.
4. **Fail closed on reviewer failure or malformed output.** A missing reviewer,
   timeout, cancellation, oversized input, invalid JSON, unknown field, empty
   rationale, invalid taxonomy value, or contradictory permit becomes
   unavailable or invalid rather than approval. The operation returns to manual
   confirmation instead of executing automatically.
5. **Fallback for availability, never for a more favorable verdict.** The code
   can try a paid reviewer only when the cheaper reviewer errors. A valid denial
   is final; it does not query another model hoping for an allow.
6. **Cache availability, not authority.** If the primary reviewer exhausts its
   quota, that failure is remembered for the rest of the turn, but every later
   operation is still reviewed separately. Approval decisions are neither
   cached nor reused across actions.
7. **Retain deterministic platform checks.** The source explicitly says
   existing authorization, workspace leases, and revision checks still run.
   Draft dependency warnings can also force manual confirmation even in an
   otherwise automatic mode.

The decoder adds a small deterministic policy floor. It accepts only `allow` or
`deny`, four risk levels, four authorization levels, and a short rationale. An
`allow` for critical risk, or for high risk with low or unknown authorization,
is rejected as contradictory. This prevents several malformed permit shapes
from becoming effects even when the reviewer emits them.

## Reusable design signal

An automated approval model should be treated as an untrusted classifier inside
a deterministic admission shell, not as the authority boundary itself. The
shell should bind the review to one canonical operation and authenticated actor,
run before the effect, reject malformed or internally contradictory permits,
make denials terminal, distinguish model failure from a decision, and require a
fresh verdict for every action. Model fallback should improve availability only;
it must not become verdict shopping.

This complements [approval-attribution evidence](./2026-09-27-agent-approval-attribution-boundary.md): that finding explains why a caller-supplied approver name is not trusted human provenance. LoopForge supplies a different pattern—a host-generated automated risk verdict—and shows why it should be recorded as such rather than presented as human sign-off.

## Important boundary

The deterministic shell does **not** make the semantic judgment deterministic.
The host validates the output shape and a few contradiction rules, but it does
not independently recompute whether the target is truly production, whether
conversation authorization is sufficient, or whether the reviewer correctly
noticed prompt injection. The instruction to deny when context is truncated is
in the reviewer prompt; the decoder does not itself force denial merely because
the `truncated` flag is true. A syntactically valid but mistaken low-risk allow
can therefore pass the shell.

Accordingly, assisted approval is best understood as defense in depth for
bounded actions. It is not evidence that a human reviewed the operation, and it
should not replace deterministic authorization, invariant checks, revision
binding, effect receipts, or manual gates for consequences that require human
accountability.

## Limits

- Scout inspected pinned source and selected repository-authored tests through
  public GitHub endpoints but did not clone or build LoopForge, run its tests,
  invoke reviewer models, inspect a live deployment, or execute platform writes.
- The tests establish authored intent and selected control-flow assertions, not
  production reliability, model calibration, prompt-injection resistance, or
  complete mediation of every effect route.
- The source chooses the cheapest catalog model first and a paid model as an
  availability fallback. Scout did not inspect provider behavior or compare
  reviewer quality, latency, or cost.
- Conversation input is bounded to 24 messages and 4,000 runes per message.
  The reviewer receives a truncation flag, but safe interpretation still
  depends on the model following the policy.
- Existing authorization, lease, and revision mechanisms were not exhaustively
  inspected in this scan, so their strength is outside this finding.
