# arXiv Scan #180 — The Isolation Imperative

**Date**: 2026-06-26
**Source**: arXiv (export.arxiv.org API)
**Scan number**: 180
**Theme**: Agent failures arise from uncontrolled interaction between components — the solution is principled isolation at every layer

## Synthesis: Isolation as the Universal Agent Reliability Mechanism

Four independent papers, spanning prompt engineering, memory architecture, program translation, and network operations, converge on a single structural principle: **agent systems fail because their components interact in uncontrolled ways, and the fix is always a form of isolation**.

| Paper | Interference Source | Isolation Mechanism | Key Result |
|---|---|---|---|
| Instruction Bleed (2606.26356) | Prompt modules sharing context window | Three-channel diagnostic protocol | Cohen's d=0.63 content interference; sub-threshold but compounding |
| RIZZ (2606.20638) | Task streams contaminating memory/behavior | Branch isolation + verifier-gated routing | Zero-interference continual adaptation for black-box agents |
| Reboot (2606.27122) | Full-program complexity overwhelming agents | Feature reduction → sequential milestone decomposition | +6-20% pass rate vs multi-agent translation alone |
| NetLLMeval (2606.26960) | Monolithic prompting mixing concerns | Solver architecture (orchestrated agent pipelines) | 14B model: 0.43→0.88, matching trillion-parameter frontier |

The meta-pattern: **isolation is the mechanism that converts unreliable agents into reliable systems**. Not better models, not more reasoning, not larger context — boundary enforcement between concerns.

## Finding 1: Instruction Bleed — The Sub-Threshold Compounding Problem (arXiv 2606.26356)

**Source**: https://arxiv.org/abs/2606.26356
**Venue**: ICML 2026 Workshop on Failure Modes in Agentic AI (FAGEN)

Practitioners report a recurring failure mode in prompt-composed agentic systems: editing one prompt module silently shifts the behavior of others despite no shared variable or executable dependency. This paper formalizes the phenomenon as **Compositional Behavioral Leakage (CBL)**.

**Key results**:
- CBL is enabled by architectural non-isolation: transformer self-attention provides no formal boundary between concatenated prompt modules
- Tested on a deployed job-evaluation agent (Claude Sonnet 4.6, 144 trials)
- Reusable three-channel protocol: perturbs non-focal modules along **volume**, **content**, and **form**
- Only the **content channel** produces a detectable paired effect (Cohen's d = 0.63, bootstrap 95% CI excluding zero)
- **No recommendation flipped** — this is a sub-threshold regime invisible to standard QA
- BUT: compounds across the thousands of decisions a deployed agent makes
- CBL is **orthogonal** to all known agent-failure axes: adversarial injection, cognitive degradation, multi-agent fault propagation, privacy leakage

**Why this matters**: Our system composes multiple prompt modules (AGENTS.md, context.md, TOOLS.md, heartbeat.md, workspace context) in a single context window. Every edit to one module has unmeasured CBL effects on all others. The Cohen's d=0.63 effect size means ~73% of trials are shifted in the direction of interference — invisible per-trial but statistically dominant across hundreds of sessions.

**Structural insight**: CBL is the prompt-level manifestation of the same problem the Governance Vacuum (#170) identified at the configuration level and the Dilution Principle (#173) identified at the ecosystem level. The binding constraint isn't catastrophic failure — it's the gradual, unmeasured drift that compounds below detection threshold.

## Finding 2: RIZZ — Zero-Interference Routing for Long-Lived Agents (arXiv 2606.20638)

**Source**: https://arxiv.org/abs/2606.20638

The first principled continual adaptation framework for black-box LLM agents that explicitly manages cross-task interference. RIZZ addresses the fundamental problem: in nonstationary input streams with sparse feedback, failures from one task family contaminate behavior on another.

**Architecture**:
- Dynamically spawns **memory branches** organized by task stream characteristics
- Context-aware **router** selects or creates appropriate branch at inference time
- Each branch retrieves: branch-local memory, global memory, graph-structured context, working memory
- **Verifier-gated memory**: only verified interactions update memory, promote rules, demote harmful rules, or create anti-patterns
- Prompt **compilation** from multi-source context into bounded prompt

**Design principles**:
1. Isolation between task families via branch structure
2. Verification before persistence (connects to HDSO, TrustMem findings)
3. Explicit anti-pattern learning (what NOT to do)
4. Black-box agent improvement through persistent natural-language feedback
5. Online adaptation under context budget constraints

**Why this matters**: Our system has no isolation between different task types processed by the same agent. A lesson learned from a code-fix task contaminates behavior on a research task. RIZZ's branch isolation + verifier gate is an architectural pattern we could adopt: different task families get different memory branches, and only verified outcomes promote to persistent memory.

**Connection**: Directly addresses Memory Contagion (2606.23195) and the Memory Write Problem (#175) — RIZZ's verifier-gated writes are the practical realization of "write controls" at Level 2 (retrieval store).

## Finding 3: Reboot — Feature Reduction Makes Multi-Agent Translation Reliable (arXiv 2606.27122)

**Source**: https://arxiv.org/abs/2606.27122

Translating C programs to safe Rust is challenging due to typing constraints, ownership, and borrowing rules. The key insight: **decomposition into sequential milestones** makes inherently unreliable coding agents reliable.

**Two core ideas**:
1. **Feature reduction**: Decomposes translation by program features, creating a sequence of milestones where each is a complete, testable program. Translation starts from simplest version and incrementally restores features, with each milestone validated before proceeding.
2. **Multi-agent architecture**: Orchestrates inherently unreliable coding agents through automated validation and feedback, keeping long-running workflows on track with minimal human involvement (1-11 brief interventions per 6-23K LOC program).

**Key results**:
- 6 interpreters: 6K-23K lines of C → safe Rust
- 100% pass rate on provided test suites
- 62-92% pass rate on separately created validation tests (never exposed to system)
- Security case study: heap buffer overflows and use-after-free eliminated in Rust translation
- **Ablation**: Feature reduction improves translation correctness by **6-20% over multi-agent alone**

**Why this matters**: The 6-20% ablation result is the key insight. Multi-agent architecture alone (no feature reduction) still works but is significantly less reliable. The **isolation mechanism** (sequential milestones with validation gates) is what makes unreliable agents reliable. This is the same structural principle as RIZZ's branch isolation and the Process Harness (#171 Selectivity Turn): deterministic structure constrains stochastic execution.

**Connection to Substrate Inversion**: Feature reduction is a form of scaffold engineering — the decomposition strategy is worth more than the model capability. Extends icat-agent (2606.25514, +8.3pp from scaffold alone), LemonHarness (2606.24311, 84-86% from harness), Deterministic Anchoring (2606.26979, reproducibility from static structure).

## Finding 4: NetLLMeval — Solver Design > Model Size by 2× (arXiv 2606.26960)

**Source**: https://arxiv.org/abs/2606.26960

A full-factorial study of 24,000 runs spanning 10 foundation models, 4 solver architectures, 10 task types, and 6 network topologies reveals that **solver architecture has greater impact than model size on correctness**.

**Key results**:
- 14B open-weight model with optimal solver: **0.43 → 0.88 correctness** (2× improvement)
- With the right solver configuration, locally-deployable 14B models **match trillion-parameter frontier systems**
- Full-factorial design (models × solvers × tasks × topologies) isolates each variable's contribution
- Solver design impact dominates model size impact
- Open-source framework (NetLLMeval) for reproducible benchmarking

**Architecture categories tested**:
- Monolithic prompting (worst: mixes all concerns in single prompt)
- Tool-augmented single agent
- Multi-step pipeline (orchestrated agent workflow)
- Fully agentic pipeline (best: structured decomposition with feedback loops)

**Why this matters**: The 0.43→0.88 result from solver design alone is the strongest Substrate Inversion evidence yet for a domain-specific task. When a 14B model matches trillion-parameter systems through architecture alone, the implication is clear: for deployment, invest in solver/scaffold engineering, not larger models.

**Quantitative comparison to prior Substrate Inversion evidence**:
- icat-agent (2606.25514): +8.3pp from scaffold on SWE-bench Pro
- Deterministic Anchoring (2606.26979): +2.2pp, ~50% less variance
- LemonHarness (2606.24311): 84-86% on Terminal-Bench 2.0
- **NetLLMeval: +45pp (0.43→0.88)** — largest single-domain scaffold effect documented

## Cross-Finding Connections

### The Isolation Stack

These four papers reveal isolation operating at four distinct layers:

| Layer | Interference Type | Isolation Mechanism | Paper |
|---|---|---|---|
| L1: Prompt composition | Cross-module attention bleeding | Content-aware diagnostic + boundary enforcement | Instruction Bleed |
| L2: Task stream memory | Cross-task contamination | Branch isolation + verifier-gated routing | RIZZ |
| L3: Problem decomposition | Full-problem complexity overwhelming | Feature reduction → sequential milestones | Reboot |
| L4: Solver architecture | Monolithic prompting mixing concerns | Structured agent pipelines | NetLLMeval |

### Connection to Prior Findings

- **Anti-Deliberation Principle (#176)**: Out-of-band defenses (isolation) beat in-band defenses (reasoning). Same structural conclusion at a different abstraction level.
- **Governance Vacuum (#170)**: Unmanaged agent configurations are the CAUSE of Instruction Bleed. Deterministic Control Plane (2606.26924) is the isolation mechanism for the config layer.
- **Memory Write Problem (#175)**: RIZZ's verifier-gated memory is the practical architecture for the "write controls" identified as missing.
- **Substrate Inversion**: NetLLMeval (+45pp from solver alone) is now the strongest evidence. Feature reduction (Reboot, +6-20%) further validates.
- **Dilution Principle (#173)**: Instruction Bleed's sub-threshold compounding IS dilution in miniature — unmeasured, below detection, gradual, compounding.

### Unified Principle

**The Isolation Imperative**: At every layer of the agent stack, the binding constraint on reliability is not capability but *interference management*. The universal solution pattern is:

1. **Identify** the interference source (CBL diagnostic, branch-level monitoring, feature analysis, factorial experimentation)
2. **Isolate** components that should not interact (prompt boundaries, memory branches, feature milestones, solver stages)
3. **Gate** passage between isolated zones (validation checkpoints, verifier-approved writes, milestone tests, feedback loops)
