## Finding 172: Agent Testing Pushback — TesterArmy (YC P26) (117pts, 55c)

**Signal strength: MEDIUM** (Launch HN, direct agent-testing value debate)

TesterArmy (YC P26) offers agents that test web and mobile apps. Community response reveals skepticism about the fundamental value proposition.

| Author | Position | Pattern |
|--------|----------|---------|
| **poisonborz** | "E2E tests are now quick to write due to LLMs, and are then deterministic AND cheap to run. How would this compare to the token costs of running an agent the whole time for each test?" | **LLM-written tests > agent-run tests** |
| **dbbk** | "If I'm already using Opus to write the code, surely it would know best what E2E tests to write to verify its own output?" | **Code-writing agent subsumes testing agent** |
| **negamax** | "Was writing E2E tests ever a problem that needs automation? Config overhead and potential security leaks makes it a no go." | **Problem doesn't exist** |
| **Eridrus** | "Has anyone tried to build their own version of this? I'm not super excited about using some 3rd party SaaS as a critical part of my testing." | **Sovereignty concern** (even for testing!) |
| **msencenb** | "Have you been able to nail down a loop where your tool can take an open PR, guess the code path and do some testing?" | **PR-triggered testing as desired feature** |
| **pranshuchittora** | Reverse-engineers stack: "gemini-3-flash for fast mode, gpt-5.4 for deep mode, 15-min timeout." | **Architecture exposed** |

### The Agent Testing Value Paradox

poisonborz and dbbk articulate a structural challenge for agent testing companies:

1. LLMs make writing deterministic E2E tests trivially cheap
2. Code-generating agents already know what tests to write
3. Running an agent for *each test execution* costs tokens every time, vs. free re-runs for deterministic tests
4. The security surface of giving a third-party agent access to your app is non-trivial

**The value proposition for agent testing narrows to:** exploratory testing that can't be pre-scripted, and ad-hoc testing of PR-specific changes (msencenb's use case). But even this faces the Bnjoroge signal from Finding 168: cheap vision-enabled models (DeepSeek v4flash + vision) could commoditize the agent testing stack entirely.

**Connection to Comprehension Cliff:** This is the testing-domain manifestation. AI makes tests cheap to write, but who verifies the tests are correct? The comprehension problem shifts from code to test correctness.

### Convergence Pattern

**davebren's counter** is the Comprehension Cliff at the review level: if you use AI review first, you'll trust it and do a less thorough manual review. The same confidence-erosion pattern as LLM-generated tests that pass (usernametaken29, scan #14).

**Connection to Specification-First Inversion (Scan #34):** Code review is migrating from "line-by-line correctness" to "does it match the spec?" — which is exactly Charity Majors' thesis. Multi-model review accelerates this by making line-level review AI's job while humans focus on spec compliance.
