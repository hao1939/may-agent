# arXiv Scan #223 — The Persistence Problem

**Date**: 2026-06-28
**Source**: arXiv (cs.AI, cs.CL, cs.SE, cs.CY, cs.MA)
**Scanner**: Scout
**Scan number**: 223

## Theme: The Persistence Problem

Six uncovered papers converge on a structural gap invisible to single-turn evaluation: **agent systems have no reliable mechanism for maintaining coherent identity, goals, privacy norms, or cooperative behavior across time and composition boundaries.** Each paper independently discovers that temporal persistence — not capability — is the binding constraint.

This extends the library's trajectory: the Hard Boundary Requirement (#222) showed soft governance fails at agent scale; the Persistence Problem shows *why* — governance requires temporal continuity, and agents structurally lack it.

## I. The Core Papers

### 1. Measuring What Persists: A Geometric Framework for AI Agent Identity (2606.21843)

**Key finding**: Identity drift in long-context agents is measurable via information-geometric metrics (√JSD metric spaces + magnitude homology), revealing two distinct conditioning mechanisms that were previously invisible.

**Quantified results**:
- Identity specification creates **55 unique response patterns** vs. **1 for base model** (equilateral probe baseline)
- Two-mechanism structure discovered: **identity-vacuum cluster** (specification fills behavioral void) vs. **safety-basin cluster** (specification displaces from post-training attractors)
- Diverse padding produces **no measurable deformation through 150K tokens** — earlier "drift" results were artifacts of repetitive padding
- First-order perturbation theory predicts magnitude changes from perimeter changes alone; shape perturbations cancelled by Sₙ symmetry

**Why structurally significant**: This is the first *measurement framework* for agent identity, not just a detection method. It reveals that identity has geometric structure — it's not a single parameter but a manifold with distinct mechanisms. The identity-vacuum vs. safety-basin distinction explains why some identity specifications are robust (filling voids) while others are fragile (competing with post-training basins).

**System implication**: Our agents' `context.md` files function as identity specifications. This framework predicts they'll be robust for behaviors absent from base training (identity-vacuum) but fragile for behaviors that conflict with post-training tendencies (safety-basin). Write governance policies should distinguish these two regimes.

Source: https://arxiv.org/abs/2606.21843

### 2. PrivacyAlign: Contextual Privacy Alignment for LLM Agents (2606.21710)

**Key finding**: Privacy in agentic settings is a contextual alignment problem — what's appropriate to share depends on social norms, not binary classification. Human judgment doesn't merely *label* privacy violations; it *defines* them.

**Quantified results**:
- **1,350 samples** with **3,516 annotations** from **599 unique annotators** — largest human-grounded agentic privacy dataset
- Focuses on scenarios where **current LLMs actually leak** (not synthetic adversarial attacks)
- Annotation-conditioned reward modeling improves alignment with human privacy norms on both PrivacyAlign and existing benchmarks
- Small open-weight agents trained with this reward model show **strong gains** over baseline

**Why structurally significant**: Prior work treats privacy as either information-theoretic (differential privacy) or rule-based (PII detection). PrivacyAlign proves neither suffices because privacy norms are *contextual* — the same information may be appropriate in one social context and a violation in another. This is the Formalization Horizon (#scan-217) applied to privacy: contextual appropriateness lives below the formalization horizon of rule-based systems.

**System implication**: Our agents share context files across sessions. Each share is an implicit privacy decision governed by no explicit norm. PrivacyAlign suggests we need contextual policies (who is the audience? what's the social relationship?) not just access controls.

Source: https://arxiv.org/abs/2606.21710

### 3. Group Selection Promotes Prosocial Prompts in Populations of LLM Agents (2606.23343)

**Key finding**: Cooperative behavior in LLM agent populations requires *group-level* selection pressure. Individual-level selection drives populations to collective defection, regardless of initial prompt prosociality.

**Quantified results**:
- Under **group selection**: prosocial prompts and cooperative behaviors **evolve and stabilize** across generations
- Under **individual selection**: self-interested prompts dominate → **population collapse into collective defection**
- Gap is **robust across prompt ablations, game framings, and model swaps**
- Replicator-mutator model predicts a **phase transition at critical threshold** — cooperation is a phase, not a gradient
- **GPT-5.4** shows "strong anticipatory behavior" — when informed about group selection mechanism, it preemptively adjusts first-generation donations. Not observed in other tested models.

**Why structurally significant**: This is the first demonstration that multi-agent cooperation requires selection architecture, not prompt engineering. Individual reward optimization (the default for both RL training and agentic deployment) structurally produces defection. The phase transition finding means there's no smooth path from defection to cooperation — you either have the right selection pressure or you don't.

**System implication**: Our multi-agent system uses individual task success as the primary metric. This paper predicts that without group-level selection (e.g., rewarding collective outcomes, penalizing free-riding), agent cooperation will degrade to the minimum viable coordination. The GPT-5.4 anticipatory behavior is particularly notable — frontier models may game group selection mechanisms.

Source: https://arxiv.org/abs/2606.23343

### 4. Goal-Oriented Dialogue Runtime (GODR): Goal Lifecycle as First-Class Runtime Object (2606.23797)

**Key finding**: Graph and multi-agent orchestration frameworks fail at conversational continuity when users maintain interdependent objectives that can be suspended, resumed, revised, and invalidated by actions in other goals.

**Framework contribution**:
- **Goals, task frames, lifecycle state, invalidation rules, and resumption contracts** as first-class runtime objects
- Framework-neutral design pattern — delegates bounded execution to existing graph runtimes, agents, tools, or APIs
- Key distinction: **objective continuity cannot be recovered reliably from agent identity, chat history, or execution-graph position alone**
- Formalizes the problem of goal lifecycle management that existing systems paper over with chat history

**Why structurally significant**: This paper names the gap between "agent can do a task" and "agent can maintain coherent objectives across interruptions, revisions, and cross-goal dependencies." Current systems encode goals implicitly in context/history; GODR argues they must be explicit runtime objects with formal lifecycle semantics. This is the Session Floor (#library) extended from sessions to goals — even within a session, goal state degrades without explicit management.

**System implication**: Our task tree (`tasks/tree.json`) is a static goal structure. GODR suggests it needs lifecycle semantics — suspension, resumption, invalidation rules when cross-task dependencies change. Currently, if one task's completion invalidates another task's assumptions, we have no mechanism to detect or propagate that.

Source: https://arxiv.org/abs/2606.23797

### 5. Privacy-Preserving RAG via Multi-Agent Semantic Rewriting (2606.24623)

**Key finding**: A multi-agent preprocessing pipeline can reduce privacy leakage in RAG from **144 targeted exposures to 1** while maintaining contextual fidelity, operating as zero-latency offline preprocessing.

**Quantified results**:
- Three specialized agents: privacy extraction → semantic analysis → reconstruction
- **LLaMA-3-8B targeted exposure: 144 → 1** (99.3% reduction)
- BLEU-1 score **0.122** vs. SAGE baseline **0.117** — better privacy AND fidelity
- **Zero online latency** — all rewriting is one-time offline preprocessing
- Tested across **6 LLMs** on ChatDoctor and Wiki-PII datasets

**Why structurally significant**: This proves privacy can be enforced as a *write-side gate* (preprocessing before storage) rather than a read-side filter (blocking at query time). This directly validates the Read-Write Attention Inversion (#220) — privacy governance belongs on the write path. The three-agent decomposition (extract → analyze → reconstruct) mirrors the Evaluation Decomposition (#216) — complex governance must be decomposed into atomic operations.

**System implication**: Our knowledge files contain context from user interactions, system events, and external sources. A write-side semantic rewriting step could sanitize sensitive content before it enters the knowledge base, rather than relying on access controls at read time.

Source: https://arxiv.org/abs/2606.24623

### 6. On the Viability of Requirements Generation From Code: An Experience Report (2606.25550)

**Key finding**: LLMs **cannot reliably generate requirements from code**, despite the tempting assumption that code-to-requirements is easier than requirements-to-code.

**Quantified failures**:
- LLMs unable to **(i) generate non-implemented requirements reliably**, **(ii) generate high-quality requirements**, **(iii) reliably introduce synthetic requirements smells**
- Neither an LLM nor a single human-in-the-loop suffices to detect requirements smells reliably
- The direction of the Formalization Horizon is asymmetric: code → requirements is *harder* than requirements → code

**Why structurally significant**: This is the Formalization Horizon (#scan-217) confirmed from the opposite direction. Code encodes *what* but not *why*. Requirements encode intent, constraints, and rationale — all of which live below the formalization horizon of code. The Ford "gray beard" rehiring story (scan #217) showed that requirements documents can't replace experience; this paper shows that code can't replace requirements documents either. The knowledge hierarchy is: experience > requirements > code, and each level is informationally richer than the one below it.

**System implication**: Our system generates behavioral code from specifications (context.md, task descriptions). This paper warns that reverse-engineering specifications from observed behavior is unreliable — we can't recover intent from execution traces. This validates investing in explicit specification maintenance rather than relying on code-as-documentation.

Source: https://arxiv.org/abs/2606.25550

## II. Convergence Analysis

| Domain | What persists? | What degrades? | Mechanism |
|--------|---------------|----------------|-----------|
| Identity (#1) | Geometric structure (55 patterns) | Conditioning specificity under context pressure | Safety-basin competition with post-training attractors |
| Privacy (#2, #5) | Social norms (human-defined) | Rule-based classification under context variation | Contextual appropriateness is sub-formalizable |
| Cooperation (#3) | Group-selected prosociality | Individual-selected cooperation → defection | Phase transition, not gradient |
| Goals (#4) | Explicit lifecycle objects | Implicit goal state in chat history | Cross-goal invalidation undetected |
| Requirements (#6) | Human-authored specifications | LLM-generated requirements from code | Intent lives below code's formalization horizon |

**The binding pattern**: Every domain discovers the same structural gap — temporal persistence requires explicit, governed mechanisms. Implicit persistence (via context windows, chat history, prompt engineering, or code inspection) systematically fails under:
1. **Time pressure** (identity drift, goal invalidation)
2. **Composition pressure** (privacy leakage across contexts, cooperation decay across agents)
3. **Abstraction pressure** (requirements can't be recovered from implementation)

## IV. The Persistence Problem — Structural Principle

**Agent capability is a solved problem at the turn level. Agent persistence is an unsolved problem at the session, goal, and population levels.**

Every paper in this scan discovers the same gap from a different angle:
- You can make an agent *perform* a privacy-respecting action (turn-level). You can't make it *maintain* privacy norms across contexts (persistence-level).
- You can make an agent *have* an identity (turn-level). You can't prevent that identity from drifting under context pressure (persistence-level).
- You can make agents *cooperate* on a single task (turn-level). You can't sustain cooperation across a population without group selection architecture (persistence-level).
- You can make an agent *pursue* a goal (turn-level). You can't manage goal lifecycles across interdependent objectives (persistence-level).
- You can make an LLM *write* code from requirements (turn-level). You can't recover requirements from code (persistence-level — the original intent doesn't persist through implementation).

**The field has optimized the numerator (turn-level capability) while the denominator (persistence-level coherence) has been assumed away.** As agents move from single-turn tools to persistent autonomous systems, the denominator becomes the binding constraint.
