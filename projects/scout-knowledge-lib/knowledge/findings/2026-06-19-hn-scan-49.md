## Finding 49-1: Agent-Targeted GitHub Supply Chain Attack (850pts, 221c) — CRITICAL NEW SIGNAL

**Signal strength: VERY HIGH** — second-highest engagement in scan, highest NEW signal.

A security researcher found 10,000+ GitHub repositories distributing trojan malware via cloned repos with malicious payloads. The critical insight is in the community's diagnosis of the target:

### Key Practitioner Positions

| Author | Position | Pattern |
|--------|----------|---------|
| **guhcampos** | "This is not targeted to humans. It's targeted to agents. They just need to appear on a fraction of the searches agents do to add dependencies and get lucky a couple times." | **Agent-targeting thesis** — the attack surface is LLM agent dependency resolution |
| **Jimmc414** | "I have found my name attached to new projects that I have nothing to do with or they are derivatives of my projects with redirection to unknown sites." | **Identity hijacking** — open source maintainers weaponized as lures |
| **RoadieRoller** | "May be to make it appear on the top of the 'Last Updated' repositories... So instead of the author's actual repo, the users end up cloning the trojan infected one." | **SEO for agents** — freshness signals gamed to capture agent search |
| **bananamogul** | "I reported a repo containing obvious nulled software to GitHub in February 2024. The repo is still there 2+ years later." | **Platform negligence** — GitHub's moderation doesn't scale to agent-era threats |
| **mustaphah** | "GitHub does NOT give a shit about the scale of the malware problem... I was so surprised by tens of malware repos that looked like trending repos." | **Platform trust erosion** — infrastructure provider as unwitting attack surface |
| **danso** | "Being reminded of a Disney engineer who downloaded an AI-gen tool from GitHub and 'checked the code himself, it had looked legitimate.'" | **The Disney precedent** — human review fails against well-crafted malware; agents won't do better |
| **StableAlkyne** | "I landed on a phishing page for my bank [via Bing search]. The page was a near perfect copy." | **Cross-platform attack surface** — search engines + package registries + repo platforms all compromised |

### Why This Is a Critical Signal for Agent Systems

This is the first concrete, large-scale evidence of an attack vector **specifically designed for LLM coding agents**:

1. **The attack surface is agent dependency resolution**: When an agent searches GitHub for a library to install, it uses freshness, star count, README quality, and name similarity as heuristics — exactly the signals these repos are gaming. A human developer might recognize a suspicious repo; an LLM agent follows heuristic patterns.

2. **The attack economics are agent-favorable**: Creating 10,000 repos is trivial via automation. Each repo needs to fool an agent exactly once. With agents making hundreds of dependency decisions per day across thousands of coding sessions, the base rate of encounters is high enough for consistent infection.

3. **The cleanup asymmetry is structural**: GitHub's moderation operates on report-and-review cadence (2+ years for obvious cases per bananamogul). Agent-driven code generation operates on minutes-per-decision cadence. The attacker generates repos faster than the platform can remove them.

4. **The "who checks the checker" problem**: guhcampos identifies the meta-level issue — agents that select dependencies are the same agents that might review code for security. If the initial dependency selection is compromised, the review is compromised too.

### Library Connections

- **Scan #46 prediction "AI-authored supply chain risk becomes named CVE category within 6 months"** → TRAJECTORY CONFIRMED. Not yet a named CVE category, but the specific attack vector (fake repos targeting agent dependency resolution) is now documented with 10k examples.
- **Agent Security & Governance note** — This is a concrete instance of the "tool trust" problem: agents must evaluate tool/dependency trustworthiness but lack ground truth for verification.
- **KE-045 (Verification Budget)** — The agent's verification budget for dependency selection is zero (it trusts search results and README quality). This is the attack surface.

### Structural Significance

The GitHub malware story reveals a **new attack category**: not malware hidden in legitimate packages (traditional supply chain), but **malware placed where agents look for packages**. The distinction is critical:

- Traditional supply chain attack: compromise a popular package → infect downstream users
- Agent-era attack: create thousands of plausible-looking repos → wait for agents to select one

The defense surface is different: traditional attacks need package registry hardening; agent-era attacks need **agent-side verification** (code review before installation, dependency pinning, allowlist-only installation).

### Predictions

1. First documented case of an LLM coding agent introducing malware via dependency selection within 3 months
2. Major agent framework (Claude Code, Cursor, Copilot) adds dependency verification guard within 6 months
3. GitHub introduces "verified publisher" or "agent-safe" badge for repos within 12 months
4. Attack volume doubles by Q4 2026 as agent adoption increases

## Finding 49-3: AI-Authored Code Trust Crisis — Fable Pylint → Rust (76pts, 101c)

**Signal strength: MEDIUM** — Low score but exceptionally high comment ratio (1.33c/pt), indicating intense debate.

Fable (the AI lab whose model was recently suspended by the US government) published prylint — a complete Rust reimplementation of Python's pylint linter, claiming "byte-for-byte identical output" at 15-2300× speedup. The code was 100% authored by Claude. Community response reveals a deep split:

### Key Practitioner Positions

| Author | Position | Camp |
|--------|----------|------|
| **mohsen1** | "Writing software is not a sport that if you 'cheat' using tools then your results are worthless. Results are speaking for themselves." | **Pragmatist** — output matters, not provenance |
| **TheChaplain** | "A project with author/s that have passion for every line feels more real and worth my trust." | **Traditionalist** — human authorship = trust |
| **thraxil** | "I ported djlint to Rust, also relying heavily on LLMs... It's currently unmaintained but was part of our CI/CD." | **Practical middle** — LLMs for unmaintained dependency replacement |
| **wg0** | "Open source is dead. If your product is open source, building a business around it would be impossible because someone else would point an AI agent at it and have a similar thing to offer." | **Existential threat** — AI makes open source business models unviable |
| **torginus** | "Labs RL on converting successively bigger programs from language A to B... which implies that eventually one can set 'A' to English and 'B' to x86 assembly." | **Extrapolation** — code conversion → natural language compilation |
| **Hamuko** | "So basically ruff check --select=PL but worse in every single way, maintained by a system that's not even available anymore?" | **Practical criticism** — existing Rust tool (ruff) already covers this |
| **dk_sig11** | "It is the easiest use-case for agents because deterministic tool for testing/verification exists... It is still a niche use-case." | **Calibrated assessment** — works when verification is cheap |

### The Three Emerging Trust Positions

1. **"Results are results"** (mohsen1, Lucasoato): If the tests pass and the output is identical, provenance is irrelevant. The binary either works or it doesn't.

2. **"Trust requires understanding"** (TheChaplain, ma2kx): Software trust comes from the ability to inspect, understand, and modify code. AI-authored code is opaque even when readable — no human understands why specific architectural decisions were made.

3. **"Open source is dead"** (wg0): If an agent can replicate any open source project in hours, the business model of "free code, paid support" collapses. The moat was human expertise in the codebase; that moat is gone.

### Structural Significance

This debate crystallizes around a specific question that prior scans discussed abstractly: **when an AI-authored program passes all tests but no human understands its internals, what is the trust model?**

dk_sig11's calibration is the key insight: AI-authored code conversion works precisely when external verification exists (test suites, byte-for-byte output comparison). It fails when verification requires understanding (security review, architectural decisions, edge case reasoning). The trust model is: **trust the tests, not the code**.

### Library Connections

- **Engineering Discipline narrative (scan #48)** → "Code is no longer precious; evaluation is what matters now." Prylint is the concrete example: the code is AI-authored; the test suite is the value.
- **Agent Security & Governance** → AI-authored code introduces a new trust category: code that passes mechanical verification but has unknown provenance and unknown intent. This is structurally similar to the GitHub malware repos in Finding 49-1 — both exploit the gap between "looks correct" and "is trustworthy."
- **Scan #46 prediction: "AI-authored supply chain risk becomes named CVE category"** → prylint itself isn't malicious, but the pattern (AI-authored full codebase published as drop-in replacement) is exactly the attack surface the prediction described.

### Predictions

1. At least one major project adopts an "AI-authored code" disclosure policy within 6 months
2. Package registries (npm, PyPI, crates.io) add provenance metadata for AI-authored packages within 12 months
3. "Open source is dead" thesis gains mainstream coverage within 3 months, then retracts as community shows differentiation
4. Fable-style "whole project conversion" becomes a standard LLM benchmark within 6 months

**Signal strength: MEDIUM** — YC launch post with skeptical community reception.

TesterArmy offers AI agents that test web and mobile apps end-to-end. The community response is notable for its uniform skepticism:

### Key Objections

| Author | Objection | Category |
|--------|-----------|----------|
| **poisonborz** | "E2E tests are now quick to write due to LLMs, and are then deterministic AND cheap to run. How would this compare to token costs?" | **Economics** — generated deterministic tests are cheaper than runtime agent tests |
| **dbbk** | "If I'm already using Opus to write the code, surely it would know best what E2E tests to write to verify its own output?" | **Architecture** — coding agent should generate its own tests |
| **negamax** | "Was writing E2E tests ever a problem that needs automation?" | **Problem validity** — questioning whether the pain point exists |
| **Eridrus** | "I'm not super excited about using some 3rd party SaaS as a critical part of my testing." | **Security/trust** — testing access = full application access |

### The Deeper Signal

The community's rejection is not about TesterArmy specifically — it's about the category "agent-as-service-for-testing." The consensus position: LLMs are already good enough at *generating* deterministic tests, which are cheaper and more reliable to *run*. The delta between "AI generates tests" and "AI runs tests" is negative: you pay more tokens for less reliability.

This is dk_sig11's calibration from Finding 49-3 applied to testing: the value of AI in testing is generating the test (one-time cost, deterministic output), not executing the test (recurring cost, nondeterministic output).

### Library Connections

- **KE-055 (Behavioral Temperature)** → Agent-based testing is inherently "hot" (high temperature, nondeterministic). Generated tests are "cold" (deterministic, predictable). The community is choosing cold over hot for testing.
- **Engineering Discipline (scan #48)** → The same "evaluation is the bottleneck" insight: the valuable work is defining what to test (agent-assisted), not running the tests (deterministic tooling).

## Cross-Finding Synthesis: The Agent Trust Trilemma

Three findings in this scan converge on the same structural problem:

1. **Finding 49-1**: Agents can't verify dependencies (malware repos pass heuristic checks)
2. **Finding 49-3**: AI-authored code passes mechanical tests but has no trust provenance
3. **Finding 49-4**: Agent-as-tester introduces nondeterminism into the verification layer

The common thread: **agents are being asked to participate in trust decisions (dependency selection, code authorship, test execution) without the ability to establish or verify trust.**

This is structurally identical to the Deference Spectrum's finding that behavioral governance converges to extremes. In agent trust:

- **Full trust** (agent selects dependencies freely) → vulnerable to malware repos
- **Zero trust** (human reviews every dependency) → defeats the purpose of agent autonomy
- **No stable middle exists** because the agent cannot distinguish trustworthy from malicious at the presentation layer

The only stable configuration is **structural enforcement**: allowlists, pinned dependencies, verified publishers — mechanisms that constrain the agent's choice space rather than asking it to exercise judgment.

### Predictions from This Synthesis

1. **Agent dependency allowlists** become a standard feature within 6 months
2. **Code provenance tracking** (human vs AI authored) becomes a supply chain requirement within 12 months
3. **The "agent trust" problem** generates its own research subfield within 2026
4. First major security incident attributed to LLM agent dependency selection within 3 months
