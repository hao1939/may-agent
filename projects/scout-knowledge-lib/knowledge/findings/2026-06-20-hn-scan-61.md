## arXiv Cross-Source: The Experience Externalization

Three papers from 2026-06-16 through 2026-06-18 independently propose that agent experience should be externalized from individual agents into shared infrastructure. Combined with Skill-MAS from scan #60, this represents a coherent wave:

---

### 📄 Multi-Agent Transactive Memory / MATM (2606.19911)

**Core thesis**: Agent trajectories encode reusable procedural knowledge but are typically discarded after single use. MATM creates population-level storage and retrieval of trajectories where producer agents contribute and consumer agents retrieve to improve task execution.

**Key results**: Retrieving trajectories from MATM improves downstream task performance and reduces interaction steps WITHOUT coordination or joint training. Tested on ALFWorld and WebArena.

**Design pattern**: "Population-level experience sharing in open agent ecosystems" — agents don't need to talk to each other; they just need access to the same experience pool.

**Connection to our system**: Our `lessons` array and `context.md` updates ARE a primitive form of MATM. But they're per-agent, not population-level. MATM suggests the winning move is pooling experience across all agents — scout's findings becoming coder's procedural knowledge, etc.

Source: https://arxiv.org/abs/2606.19911

---

### 📄 AtomMem: Atomic Facts for LLM Agent Memory (2606.19847)

**Core thesis**: Coarse memory representations and unstable unconstrained updates degrade long-term memory. Solution: decompose experience into atomic facts, organize into hierarchical event structures and temporal profiles, then retrieve via associative memory graph.

**Key results**: State-of-the-art on LoCoMo benchmark across reasoning tasks. "Scalable and economically viable" for personalized agents.

**Architecture**: 
1. Fact Executor → selectively extracts high-value atomic facts from interactions
2. Hierarchical event structures capture episodic context
3. Temporal profiles track evolving attributes
4. Associative memory graph connects fragmented memories

**Connection to our system**: Our `context.md` approach is "coarse and unstable" by AtomMem's taxonomy. We append facts as text bullets with no structure, no temporal evolution tracking, no associative linking. AtomMem suggests a next step: structured atomic facts with explicit temporal evolution.

Source: https://arxiv.org/abs/2606.19847

---

### 📄 Deontic Policies for Runtime Agent Governance / AgenticRei (2606.19464)

**Core thesis**: Current policy engines (XACML, Rego, Cedar) only handle permit/prohibit. Agent governance requires the full deontic structure: obligations (must-do-after), dispensations (waive obligation under conditions), meta-policy conflict resolution, and ontological reasoning over domain hierarchies.

**Key contributions**:
- Deontic policy language expressed as OWL, evaluated by logic engine entirely outside the LLM
- Same pipeline governs both tool invocations AND agent-to-agent messages
- Composes with A2AS (Agent-to-Agent Services) framework
- Names the gap: "obligation lifecycle management" is absent from all production engines

**Connection to our system**: Our guard system (C1.3 Verify-After-Write, EXP-267 format checking) is permit/prohibit only. AgenticRei suggests the next maturity level: after-action obligations ("after editing a KE, you MUST update the index"), dispensations ("waived if file is <10 lines"), and conflict resolution between competing guards.

**Connection to Compilation Gradient**: This paper IS Stage 3 compilation applied to governance — moving from "please follow conventions" (Stage 1) to "typed guards block execution" (Stage 2) to "formal deontic reasoning with obligation lifecycle" (Stage 3).

Source: https://arxiv.org/abs/2606.19464

---

### 📄 Leadership as Coordination Control (2606.19111)

**Core thesis**: Leadership adds value to multi-agent LLM teams ONLY where: (1) the round-0 majority is unreliable, (2) the task is recoverable, and (3) undirected interaction does not already repair it. Outside this narrow region, leadership is redundant.

**Key result**: Across 12 (model, regime) combinations, transactional control matches a shared vote to within 1.3pp. Gains appear on exactly ONE combination (llama-4-scout social; situational +8pp over flat). This is a LARGELY NULL RESULT — which is what contingency theory predicts, not a failure.

**Design implication**: Don't add coordination controllers unless you've measured that (a) round-0 consensus fails, (b) the task allows recovery, and (c) agents can't self-repair. Most tasks that seem to need orchestration actually don't.

**Connection to our system**: Our hierarchical dispatch (manager → specialist) is appropriate when tasks are well-defined and clear. But for creative/exploration work (like this scan), flat structure with stigmergic coordination (shared files) may be equally effective — which is already our architecture.

Source: https://arxiv.org/abs/2606.19111

---

### 📄 Beyond Static Leaderboards: Predictive Validity (2606.19704)

**Core thesis**: Aggregate-score leaderboards systematically underspecify deployed-agent evaluation. Rankings don't transfer to out-of-distribution settings. Proposes "predictive validity" (correlation between in-sample and out-of-sample rank) as the correct metric.

**Key contribution**: Twelve-tier measurement apparatus exposing deployment-relevant dimensions that HELM and successors collapse. Three falsifiable out-of-distribution criteria with explicit thresholds.

**Connection to Evaluation Mirage**: Extends our existing KE on evaluation problems. The paper operationalizes what we've been calling "the evaluation mirage" — benchmarks that don't predict deployment performance.

Source: https://arxiv.org/abs/2606.19704

---

### 📄 Phoenix: Safe Multi-Agent GitHub Issue Resolution (2606.20243)

**Core thesis**: Seven layered safety controls + baseline-aware test evaluation for multi-agent issue resolution. Six specialized agents (planner, reproducer, coder, tester, failure analyst, PR agent) coordinated by label-based GitHub webhook state machine.

**Key results**: 75% oracle-resolution on SWE-bench Lite slice; 100% correctness preservation on 42 real issues. Half of PRs are well-targeted fixes; half place code at incorrect paths (planner localization limitation).

**Design implications**: 
- Label-based state machine for agent coordination (stigmergic, not message-passing)
- Deployment failure modes are instructive: WAF filtering, token expiry, permission boundaries, flaky CI — these are the REAL challenges, not algorithmic ones
- 50% mislocalization rate suggests the "trajectory collapse" from scan #60 is real and common

Source: https://arxiv.org/abs/2606.20243

## Meta-Pattern: The Experience Externalization

Extending the Decoupling Cascade from scan #60, three independent research teams propose the same architectural shift within 72 hours:

| Paper | Experience Problem | Externalization Response |
|-------|-------------------|------------------------|
| **Skill-MAS** (scan #60) | Can't learn from past sessions without fine-tuning | Meta-Skills: strategy as distilled artifact |
| **MATM** | Trajectories discarded after single use | Population-level trajectory repository |
| **AtomMem** | Coarse memory, unstable updates | Atomic facts → hierarchical events → associative graph |

**The common move**: Agent experience is migrating from *private internal state* (context window, fine-tuned weights) to *shared population-level infrastructure* (trajectory stores, fact databases, meta-skill registries).

This is the memory analogue of the Substrate Inversion:
- **Substrate Inversion**: Intelligence migrates from model weights to architecture
- **Experience Externalization**: Learning migrates from individual context to shared infrastructure

**Why this matters for us**: Our system already implements a primitive version — `lessons` in finish() calls feed `context.md`, which is per-agent but readable by all. The research suggests the next step is:
1. **Structured atomic facts** (not free-text bullets)
2. **Cross-agent retrieval** (scout's findings → coder's procedural knowledge)
3. **Temporal profiles** (tracking how facts evolve, not just current state)
4. **Associative linking** (connecting related facts across agents)

**Prediction**: Within 6 months, the dominant agent architecture pattern will include an explicit "experience layer" that sits between agents and their context — a shared, structured, retrievable pool of procedural knowledge that no individual agent owns.

## Governance Evolution: From Guards to Obligations

The AgenticRei paper + UK VPN age-gate discourse reveal a parallel maturation in governance:

| Current State | Next State | Paper/Signal |
|---------------|-----------|------|
| Permit/prohibit guards | Full deontic structure (obligations, dispensations, conflicts) | AgenticRei |
| "Age-gate the content" | "Age-gate the circumvention tools" (recursive arms race) | UK VPN discourse |
| Identity before action | Action before identity (Cloudflare ephemeral) | Temp accounts |
| Leadership for all tasks | Leadership only where round-0 consensus fails | Leadership paper |

The governance field is discovering that binary allow/deny is as insufficient for agents as it was for human systems. The full stack requires: permissions + obligations + exceptions + conflict resolution + temporal lifecycle. Our guard system is at Stage 2; AgenticRei shows what Stage 3 looks like.
