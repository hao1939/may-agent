# Scan #240: The Capability Mutual Exclusion Problem

**Date**: 2026-11-01
**Sources**: arXiv (4 uncovered papers + 4 library cross-references)
**Scan number**: 240
**Theme**: Agent capabilities that pass evaluation independently suppress each other when co-deployed

---

## Thesis

The field evaluates agent capabilities in isolation — tool calling accuracy, structured output compliance, semantic reasoning, social deduction — and declares them solved. But when these capabilities must co-exist in the same system at inference time, they don't merely degrade. They **mutually exclude**: enabling one suppresses another through mechanisms invisible to independent evaluation.

This is not the Competence Composition Illusion (scan #228, step competence ≠ system competence) — that was about aggregation failure across sequential steps. This is about **simultaneous capability conflict within a single inference pass**. Two capabilities, each individually functional, become architecturally incompatible when activated together.

Four uncovered papers, cross-referenced with four library findings, independently demonstrate this from different entry points.

---

## Signal Cluster

### Signal 1: The Constraint Tax — Tool Calling Dies Under Structured Output (arXiv 2606.25605)

**"Constraint Tax in Open-Weight LLMs: An Empirical Study of Tool Calling Suppression Under Structured Output Constraints"**

Source: https://arxiv.org/abs/2606.25605

The most mechanistically clear demonstration of capability mutual exclusion. When tool calling and JSON Schema structured output constraints are simultaneously enabled in production agent systems:

- **Tool calling ceases entirely** despite maintained high schema compliance
- **Each capability works perfectly in isolation** — tool execution succeeds alone, schema compliance succeeds alone
- **Mechanism identified**: JSON Schema constraints are compiled into grammar-based token masks at the decoding level. These masks make tool-call control tokens **literally unreachable** during decoding. The structured output constraint physically blocks the token paths that tool calling requires.
- **Formalized as Constraint Priority Inversion (CPI)**: Schema satisfaction dominates action-selection behavior when multiple constraints are simultaneously active. The model doesn't "choose" not to call tools — the decoding infrastructure prevents it.
- **Fix proposed**: "Transparent Two-Pass Execution" — decouples tool execution from schema-constrained response generation into separate inference passes. Restores tool invocation while preserving structured output guarantees without retraining.

**Why this is structurally significant**: This isn't a bug. It's a *category* of failure. Grammar-based constrained decoding — the mechanism that makes structured output reliable — operates at the token-mask level, below the model's reasoning. It doesn't know about tool-call semantics. It simply blocks tokens that violate the grammar. When tool-call tokens happen to violate the output grammar, capability B (tool calling) is physically suppressed by capability A (structured output) even though neither "knows" about the other.

**Library cross-reference — Inseparability Proof (2606.27567, Scan #236)**: The Constraint Tax is a concrete instance of the inseparability theorem's prediction. Shared-embedding architectures cannot maintain independent control channels. Here, the control channel for structured output (token masks) and the control channel for tool calling (control tokens) share the same decoding path and cannot be independently governed.

**Library cross-reference — Tool-RL Collapse (2606.26027, Scan #165)**: The Latent Capability Problem showed that RL training can destroy tool-calling *format* while preserving tool-calling *knowledge*. The Constraint Tax shows the same pattern at inference time rather than training time — the capability is intact but its expression channel is blocked by a co-active constraint.

### Signal 2: Probabilistic Agents in Deterministic Audits — The Phase Boundary (arXiv 2606.25622)

**"Probabilistic Agents in Deterministic Audits: Evaluating Multi-Agent Systems for Automated Audits Based on the German IT-Grundschutz"**

Source: https://arxiv.org/abs/2606.25622

A real-world deployment evaluating multi-agent systems for IT security certification under the German IT-Grundschutz standard. Two architectural contributions:

1. **Hypothesis-Verification Loop**: Cross-references agent-inferred dependencies against a Knowledge Graph to reduce hallucinations in Structural Analysis
2. **Decoupled Reasoning Pipeline**: Separates agent-driven semantic extraction from deterministic protection-need inheritance

**Key empirical result**: The MAS achieves high efficacy in **semantic tasks** (Structural Analysis, Modeling) but exhibits significant limitations in **logical reasoning phases** (Protection Needs Assessment, IT-GS Check). The probabilistic nature of LLMs "struggles to meet the deterministic rigor required by IT-GS."

**Why this is capability mutual exclusion**: The system needs two capabilities — semantic understanding (what is this system? what are its components?) and deterministic logical reasoning (given these components, what protection needs propagate?). LLMs excel at the first. But the *same property* that makes them good at semantic extraction (probabilistic, context-sensitive, flexible reasoning) is exactly what makes them fail at deterministic inheritance (rigid, rule-following, reproducible logic).

This is not "the model isn't smart enough." It's that **semantic capability and deterministic rigor are architecturally antagonistic** within a single LLM inference. Improving semantic flexibility worsens deterministic compliance, and vice versa. The paper's fix — the Decoupled Reasoning Pipeline — is structurally identical to the Constraint Tax's Two-Pass Execution: split the capabilities into separate phases that don't share inference state.

**Library cross-reference — Compilation Gradient (governance-compilation-gradient.md)**: This paper provides empirical evidence for the Compilation Gradient's prediction: governance properties that require determinism cannot be achieved by probabilistic systems, and the boundary is not gradual but a phase transition. Semantic tasks work; deterministic tasks fail. There's no middle ground.

### Signal 3: Vulnerability Communication Across Entity Types — Channel Mutual Exclusion (arXiv 2606.28125)

**"How Humans, Bots, and Agents Communicate About Vulnerabilities in Pull Requests"**

Source: https://arxiv.org/abs/2606.28125

A registered report (pre-registered methodology) studying vulnerability communication in pull requests across three entity types: humans, bots, and coding agents. Built on the AIDev-pop dataset.

**Key structural observation**: Each entity type communicates about vulnerabilities through categorically different channels:
- **Humans**: Implicit security-related language ("unauthorized access," "SQL injection") — semantic, contextual, distributed across PR discussions
- **Bots**: Explicit identifiers (CVEs, GHSAs) — formal, structured, reference-based
- **Agents**: Neither pattern clearly — agents are entering a communication ecology where vulnerability signals are split across channels that each entity type cannot access

**Why this is capability mutual exclusion at the communication level**: The study frames a system-level problem — vulnerability detection in a mixed human-bot-agent codebase requires reading *both* explicit identifiers AND implicit security language. But each entity type's communication strength is the other's blind spot:
- Bots catch CVEs humans miss; humans catch semantic vulnerability patterns bots can't parse
- Agents generate code that may introduce or fix vulnerabilities without using either communication channel
- Prior work focused on explicit identifiers "potentially overlooking vulnerability discussions that lack formal references"

This is mutual exclusion at the **information channel** level: formal-reference capability and semantic-implication capability serve the same goal (vulnerability awareness) but operate through incompatible detection mechanisms. A system optimized for one channel systematically misses the other.

**Library cross-reference — Admission-Execution Separation (Scan #238)**: The paper's framing maps directly to the admission-execution split. Whether a vulnerability "enters" awareness (admission) depends on which communication channel is monitored. If only CVE identifiers are tracked (bot channel), semantic vulnerability discussions are structurally invisible. If only prose is tracked (human channel), formal references are missed. The admission mechanism excludes one capability by design.

### Signal 4: Triadic Werewolf — Dyadic Evaluation Hides Compositional Failure (arXiv 2606.27909)

**"Triadic Werewolf: A Jester Role for Multi-Hop Theory of Mind in LLMs"**

Source: https://arxiv.org/abs/2606.27909

Extends the Werewolf social deduction game with a Jester — a third faction whose utility function is inverted (wins by being voted out). This creates a triadic incentive structure requiring reasoning across three opposing utility functions simultaneously.

**Key results across 60 games (GPT-4.1, DeepSeek-V3.1, Llama-3.3-70B)**:
- **Jester wins 60-70% of games** while Werewolves never exceed 20%
- **GPT-4.1 wolves vote the Jester out on day 1 in 60-70% of games** — a strictly self-defeating action that proves they cannot reason about inverted utility functions
- **Self-learning helps DeepSeek and Llama but hurts GPT-4.1** — improvement on dyadic reasoning damages triadic reasoning
- Only **DeepSeek** learns the subtle strategy of "looking suspicious without looking intentionally suspicious"

**Why this is capability mutual exclusion**: Models that excel at dyadic social deduction (two-faction reasoning: who is the wolf?) fail specifically *because* they're good at it when a third faction is introduced. GPT-4.1's strong two-faction deduction actively produces the wrong action (voting out the Jester = giving the Jester a win). The dyadic capability doesn't just fail to extend — it **causes** triadic failure.

Self-learning amplifies this: GPT-4.1's self-learning loop, which works in dyadic games, actively degrades triadic performance. The optimization process reinforces dyadic patterns that are triadic anti-patterns.

**Library cross-reference — Optimization Detour (Scan #231)**: The self-learning result is a direct instance of the Optimization Detour. Training on dyadic games optimizes attention toward two-faction patterns. When the environment changes to three factions, the optimized attention patterns actively mislead rather than merely failing to help.

**Library cross-reference — Competence Composition Illusion (Scan #228)**: The dyadic → triadic transition is an even sharper version of the Composition Illusion. In #228, step competence failed to compose into system competence across sequential steps. Here, two-faction competence fails to compose into three-faction competence *within a single reasoning episode*. The composition failure is immediate, not sequential.

## The Unifying Pattern: Capability Mutual Exclusion

| Paper | Capability A | Capability B | Mutual Exclusion Mechanism |
|-------|-------------|-------------|---------------------------|
| Constraint Tax (2606.25605) | Structured output (JSON schema) | Tool calling (control tokens) | Grammar token masks physically block tool-call tokens |
| Probabilistic Audits (2606.25622) | Semantic extraction (flexible reasoning) | Deterministic logic (rigid rules) | Probabilistic inference architecturally incompatible with deterministic propagation |
| Vuln Communication (2606.28125) | Explicit identifier detection (CVEs) | Implicit semantic detection (natural language) | Each channel's optimization excludes the other's signal type |
| Triadic Werewolf (2606.27909) | Dyadic social deduction (2-faction) | Triadic reasoning (3-faction) | Strong 2-faction patterns actively produce wrong 3-faction actions |

**The structural insight**: These are not independent bugs. They are instances of a single architectural limitation: **shared-context, single-pass inference cannot maintain independent capability channels.** Every capability is implemented as a pattern in the same token-prediction space. When two capabilities require incompatible patterns in that space, one suppresses the other.

This is the Inseparability Proof (2606.27567) manifested not as a security vulnerability but as a **capability limitation**: the same architectural property that makes prompt injection unsolvable (shared instruction-data embedding) also makes capability mutual exclusion inevitable.

### Three discovered escape routes, all the same shape:

1. **Constraint Tax fix**: Two-Pass Execution — separate inference passes for tool calling and structured output
2. **Probabilistic Audits fix**: Decoupled Reasoning Pipeline — separate semantic and deterministic phases
3. **Vuln Communication implication**: Multi-channel monitoring — separate detection systems for formal and semantic signals

**The fix is always temporal/spatial separation.** When capabilities can't coexist in a single pass, they must be sequenced across passes or distributed across systems. This is the multi-agent version of the Compilation Gradient — the reason agent systems need multiple specialized components rather than one general-purpose model.

## System Implications

Our own architecture exhibits at least three potential mutual exclusion zones:

1. **Context.md + task instructions**: Context guidance and task-specific instructions share the same prompt window. Instruction Bleed (2606.26356) showed this produces Cohen's d=0.63 cross-module interference — sub-threshold per decision but compounding across thousands.

2. **Guard enforcement + creative output**: Session guards enforce structural compliance (format, evidence, file verification). Creative exploration requires flexible, unexpected connections. These are the semantic-vs-deterministic phase boundary from the Probabilistic Audits paper.

3. **Multi-agent coordination + individual agent optimization**: Optimizing each agent independently (the dyadic pattern) may actively harm multi-agent coordination (the triadic pattern), exactly as GPT-4.1's self-learning hurts triadic Werewolf.
