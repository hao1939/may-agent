# HN Scan #171 — The Selectivity Turn

**Date**: 2026-10-10
**Source**: Hacker News (front page, Algolia API), arXiv
**Scan number**: 171
**Theme**: Across every stack layer — multi-model composition, code execution, agent navigation, evaluation, security, workflow governance — the binding constraint shifts from "add more capability" to "apply capability precisely." The gains come not from having more models, running more tests, or granting more autonomy, but from *selecting where each applies*.

---

## Synthesis: Why This Matters

Seven independent signals from the last 24 hours converge on a single structural pattern:

1. More models don't help when they all fail on the same queries — the gain comes from *different* failures.
2. More test execution doesn't improve repair success — it's effective only in concentrated cases.
3. More navigation doesn't make agents better — stable structural anchors make them *reproducible*.
4. More holistic judgment doesn't improve evaluation — decomposed binary questions give clearer signal.
5. More agent autonomy doesn't improve workflow quality — designated intervention points outperform full control.
6. More spec documentation doesn't prevent drift — only blocking merge conditions enforce alignment.
7. More fine-tuning doesn't guarantee security — it can create invisible attack surfaces.

The common thread: **the dominant constraint has shifted from capability to selectivity**. This is the architectural consequence of the Substrate Inversion reaching maturity — when the model is commodity, the intelligence is in *knowing where to apply it*.

## Findings

### 1. Co-Failure Ceiling (arXiv 2606.27288)

**Title**: When Does Combining Language Models Help? A Co-Failure Ceiling on Routing, Voting, and Mixture-of-Agents Across 67 Frontier Models

**Source**: https://arxiv.org/abs/2606.27288

The first formal proof that multi-model systems have a hard accuracy ceiling. For any policy whose output is one member model's answer, accuracy ≤ (1 − β), where β is the rate at which *every* model is wrong on the same query.

Key findings across 67 models from 21 providers:
- The usual diagnostic (pairwise error correlation ρ) **cannot identify β** — error distributions with identical marginals and correlations can have different all-wrong rates
- On open-ended math: observed β = 0.052 vs. 0.023 under Gaussian copula (2.5× underpricing)
- On execution-graded code: β = 0.079
- On free-response GPQA-Diamond: β = 0.127 — answer format, not subject matter, drives co-failure
- Low-ρ heterogeneous ensembles beat high-ρ Self-MoA, but combining models **rarely beats the single best model** without a strong query-level routing signal

**Implication for our system**: Multi-agent architectures that route between models (MoA, cascading, voting) are subject to this ceiling. The productive strategy is not "add more models" but "ensure models fail on *different* queries." β becomes a first-class metric for any multi-model system. Our current single-model-per-agent design may be accidentally near-optimal — the right move is better harness selectivity, not model proliferation.

### 2. Deterministic Anchoring Effect (arXiv 2606.26979)

**Title**: How Much Static Structure Do Code Agents Need? A Study of Deterministic Anchoring

**Source**: https://arxiv.org/abs/2606.26979

Systematic study of injecting static analysis (call graphs, inheritance hierarchies) into LLM code agents. Uses Codex as baseline across 200 SWE-bench instances.

Key findings:
- Lightweight call/inheritance topology: **+2.2pp Func@5**, **-1.6 interaction rounds**
- Link-following rate: 0.15–0.18 → 0.21–0.24 with tags
- Run-to-run variance roughly halved; Pass@1 **+3.4pp** on medium repos
- Cost: ~10% more input tokens
- **Scale-sensitive**: dense semantics show diminishing returns; hub-heavy projects benefit from inverse-only ("who-calls-me") links
- The core finding: "Static structure helps less by making agents *smarter* and more by making their navigation *disciplined and reproducible*"

**Implication for our system**: Our AGENTS.md / context.md files function as a form of deterministic anchoring — they constrain agent navigation toward known-good paths. The research validates this approach but suggests the value is *stability*, not capability. This reframes our architecture: context files are anchors against stochastic drift, not intelligence repositories.

### 3. Execution Cost-Effectiveness (arXiv 2606.26978)

**Title**: To Run or Not to Run: Analyzing the Cost-Effectiveness of Code Execution in LLM-Based Program Repair

**Source**: https://arxiv.org/abs/2606.26978

First large-scale empirical study of whether code execution actually helps in agent-based repair. 7,745 traces from SWE-bench + 3,000 end-to-end repair attempts across Claude Code, Codex, and OpenCode.

Key findings:
- Average: 8.8 test runs per task (range: 2–19)
- Execution frequency varies substantially across agents, but **late-stage executions consistently outperform early-stage**
- **Restricting execution barely affects success**: Prohibited vs. Unrestricted gap is only **1.25 percentage points** (not statistically significant) on commercial agents with SOTA models
- Prohibited mode **saves substantial token and wall-clock cost**
- Execution benefit is **concentrated, not uniform** — agents apply it indiscriminately

**Implication for our system**: This is the strongest evidence yet for treating execution as a *budget*, not a default. The "generate-run-revise" loop is the dominant paradigm, but most of its runs provide zero signal. The efficient strategy is selective execution — run tests when uncertainty is high, skip when the patch is high-confidence. Connects directly to Bayesian Control for Coding Agents (2606.24453, scan #161) which proposed the same idea from theory.

### 4. Spec Growth Engine (arXiv 2606.27045)

**Title**: The Spec Growth Engine: Spec-Anchored, Code-Coupled, Drift-Enforced Architecture for AI-Assisted Software Development

**Source**: https://arxiv.org/abs/2606.27045

Identifies two structural failure modes of AI coding agents:
1. **Context explosion** — agent must reason over entire repository, quality degrades as context fills
2. **Silent spec-code drift** — code evolves, spec doesn't, divergence is invisible until costly

The solution: a machine-readable spec graph with:
- **Contract/design separation** per node
- **Spine context assembler** scoping agent context to an ownership path (not whole repo)
- **Vertical-slice growth** enforcing hardest-first ordering
- **Drift gate** making spec-code divergence a **blocking merge condition**

Synthesizes Parnas information hiding, C4, ADRs, Walking Skeleton, Reflexion Models into a lean, code-coupled, machine-enforced framework.

**Implication for our system**: The "drift gate" concept directly addresses our governance findings. Our convention checks are a weak form of drift detection — they catch behavioral violations but don't enforce spec-code alignment. A drift gate that blocks merges when architectural documentation diverges from implementation would close the governance vacuum identified in scan #170.

### 5. Process Harness — Agentic BPM (arXiv 2606.27188)

**Title**: A Process Harness for Uplifting Legacy Workflows to Agentic BPM: Design and Realization in CUGA FLO

**Source**: https://arxiv.org/abs/2606.27188

Introduces the "process harness" — a policy-governed agentic layer around a deterministic workflow engine that:
- Intercepts **designated control points** to contribute reasoning
- Retains the workflow engine's **structural authority** over the process
- Defines three policy-governed agent types:
  - **TaskAgent**: knowledge-intensive task execution
  - **DecisionAgent**: per-case gateway routing
  - **FlowAgent**: runtime flow adaptation via hook mechanism
- All agents reason within an **explicit policy** drawn from the process FRAME (aggregate policy set)

The key design decision: **the deterministic engine retains authority; agents are invited in at specific control points, not given full autonomy.**

**Implication for our system**: This validates our architecture pattern where managers dispatch to specialized agents at known decision points. The CUGA FLO distinction between imperative requirements (enforced by deterministic workflow) and normative requirements (resolved by policy-framed agentic autonomy) maps directly to our structure: task trees and conventions are imperative; agent context and skills are normative. The insight is that mixing them is the structural error — they should be *explicitly separated* and governed differently.

### 6. BinEval — Decomposed Evaluation (arXiv 2606.27226)

**Title**: Ask, Don't Judge: Binary Questions for Interpretable LLM Evaluation and Self-Improvement

**Source**: https://arxiv.org/abs/2606.27226

Proposes decomposing evaluation criteria into atomic binary questions instead of holistic scoring:
- Given a task prompt, a meta-prompt generates fine-grained evaluation questions
- An LLM answers them independently, yielding transparent question-level feedback
- Matches or outperforms UniEval and G-Eval across SummEval, Topical-Chat, QAGS
- **Avoids ceiling effects** common in LLM judges — better discrimination between borderline and clearly flawed outputs
- Same question-level feedback enables iterative **prompt optimization**

**Implication for our system**: Our evaluation system produces 3 bits of entropy from 14,345 evals (scan #167). BinEval's decomposition approach directly addresses this — instead of holistic pass/fail, decompose into atomic binary dimensions. Each question becomes independently measurable and debuggable. This aligns with the Diagnostic Refinement wave (agent-evaluation.md §10) but provides a concrete, training-free framework.

### 7. Inherited Circuit Vulnerabilities (arXiv 2606.27091)

**Title**: Inherited Circuits, Learned Semantics: How Fine-Tuning Creates Evasion Vulnerabilities Invisible to Standard Evaluation

**Source**: https://arxiv.org/abs/2606.27091

Shows that fine-tuning for security classification can create *invisible* attack surfaces:
- Foundation-Sec-8B inherits a late-attention classification circuit from Llama 3.1
- Fine-tuning concentrates and specializes this inherited structure
- Improves baseline accuracy **while creating transformation-sensitive attack surfaces**
- PowerShell alias substitution, command reconstruction, case mutation all evade the fine-tuned model but not the base model
- A linear probe at the classification boundary can identify vulnerable command families using only canonical inputs

**Implication for our system**: This is a concrete instance of the quality ceiling (scan #167) applied to security. Fine-tuning improves the metric while degrading the actual capability surface. The fix is the same: evaluate the *transformation space*, not just the canonical inputs. For our agent security, any fine-tuned safety classifier should be tested against behavioral transformations, not just in-distribution examples.

## The Structural Pattern

```
           BEFORE (Capability Era)              AFTER (Selectivity Turn)
    ┌──────────────────────────┐         ┌──────────────────────────┐
    │  More models → better    │         │  Right model per query   │
    │  More tests → more safe  │         │  Right test per patch    │
    │  More context → smarter  │         │  Right anchor per repo   │
    │  More autonomy → faster  │         │  Right control point     │
    │  More judgment → quality │         │  Right binary question   │
    │  More fine-tuning → safe │         │  Right eval transform    │
    │  More docs → aligned     │         │  Right drift gate        │
    └──────────────────────────┘         └──────────────────────────┘
              ↓                                      ↓
       Diminishing returns                   Compounding precision
```

The phase transition: **"more X" has exhausted its returns across every stack layer simultaneously.** The productive direction is precision of application — knowing *where* each capability helps and applying it *only there*. This is the architectural maturity curve: naive application → uniform application → selective application.
