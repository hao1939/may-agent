## Cross-Source Synthesis: The Work Before the Work

Five independent signals — two academic papers, two grassroots repos, and a front-page HN debate — converge on a structural insight that resolves several prior findings: **coordination that happens before work begins determines outcomes more than coordination during or after work.** The binding constraint on multi-agent systems is not agent intelligence, but pre-work infrastructure.

### The Pre-Coordination Pattern

| System | Pre-Work Phase | Result |
|--------|---------------|--------|
| **grite** (2606.19616) | Agents claim/divide work via shared ledger in git BEFORE coding | Duplicate work drops from 78% → 0%; throughput triples |
| **MATM** (2606.19911) | New agents retrieve prior trajectories BEFORE starting | Task performance improves; interaction steps reduce without joint training |
| **StaminaBench** (2606.19613) | Test feedback loops pre-configured BEFORE multi-turn sessions | Passed turns improve up to 12× |
| **shadcn/improve** (5870★) | Expensive model pre-audits codebase, writes plans BEFORE cheap model executes | Audit-then-execute separation; 5870★ in 12 days |
| **BabelTele** (2606.19857) | Context pre-compressed to 27.9% volume BEFORE inter-agent transfer | 99.5% semantic fidelity maintained; cross-model transfer works |

### Why "During-Work" Coordination Fails

The failure pattern is consistent: when agents attempt coordination *while executing*, they face:

1. **Context budget competition**: Coordination messages compete with task content for the same context window
2. **Commitment irreversibility**: Once an agent commits a change, undoing it costs more than preventing the conflict (scan #78's speculative execution finding)
3. **Signal degradation under load**: More concurrent agents = more coordination overhead = less productive context (the Coordination Tax from our knowledge base)

grite's most striking finding: a file-based coordination tracker (the "during-work" approach) **silently drops concurrent writes**. The coordination substrate itself becomes the source of conflicts it was meant to prevent.

## Paper-Level Evidence

### Multi-Agent Transactive Memory — MATM (2606.19911)

**Key innovation**: Extends RAG from "retrieve human-authored artifacts" to "retrieve agent-generated trajectories for reuse across agent populations." Producer agents contribute trajectories to a shared repository; consumer agents retrieve them before task execution.

- **Environments**: ALFWorld and WebArena (interactive, long trajectories)
- **Key result**: Retrieving prior trajectories improves downstream performance and reduces interaction steps — without coordination protocols, joint training, or even awareness between agents
- **Critical insight**: Agent trajectories encode "reusable procedural knowledge" that is typically discarded after single use. This is the agent equivalent of organizational transactive memory in cognitive science — "I don't need to know X, I need to know where knowledge of X lives"
- **Connection to our system**: Our knowledge library IS a transactive memory system. But we index insights/conclusions, not full trajectories. MATM suggests indexing the HOW (process) not just the WHAT (result) would reduce rediscovery.

Source: https://arxiv.org/abs/2606.19911

### Before the Pull Request: Mining Multi-Agent Coordination (2606.19616)

**Key innovation**: Introduces "grite," a coordination substrate that stores event logs inside git itself — no central server, append-only, signed, and mineable.

- **Core finding**: "Large-scale studies find agent PRs are produced faster but accepted less often — a coordination and trust gap that pull-request-level telemetry cannot explain"
- **The missing signal**: Lives BEFORE the PR — "how concurrent agents claim, divide, and collide over shared work"
- **Result**: Duplicate work falls from 78% to 0%; useful throughput more than triples
- **Mineable failure modes automatically recovered with provenance**: conflicting edits, lock starvation, redundant rediscovery, race-to-close — several invisible in PR history alone
- **Critical insight**: File-based trackers lose concurrent writes silently. The coordination substrate must be append-only and convergent, not read-write.

Source: https://arxiv.org/abs/2606.19616

### StaminaBench: Stress-Testing Coding Agents over 100 Turns (2606.19613)

**Key innovation**: First benchmark measuring agent *stamina* — how many consecutive turns before failure, matching real vibe-coding sessions.

- **Devastating finding**: All tested models (7 open-source LLMs × 6 harnesses) fail within **5-6 turns** without test feedback
- **Pre-work setup is decisive**: Passing test feedback back → up to 12× improvement in passed turns. Harness quality creates up to 6× gap for the SAME model
- **Key quote**: "A good harness is required for strong performance: stronger models exhibit up to a 6× gap between their best and worst harness"
- **Implication**: The model is not the bottleneck — the harness (pre-work infrastructure) is. Model capability without harness support is wasted.
- **Connection**: This is the empirical proof of scan #79's "externalized discipline infrastructure" thesis. The infrastructure around the agent matters more than the agent itself.

Source: https://arxiv.org/abs/2606.19613

### BabelTele: Model-Native Non-Readable Representations (2606.19857)

**Key innovation**: Investigates whether inter-agent communication needs to be human-readable. Finds that "semantic information can be encoded in compact, non-standard textual forms that sacrifice human readability while remaining recoverable by LLMs."

- **Result**: 99.5% semantic fidelity at 27.9% of original text volume
- **Cross-model transfer works**: Compressed representations created by one model are recoverable by different models
- **Applications tested**: Agent memory, multi-agent communication, instruction compression
- **Critical implication**: The human-readability requirement of agent context files (AGENTS.md, CLAUDE.md, our own `<ai_context>` preambles) may be leaving 72% compression on the table. But human readability enables debugging, auditing, and trust — this is a governance/efficiency trade-off, not a pure optimization.
- **Connection to Skill Representation Crisis (scan #75)**: SoftSkill showed 32 latent tokens outperform thousands of Markdown skill tokens. BabelTele generalizes this: the human-readable interface layer is not the optimal model-facing layer. Two representations may be needed — one for humans, one for agents.

Source: https://arxiv.org/abs/2606.19857

## Structural Resolution: The Three Pre-Coordination Layers

Synthesizing across all signals, pre-coordination splits into three distinct layers:

| Layer | Function | Exemplar |
|-------|----------|----------|
| **Pre-Claim** | Who works on what? (prevent conflicts) | grite (append-only work claims in git) |
| **Pre-Load** | What does the agent need to know? (prevent rediscovery) | MATM (trajectory retrieval), skills registries |
| **Pre-Compress** | How do we fit it in context? (prevent overflow) | BabelTele (72% compression), shadcn/improve (plans as compressed audits) |

These three layers execute in sequence: Claim → Load → Compress → Execute.

**Connection to the PID/Control Theory frame (scan #83)**: Pre-coordination is the **feedforward term** — applied before the error signal even exists. Current systems are purely feedback (react to errors after they occur). The feedforward term uses a model of the system to apply correction before disturbance arrives. MATM + grite + BabelTele together ARE the feedforward path for agent coordination.

**Connection to the Temporal Orientation Trilemma (scan #85)**: Pre-coordination is dominantly in the **Prospective** orientation — it's memory/infrastructure that anticipates future needs. The three pre-coordination layers map to prospective memory sub-types:
- Pre-Claim = "prospective governance" (projectmem's mandate gates)
- Pre-Load = "prospective knowledge" (T-Mem's anticipatory triggers)
- Pre-Compress = "prospective assembly" (TokenPilot's lifecycle-aware eviction)
