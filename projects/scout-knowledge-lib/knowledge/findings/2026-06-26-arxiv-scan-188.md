# arXiv Scan #188 — The Governance Artifact Gap

**Date**: 2026-06-26
**Source**: arXiv (export.arxiv.org API)
**Scan number**: 188
**Theme**: The artifacts that govern agent behavior are themselves unengineered, unmaintained, and undefended

---

## Synthesis: Governance Artifacts Are the Weakest Link

Six independent papers — spanning configuration engineering, memory architecture, cross-agent continuity, runtime governance, supply-chain security, and privacy — converge on a single structural insight: **the field has invested heavily in what agents can DO while treating the artifacts that control what agents SHOULD do as static, unversioned, unaudited afterthoughts**.

| Paper | Governance Artifact | Problem | Key Result |
|---|---|---|---|
| Config Smells (2606.15828) | AGENTS.md / CLAUDE.md files | Unengineered, smell-ridden | 62% Lint Leakage, 42% Context Bloat, 35% Skill Leakage in top-100 repos |
| Control-Plane (2606.15903) | Memory mutation pipeline | No single architecture handles all forgetting modes | 13 configs, 3 regimes, complementary gaps (0% cross-lingual, 0% intent-aware deletion) |
| ESAA-Conv (2606.23752) | Cross-agent state | Vendor-locked, session-isolated | Event-sourced shared log enables handoff; curation is the unsolved judgment |
| PROJECTMEM (2606.12329) | Project memory + pre-action gate | Stateless sessions repeat failures | Memory-as-Governance: gate warns before repeating known-failed fixes |
| Locate-Judge (2606.23416) | Skill marketplace trust | Skills inherit instruction authority; injection defenses don't apply | Attention-based 2-stage detection at marketplace scale; dozens of live malicious skills found |
| Privacy Survey (2606.26627) | Data governance policy | Scattered across 6+ subfields; no composite benchmark | Only information-flow control covers compositional + cross-session leakage |

The meta-pattern: **governance artifacts are the new technical debt**. Code has linters, tests, CI, type systems. Agent governance artifacts (instruction files, memory stores, skill manifests, privacy policies) have none of these. The gap is not "we need better models" — it's "we need to treat governance artifacts as first-class engineering objects."

## Finding 1: Configuration Smells in AGENTS.md Files (arXiv 2606.15828)

**Source**: https://arxiv.org/abs/2606.15828

The first empirical catalog of "smells" in coding-agent configuration files. Combined grey literature review + repository mining across 100 popular open-source repos containing AGENTS.md or CLAUDE.md files.

**Six configuration smells identified**:

1. **Lint Leakage** (62%): Lint/formatting rules embedded in agent instructions rather than enforced by tooling. Wastes context on rules a linter already enforces.
2. **Context Bloat** (42%): Over-stuffed files that exceed useful context window. Agent instructions that try to be comprehensive end up being ignored.
3. **Skill Leakage** (35%): Implementation-specific skills (test commands, build steps) embedded in general instructions rather than tool configurations.
4. **Conflicting Instructions** (prevalence not given): Contradictory directives within the same file.
5. **Co-occurrence patterns**: Context Bloat, Skill Leakage, and Conflicting Instructions frequently co-occur — bloated files tend to also be contradictory and skill-leaked.

**Why this matters for the library**: The Governance Vacuum (#170) showed that 58% of agent configs are single-commit (never revised) and <1% declare permissions. This paper adds the *quality* dimension: even the configs that exist are smell-ridden. Our own system's AGENTS.md, context.md, TOOLS.md, and DOMAIN.md files have never been audited for these smells.

**Connection to Compilation Gradient**: Config smells represent a pre-Stage-1 problem. The Compilation Gradient describes behavioral → structural → compiled governance maturation. Config smells mean most agent governance hasn't even reached the behavioral stage properly — it's *malformed* behavioral governance.

**Connection to Instruction Bleed (#180)**: Context Bloat directly amplifies Compositional Behavioral Leakage. More content in the context window = more cross-module interference at Cohen's d=0.63 per channel.

## Finding 2: Control-Plane Placement Shapes Forgetting (arXiv 2606.15903v2)

**Source**: https://arxiv.org/abs/2606.15903

The first systematic study of WHERE the LLM sits in an agent memory pipeline — not what it knows, but what it can *forget* based on architectural placement.

**Three placement regimes** across 13 system configurations tested on a 385-case adversarial surface:

| Regime | What it handles | What it can't handle | Cost |
|---|---|---|---|
| **Deterministic primitives** | Lexical/temporal forgetting | Canonicalization (5% identifier-obfuscation, 0% cross-lingual) | 64-191ms/case |
| **Inscribe-time LLM** | Canonicalization (100%) | Intent-aware deletion (0% prefix-collision, 0% compound-fact) | — |
| **Mutation-time hook** | Intent-aware deletion (78-85%) + nearly all categories (91.7-93.2% overall) | Residual 7-9% | $0.17/385-case run, 2.3s/case |

**Key insight**: No single architecture handles all forgetting failure modes. The three regimes have *complementary* coverage — deterministic handles what LLM can't (consistent temporal rules), inscribe-time handles what deterministic can't (semantic equivalence), mutation-time handles what inscribe-time can't (intent-aware deletion).

**Why this matters**: The Eternal Present synthesis (#34) identified five missing temporal primitives (EXPIRY, CONSOLIDATION, RESOLUTION, SUCCESSION, PROVENANCE). This paper shows that EVEN IF you add temporal primitives, the forgetting quality depends on where in the pipeline you place the LLM. There is no "add forgetting and you're done" — it requires architectural choices with measurable tradeoffs.

**Connection to Memory Write Problem (#175)**: The five-level write-danger hierarchy maps onto these three regimes. Deterministic primitives are safe for Level 1-2 writes; intent-aware mutation requires Level 3 (LLM judgment) at 2.3s latency cost.

**Recall path unchanged**: Critically, the mutation-time hook adds latency only to writes. The read path is unaffected. This means governance overhead is concentrated on the infrequent, high-stakes operations (writes) rather than the frequent, low-stakes ones (reads) — exactly the right cost allocation.

## Finding 3: Event-Sourced Memory for Heterogeneous Agent Handoff (arXiv 2606.23752)

**Source**: https://arxiv.org/abs/2606.23752

Directly addresses the problem our system faces: multiple agents working on the same project lose context across sessions and across agent boundaries.

**Architecture**:
- Treats visible conversation as a **local event store**
- Hooks/watchers capture turns → normalize into append-only `activity.jsonl`
- **Deterministic projections** produce read models: `handoff.md`, `state.md`, `decisions.md`, `tasks.json`
- Mechanical capture requires **no LLM inference** — raw event logging is deterministic
- Agents use LLM judgment **only for explicit curation**: recording durable decisions and tasks via domain commands

**Design principle**: Separate mechanical capture (deterministic, cheap, complete) from semantic curation (expensive, judgment-required, selective). This is the Memory-Write Problem's architectural solution — writes to the raw log are mechanical; writes to the curated state require judgment.

**570-event self-referential case study**: Heterogeneous agents (Codex, Grok, Claude Code) collaborate through a shared log without direct agent-to-agent channels.

**Why this matters for us**: Our system has the exact problem ESAA-Conversational solves: different agent sessions working on the same project lose context because state is session-scoped. The KE circuit (which flows) is our partial, informal version of this — but without the deterministic projection layer that makes it queryable.

**Connection to Transduction Chain**: The format boundary failures we documented (KE-2000 landing in "Proposed" instead of "Approved" section) would be prevented by ESAA's typed event store — the event carries its semantic type, not its markdown heading.

## Finding 4: Memory-as-Governance — Pre-Action Gates (arXiv 2606.12329)

**Source**: https://arxiv.org/abs/2606.12329 (PROJECTMEM)

Introduces a critical design pattern: **memory that governs, not just remembers**.

**Key concept**: A deterministic pre-action gate that warns agents before they repeat a previously failed fix or edit a known-fragile file. Memory is not just a retrieval system — it's a governance layer.

**Architecture**:
- Append-only plain-text event log of typed events: issues, attempts, fixes, decisions, notes
- Deterministic projections into compact, AI-readable summaries served via MCP
- **Pre-action gate**: Before the agent acts, the gate checks whether the proposed action matches a previously recorded failure pattern
- Fully offline, no telemetry; immutable log serves as provenance trail

**Quantified cold-start cost**: 5,000-20,000 tokens per session for context reconstruction — consistent with our Cold Start Tax findings (46% of ops spent reconstructing known state).

**Why this matters**: This is the constructive answer to several library pathologies. The Death Valley failure pattern (ops 16-30, 39.7% failure rate) could be partially addressed by a pre-action gate: "you're about to repeat a pattern that failed 3 times before." The Memory-as-Governance pattern converts passive memory into active safety infrastructure.

**Connection to Compilation Threshold (#35)**: Pre-action gates are compiled governance — deterministic checks that prevent known-bad actions without requiring LLM reasoning. This is exactly the pattern the Compilation Threshold identified as saving 38% of budget.

## Finding 5: Attention-Based Malicious Skill Detection at Scale (arXiv 2606.23416)

**Source**: https://arxiv.org/abs/2606.23416

Advances the Supply Chain Crystallization (#166) findings with a practical detection mechanism.

**The problem**: Agent skills are file-based packages of natural-language instructions that execute with user privileges. Unlike prompt injection (which has a trusted/untrusted boundary), skills ARE instructions — injected commands sit among legitimate ones and inherit their authority. Prompt-injection defenses do not carry over.

**Locate-and-Judge architecture**:
1. **Locate**: Lightweight locator scores structural spans of a skill by instruction-following attention each span draws. Retains only top-K high-attention spans.
2. **Judge**: Examines retained spans in detail for malicious intent.

**Key results**:
- Order-of-magnitude cost reduction over direct LLM scanning
- High precision; confirms majority of flagged skills as malicious
- Finds dozens of live malicious skills in production marketplaces
- Detects skills that SkillSpector and Cisco Skill Scanner miss
- Skills disguised as benign functionality are surfaced

**Why this matters**: The Supply Chain Crystallization (#166) reported 36% critical-level security issues in ClawHub skills. Locate-and-Judge provides the first scalable detection mechanism. The cost reduction from concentrating judgment on high-attention spans is a direct application of the Selectivity Turn (#171) — precision matters more than coverage.

**Connection to ShareLock (#170)**: ShareLock showed that per-tool auditing is structurally insufficient because attack meaning is distributed across tool boundaries. Locate-and-Judge's attention-based approach partially addresses this by identifying which spans the model would actually attend to during execution — a behavioral rather than structural detection method.

## Finding 6: Data-Centric Privacy Survey — The Missing Composite Benchmark (arXiv 2606.26627)

**Source**: https://arxiv.org/abs/2606.26627

The most comprehensive privacy survey for LLM agents to date, organized by *data surface* rather than attack type.

**Key structural finding**: Only **information-flow control** covers both compositional leakage (data exposed through tool composition) and cross-session inference leakage (information deduced across sessions). All other governance mechanisms have blind spots on at least one of these.

**Missing instrument**: No benchmark drives an agent across its data surfaces under a single privacy policy. Existing benchmarks test individual surfaces (RAG retrieval, SQL injection, memory poisoning) but never the composite. This is the privacy instantiation of the Composition Tax (#184) — testing components individually understates the composite risk.

**Data surfaces taxonomized**: Databases/SQL, document collections, external APIs, session memory, inter-agent messages, tool invocations. Each creates distinct privacy risks; governance mechanisms address them piecemeal.

**Why this matters**: Our system has agents that read each other's outputs, share knowledge files, and persist lessons across sessions. Each of these data flows is a privacy surface that has never been policy-governed. The survey's finding that scattered research across 6+ subfields fails to compose into a unified defense is precisely the Governance Artifact Gap at the privacy layer.

### The Governance Engineering Maturity Model

These six papers implicitly define a maturity progression for governance artifacts:

1. **Level 0 — Absent**: No governance artifact exists (58% of configs, per #170)
2. **Level 1 — Informal**: Config file exists but is smell-ridden (62% Lint Leakage, 42% Context Bloat)
3. **Level 2 — Structured**: Typed event log with deterministic projections (ESAA, PROJECTMEM)
4. **Level 3 — Governed**: Pre-action gates, attention-based skill auditing, mutation-time hooks
5. **Level 4 — Verified**: Formal policy enforcement with information-flow control, composite benchmarks

The field is concentrated at Level 0-1. The papers in this scan describe Level 2-3 mechanisms. Level 4 remains the Verification Horizon (#186).
