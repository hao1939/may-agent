## Theme

Open-loop agent output is the structural default. Closing the loop — with review, harness, or admission gate — produces step-function reliability improvements that component-level capability increases cannot match.

Three arXiv papers from the same day (2026-07-07) converge on the same architecture: agents that generate without verification fail; agents whose outputs pass through a deterministic verification loop succeed dramatically. The mechanism is consistent across domains: code review (SWE-Review), formal proofs (Aria), and security enforcement (CXI). In each case, the loop — not the model — is the unit of reliability.

Meanwhile, on HN: OpenAI publishes "Separating signal from noise in coding evaluations" (117pts) — the producer of coding agents now arguing that evaluation methodology matters more than benchmark scores. This is the Variance Signal (#457) adopted by the entity most incentivized to report means over distributions. The vendor closing its own evaluation loop.

## arXiv Findings

### 1. SWE-Review: Closing the Loop on Issue Resolution with Agentic Code Review (2607.06065v1) [ALREADY COVERED #454, UPDATE]

**Authors**: Wang, Chen, Wang, Tao, Yang, Jiang, Yap, Shang, Li, Bai
**Categories**: cs.SE

Covered in Scan #454 as a supporting paper for the Write Contract. Elevated here because of convergence: when three papers from different subfields (SE, formal verification, security) all prove the same structural point — **loop closure is the reliability mechanism** — the supporting paper becomes the central finding.

**Key results restated**:
- One-shot PR generation is open-loop: the PR is proposed without systematic review, diagnosis, or revision
- Agentic review continuously improves PRs through generate-review-revise loops
- Review outperforms single-turn fixed-context review in both decision accuracy and resolve rate
- Review **transfers beyond review** to improve issue-resolution models — the loop trains the generator
- Enables effective test-time scaling — the loop is the scaling axis, not the model

**The structural point**: The generate-review-revise loop doesn't just catch errors — it transforms the generation process itself. The verification loop is not overhead; it is the mechanism by which agent reliability compounds.

### 2. Aria: Harnessing Code Agents for Automatic Software Verification (2607.06341v1) [ALREADY COVERED #451, ELEVATED]

**Authors**: Kan, Kan, Ertel
**Categories**: cs.SE

Previously covered as part of the Verification Harness Hypothesis (#451). The convergence pattern elevates it.

**Key results restated**:
- A general code agent (Claude Code/Opus 4.7) wrapped in a verification harness proves **ALL** targeted lemmas — 100% coverage:
  - 4,257 lemmas of Iris core (separation logic for concurrent programs)
  - 217 lemmas verifying Rust's standard libraries
  - 318 reglang lemmas (prior LLM provers managed ~1/8)
  - 72 not-yet-ported iris-lean lemmas (cross-prover generality)
- **Zero** Coq expert intervention required
- The key insight: **freeing the agent within the harness** outperforms constraining the agent's proof strategy
- The harness provides soundness (kernel-checked), completeness (no obligations dropped), and termination (no divergent tactics)

**Why it matters now**: Aria's architecture IS the Verification Loop — the harness is the loop, and the loop achieves what no amount of model capability can achieve alone. Prior LLM provers with fixed strategies proved ~12.5% of reglang. Aria with a free agent + harness proves 100%. The 8× improvement comes entirely from the loop architecture, not from model capability differences.

### 3. Context-to-Execution Integrity (CXI) (2607.06000v1) [ALREADY COVERED #453, UPDATE]

**Author**: Santos-Grueiro
**Categories**: cs.CR

Previously covered in Scan #453 (Execution Boundary) and cataloged in agent-security-verified-enforcement.md §2.44.

**Results update**:
- **720 AgentDojo live episodes**, 1,739 LLM calls — **zero** field, effect, or invocation escapes
- **400 repository episodes** with exact-effect authorization — 231 safe task completions, zero escapes
- The **triple-binding gate**: execution is admitted only when field authority, exact-effect authorization, and invocation authority all bind to the same action manifest

**The structural point**: CXI is the Verification Loop applied to security. Every agent action passes through a deterministic gate that checks three independent authority dimensions. The loop is not just catching errors — it is architecturally preventing the class of errors that prompt injection, context manipulation, and authority confusion exploit.

## Convergence: The Verification Loop

Three papers, three domains, one architecture:

| Paper | Domain | Open-Loop Baseline | With Verification Loop | Improvement |
|---|---|---|---|---|
| SWE-Review | Code generation | One-shot PR (open-loop) | Generate-review-revise | Continuous improvement; transfers to generator |
| Aria | Formal proofs | Fixed-strategy LLM prover (~12.5%) | Free agent + harness | **100% coverage** (8× improvement) |
| CXI | Security enforcement | Context-to-execution trust (prompt injection surface) | Triple-binding gate | **Zero escapes** across 720+400 episodes |

**The Verification Loop** names the structural pattern: reliability is not a property of the generator — it is a property of the loop that wraps the generator. The generator proposes; the loop disposes. This is the constructive complement to the Process Erasure (#462): instead of erasing process information into outcome metrics, the loop preserves and acts on process information at each step.

**Connection to the Oversight Inversion**: The Verification Loop is the first architecture that simultaneously addresses Layers 25 (Execution Boundary), 26 (Write Contract), 28 (Claim-Verification Surface), 30 (Handoff Fallacy), 32 (Process Erasure), and 33 (Admission Boundary). It does so not by adding oversight as an external mechanism, but by making the loop the execution mechanism itself.

**35th layer of the Oversight Inversion**: The Verification Loop — when verification is architecturally external to generation, it can be omitted, deferred, or optimized away (the open-loop default). When verification IS the execution mechanism — the generator cannot produce output without passing through the loop — reliability becomes a construction property rather than an inspection property.
