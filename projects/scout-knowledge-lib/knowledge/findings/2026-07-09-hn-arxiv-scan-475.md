# Scan #475: The Verification Loop

## Theme

Open-loop agent output is a common baseline. Making review, proof checking, or admission executable can improve tested outcomes or enforce a narrower safety property, but the effect depends on the model, scaffold, tool access, budget, and evaluation contract.

Three arXiv papers from the same day (2026-07-07) study related but non-equivalent mechanisms: model-mediated code review and revision (SWE-Review), kernel-checked proof construction (Aria), and deterministic security admission (CXI). Their evaluations support executable verification at the tested boundary; they do not isolate a shared causal mechanism or show that the loop rather than the model is the unit of reliability.

Meanwhile, on HN: OpenAI publishes "Separating signal from noise in coding evaluations" (117pts) — the producer of coding agents now arguing that evaluation methodology matters more than benchmark scores. This is the Variance Signal (#457) adopted by the entity most incentivized to report means over distributions. The vendor closing its own evaluation loop.

## arXiv Findings

### 1. SWE-Review: Closing the Loop on Issue Resolution with Agentic Code Review (2607.06065v1) [ALREADY COVERED #454, UPDATE]

**Authors**: Wang, Chen, Wang, Tao, Yang, Jiang, Yap, Shang, Li, Bai
**Categories**: cs.SE

Covered in Scan #454 as a supporting paper for the Write Contract. Primary review retains it as useful evidence for executable code review while retracting the earlier categorical convergence claim.

**Primary-reviewed results and limits**:
- One-shot generation is the no-review baseline; executable review/revision improves several reported resolve-rate cells, especially for weak generators.
- Reviewer-relative gains vary substantially: Opus gives +3.0/+16.4/+25.1 points, SWE-Review-8B -0.6/+1.9/+7.6, and SWE-Review-30B +0.4/+2.8/+8.3 across generators.
- The single-turn comparison lacks repository exploration and execution available to the agentic condition. It therefore combines interaction, context, tools, and scaffold rather than isolating multiple turns.
- Mixed review training improves direct issue-resolution point estimates by +0.8/+5.6/+3.8 points across scales. No repeated-run intervals establish a model-independent transfer effect.
- The 100-instance functional sample reports 3% no-review, 8% decision-only, 21% teacher-review, and 32% oracle-review resolution. The difficulty analysis is post hoc.
- Iterative test-time scaling reports 38.4% resolution at 2.44 average samples against 22.9% for a differently budgeted/procedural baseline.

**The structural point**: The package supports the practical value of an executable review/revision path. It does not show that revision continuously helps every generator, that multi-turn interaction alone causes the gain, or that review is the sole reliability mechanism.

### 2. Aria: Harnessing Code Agents for Automatic Software Verification (2607.06341v1) [ALREADY COVERED #451, ELEVATED]

**Authors**: Kan, Kan, Ertel
**Categories**: cs.SE

Previously covered as part of the Verification Harness Hypothesis (#451). The convergence pattern elevates it.

**Primary-reviewed results and limits (2026-09-04)**:
- A Claude Code/Opus 4.7 campaign with kernel checking and coverage/lint hooks reports **ALL** targeted lemmas proved:
  - 4,257 lemmas of Iris core (separation logic for concurrent programs)
  - 217 lemmas verifying Rust's standard libraries
  - 318 reglang lemmas (prior LLM provers managed ~1/8)
  - 72 not-yet-ported iris-lean lemmas (cross-prover generality)
- **Zero** Coq expert intervention during the reported campaign; Iris used 379.7 model-hours, a 30-retry cap, 79.2% first-attempt success, and 0.51 mean retries
- Kernel checking directly supports validity of accepted proofs under retained statements; coverage/lint hooks separately check that target obligations remain
- No matched no-feedback, fixed-strategy, or alternate-harness control isolates the harness or strategy-freedom effect, and no repeated campaign supplies run uncertainty
- The reglang “one in eight” contrast changes model, system, context, and budget. An easier 40-lemma model comparison reaches 40/40 for both Opus 4.7 and Kimi K2.6 but differs sharply in retries and time; longer-proof model failures are qualitative rather than fully enumerated
- The named anonymous repository returned HTTP 401 and no attributable public GitHub repository was found, so the implementation and outcome logs were not independently reproduced

**Why it matters now**: Aria strongly supports kernel-backed checking plus obligation-preservation controls as an executable proof contract. Its 100% campaign result belongs to the full model-agent-harness-retry system; the evidence does not attribute an 8× causal improvement entirely to loop architecture.

### 3. Context-to-Execution Integrity (CXI) (2607.06000v1) [ALREADY COVERED #453, UPDATE]

**Author**: Santos-Grueiro
**Categories**: cs.CR

Previously covered in Scan #453 (Execution Boundary) and cataloged in agent-security-verified-enforcement.md §2.44.

**Results update**:
- **720 AgentDojo live episodes**, 1,739 LLM calls — **zero** field, effect, or invocation escapes
- **400 repository episodes** with exact-effect authorization — 231 safe task completions, zero escapes
- The **triple-binding gate**: execution is admitted only when field authority, exact-effect authorization, and invocation authority all bind to the same action manifest

**The structural point**: CXI is the Verification Loop applied to security. Every agent action passes through a deterministic gate that checks three independent authority dimensions. The loop is not just catching errors — it is architecturally preventing the class of errors that prompt injection, context manipulation, and authority confusion exploit.

## Convergence: The Verification Loop

Three papers, three domains, one architecture:

| Paper | Domain | Open-Loop Baseline | With Verification Loop | Improvement |
|---|---|---|---|---|
| SWE-Review | Code generation | One-shot PR (open-loop) | Generate-review-revise | Heterogeneous resolve-rate gains and benchmark-specific training transfer; multi-turn effect not isolated |
| Aria | Formal proofs | Prior cross-system reglang result (~12.5%) | Opus agent + kernel/coverage harness + up to 30 retries | **100% reported coverage; cross-system contrast, not an isolated 8× harness effect** |
| CXI | Security enforcement | Context-to-execution trust (prompt injection surface) | Triple-binding gate | **Zero escapes** across 720+400 episodes |

**The Verification Loop** names a design pattern, not a guarantee: the generator proposes and an executable reviewer, checker, or gate can affect what is revised or admitted. The three evaluations test materially different contracts, so reliability remains a property of the full model-scaffold-tool-budget-evaluator system.

**Connection to the Oversight Inversion**: The Verification Loop is the first architecture that simultaneously addresses Layers 25 (Execution Boundary), 26 (Write Contract), 28 (Claim-Verification Surface), 30 (Handoff Fallacy), 32 (Process Erasure), and 33 (Admission Boundary). It does so not by adding oversight as an external mechanism, but by making the loop the execution mechanism itself.

**35th layer of the Oversight Inversion**: The Verification Loop — when verification is architecturally external to generation, it can be omitted, deferred, or optimized away (the open-loop default). When verification IS the execution mechanism — the generator cannot produce output without passing through the loop — reliability becomes a construction property rather than an inspection property.

20. **Verification Loop (#475): Make verification the execution mechanism, not an external inspection — the generator proposes, the loop verifies and admits, and the loop's verdicts feed back to improve future generation; reliability is a property of the loop architecture, not the model capability (the loop-as-mechanism condition)**

## Synthesis: The Verification Loop as Unifying Pattern

This scan reveals the Verification Loop as the constructive answer to multiple layers of the Oversight Inversion:

1. **Open-loop is the default**: One-shot generation (PRs, proofs, tool calls) without verification is how most agent systems operate
2. **Executable verification can matter**: SWE-Review reports heterogeneous revision gains, Aria checks completed proofs, and CXI denies actions outside its admission contract
3. **Transfer is conditional**: SWE-Review reports benchmark-specific generator gains; Aria and CXI test different mechanisms and do not establish the same causal loop
4. **The community knows this**: 30papers (616pts), SICP (343pts), Chat Control (1,508pts), and the idTech firing (650pts) — the HN front page is dominated by verification, comprehension, and sovereignty; not by new capabilities

**The Verification Loop** is the 35th layer of the Oversight Inversion, qualified: when verification is executable rather than optional inspection, its tested contract can become a construction property. End-to-end reliability still depends on what the contract checks and on the surrounding model, tools, scaffold, budget, and evidence.
