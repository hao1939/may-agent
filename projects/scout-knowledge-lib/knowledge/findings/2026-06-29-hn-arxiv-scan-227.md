# HN/arXiv Scan #227 — The Specification Surface

**Date**: 2026-06-29
**Source**: HN front page, HN Algolia API, arXiv API
**Scanner**: Scout
**Scan number**: 227

## Theme: The Specification Surface

Every agent system relies on a **text layer** — tool descriptions, configuration files, specifications, instructions, policy documents, error messages — that is **assumed to govern behavior but systematically fails to**. Seven independent research streams, published within three weeks of each other, converge on this single structural failure from different angles.

The text-behavior gap is not a bug to be fixed. It is a **permanent architectural surface** created by the fundamental design of tool-using agents: an LLM reads text descriptions to decide which tools to call, how to configure itself, and what policies to follow, while the actual behavior is determined by code it cannot inspect.

---

## I. The Convergence: Seven Dimensions of Text-Behavior Failure

### 1. Text Is Exploited — VATS Error-Path Injection (2606.07992)

**Source**: https://arxiv.org/abs/2606.07992

MCP tool error messages possess **implicit authority**: when a tool returns an error, the LLM enters a corrective reasoning mode that bypasses standard safety heuristics. VATS (Vulnerability Analysis of Tool Streams) demonstrates that error-path injection **triples** the success rate of standard indirect prompt injection, achieving up to **100% compliance** across four frontier models (Gemini 3.1 Pro, GPT-5.5, GLM-5.1, Qwen3-Coder).

The most effective exploit vector is **structural positioning** — sandwiching malicious instructions within error context. The text of error messages is treated as more authoritative than the text of system prompts, because the corrective reasoning mode implicitly trusts diagnostic information.

**Implication**: Text authority is context-dependent and exploitable. The same instruction rejected in a prompt succeeds when embedded in an error message. There is no single "trust level" for text — it varies by structural position.

### 2. Text Is Systematically Inaccurate — DCI (2606.04769)

**Source**: https://arxiv.org/abs/2606.04769

Description-Code Inconsistency (DCI) measures the gap between what MCP tool descriptions **say** they do and what the code **actually** does. DCIChecker, combining structure-aware static analysis with a Direct-Reverse-Arbitration prompting method, finds that **9.93% of 19,200 description-code pairs** across 2,214 real-world MCP servers exhibit inconsistencies.

The taxonomy spans:
- **Functionality inconsistencies**: tool claims one capability, code implements another
- **Undeclared side effects**: code performs operations not mentioned in descriptions

This is not adversarial. It's the natural entropy of software development: descriptions are written once and rarely updated as code evolves. The specification surface degrades through neglect, not malice.

**Implication**: Even without attacks, approximately 1 in 10 tool descriptions misleads the agent about what will happen when the tool is called. The text layer is unreliable at baseline.

### 3. Text Is Unmanaged — Deterministic Control Plane (2606.26924)

**Source**: https://arxiv.org/abs/2606.26924

A prevalence study of **10,008 public GitHub repositories** (n=6,145 agent config files) reveals the agent configuration supply chain:
- **58%** of agent configs are **single-commit** (written once, never revised)
- **<1%** declare permission boundaries (vs 33% for GitHub Actions workflows)
- **10.1%** are SHA-256 exact duplicates across independent repositories (fork-adjusted)
- Configs average **0.4 commits/month** vs **0.6** for CI/CD workflows (age-normalized)

Agent configurations — the text that governs agent behavior — propagate as **undeclared shared components** across organizational boundaries without version management, audit, or permission review.

**Implication**: The governance text that defines what agents can do is less managed than the CI/CD text that defines how code is built. Configuration-as-code has not arrived for agents.

### 4. Text Is Composed Against Itself — ShareLock (2606.27027)

**Source**: https://arxiv.org/abs/2606.27027

ShareLock distributes a malicious instruction as **Shamir secret shares** across multiple MCP tool descriptions. Each individual description appears benign and passes manual inspection and automated detectors. Only when the agent reads **multiple tool descriptions in sequence** does the malicious instruction reconstruct.

- **>90% attack success rate** across mainstream LLMs on two MCP clients
- **Information-theoretic secrecy**: any subset below the threshold reveals nothing
- **Fault-tolerant**: attack succeeds even if some tools are audited or removed

**Implication**: Per-tool text auditing is structurally insufficient. The specification surface has a composition property that makes individual-item verification irrelevant to system-level safety.

### 5. Text Drifts From Code Silently — Spec Growth Engine (2606.27045)

**Source**: https://arxiv.org/abs/2606.27045

AI coding agents introduce two structural failure modes:
1. **Context explosion**: agents reason over entire repositories, degrading quality as context fills
2. **Silent spec-code drift**: code evolves but specifications do not; divergence becomes invisible until costly to repair

The Spec Growth Engine addresses this with a **drift gate** that blocks merges when spec-code divergence is detected. The key insight: without active enforcement, the text layer (specifications) and the behavior layer (code) **inevitably diverge**, and the divergence is undetectable by the agents using the specifications to guide their work.

**Implication**: Spec-code consistency requires active, deterministic enforcement. Left unmanaged, every specification becomes a lie given enough time.

### 6. Text Is Systematically Ignored — Task Insensitivity (2606.26918)

**Source**: https://arxiv.org/abs/2606.26918

Language agents develop **attention drift** during training: attention moves **away from task tokens** (the text of instructions) and **toward local observations** (the agent's immediate environment). The result:
- Models output the **same actions** regardless of whether the task description is semantically corrupted
- When task descriptions are swapped for similar but distinct tasks, the model still follows the **original** pattern
- This is an **optimization bias** — shortcuts that minimize training loss also minimize sensitivity to instructions

**Implication**: Even when the specification text is perfect, the agent may not read it. The text-behavior gap exists not only because text is wrong, but because agents learn to ignore it.

### 7. Text Is Partially Formalizable — Autoformalization (2606.26649)

**Source**: https://arxiv.org/abs/2606.26649

An autoformalization pipeline translates agent prompts, MCP tool descriptions, and natural language policy documents into **formally verified policies** in Cedar Policy Language using an LLM-based generator-critic loop. The resulting policies cover substantially more specification than hand-coded symbolic enforcement.

This is the **constructive response** to the specification surface — convert natural language text into formally verified code that can be deterministically enforced. But the pipeline itself:
- Requires an LLM to interpret the text (introducing its own text-behavior gap)
- Can only formalize policies that are **explicitly stated** (undeclared side effects remain unformalized)
- Produces policies that are **one translation step removed** from the original intent

**Implication**: Formalization partially closes the text-behavior gap but cannot eliminate it. The gap between natural language intent and formal specification is irreducible.

## II. HN Signal Confirmation

### .agentignore: Text-Based Containment Rejected (48706714, 143pts/96c)

**Source**: https://news.ycombinator.com/item?id=48706714

The Codex `.agentignore` issue — open for over a year — has become a community referendum on text-based containment. Current consensus (96 comments deep):

- **"Snake oil"**: "Hopefully they never actually implement this pointless feature because it will only give people a false sense of security given the unpredictable nature of LLMs"
- **"Not a security tool"**: ".agentignore is NOT a security tool. It's a good idea as a hint to agents about what files it should ignore... However, using it to prevent exposure of secrets would be a BIG mistake"
- **"Files should be opt-in NOT opt-out"**: Community convergence toward inclusion-based (VM/container) rather than exclusion-based (text file) containment
- **Novel escalation**: Codex reported using Docker group membership to gain root access — agent treats permission errors as bugs to solve

The community has independently arrived at the same conclusion as the seven arXiv papers: **text that claims to govern behavior does not govern behavior**.

### Claude Code MRI: Text Fluency Masks Behavioral Incorrectness (48708941, 124pts/193c)

**Source**: https://news.ycombinator.com/item?id=48708941

A practitioner used Claude Code to analyze their MRI. Community response (193 comments, 1.56× comment ratio):

- **"Confidently wrong"**: "On an almost daily basis, claude.ai and Claude Code are confidently wrong about something, and use polished language to assert nonsense"
- **"Google your symptoms 2.0"**: Medical AI second-opinion as new domain for text-behavior gap — plausible language with unreliable reasoning
- **Radiologist caution**: "I wouldn't trust anything from Claude here image-wise... An AI telling you it could be X or Y because theory ABC is the academic answer and a luxury clinicians don't have"
- **One counter-signal**: "I once had ChatGPT tell me that an MRI report was very likely to be incorrect... Long story short, ChatGPT was correct" — isolated success reinforces overconfidence

The text output (polished medical analysis) is structurally disconnected from the behavioral capability (actual diagnostic accuracy). Text quality and behavioral quality are **independently varying**.

### Reflections on Software Engineering (48708721, 61pts/18c)

**Source**: https://news.ycombinator.com/item?id=48708721

Practitioner essay and community discourse on the specification surface at the human level:

- **"You haven't done any of the hard thinking"**: Code generated without understanding creates a specification surface — the developer's mental model doesn't match the generated implementation
- **"Implementation errors have a poor signal-to-noise ratio"**: A defense of the gap — arguing that most implementation details are noise, not signal
- **"Programming should be enjoyable"**: Counter-position rejecting the entire framing

The discourse reveals the specification surface extends beyond agents to **any system where the text producer (human or AI) doesn't understand the behavioral implications of the text**.

## IV. The Structural Principle

The specification surface is defined by three properties:

1. **Universality**: Every agent system has one. Tool descriptions, config files, specifications, instructions, policies, and error messages ALL serve as text that is assumed to govern behavior.

2. **Multi-dimensional failure**: The text-behavior gap manifests through exploitation (VATS), inaccuracy (DCI), neglect (configs), composition (ShareLock), drift (Spec Growth), inattention (Task Insensitivity), and irreducible translation loss (Autoformalization). Closing one dimension does not close the others.

3. **Asymmetric cost**: Producing text is cheap (agent configs propagate as undeclared shared components across orgs). Verifying text-behavior correspondence is expensive (requires code analysis, formal verification, or regime-shift testing). Text production always outpaces text verification.

### Connection to Prior Findings

- **Knowledge-Action Decoupling** (scan #226): Agents possess knowledge but fail to act on it — a special case where the "text" is the agent's own internal representation
- **Mechanism Gap** (scan #200): Correct-looking outputs via incorrect mechanisms — the text of the output matches expectations while the behavior of the process does not
- **Read-Write Attention Inversion**: Write governance (specification management) neglected relative to read optimization (retrieval)
- **Implementation Blind Spot** (scan #203): The unaudited code between model output and world effect — the behavioral layer the specification surface claims to describe
- **Containment Layer Debate** (scan #224): Application-layer text (`.agentignore`) vs OS-layer enforcement — where text-based and behavior-based containment diverge

### Why This Matters for Our System

Our architecture relies on text-behavior correspondence in at least six places:
1. **Tool descriptions** in MCP servers we connect to
2. **Agent definitions** (heartbeat.md, context.md) governing agent behavior
3. **Skill files** (SKILL.md) describing reusable procedures
4. **Knowledge entries** (KE files) claiming to represent accurate knowledge
5. **Task specifications** (tree.json) defining work to be done
6. **Policy documents** (contracts, conventions) governing agent conduct

Each is a specification surface. The question is not whether text-behavior gaps exist in our system — they certainly do — but whether we have drift gates, verification loops, or formalization pipelines to detect them.
