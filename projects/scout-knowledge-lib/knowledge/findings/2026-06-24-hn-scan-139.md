## Core Finding

Six independent June 2026 signals converge on a **phase transition from outcome-optimized to process-optimized** agent development. The question has shifted from "can the agent produce correct output?" to "does the agent follow sound engineering process?" — and the data shows that answering the second question automatically improves the first (RigorBench: +17% outcome correctness from process discipline alone).

This is the same maturation that human software engineering underwent — from "does it compile?" to "is it tested/reviewed/maintainable?" — now happening for AI agents on a compressed timescale of months rather than decades. The prior scans identified the enforcement layer (#118) and the protocol replacement architecture (#131). This scan identifies what those architectures ENFORCE: engineering process discipline.

## Signal 1: The Process Benchmark — RigorBench

### Benchmarking Engineering Process Discipline in Autonomous AI Coding Agents (2606.22678)

**Source:** https://arxiv.org/abs/2606.22678

The first benchmark designed to measure **process discipline** rather than outcome correctness. Introduces five pillars:

| Pillar | What It Measures |
|--------|-----------------|
| **Planning Fidelity** | Does the agent plan before executing? |
| **Verification Coverage** | Does the agent verify its own work? |
| **Recovery Efficiency** | How well does the agent recover from failures? |
| **Abstention Quality** | Does the agent know when to stop? |
| **Atomic Transition Integrity** | Are state changes atomic and reversible? |

Key results:
- Structured process discipline improves process quality scores by **41% average**
- Process discipline also raises **downstream outcome correctness by 17%**
- First quantitative evidence that *how* agents code matters as much as *what* they produce
- 30 tasks across 5 categories: Plan-Then-Build, Verify-Or-Die, Doom Loop Gauntlet, Know When to Fold, Don't Break the Build
- Controlled with/without design evaluating harnesses (Agent-Skills, Superpowers, Agent-Rigor) against baseline assistants

**Why this matters structurally**: Every prior coding benchmark (SWE-bench, Terminal-Bench, HumanEval) measured outcome only. An agent that brute-forces through 47 edit cycles to pass tests scores identically to one that plans, implements once, and verifies. RigorBench proves the brute-force agent is measurably worse even on outcome metrics — reckless trial-and-error accumulates state corruption that eventually prevents correct solutions.

**Cross-reference**: Connects to Diagnostic Architecture Crisis (#137) — SAFARI diagnoses failures after the fact; RigorBench measures the process discipline that prevents them. Also connects to Effort Signal Collapse (#130) — process discipline IS the new effort signal in an age of infinite generation.

## Signal 2: The Workspace Boundary — LemonHarness

### LemonHarness Technical Report (2606.24311)

**Source:** https://arxiv.org/abs/2606.24311

Formalizes the problem: as LLM agents modify workspace state across multiple rounds, state changes scatter across paths, making modified files difficult to track. LemonHarness introduces:

1. **Explicit execution boundary**: All state-changing operations constrained within a defined workspace
2. **Structured tool interfaces**: File writes, dependency installation, and artifact creation mediated through structured interfaces with execution feedback recorded as observations
3. **Reusable rule knowledge base**: Recurring execution rules and acceptance criteria turned into runtime-accessible knowledge
4. **Time-aware execution**: Elapsed and remaining budget exposed to the model, enabling rebalancing of exploration, implementation, and validation effort

Results on Terminal-Bench 2.0:
- LemonHarness + GPT-5.3-CodeX: **84.49%** (445 trials)
- LemonHarness + GPT-5.5: **86.52%** (5 jobs)

**Structural insight**: The key idea is that agents suffer from **state blindness** — they observe tool outputs and log fragments but not the actual filesystem state changes. LemonHarness makes workspace state changes first-class observations. This is the workspace equivalent of TMA-NM's write-time origin binding (#138) — authority over state requires explicit boundary at mutation time.

**Cross-reference**: Our system partially implements this via project boundary conventions, but agents can still write outside their workspace with bash. LemonHarness makes the boundary enforced, not advisory.

## Signal 3: The Execution Modality Split — GUI vs. CLI

### GUI vs. CLI: Execution Bottlenecks in Screen-Only and Skill-Mediated Computer-Use Agents (2606.24551)

**Source:** https://arxiv.org/abs/2606.24551

First matched benchmark (440 desktop tasks, 18 applications, 12 workflow categories) proving that execution modality matters independently of model capability:

- Strongest GUI agent: **59.1%** full pass rate
- Strongest original-skill CLI agent: **48.2%** (lower!)
- CLI with verifier-guided skill augmentation: **69.3%** (highest!)

**Key insight**: GUI and CLI expose **different execution bottlenecks**:
- GUI agents are limited by reliable grounded interaction over long-horizon workflows
- CLI agents are limited by coverage and scalability of their skill interfaces

The 21-point swing from original-skill CLI (48.2%) to augmented CLI (69.3%) proves the bottleneck is skill coverage, not model capability. "Much of the CLI deficit comes from incomplete skill coverage rather than model capability alone."

**Structural implication**: The harness (skill interface) is doing more work than the model for CLI agents. This validates the meta-harness trend — the execution layer is the primary engineering surface, not the model.

## Signal 4: The Skill Compilation Problem — SoftSkill

### SoftSkill: Behavioral Compression for Contextual Adaptation (2606.20333)

**Source:** https://arxiv.org/abs/2606.20333

Reveals a fundamental problem with the current skill-file paradigm: natural-language Markdown skills are **consumed indirectly** — the frozen model must re-interpret long textual artifacts into generation-time behavior for every task instance. This re-interpretation is lossy.

SoftSkill proposes compiling skills into 32-token latent prefixes via next-token prediction training:

| Benchmark | No-Skill | SkillOpt | SoftSkill | Gain |
|-----------|----------|----------|-----------|------|
| SearchQA | baseline | +3.1 | +8.3 | +5.2 over SkillOpt |
| LiveMath | baseline | +29.6 | +42.1 | +12.5 over SkillOpt |
| DocVQA | baseline | - | +1.3 | - |

Key findings:
- Length-32 prefix replaces hundreds to thousands of Markdown skill tokens
- Base model remains frozen — skill is a behavioral prior, not fine-tuning
- **Critical limitation**: "sparse trajectory imitation provides useful signal but does not yet robustly compress long-horizon procedural behavior"
- Implication: declarative/knowledge skills compile well; procedural/agentic skills do not (yet)

**Why this matters for our system**: We deploy skills as Markdown files (literally the paradigm SoftSkill challenges). The paper proves this is interpretively lossy — every session re-reads CLAUDE.md and must translate it into behavior. The loss is measurable: +42.1 points on LiveMath from compilation vs. text-based prompting.

**Boundary case**: SoftSkill explicitly fails on long-horizon procedural behavior — exactly what our CLAUDE.md encodes (multi-step workflows, verification procedures, output protocols). The text format may be lossy but is currently irreplaceable for procedural skills.

## Signal 6: The Effort Signal Collapse (Discourse Continuation)

### "Vulnerability Reports Are Not Special Anymore" (298pts/165c)

**Source:** https://words.filippo.io/vuln-reports/

Filippo Valsorda (former Go Security lead) articulates the collapse from the practitioner side. HN discourse crystallizes:

- "I get 2-5 unsolicited vulnerability reports per week. Half are LLMs finding bad CSS."
- "It's become even harder to sift through the noise — I triage well over a dozen reports a week"
- "Are truths spoken by folks one dislikes... less true? You triage and fix the vulnerability just like any other one."
- "I'm wondering whether this is a permanent change."
- "More broadly this is a big piece of AI-cynicism — 'x isn't special anymore'"

**Structural connection to process discipline**: The effort signal that made vulnerability reports "special" (they required skill to produce) has collapsed. The replacement is triage discipline — exactly the process discipline RigorBench measures for code. The signal shifts from *production quality* (how hard was it to find?) to *process quality* (how well was it validated and contextualized?).

## The Process Discipline Stack

```
┌─────────────────────────────────────────────────────┐
│  L5: Meta-Harness (Omnigent, harness-generator)     │
│  Swap/orchestrate harness runtimes; standardized    │
│  interfaces between model ↔ harness ↔ workspace     │
├─────────────────────────────────────────────────────┤
│  L4: Process Measurement (RigorBench)               │
│  Five-pillar discipline scoring; composite          │
│  RigorScore; evidence that process → outcome        │
├─────────────────────────────────────────────────────┤
│  L3: Execution Modality (GUI vs CLI)                │
│  Matched modality to task bottleneck; skill         │
│  augmentation as primary engineering lever          │
├─────────────────────────────────────────────────────┤
│  L2: Workspace Boundary (LemonHarness)              │
│  Explicit state boundary; structured tool           │
│  interfaces; time-aware budget management           │
├─────────────────────────────────────────────────────┤
│  L1: Skill Representation (SoftSkill)               │
│  Compile knowledge skills to latent prefixes;       │
│  procedural skills remain textual (for now)         │
└─────────────────────────────────────────────────────┘
```

**Why it's a stack, not a menu**:
- Without L1: Skills are re-interpreted lossily every session (up to 42pts lost)
- Without L2: State changes scatter untracked; doom loops compound state corruption
- Without L3: Wrong modality creates 21pp deficit regardless of model capability
- Without L4: No feedback on process quality; outcome-only optimization leads to brute-force
- Without L5: Harness lock-in; can't match best harness to task type

## Self-Application

Our system has:

| Layer | Our Status | Gap |
|---|---|---|
| L1: Skill Representation | ⚠️ Textual Markdown (lossy) | Skills re-interpreted every session; compilation not available for open-weight |
| L2: Workspace Boundary | ⚠️ Advisory (convention-enforced) | Agents CAN write outside workspace via bash; no hard enforcement |
| L3: Execution Modality | ✅ CLI-native | Correct for our task type; skill augmentation via CLAUDE.md + tools |
| L4: Process Measurement | ❌ Absent | No RigorScore equivalent; outcome (task completed) is all we measure |
| L5: Meta-Harness | ❌ N/A | Single harness (our custom system); no swapping needed |

**Most critical gap**: L4 — Process Measurement. We have no way to distinguish an agent that planned, verified, and committed atomically from one that brute-forced through 47 retries. Both look identical in last-session.md. The 17% outcome improvement from process discipline is being left on the table.

**Minimum viable intervention**: Add process metrics to session records — planning evidence (was a plan stated before implementation?), verification coverage (were outputs verified?), abstention quality (did agent stop when stuck vs. doom-loop?), atomic transitions (were edits atomic or scattered?).
