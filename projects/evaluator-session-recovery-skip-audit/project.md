# Evaluator Session-Recovery Skip Audit

## Goal
Determine whether repeated `session-recovery` skips with reason `classifier chose nothing` are dropping recoverable interrupted sessions, starting with the high-volume `aks-explorer` planner wakes, and package evidence-backed calibration or escalation.

## Signals
- `handler.skipped` events with `handler=session-recovery` and reason `classifier chose nothing` totaled 234 in the last 24h.
- `aks-explorer` accounts for 213 of those 234 skips.
- `aks-explorer` planner sessions matching `task LIKE 'Planning Update Step%'` recorded 159 interrupted sessions in the last 24h.
- Example session `s_project_planner_planning_update_20260615135339_ga3xoo` ended `interrupted` after identifying concrete next work, was routed by evaluator to `needs_triage`, but `session-recovery` still skipped it with `classifier chose nothing`.

## Current State
- No red metrics are firing, so this is a silent quality/coverage concern rather than an alert-driven incident.
- The reviewed example is not an aftermath false-positive problem: evaluator routing behaved as expected by marking the interrupted planner session `needs_improvement` / `needs_triage` because terminal status was `interrupted`.
- The suspicious gap is downstream of that: `session-recovery` appears to routinely skip interrupted sessions without a recoverability decision, even when the session-end summary contains obvious unfinished work.
- Existing archived routing-drift notes show earlier aftermath coverage issues, but there is no current active shared project focused on today’s recovery-skip concentration.
- 2026-06-15 follow-up heartbeat confirmed the pattern persists on a fresh pending-event sample: `s_project_planner_planning_update_20260615142042_yy8hlu` ended `interrupted` after a summary naming accepted review work plus two newly created staging-execution tasks, evaluator again routed it to `needs_improvement`, and `session-recovery` still emitted `handler.skipped` with `reason="classifier chose nothing"` from `decisionSource="digest"`.
- Latest heartbeat review widened the evidence with a new sample `s_project_planner_planning_update_20260615144111_hs4kk7`: the planner landed four `mark-done` mutations plus a new assigned staging batch, evaluator aftermath reviewed it to `acceptable`, yet `session-recovery` still skipped it immediately with `reason="classifier chose nothing"`.
- Live runtime counts remain high: 24h `classifier chose nothing` skips are now `248`, with `aks-explorer=225`.
- Fresh heartbeat sample `s_project_planner_planning_update_20260615194943_9t3seu` shows the gap still reproducing in the newest planner wake: `session.completed` (`interrupted`) was followed 22ms later by `handler.skipped` with `decisionSource="digest"` / `reason="classifier chose nothing"`, and evaluator then routed the same session to `needs_triage`.
- Refreshed live concentration counts from the current heartbeat are still effectively unchanged at the project level: `246` `classifier chose nothing` skips in the last 24h, `184` on planner-update sessions, and `aks-explorer=224` by agent.
- A fresh pending-event sample `s_project_planner_planning_update_20260615150615_4pvx91` reproduced the same behavior: the planner ended `interrupted` after 33 ops with a summary explicitly saying it still needed to run domain checks and commit, then `session-recovery` skipped it within milliseconds using `decisionSource="digest"` and `reason="classifier chose nothing"`.
- Latest pending-event sample before this heartbeat, `s_project_planner_planning_update_20260615151820_rctryy`, reproduced it again: the planner ended `interrupted` after 31 ops with a summary explicitly saying it was about to create three frontier-refill tasks, then `session-recovery` skipped it 26ms later with `decisionSource="digest"` / `reason="classifier chose nothing"` before evaluator aftermath routed it to `needs_triage`.
- New heartbeat sample `s_project_planner_planning_update_20260615184556_zmszmz` preserves the same downstream gap with a slightly different shape: the planner woke on `watchdog-capacity-underfilled`, found no runnable backlog, then ended `interrupted` mid-review with summary `"The worker claims done with a product-level deprecation classification. Let me verify the evidence:"`; `session-recovery` still skipped it 18ms later with `decisionSource="digest"` / `reason="classifier chose nothing"`, and evaluator routed it to `needs_triage` for the interrupted terminal state.
- Root cause is now specific, code-level, and likely broader than the sampled planner wakes: `agents/may/handlers/session-recovery.ts` trusts `digest.action` verbatim, while `projects/may-agent/src/lib/session-digest.ts` only returns `resume` for `auto_resume` when `digest.outcome === "in_progress"`. But `session-recovery` runs on `session.completed` terminal outcomes (`error`/`interrupted`), so interrupted sessions can never satisfy that predicate and therefore collapse to `nothing` whenever the digest classifier is consulted here.
- The existing unit tests codify the same impossible condition: `projects/may-agent/src/lib/session-digest-classify.test.ts` expects `auto_resume` to do nothing for `outcome="failure"`, which matches the current skip behavior instead of the intended interrupted-session recovery path.

## Plan
1. Package the code-level root cause and the strongest session sample into an owner-facing recommendation for May.
2. Request a narrow implementation/test patch around the impossible `auto_resume` predicate and handler expectations.
3. After owner response or implementation lands, validate on fresh interrupted planner samples that `session-recovery` stops collapsing all digest-driven interrupted sessions to `nothing`.
4. Re-sample skipped sessions afterward to confirm the remaining skip population is truly non-recoverable.

## Validation
- Evidence clearly distinguishes benign skips from actionable recovery misses.
- If the issue is real, owner guidance or code changes reduce `classifier chose nothing` skips for interrupted planner sessions.
- Follow-up samples show interrupted sessions with explicit unfinished work are either resumed, triaged, or intentionally classified with a concrete reason.
