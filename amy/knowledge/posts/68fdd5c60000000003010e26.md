# agent lightning 第一个真正意义上的通用 agent RL 库

在遇到 agent lightning 之前，我研究过的 LLM RL 库基本服务于大模型的单轮推理场景，或是针对特定场景的 agent 来设计。直到看到 agent lightning，我笃定这是第一个真正意义的通用 agent RL 库（后来粗浅研究过 ART 之后，我认为它也算是）

为什么我这么认为？这就不得不提它的核心思想——将 agent 和 training 解耦

[Slide 2]
回想上古时代用 pytorch 训练神经网络时，我们不仅需要用 pytorch 写训练的逻辑，还需要使用 pytorch 定义神经网络 model。

而在 huggingface 出现后，实际上 model 已经与训练框架在某种程度解耦。后来我训练神经网络一般用 pytorch lightning 库，而模型基本上使用的 huggingface 读一个 bert，再用 pytorch 加点 trick，不再需要用 pytorch 包办底层 model 和 train loop 逻辑。




这是历史证明的大趋势——模块化模型和训练




而在 agent RL 中，我大胆做一个类比：agent 就是以前的 model，traning 还是以前的 training

但 agent 不同于神经网络的一点是，它需要在一个真实数字世界中规划步骤、使用工具进行交互，获取反馈更改错误等等，它的工程复杂度远比神经网络复杂。

[Slide 3]
如果一个开源框架，它既能搭 agent，又能做强化学习，我认为这样的框架很容易难产——复杂度太高，要做到两头都好用，及其困难。

agent lightning 走了一个邪修的路子，它把 agent 的搭建完全剥离出去，用户自己解决 agent 的搭建，只要最后用 agent lightning 简单地包一层，把一次 agent run 对应的 reward 设计好即可。agent lightning 自动搞定任务接收、轨迹——奖励对收集、回传 training 端。

而 training 也是站在巨人 verl 和 ray 的肩膀上进行改造，只要熟悉 verl 和 ray，那么超参调整和分布式训练都能相当丝滑。相信做过分布式强化学习的朋友对这两个框架都非常熟悉了。




但 agent lightning 毕竟还只是实验室级框架，实际使用下来，虽然丝滑，但在 debug 时却痛苦万分。一是错误追踪和日志并不完善，错误信息不够明确，很多时候还要去翻看源码、修改源码才能 debug二是解耦后，有些错误可能在 agent 端发出，但实际是 training
