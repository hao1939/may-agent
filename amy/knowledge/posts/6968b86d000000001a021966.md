# Agent+Skills能取代workflow吗？

不知道你有没有和我有一样的疑惑：现在Claude Skills出来以后，能不能取代现有的workflow模式？

这两者之间是取代的关系？还是各自有自己的应用场景？

今天我看到一篇文章，其中讲到说是使用Agent+Skills 在大多数情况下是可以取代workflow模式的，主要内容是以下这五点：

1/ 告别拖拽，用自然语言编排

可视化 workflow 有硬伤：不够强大、不够灵活、难以移植。流程一旦定死，输入变化就卡住。

[Slide 3]
Agent + Skills 用自然语言描述协作关系，不用拖拽，像给同事交代任务一样说清楚就行。条件分支、并行执行、错误处理，AI 都能理解。

2/ 五步框架

拆分：把工作流拆成单一职责的 skill，每个只做一件事

编排：用自然语言描述整个流程

存储：所有中间结果保存成本地文件，可追溯、可断点续传、可人工干预

分摊：subagent 之间只传文件路径，不传内容，上下文干净

迭代：可以持续进化，越用越好

3/ 混合架构思路

确定性逻辑不一定要交给 Agent。需要确定性的部分写成脚本，skill 调用脚本就行。代码处理确定性逻辑，Agent 处理需要判断的任务。两者各司其职，取长补短。

4/ 最大的优势：可进化

[Slide 4]
传统 workflow 一旦搭好就定型，改起来小心测试，还可能引入新问题。

Skill 不一样。基于本地文件系统，可以让 AI 帮你维护更新。用了一段时间，积累问题，直接让 AI 分析改进。投入时间打造的 skill，会随着使用越来越好，而不是像 workflow 那样搭好就开始过时。

5/ 成本要算总账

开发成本： skill 用自然语言描述，比 workflow 逐个配置节点更快

维护成本：skill 改起来更灵活

迭代成本：skill 可以让 AI 帮你改进

Token 成本在整体效率提升面前不算什么。

# 01 讨论

前两天有人讨论这样的话题。

就是 Dify 这种可视化拖拽 workflow 和 Claude Code Skills 的较量。

有人说："使用 Agent + Skills 能打天下吗？"

这话对，也不对。

对在传统 workflow 有价值——结果可预测，出问题能排查，流程图普通人能看懂。

不对在很多人低估了 Agent + Skills 的潜力。

我的观点：大部分 workflow 编排场景，都可以被 Agent + Skills 取代。

---

# 02 Workflow的舒适区与硬伤

可视化工作流能火，有道理。

拖拽节点、连连线，流程就搭好了。不用写代码，

[Slide 6]
改起来直观。更重要的是确定性——节点 A 执行完一定是节点 B。审计、合规的业务场景，这种确定性很重要。

但 workflow 有硬伤。

不够强大。可视化节点能做的事情有限，复杂逻辑很难表达。

不够灵活。流程一旦定死，输入变化就容易出错。设计好的流程处理 A 类文档，来了 B 类文档，整个流程卡住。

难以移植。搭了个厉害的工作流，想给别人用？导出导入一通操作，还得在对方环境调半天。平台锁定效应明显。

———

# **03 五步框架**

几乎所有能用 workflow 完成的 AI 任务，都可以用 Agent + Skills 实现。

关键是 skill 不是单一技能，而是可组合的模块。把多个 skill 串起来，用自然语言描述协作关系。

[Slide 7]
第一步：拆分

把工作流拆成单一职责的 skill。每个模块只做一件事，做好一件事。写作工作流拆成：analyzer 分析素材、outliner 生成提纲、writer 写草稿、polish 润色定稿。原来 workflow 里画的每个功能节点，基本都可以对应一个 skill。

第二步：编排

主 skill 里用自然语言描述整个流程。不需要写代码，就像给同事交代任务。"先调用 analyzer 分析素材，然后生成提纲方案，并行启动 writer 写草稿。"条件分支、并行执行、错误处理，Agent 都能理解。

第三步：存储

所有中间结果保存成本地文件。三个好处：可追溯、可断点续传、可人工干预。source.md → analysis.md → outline-a.md → draft.md → final.md，每步产出有迹可循。

第四步：分摊

Subagent 之间只传文件路径，不传内容。把一大

[Slide 8]
段内容直接塞给 subagent，上下文窗口很快撑满。只传路径，subagent 自己去读文件，上下文干净很多。还可以并行启动多个 subagent，互不干扰。

第五步：迭代

这是相比传统 workflow 最大的优势：可以持续进化。发现某个 skill 的提示词不够好？让 Claude Code 帮你改。Skills 会越用越好，而不是搭完就吃灰。

———

# **04 回应三大质疑**

质疑一：稳定性怎么办？

确定性逻辑不一定要交给 Agent。需要确定性的部分写成脚本，skill 调用这个脚本就行。我的写作流程里有个格式化步骤，规则明确的操作写了个脚本，polish 技能执行完润色后自动调用。混合架构思路：代码处理确定性逻辑，Agent 处理需要判断的任务。两者各司其职。

[Slide 9]
质疑二：成本太高

成本要算总账。开发成本：skill 用自然语言描述，比 workflow 逐个配置节点更快。维护成本：skill 改起来更灵活。迭代成本：skill 可以让 AI 帮你改进。Rakuten 用 Claude Skills 处理财务报表，原本一天的工作现在一小时完成。Token 成本在整体效率提升面前不算什么。

质疑三：门槛太高

AI 本 身 就 能 帮 你 创 建 skill 。 借 用 /skill-creator，把需求描述清楚，Claude Code 可以帮 你 生 成 skill 配 置 。 长 期 来 看 ， skill 比 workflow 更易维护。文本文件，可以用 Git 管理版本，可以在不同机器间同步。Workflow 锁在平台里，换个环境就得重来。

---

# **05 边界在哪**

不是说 workflow 毫无价值。两种方案各有适用场景。

[Slide 10]
Agent + Skills 更适合： 输入多变需要判断的任务、跨系统协调的复杂流程、需要频繁迭代的工作流、需要分享复用的自动化逻辑。

Workflow 仍有优势的场景：严格审计要求的合规流程、超高频执行的简单任务、非技术用户的可视化需求。

———

# **06 尾声**

Skill 架构有个经常被忽略的好处：它是活的，可以不断进化。

传统 workflow 一旦搭好就定型。改动需要人工介入，要小心测试，改完可能还会引入新问题。

Skill 不一样。基于本地文件系统，可以让 Claude Code 帮你维护更新。用了一段时间，积累问题，直接让 AI 分析并改进。

更激进的玩法是 subagent 可以自我迭代 system prompt。听起来有点科幻，但已经有人在实践了。

[Slide 11]
McKinsey 的报告印证了这一点： 法律文档审核流程中， agent 系统会记录每次人工修正，然后用这些反馈来改进自己的 prompt，逐渐将新的专业知识编码进系统。

这意味着什么？ 投入时间打造的 skill，会随着使用越来越好。而不是像 workflow 那样，搭好就开始慢慢过时。

把你常用的 workflow 沉淀为 skill 吧。这不只是换个工具，而是在积累可复用、可进化的自动化资产。

下 次 有 人 说 " 这 个 流 程 太 复 杂 ， 只 能 用 workflow"，不妨想想： 真的吗？ 还是只是没找到正确的拆分方式？
