Anthropic 新文章《如何为 Agent 构建工具》
	
做 Agent 工具最容易踩的坑：把传统 API / 函数直接搬过来用！
	
Anthropic 的核心逻辑是 ——Agent 有非确定性行为（可能幻觉、多路径决策），工具必须针对性设计，分享优化后的实操框架👇​
	
🔍 关键差异：别用 "系统思维" 套 Agent​
	
传统软件是「确定的函数调用」，但 Agent 工具要应对「非确定决策」：​
❌ 照搬 API：比如把list_contacts直接当工具，Agent 可能反复调用还抓不住重点​
✅ 适配非确定性：工具要预留容错空间（如多响应格式），帮 Agent 减少决策混乱​
	
🔄 开发迭代：3 步走，实测高效​
1️⃣ 快速原型 + 本地测​
用 MCP 协议（claude mcp add命令）搭本地环境，带 SDK 文档让 Claude Code 先试，避免空想设计​
	
2️⃣ 真实评测：Agent 协作生成任务​
和 Agent 一起造贴近工作流的任务（如 "排查客户重复收费 + 同步日志 + 评估影响"），再用「自动化评测 + Agent 推理反馈」双维度验证​
	
3️⃣ 持续优化：跟着反馈调​
拿评测数据（准确率 / 错误率）和 Agent 的困惑点（如参数混淆）迭代，保留测试集防过拟合​
	
✨ 5 大原则：精准踩中 Agent 需求​
▪️ 优先高影响力工具​
聚焦关键工作流（如客户留存全流程工具），拒绝 "包 API" 式无效工具（如单独的get_user_id）​
	
▪️ 命名空间划清边界​
用前缀 / 后缀分组（如asana_projects/jira_tasks），Agent 选工具不迷路​
	
▪️ 高信号上下文优先​
返回自然语言 + 可读标识符（别堆 UUID！），支持「详细 / 简洁」双格式（详细供下游调用，简洁省 token）​
	
▪️ 控 token：分页 + 过滤 + 优化参数​
默认限制输出（如 25000 tokens），冗余信息直接截断，避免浪费上下文​
	
▪️ 清晰描述 + 具体错误提示​
工具文档像给新同事写的：参数写死user_id（别写模糊的user），错误提示给解决方案（如 "缺 customer_id，示例：12345"），帮 Agent 自我修正​
